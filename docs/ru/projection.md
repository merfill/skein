# Skein — проекция контекста: лента сообщений

> Английское зеркало — `docs/en/projection.md`.

> **Свёрнуто из ревизии.** Проекция — лента сообщений, собираемая из дерева каждый ход;
> прежние блоки `path`/`lastResult`/`shown`/`calls`/`budget` убраны (лента — это весь контекст;
> `Context.applicable` сохранён только чтобы связать предложенную поверхность инструментов, §2).
> Источник истины — `docs/ru/ir.md` §7; as-built — `docs/ru/ir.md`; справочник
> операторов — `docs/ru/ir.md`.

## 1. Назначение

Контекст — то, что модель видит на очередном шаге: **вся её память**. Он выглядит как обычная
лента сообщений (как в ReAct-агенте), но **собирается из дерева заново каждый ход** — это
проекция, а не накопительная переписка. Одни события всегда дают одну ленту.

## 2. Роли и ходы

- `system` — базовый промпт, ограничения, блок факта для **текущего** состояния (координаты
  плюс его набор environment) и инструкция текущей ситуации (в конце, временно); у закрытого
  состояния нет блока фактов;
- `user` — запрос (вверху ленты, каждый ход) и per-turn working-промпт после ходов открытого
  состояния;
- `assistant` — маркеры состояний и вызовы доксы;
- `tool` — результаты команд.

| Ход | Сообщения |
|---|---|
| `move` | **состояние — это решение, а не вызов инструмента**: маркер `system` `Start state <label>`, блок факта текущего состояния ходом `system`, затем — пока состояние открыто — его ходы. Цель, критерий и план добавляет `buildMessages` одним `user`-working-промптом после ходов (`Goal: <island.what>`, догадка доксы, если задана, `Done when`, `Plan`, запрос как reference). Запрос — второе сообщение ленты (сразу после базового промпта), на **каждом** ходу, не убирается |
| `apply` | `assistant` (вызов) + `tool` (наблюдение); первый `apply` после `move` засевает ходы состояния и его первое действие |
| `stop` | закрытие состояния, рендерится маркером `system` `Finish state <label> — <why>`; вызова инструмента не добавляет. На терминальном состоянии запрос завершается |
| `decline` | `assistant` (причина `why`): запрос отклонён |

Каждый ход — пара `assistant` + `tool`; первый `apply` после `move` засевает ходы
состояния. Команда, исполнившаяся и изменившая файл (правка), наблюдения не имеет, поэтому её
`tool`-сообщение читается как `mutated <path>`. Открытое состояние — это `Start state <label>` /
brief / ходы, и после ходов добавляется один `user`-working-промпт; закрытое — только
`Start state <label>` / `Finish state <label>`. Маркер `Finish state` несёт **только**
метку и причину `stop` — никогда список изменённых файлов: состояние, запускающее сборку,
мутирует тысячи артефактов.

## 3. Лента собирается обходом дерева

- запрос — первое `user`-сообщение ленты (сразу после базового промпта), на каждом ходу;
- **probe** — один сессионный `fact` (`add_node kind:"fact"`, `id: fact:session`) с
  `{ environment, material }`, записанный на старте запроса. Он не идёт отдельным сообщением
  после запроса; проекция выбирает нужный блок для **текущего** состояния.
  Блок строит собственная функция брифа состояния (`src/ir/briefs.ts`): каждое рабочее
  состояние получает координаты (`Workspace root`, статус `Workspace repository`,
  `Working directory`, если shell стартует не в root) плюс свой набор environment; End —
  ничего. Environment — короткий список фактов
  (`Network is available`, interpreters, package managers, build/test tools, version-control
  tools), не инвентарь стоковых утилит. Блок идёт отдельным `system`-ходом в записи текущего
  состояния. Закрытые состояния блоков не несут; на request-ходу их нет;
- координаты детерминированы и не являются списком: ни top-level entries, ни paths, ни числа
  файлов. Состояние, которому нужны файлы, запрашивает их через `list`. Environment, расширения,
  конфиги, команды сборки и build state **не** показываются; объявленная команда
  не выдаётся за acceptance;
- его состояния (дети `move`) рендерятся по порядку: **открытое** (текущее) состояние рендерит
  маркер `Start state`, brief и ходы; **оставленное позади** или остановленное состояние
  сворачивается в `Start state <label>` / `Finish state <label> — <why>`. Ни brief, ни
  сообщений ходов, ни отдельного сообщения `stop` не остаётся;
- `buildMessages` добавляет после ходов открытого состояния один `user`-working-промпт:
  `Goal` состояния, непроверенная догадка доксы (`Your earlier guess (may be wrong): …`), если
  задана, `Done when`, `Plan` и исходный запрос как reference; предположения запроса не
  переносятся в состояние как факты;
- **лента не монотонна.** Когда состояние оставлено позади, его `apply`-ходы уходят из ленты;
  остаётся лишь его тройка. Уходит только вид, а не данные: дерево остаётся полным;
- **рассуждение доксы не хранится**: сырое `thought` в дереве нет и в ленту не попадает; его
  смысл живёт в полях `why`.

## 4. Пометки и адреса

  модель видела, что уже не сработало;
- каждое `assistant`/`tool`-сообщение начинается с id узла (`[id] …`), чтобы результат можно
  было адресовать по `id` через `recall`/`search`.

## 5. Работа с данными

Тело результата ограничено самим инструментом, с **per-tool** бюджетом (окно `read` 32K;
`grep`/`list`/`run` 8K; `recall` 64K); `tool`-сообщение показывает окно инструмента целиком и никогда не
вырезает середину. Результат инспекции (`read`/`grep`/`list`) читается с начала, поэтому
остаётся голова; вывод команды важен в конце, поэтому `run` держит хвост. Усекается с пометкой
об усечении лишь тело, превышающее бюджет своего инструмента. Полное тело движок сохраняет файлом, а в узле остаётся ссылка. Доступ — по
идентификатору, не по пути:

- прочитать фрагмент — `recall { id, start, end }`;
- поискать по телу — `search { id, pattern }`.

`recall`/`search` оставляют узел (действие + его наблюдение среди ходов состояния), поэтому
полученное окно остаётся на ленте состояния как любой шаг и уходит вместе с состоянием на `stop`.
Отказ структурного хода узла не создаёт: причина приходит транзиентным `tool`-сообщением
(`rejected <ход>: <причина>`) на следующий ход.

## 6. Системная часть

Системная часть собирается по ситуации, а не монолитом:

- **базовый промпт** несёт только то, что верно на любом ходу — роль и контракт. Он стабилен,
  поэтому хорош как префикс кэша. Карта состояний и переходы вынесены в промпты
  request/transition. Имён/параметров/описаний инструментов здесь **нет** — они уходят полем
  `tools` запроса;
- **поверхность инструментов** в этом поле связана из `Context.applicable`: на
  `request`/`transition` предложен только `move`, пока состояние открыто — apply-инструменты
  (`recall`/`search` всегда); `stop` принадлежит движку (докса закрывает состояние текстом);
- **промпт ситуации** добавляется в конце для `request`, `transition`, `terminal` и открытого
  состояния (`working`), всегда временно, не хранится. `working` добавляет один `user`-ход с
  `Goal`, догадкой, `Done when`, `Plan` и запросом как reference. `request` (выбери первое
  состояние или `decline`; `what`/`done` — **из запроса**), `transition`
  (`transitionInstruction(island)`: источник `what`/`done` — строка `Finish state <label>`
  закрытого состояния; перечислены соседи по `next`; выбери следующее или End), `terminal`
  («This is End.» + правило текстового завершения);
- **ограничения** добавляются отдельными `system`-сообщениями.

Точная граница базы и ситуации — предмет следующего этапа (составной системный промпт).

## 7. Детерминизм

`project` чист: одни события дают одну ленту. Единственный транзиентный вход — результат
`recall`/`search` текущего хода (§5); поскольку он производится тем же ходом, проекция остаётся
детерминированной.

## 8. Цена проекции

Смена фокуса перезаписывает ленту, поэтому проекция не бесплатна. Цена делится на три части,
и структурны только первые две:

- **промах кэша префикса.** Базовый промпт — стабильный префикс, но `move` меняет ленту начиная
  с точки фокуса, поэтому хвост префиллится заново. Это латентность и деньги, а не лишний
  выход;
- **один ход на переход.** Вход в состояние — это ход (вызов модели); обход с бо́льшим числом
  состояний стоит больше ходов, чем один проход. Это плата за явные точки решения и за то, что
  проекция выбрасывает устаревшее содержимое, а не тащит его;
- **рассуждения на переориентацию.** Модели нужно свести «что было → почему сюда → что делать».
  Эта часть **не** неизбежна: это свойство спеки состояния, а не переходов как таковых. Чёткие
  `Goal`, brief, инструкция, критерий и строка `Finish state` стоят дёшево; тонкое состояние
  (Construction только со спекой после `O→C`) приглашает модель пойти осматриваться. Мерить
  надо reasoning на первом ходе после перехода против второго; стабильно дорогой первый ход —
  дефект определения состояния, а не шум провайдера.

Два следствия:

- первые две цены принимаются осознанно: они покупают детерминированную проекцию и адресуемость
  закрытых состояний. Обычный транскрипт платит в другом месте — растущим контекстом и
  устаревшим содержимым;
- считать надо цену **результата** (рубли на решённую задачу, ходы на задачу), а не цену
  перехода: один лишний короткий ход может быть дешевле одного длинного растерянного хода в
  старой ленте.

Шум провайдера — отдельно. За мета-провайдером разные субподрядчики могут вернуть ход вообще
без рассуждений; тогда один и тот же вход даёт разный маршрут. Это статистическая флуктуация,
промтом или effort её не вылечить; метрику маршрута читаем по сэмплам, где рассуждения есть.
Ретрай по лимиту завершения — не контрпример: он не переиспользует закэшированный «ход мысли»,
а пересобирает модель с выключенными рассуждениями (`reasoningOff`) и добавляет brevity-ноту
(`src/llm/structured.ts:490`), то есть меняет сам запрос. Попадание в кэш префикса пропускает
prefill и не меняет распределение сэмплирования.
