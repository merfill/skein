# Skein — операции IR и реестр операторов

> Английское зеркало — `docs/en/ir_operations.md`.
>
> Это формальный справочник: поверхность модели, операторы, запись закрытия, подробные
> таблицы инструментов, отказы и реестр покрытия. Концептуальная модель — в `ir.md`;
> лента сообщений — в `projection.md`.

## 1. Поверхность модели

Модель вызывает `move`, `apply` и `decline`; `recall` и `search` — инструменты только для чтения. Состояние закрывается обычным текстовым ответом, который исполнитель записывает как `stop`. Инструмента `stop` на поверхности модели нет.

## 2. Операторы

Модель располагает тремя вызываемыми операторами: `move`, `apply` и `decline`. `recall` и
`search` — инструменты только для чтения. Состояние закрывается обычным текстовым ответом;
исполнитель записывает это как `stop`-запись. Каждый оператор и запись закрытия описываются
предусловием, эффектами на журнал и модель работы, изменяемыми производными фактами, причинами,
по которым допустимость может быть отклонена, и проекцией. Каждая спецификация несёт стабильный
идентификатор, который тест цитирует как токен `ID` в своём заголовке.

Семейства идентификаторов: `OP-MV` для `move`; `OP-CG` для первого хода состояния, создаваемого
его первым `apply`; `OP-AP-READ`, `OP-AP-GREP`, `OP-AP-LIST`, `OP-AP-EDIT`, `OP-AP-WRITE`,
`OP-AP-RUN`, `OP-AP-FETCH` и `OP-AP-PATCH` для под-инструментов apply (префикс `RUN` обозначает
инструмент `bash`); `OP-AP-PLACE` для размещения `apply` в состоянии; `OP-ST` для `stop`;
`OP-DC` для `decline`; `OP-RC` и `OP-SR` для `recall` и `search`; `TR` для фокуса и
списков; `DER` для производных фактов; `REF` для отказов; `PRJ` для правил проекции.

### 2.1 `move`

`move` объявляет состояние — вид работы, — в котором модель будет работать. Это переход
автомата.

**Вход.** `{ state, what? }`. Поле `state` есть одно из имён состояний, предлагаемых промптом
запроса или перехода. Поле `what` есть необязательная заметка о конкретном предмете — догадка,
которая может быть ошибочной, а не цель состояния. Поле `done`, сохранённое для совместимости, принимается в старых
журналах, но не предлагается модели и не отображается.

**Действие.** Исполнитель создаёт узел `move` `M` с содержимым `{ state, what }`, связывает его как
новейшего `move`-ребёнка запроса и записывает смещение фокуса. `move` законен на свежем запросе
(`move` ещё отсутствует) и на завершённом состоянии (`move`, несущем `stop`). Он отклоняется,
пока состояние открыто (`state_open`), и при недопустимом имени состояния (`empty_state`).

| Случай | Предусловие | Эффекты | Производные факты | Отказы | ID |
|---|---|---|---|---|---|
| открыть состояние | фокус есть запрос, и `move` отсутствует | добавить `move` (`state`, `what`); добавить связь `move` от запроса; сместить фокус | состояние объявлено; его ходы пусты до первого `apply` | `empty_state` | `OP-MV-1` |
| переход в следующее состояние | текущее состояние finished | добавить `move` как нового ребёнка запроса, сиблинга предыдущего состояния; оставить завершённое состояние позади; сместить фокус | завершённое состояние остаётся на ленте как `Start` + `Finish`; фокус есть новый `move` | `empty_state`, `state_open`, `unreachable`, `not_startable` | `OP-MV-2` |
| вход в терминальное состояние | цель есть `end` | как выше, без `what`; терминальное состояние принимает `stop` напрямую | вход в терминальное состояние отмечает конец запуска | `empty_state` | `OP-MV-3` |

- **Проекция** (`PRJ-MV`): открытое состояние отображает маркер `Start state <label>` (ход
  `system`), краткую справку об этом состоянии (ход `system`) и свои ходы. Рабочий промпт хода
  добавляется `buildMessages` после ходов (ход `user`) и несёт `Goal`, догадку модели,
  `Done when` и `Plan`. После остановки состояния остаются только `Start state <label>` и
  `Finish state <label> — <why>` (плюс `Artifacts:`, если состояние записало файлы); краткая
  справка, рабочий промпт и сообщения ходов элидируются.
- `move` отклоняется, пока состояние открыто (`state_open`). Исполнитель не решает, когда
  состояние завершено: модель закрывает его через `stop` и выбирает следующее состояние. Поле
  `what` необязательно.

### 2.2 `apply`

`apply` исполняет одну команду в текущем состоянии. Он же порождает ходы состояния: первый
`apply` после `move` создаёт узел `turns` и его первый `turn` (`OP-CG-1`). Этот первый ход
является обычным вызовом инструмента, а не отдельным оператором.

**Вход.** `{ tool, … }`, где `tool` есть один из `read`, `grep`, `list`, `edit`, `write`,
`bash`, `fetch` или `apply_patch`, вместе с параметрами соответствующего инструмента.

**Действие.** Команда исполняется. Её исход записывается либо как `A.result = observation` (для
`read`, `grep`, `list`, `bash` и `fetch`), либо как `A.mutates += file` (для `edit`, `write` и
`apply_patch`); если команда не исполнялась, исходом является наблюдение с причиной. Действие
дописывается в ходы состояния (см. `ir.md` §3). Фокус не перемещается. `apply` допустим только внутри
открытого состояния; в остальных случаях он отклоняется с `no_state`.

**Размещение.** Каждый `apply` дописывает ровно один ход в `turns` открытого состояния, по
порядку (`OP-AP-PLACE-1`). После исполненного хода следующий `apply` дописывает следующий ход
(`OP-AP-PLACE-2`). Промежуточного слоя пунктов плана и курсора не существует. Исполнитель никогда не
входит в действие.

**Пакеты.** Исполнитель принимает один или несколько вызовов за ход и применяет их по порядку в
пределах одного хода, с общим номером хода. Терминальный ход (`move`, `stop` или `decline`)
завершает пакет, поэтому всё, что модель испускает после него, отбрасывается
(`src/loop/graph.ts`, `executeNode`). Проекция отображает пакет как одно сообщение `assistant` с
N `tool_calls`, за которым следуют N результатов `tool` (`ir.md` §4).

| Случай | Предусловие | Эффекты | Производные факты | Отказы | ID |
|---|---|---|---|---|---|
| первый ход | фокус есть нетерминальный `move` без ходов | `apply` создаёт узел `turns` и его первый `turn` для любого инструмента; исполнитель исполняет его немедленно | состояние приобретает ходы; первый ход исполнен | отсутствуют; пустой `bash` есть провальное наблюдение, `REF-RUN-EMPTY` | `OP-CG-1` |
| следующий ход | фокус есть открытое состояние, имеющее ходы | `apply` дописывает следующий `turn` (`OP-AP-PLACE-1`); после исполненного хода следующий `apply` дописывает следующий ход (`OP-AP-PLACE-2`) | ходы растут в порядке добавления | `no_state` | `OP-AP-PLACE-1`, `OP-AP-PLACE-2` |

#### 2.2.5 `bash` (`OP-AP-RUN`)

`bash` — одна синхронная команда. `target` и машинерия фоновых задач отсутствуют.
Префикс реестра `RUN` исторический; имя инструмента в IR — `bash`.

| Случай | Предусловие | Эффекты | Производные факты | Отказы | ID |
|---|---|---|---|---|---|
| команда | `command` задан | действие и `observation`, несущее `command` и `exitCode`; `mutate` для каждого изменённого файла | версии изменяются; прежние чтения устаревают | `repeated_action` | `OP-AP-RUN-1` |
| большой вывод | поток превышает байтовый лимит | наблюдение сохраняет хвост встроенно, где находятся ошибка и код завершения, с пометкой об опущении; полный поток остаётся за `outputRef` и `errorRef` и извлекается посредством `recall` | — | — | `OP-AP-RUN-2` |
| workdir | `workdir` называет существующий путь внутри рабочей области | команда исполняется в этом каталоге | — | провальное наблюдение с `workdir does not exist` (каталог не существует) или `path escapes workspace` (путь выходит за пределы рабочей области) | `OP-AP-RUN-3` |

ограничивает одну эту команду в миллисекундах. Оба поля входят в сигнатуру повтора, поэтому тот
же текст в другом каталоге или с другим ограничением считается новым действием.

### 2.3 Закрытие (запись `stop`)

`stop` — это запись закрытия состояния, а не вызов инструмента. Модель закрывает открытое
состояние текстовым ответом; исполнитель записывает связь `stop`, принимая ответ в качестве
причины. В терминальном состоянии (`end`), не имеющем ходов, то же закрытие завершает запуск.
Модель решает по ходу работы.

**Вход.** Текст ответа; он сохраняется в `why`.

**Действие.** Если фокус есть открытое состояние, исполнитель создаёт узел `stop` `S` и связывает
`M.stop = S`. Состояние становится finished, и следующим решением является переход (§2.1). Если
фокус есть терминальное состояние, то же закрытие завершает запрос с `request_addressed`.
`stop` на запросе или на уже завершённом состоянии отклоняется с `not_addressed`.

| Случай | Предусловие | Эффекты | Производные факты | Отказы | ID |
|---|---|---|---|---|---|
| завершить работу состояния | фокус есть открытое состояние | добавить узел `stop` и связь `stop` от `move` состояния | состояние finished; фокус возвращается к его `move` | — | `OP-ST-1` |
| записать закрытие на move | состояние | узел `stop` висит на `move`, а не на ходе; причина хранится в `why` | закрытие и его причина находятся на `move` | — | `OP-ST-2` |
| завершить запрос | фокус есть терминальное состояние (`end`) | добавить узел `stop` и связь `stop` от `move` | запуск завершается со stopReason `request_addressed` | — | `OP-ST-3` |
| не в закрываемом состоянии | фокус есть запрос или нетерминальный `move` | — | — | `not_addressed` | `REF-ST-STATE` |

- **Проекция** (`PRJ-STOP`): закрытие состояния отображается маркером `Finish state <label> —
  <why>`. `stop` не добавляет вызова инструмента, а сообщения ходов состояния уходят с ленты.
- Состояние закрывается только посредством `stop`, связи на его `move`. Терминальное состояние
  закрывается тем же способом. На запросе `stop` отсутствует; запрос завершается, когда
  остановлено его терминальное состояние.

### 2.4 `decline`

`decline` завершает запрос, намерение которого недейственно, не изобретая состояния. Он
доступен только пока запрос не имеет `move`. Он записывает узел `unactionable` под запросом и
завершает запуск.

**Вход.** `{ why? }` — причина.

**Действие.** Исполнитель создаёт узел `unactionable` `U` и связывает `R.unactionable = U`. Ни
`move`, ни ходы не создаются. Запуск завершается с `request_unactionable`. На `move` операция
отклоняется с `not_request`, на уже интерпретированном запросе — с `interpreted`.

| Случай | Предусловие | Эффекты | Производные факты | Отказы | ID |
|---|---|---|---|---|---|
| отклонить запрос | фокус есть запрос без `move` и без узла `unactionable` | добавить узел `unactionable` и связь от запроса; запуск завершается | запрос терминален (`request_unactionable`) | — | `OP-DC-1` |
| не на запросе | фокус есть `move` | — | — | `not_request` | `REF-DC-NOTREQ` |
| запрос уже начат | запрос уже имеет `move` | — | — | `interpreted` | `REF-DC-ADDR` |

- **Проекция** (`PRJ-DC`): `decline` предлагается на свежем запросе наряду с `move`.

### 2.5 `recall` и `search`

`recall` и `search` представляют собой инструменты только для чтения, адресующие сохранённый
результат по идентификатору. Ни один из них не изменяет модель работы. `recall` открывает тело,
при необходимости окно строк; `search` ищет шаблон внутри него. Оба оставляют `action` и его
`observation` в ходах состояния, как и любой другой шаг, поэтому полученное окно остаётся на
ленте состояния, пока состояние открыто, и элидируется при его остановке (`ir.md` §4). Они являются
различными инструментами, чтобы модель не смешивала чтение файла или результата (`read`) с
поиском (`grep` или `search`).

`recall { id, start?, end? }` (`OP-RC`):

| Случай | Предусловие | Эффекты | ID |
|---|---|---|---|
| по идентификатору | идентификатор адресует сохранённое тело — наблюдение или встроенное тело | `action` и `observation` в ходах состояния; запрошенное окно возвращается, а при более длинном теле добавляется курсор `continue from N` | `OP-RC-1` |
| окно | `start` и `end` | окно строк, продолжение выполняется новым `recall` | `OP-RC-2` |
| большое тело | тело превышает байтовый бюджет | окно сокращается по целым строкам (`QUERY_BODY_LIMIT`) и остаётся корректным JSON, никогда не обрезаясь посреди строки; поток ошибок, если он есть, представляет собой ограниченный встроенный хвост | `OP-RC-3` |
| тело отсутствует | идентификатор обозначает действие или другой узел без тела | `(nothing to recall: <id> has no stored body)` | `OP-RC-4` |
| неизвестный идентификатор | — | `(nothing to recall: <id> is not a node)` | `OP-RC-5` |
| отображение в состоянии | — | recall отображается как ход открытого состояния и элидируется вместе с состоянием при `stop`, без TTL и без рабочего набора | `OP-RC-6` |

`search { id, pattern, before?, after? }` (`OP-SR`):

| Случай | Предусловие | Эффекты | ID |
|---|---|---|---|
| по шаблону | идентификатор адресует сохранённое тело, а `pattern` является регулярным выражением | `action` и `observation` с окнами совпадающих строк по stdout и stderr в формате JSON, вместе с контекстом | `OP-SR-1` |
| stderr | тело имеет поток ошибок | совпадения в потоке ошибок несут `stream: "stderr"` | `OP-SR-2` |
| широкий шаблон | совпадений больше, чем вмещает окно | хвостовые результаты отбрасываются целиком; примечание сообщает `showing N of M; narrow the pattern`, и висячий `next` не создаётся, поскольку у `search` нет постраничности | `OP-SR-3` |
| отсутствие совпадений | — | пустой массив `results` | `OP-SR-4` |
| недопустимый шаблон | `pattern` не является регулярным выражением | `{ …, error: "invalid pattern" }` | `OP-SR-5` |
| тело отсутствует | идентификатор не имеет сохранённого тела | `(nothing to search: <id> has no stored body)` | `OP-SR-6` |
| контекст | `before` и `after` | заданное число строк контекста на совпадение, по умолчанию три | `OP-SR-7` |

- **Проекция** (`PRJ-RC`): полученное тело входит на ленту как `action` и `observation`,
  отображается, пока состояние открыто, и элидируется при `stop`.
- **Проекция** (`PRJ-REF`): отклонённый структурный ход не создаёт узла; его причина входит на
  ленту как временное сообщение `tool`, `rejected <move>: <reason>`, на следующий ход.

### 2.6 Фокус, списки и производные факты

Фокус есть детерминированная часть исполнителя: он вычисляет допустимые ходы в текущей точке.
Производные факты читаются из журнала; ничего не хранится.

| Случай или предикат | Правило | ID |
|---|---|---|
| фокус | фокус есть `branch[last]`, а при пустой ветви — корень | `TR-1` |
| descend | `focusEvents` спускается в текущий `move` запроса | `TR-2` |
| return | завершённая вершина снимается при `stop` или при следующем `move`; `return` допустим | `TR-3` |
| плоские состояния | состояния являются детьми запроса через `move` и никогда не вложены; `move` после завершённого состояния есть сиблинг | `TR-4` |
| выбор списка | запрос содержит `move`, `move` содержит `turns`, `turns` содержит `turn` | `TR-5` |
| порядок ходов | ходы следуют порядку связей `turn`; последний является текущим; список только растёт и не имеет курсора | `TR-6` |
| размещение | входящий `apply` дописывает следующий ход (`OP-AP-PLACE`) | `TR-7` |
| множество допустимых ходов | `applicable` вычисляет `move`, `apply`, `stop` и `decline` из тех же фактов, что используют проверки допустимости; модель выбирает | `TR-8` |
| отображение хода | каждая команда отображается как собственная пара штатного вызова и результата, без маркера вариантов | `TR-9` |
| состояние closed или finished | `move` имеет связь `stop` с узлом `stop` | `DER-MOVE-1`, `DER-STATE-1` |
| запрос finished | существует узел `unactionable` либо текущий `move` есть терминальное состояние и finished | `DER-REQ-1` |
| текущее состояние | `state` последнего `move`-ребёнка запроса | `DER-STATE-2` |
| структурный лес | рабочие связи `move`, `turns`, `turn`, `stop` и `unactionable` образуют лес, в котором у каждого узла один родитель | `DER-FOREST-1` |
| действие executed | действие имеет связь `result` или `mutates` | `DER-ACT-1` |
| свидетельство запуска | наблюдение запуска несёт `witness`, основу устаревания | `DER-STALE-1` |

## 3. Версии и свидетельство

- Версия файла есть идентификатор его содержимого, а именно хэш. Содержимое предыдущих версий
  не хранится в IR; блобы находятся в рабочей области.
- `history(ref)` есть последовательность версий `ref` в порядке событий `mutate`, а
  `current(ref)` — последняя из них. Обе являются производными.
- Наблюдение, полученное чтением файла, несёт прочитанную версию. Хранимого флага «stale» не
  существует: актуальность есть отношение между фактом и текущим контекстом, а именно
  `actual(fact) ⇔ fact.version = current(fact.ref)`.
- Журнал только растёт. Изменение знания — новая версия, наблюдение или гипотеза — есть новая
  запись; пересчитывается только производный вид.
- Наблюдение запуска несёт свидетельство — снимок рабочей области на момент запуска. Последующий
  `mutate` делает факты о предыдущей версии устаревшими, поэтому успешная проверка не может
  молча остаться действительной.

## 4. Завершение и ошибки

| Условие | Чем закрывается | Производное состояние |
|---|---|---|
| открытое состояние | `stop`, без дополнительного условия | closed; связь `stop` ведёт от move к stop; состояние finished, а фокус остаётся на его `move` |
| терминальное состояние (`end`) | `stop`, без дополнительного условия | closed; запрос завершается с `request_addressed` |
| запрос | завершается, когда остановлено терминальное состояние (`request_addressed`), либо при отклонении (`request_unactionable`); на запросе `stop` отсутствует | запуск завершается |

**Ошибка есть результат.** При устойчивой ошибке модели (`llm_error`) исполнитель закрывает
состояние, в котором произошёл сбой вызова, посредством принадлежащего исполнителю `stop` с
`error: true`, входит в терминальное состояние и пишет там окончательный отчёт. Если отчётный
вызов также завершается сбоем, отчёт детерминированно строится из строк `Finish`. Значение
`stopReason` остаётся `llm_error`, а терминальный `stop` помечен `error`, поэтому сессия
выводит `abandoned`, а не `completed`.

**В IR нет оценки запроса.** Терминальное состояние завершает запуск; запрос заканчивается,
когда оно закрыто. В IR нет узла «принято» и нет поля «успех/неуспех»: журнал фиксирует
происшедшее. Код возврата команды — обычное наблюдение. Гипотеза не хранится как допущение.

## 5. Отказы и неисполнение команд

Проверка допустимости `classify` (`src/loop/classify.ts`) отклоняет только структурные ходы. Отказ испускает
`record_rejection` и обязан изменить проекцию, как того требуют инварианты. Команда
обрабатывается исполнителем (`src/tools/index.ts`); её неисполнение записывается как `action` и
`observation` с причиной, а не как отказ без узла.

**Структурные отказы (`record_rejection`).**

| Токен причины | Триггер | Оператор | ID |
|---|---|---|---|
| `empty_state` | некорректный `move` с неизвестным `state` | `move` | `REF-MV-EMPTY` |
| `not_startable` | `move` в живое состояние, которое не может начать запрос | `move` | `REF-MV-NOT-STARTABLE` |
| `unreachable` | `move` вне `next`-соседей завершённого состояния | `move` | `REF-MV-UNREACHABLE` |
| `no_state` | `apply`, когда фокус не является открытым состоянием | `apply` | `REF-AP-NO-STATE`, `REF-NO-STATE` |
| `not_in_state` | `apply` с инструментом вне `applies` вида состояния | `apply` | `REF-NOT-IN-STATE` |
| `state_open` | `move`, пока текущее состояние открыто | `move` | `REF-STATE-OPEN` |
| `not_addressed` | `stop`, когда фокус не является ни открытым, ни терминальным состоянием | `stop` | `REF-ST-STATE` |
| `not_request` | `decline` в фокусе, отличном от запроса | `decline` | `REF-DC-NOTREQ` |
| `interpreted` | `decline` на запросе, уже имеющем `move` | `decline` | `REF-DC-ADDR` |

Идентификаторы `REF-AP-NO-STATE` и `REF-NO-STATE` называют один и тот же отказ; они сохранены
как токены реестра, поскольку их цитируют разные семейства тестов.

**Неисполнение команд, записываемое как `action` и `observation` с причиной.**

| Причина | Триггер | Оператор | ID |
|---|---|---|---|
| `repeated_action` | идентичные `read`, `grep` или `bash` при неизменном мире | `read`, `grep`, `bash` | `REF-REPEAT` |
| `no_state` | `recall` или `search` вне открытого состояния | `recall`, `search` | `REF-RC-STATE` |
| пустая команда | пустой `bash` | `bash` | `REF-RUN-EMPTY` |
| `stale_base` | `edit` файла, изменённого после чтения | `edit` | `REF-EDIT-STALE` |
| запрещённый шаблон | `edit` запрещённого пути | `edit` | `REF-EDIT-CONSTRAINT` |
| `stale_base` | `write` поверх файла, изменённого после чтения | `write` | `REF-WRITE-STALE` |
| запрещённый шаблон | `write` в запрещённый путь | `write` | `REF-WRITE-CONSTRAINT` |

Провалы инструментов, напротив, записываются как провальные наблюдения: отсутствующий файл в
`read`, недопустимая область в `grep` или `list`, отсутствующий `find` в `edit`, а также
ненулевой код возврата, таймаут или сигнал в `bash`.

## 6. Реализация

Система различает четыре уровня.

```
                 только пополнение          pure            pure
  actions ─▶ journal (Event[]) ──fold──▶ State ──project──▶ Context ──▶ LLM
     ▲                                                             │
     └─────────── предложение: один или несколько операторов за ход ◀────────┘
```

1. **Журнал** (`src/ir/events.ts`) только пополняется и представляет собой единственный
   источник истины.
2. **Состояние** (`src/ir/graph.ts`, `src/ir/traversal.ts`) есть `fold(events)`: оно включает
   узлы, связи, порядок списков, производные вспомогательные функции, фокус и версии файлов.
3. **Контекст** (`src/ir/project.ts`) есть `project(state)`, детерминированная лента сообщений.
4. **Лента** является единственной поверхностью ввода-вывода: системная часть, включающая
   базовый промпт, краткую справку состояния и ограничения; запрос; и история. Факты пробы
   появляются в записи текущего состояния.

Перед выполнением `project` исполнитель согласует активные `ref` с файловой системой
(`src/loop/observe.ts`), и любое расхождение становится событием `mutate`.

**Карта кода.**

| Область | Файлы |
|---|---|
| виды узлов и связей, содержимое | `src/ir/types.ts` |
| схема событий и закрытый словарь | `src/ir/events.ts` |
| свёртка, производные факты, версии | `src/ir/graph.ts` |
| фокус и допустимые ходы | `src/ir/traversal.ts` |
| состояния, цели, критерии и поверхности apply | `src/ir/islands.ts` |
| проекция | `src/ir/project.ts`, `src/loop/propose.ts` |
| проверка структурных отказов | `src/loop/classify.ts` |
| команды, наблюдения и отказы | `src/tools/index.ts` |
| схема инструментов и имена на поверхности модели | `src/llm/schemas.ts`, `src/llm/tools.ts` |

## Расширение реестра

1. Добавить точку спецификации в настоящий документ с новым стабильным идентификатором, её
   предусловием, эффектами, производными фактами и отказами; если отказ новый, добавить его
   токен в §5.
2. Добавить офлайн-тест, цитирующий идентификатор в своём заголовке.
3. Добавить live-сценарий только в том случае, если семейству операторов требуется проверка
   end-to-end.
4. Проверка полноты покрытия завершается неудачей, пока матрица не содержит тест.
