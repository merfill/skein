# Skein — системный промпт: поведение и блоки

> Английское зеркало — `docs/en/system_prompt.md`.
>
> Это источник истины о поведении промпта. Правка поведения идёт так: правка здесь, правка блока
> в `src/loop/prompt/blocks.ts`, тест. Связанные документы: `ir.md` (состояния и лента),
> `ir_operations.md` (реестр инструментов), `projection.md` (что видит модель), `states.md`
> (цели состояний).
>
> Документ описывает промпт **агента задачи**. У `general`, `plan` и `document` свои базовые
> промпты (`GENERAL_BASE_PROMPT`, `PLANNER_BASE_PROMPT`, `DOCUMENT_BASE_PROMPT`); их единицы
> request-anchored и не используют `move`.

## 1. Назначение

Промпт описывает **пространство состояний работы**, а не список действий. У состояния есть цель,
условие завершения, инструкция и поверхность инструментов; переход вызван результатом самого
состояния. Эта форма удерживает траекторию сходящейся: без неё модель теряется и не знает, что
делать дальше.

Промпт проверяется на трёх уровнях:

- **L1 — статический контракт** (`tests/prompt.test.ts`, офлайн, CI): сборка, id блоков, имена
  инструментов, обязательные формулировки;
- **L2 — живые сценарии** (`tests/live/scenarios.test.ts`): форма траектории на фикстуре;
- **L3 — бенч и реальные задачи**: поведение на настоящей работе.

L2 и L3 зависят от недетерминизма модели и потому слабее; L1 обязателен.

## 2. Терминология

| Понятие | Термин | Где |
|---|---|---|
| состояние работы | **state** | `move { state, what? }`, `Start state <label>` |
| переход в состояние | **move** | инструмент `move` |
| условие завершения состояния | **Done when** | условие вида состояния, отображается в рабочем промпте |
| закрытие состояния | **текстовый ответ** | модель отвечает без вызова инструмента; исполнитель записывает `stop` |
| строка закрытия состояния | **`Finish state <label> — <why>`** | маркер на ленте |
| терминальное состояние | **End** (`end`) | `move { state: "end" }` |

`what` — необязательная заметка о конкретном предмете. Поле `done`, сохранённое для
совместимости, модели не предлагается и не отображается. Инструмента `stop` нет: состояние
закрывается только текстовым ответом модели, записанным как `stop`. Запрос — справочный
контекст, а не цель.

## 3. Сборка

- Промпт состоит из стабильной **базы** (`BASE_PROMPT`, верна на любом ходу) и **промптов
  ситуаций** (`request`, `working`, `transition`, `terminal`), собираемых в
  `src/loop/prompt/blocks.ts`.
- Базовые блоки — `B1` (роль) и `B2` (принципы). Промпты ситуаций именованные, никогда не `B…`.
- `src/loop/propose.ts` собирает список сообщений так: `BASE_PROMPT`, ограничения, лента
  (история), затем промпт ситуации **в конец** — временно: он пересобирается из ситуации каждый
  ход и никогда не хранится. `working` добавляет один ход `user`; `request`, `transition` и
  `terminal` — ход `system`.
- Контракт инструментов (имена, параметры, описания) **не** копируется в текст промпта: он
  уходит полем `tools` запроса, генерируется из единого реестра `PROPOSAL_TOOLS`
  (`src/llm/tools.ts`).

**Инварианты сборки:**

1. один блок = одно поведение; нет дублирования между блоками;
2. у каждого поведения есть id (базовый блок) или имя (промпт ситуации);
3. собранный промпт равен склейке блоков;
4. промпт **не** повторяет описания инструментов — они уходят в поле `tools`.

## 4. Блоки

Промпт намеренно простой: он задаёт требования исполнителя, а не способ думать. Стратегия живёт
в описаниях инструментов и в ленте.

| ID | Блок | Поведение |
|---|---|---|
| B1 | `role` | Агент кодирования; ровно одно состояние за раз; состояние — его цель с собственным условием завершения; работать, пока оно не выполнено, затем ответить только текстом; после закрытия выбрать следующее состояние через `move`; каждый ход — вызовы инструментов, исполняются по порядку, независимые вызовы батчатся |
| B2 | `principles` | Следовать проекту; работать только цель состояния; предпочитать специальные инструменты; инспектировать узко; результат берётся из материала или спецификации; не восстанавливать внешнюю версию по памяти; сохранять материал; не перепроверять факты исполнителя; без секретов; краткий вывод — самый короткий ответ, если не попросили подробнее |

### Промпты ситуаций

| Имя | Ситуация | Роль | Содержание |
|---|---|---|---|
| `request` | свежий запрос | `system` | выбрать ровно одно из Patch, Construction или Research; `decline` тоже доступен; запрос — контекст, а не цель |
| `working` | открытое состояние, после его ходов | `user` | `Goal`, прежняя догадка модели, `Done when`, `Plan` и запрос, помеченный как справочный |
| `transition` | после строки `Finish state` | `system` | строка `Finish` — источник результата; следующие состояния перечислены по их условию `next`; вызвать `move` отдельно с `what`, `done` не передавать |
| `terminal` | End | `system` | `This is End.` плюс инструкция End; ответить окончательным отчётом текстом, без вызовов инструментов |

### Лента состояния

Состояние отображается на ленте по порядку:

| Имя | Сообщение | Роль |
|---|---|---|
| `start` | `Start state <Label>` | `system` |
| `справка` | факты исполнителя для состояния | `system` |
| `turns` | вызовы инструментов состояния и их результаты | `assistant` / `tool` |
| `working` | один ход после ходов: `Goal`, догадка, `Done when`, `Plan`, запрос как справочный | `user` |
| `finish` | `Finish state <Label> — <why>` | `system` |

Запрос ведёт ленту после базового промпта и ограничений, на каждом ходу. `start` и `справка`
показываются, пока состояние открыто; `working` пересобирается каждый ход и не хранится. При
закрытии остаются только `start` и `finish`, а при использовании `write` или `edit` — строка
`Artifacts:`.

## 5. Карта тестов

| Уровень | Где | Что проверяет |
|---|---|---|
| L1 | `tests/prompt.test.ts` | сборка из блоков; уникальность id; промпт не повторяет описания инструментов; раздельность потоков и `pipefail` в описании `bash`; защита от устаревшего чтения в `edit`/`write`; корень рабочей области |

## 6. Открытые вопросы

- Целевой бюджет символов промпта и что вынести в описания инструментов.
- Насколько строгими должны быть `B1`/`B2`: сколько порядка задавать, сколько гибкости оставлять.
- Эвристика diff или локализации, если она понадобится, — это опциональная подсказка инструмента,
  а не базовый блок.
