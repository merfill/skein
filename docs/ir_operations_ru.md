# Skein — операции над IR: справочник и матрица тестов

> Английский оригинал — `docs/ir_operations.md`.

Связанные: `docs/ir_semantics_ru.md` (формальная семантика — этот документ есть
операционный справочник и контракт покрытия, а не вторая формализация),
`docs/projection_ru.md`, `docs/tools_ru.md`, `docs/ir_ru.md`, `docs/walkthrough_ru.md`,
`docs/testing_ru.md`.

Статус: **Специфицировано (протокол состояний) — реализация в работе.** §1–§4 специфицируют
модель и каждую операцию; §5 — матрица покрытия (перезаполняется по мере реализации протокола
состояний, `docs/plans/archive/state_protocol_plan_ru.md`). Идентификатор **стабилен**: у пункта могут
появиться тесты, но его смысл не меняется.

> **Протокол состояний** (`docs/plans/archive/goal_into_move_plan_ru.md`). Обход — машина состояний по
> островам: `move` объявляет состояние — его цель — собственное определение острова, — и,
> необязательно, заметку `what` (узел `move`, плоский ребёнок запроса), первый `apply` засевает
> план состояния, `apply` работает его, `stop` закрывает и
> вынуждает переход. Узла `goal` и оператора `create_goal` нет — состояние само несёт свою
> цель; `state` живёт
> на её `move`. Закрытие динамическое: `stop` доксы закрывает цель/состояние; нет критерия, нет
> гейта по exit code, нет `done_when`/`step`/`revises` и нет `state` у цели (`exitCode` —
> обычный вывод).

## 0. Как читать этот документ

Каждая операция описана как:

- **Pre** — когда допустима (допустимые ходы/предусловие логоса).
- **Effects** — какие события журнала и какое изменение дерева она эмитит.
- **Derived** — какие факты меняются в результате.
- **Refuses** — причины отказа (`classify`), каталог в §3.
- **Projection** — как результат виден в следующем контексте (§ проекция).
- **ID** — стабильный идентификатор; тест ссылается на него как на токен `ID` в заголовке.

Семейства ID: `OP-MV` move, `OP-CG` первый пункт плана состояния (его первый `apply`), `OP-AP-READ|GREP|LIST|EDIT|WRITE|RUN|FETCH|PATCH`
инструменты `apply`, `OP-AP-PLACE` как `apply` ложится в дерево, `OP-ST` stop,
`OP-DC` decline, `OP-RC`/`OP-SR` recall/search, `TR` обход/контейнеры, `DER` производные
факты/предикаты, `REF` отказы (каталог), `PRJ` проекция (ссылки).

## 1. Модель

### 1.1 Рабочие узлы (`src/ir/types.ts`)

| Kind | Payload | Роль |
|---|---|---|
| `request` | `{text}` | сырая мотивация; корень; проходится как последовательность состояний; завершается, когда остановлено терминальное состояние |
| `move` | `{state, what}` | объявленное доксой состояние (остров) и необязательная заметка `what`; плоский ребёнок запроса |
| `goal` | `{what}` | конкретная работа одного состояния (`move.goal`) |
| `plan` | — | упорядоченный контейнер пунктов цели (`items`); ПОСЛЕДНИЙ пункт — текущий |
| `item` | — | упорядоченный контейнер альтернатив пункта (`alts`: действия); ПОСЛЕДНЯЯ — текущая |
| `action` | `{command, ...}` | один прогон инструмента; альтернатива пункта |
| `observation` | `{ref?, version?, command?, exitCode?, output/error/...}` | тело результата инструмента; `exitCode` — обычный вывод, не оракул закрытия |
| `stop` | `{why?}` | закрывает цель в фокусе (stop цели) либо терминальное состояние (stop `move`) |
| `unactionable` | `{why?}` | намерение запроса не действенно; докса отказывается формулировать цель (связь `unactionable`) |
| `constraint` | `{forbid: string[]}` | инвариант; сеется при старте прогона |
| `file` (artifact) | — | упомянутый файл; порождается `mutates` |

### 1.2 Связи (`src/ir/types.ts`)

| Связь | From → To | Смысл |
|---|---|---|
| `move` | request → move | состояния запроса, по порядку (ПОСЛЕДНЕЕ — текущее) |
| `unactionable` | request → unactionable | докса отказалась формулировать цель для запроса |
| `goal` | move → goal | работа состояния |
| `stop` | move → stop | терминальное состояние закрыто доксой |
| `plan` | goal → plan | контейнер плана цели |
| `stop` | goal → stop | цель закрыта доксой |
| `items` | plan → item | упорядоченное членство (порядок = последовательность; ПОСЛЕДНИЙ пункт — текущий) |
| `alts` | item → action | упорядоченные альтернативы пункта (ПОСЛЕДНЯЯ — текущая) |
| `result` | action → observation | тело результата действия |
| `mutates` | action → file | действие изменило файл |

### 1.3 События (`src/ir/events.ts`)

`add_node`, `add_edge`, `descend`, `return`, `mutate`, `record_rejection`. `fold`
применяет их по порядку; состояние (`children`, `branch`, `focusOf`, версии) —
**производное**, никогда не хранится. Нет `record_check` и нет `set_status`: смена
состояния — это новое событие-узел (`move`/`observation`/`stop`). Результат прогона — обычная
`observation`; её `exitCode` — вывод, не вердикт.

### 1.4 Контейнеры и обход

- **branch** — стек кадров состояния (`move` → `goal`) от корня-запроса до фокуса; `descend` кладёт, `return` снимает (`TR-1`).
- **focus** — `branch[last]`, иначе корень (`TR-1`).
- **plan** — цель связи `plan`; **пункты** — рёбра `items` в порядке вставки;
  **последний** пункт — текущий.
- **alternatives** — дети пункта (`alts`); **текущая** альтернатива — последний
  ребёнок (связи `chosen` нет).
- **frontier** — допустимые ходы в фокусе, вычисляются **один раз** и разделяются
  проекцией и `classify` (`TR-8`). Движок не диктует единственный следующий ход.

## 2. Операции

### 2.1 `move` (`OP-MV`)

Объявляет состояние (остров работы), в котором докса будет работать, И текст цели состояния
(`what`) — состояние **ЕСТЬ** своя цель (docs/plans/archive/goal_into_move_plan.md); план вешается
прямо на `move`. Состояния — **плоские дети** запроса (связь `move`): новый `move` после
завершённого состояния — новый ребёнок запроса (сиблинг предыдущего состояния), никогда не
вложен под него.

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| открыть состояние | фокус — запрос ещё без `move` | добавить `move` (`state`, `what`); связь `move` request → move; `descend` | состояние объявлено; фокус → `move`; план пуст до первого `apply` | `empty_state` | `OP-MV-1` |
| переход к следующему состоянию | текущее состояние **завершено** (остановлено) | добавить `move` (новый ребёнок запроса, сиблинг предыдущего состояния); `return` из завершённого состояния, затем `descend` | завершённое состояние оставлено позади; фокус → новый `move` | `empty_state`, `state_open` | `OP-MV-2` |
| терминал | состояние — `end` | как выше (без `what`); терминальное состояние принимает `stop` напрямую (`OP-ST`) | переход в терминал — знак конца | `empty_state` | `OP-MV-3` |

- **Projection** (`PRJ-MV`): открытое состояние получает маркер `Start state <label>`
  (`assistant`), инструкцию (`system`) и цель (`user`). Когда состояние остановлено, остаются
  только `Start state <label>` / `Finish state <label> — <why>` (из связи `move.stop`); brief,
  инструкция, цель и ходы плана элиминируются (§7 семантики).
- **Notes.** `move` отклоняется, пока состояние ещё открыто (`state_open`). Движок **не**
  гейтит `move` по критерию: докса решает, когда состояние завершено (она его `stop`ит) и куда
  идти дальше. `what` обязателен, кроме терминального `end`.

### 2.2 первый пункт плана состояния (`OP-CG`)

Конкретная работа состояния — это его план, повешенный прямо на `move` (узла `goal` **нет**).
Первый пункт плана — обычный `apply`: первый вызов инструмента, который докса делает после
`move`, сеет план (docs/plans/archive/goal_into_move_plan.md §3).

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| первый пункт плана | фокус — нетерминальный `move` без плана | `apply` создаёт `plan` с одним `item`, чья единственная альтернатива — `action` (любой инструмент); движок сразу исполняет его | состояние получает план; первый пункт исполнен | — (bash без команды — это fail-наблюдение, `REF-RUN-EMPTY`) | `OP-CG-1` |

- **Projection** (`PRJ-CG`): лента получает нативный вызов `apply` + его `tool`-результат под
  вызовом `move` состояния; пункты и альтернативы плана следуют как история.
- **Notes.** `action` — любой инструмент (та же уния, что у `apply`). Подсостояний нет: одно
  состояние владеет одним планом.

### 2.3 `apply` (`OP-AP`)

Диспетчер одного инструмента в фокусе (`src/tools/index.ts`, `OP-AP-*`).

**Как `apply` ложится в план** — движок размещает приходящую команду по исходу текущего
(первого невыполненного) пункта (`docs/ir_semantics_ru.md` §2.7): если пункт уже выполнен (его
текущая альтернатива успешна), команда становится новым пунктом плана (`OP-AP-PLACE-2`);
иначе — новой альтернативой этого пункта (`OP-AP-PLACE-1`). Альтернативы пункта — **только
действия** (альтернативы-подцели больше нет). Движок никогда не входит в действие.

**Ход может быть батчем.** Движок принимает один или несколько вызовов за ход и применяет
каждый по порядку в том же ходу (общий `payload.turn`); терминальный ход
(`move`/`stop`/`decline`) завершает батч, поэтому всё, что модель выдала после
него, отбрасывается (`src/loop/graph.ts` `executeNode`). Проекция рисует батч одним `assistant`
с N `tool_calls` + N `tool`-результатами (`docs/ir_semantics_ru.md` §7).

#### 2.3.1 `read` (`OP-AP-READ`)

| Случай | Pre | Effects | ID |
|---|---|---|---|
| новое окно | путь существует; мир не менялся с прошлого идентичного чтения | добавить `action`; добавить `observation` (`result`); записать наблюдённую версию | `OP-AP-READ-1` |
| продолжение окна | другие `start/end` | новое действие/наблюдение | `OP-AP-READ-2` |
| отсутствующий файл | — | действие + fail-observation | `OP-AP-READ-3` |
| повтор | идентичное окно, мир не менялся | отказ `repeated_action` | `OP-AP-READ-4` |
| путь вне workspace | — | действие + fail-observation (записанный отказ, без краха) | `OP-AP-READ-5` |
| трэш чтения | несколько разных окон одного файла | каждое разное окно — новое действие/наблюдение (лимита на файл нет); идентичное окно — `OP-AP-READ-4` | `OP-AP-READ-6` |
| большое окно | запрошенное окно больше байтовой границы | наблюдение показывает окно целиком (середина никогда не отбрасывается); обрезается лишь отдельная сверхдлинная строка, полное окно — за `outputRef`, достаётся `recall` | `OP-AP-READ-7` |
| бюджет чтения | файл длиннее байтового бюджета | окно режется по целым строкам до `READ_LIMIT`; трейлер `continue from N` указывает следующее окно | `OP-AP-READ-8` |

|---|---|---|---|

| повтор | идентичные scope+паттерн, мир не менялся | отказ `repeated_action` | `OP-AP-GREP-4` |
| байтовый бюджет | окно совпадений превысило бы байтовую границу | целые хвостовые совпадения отбрасываются, чтобы окно уложилось в границу; трейлер `[showing N of M matches; continue from K]` указывает продолжение; отдельное огромное совпадение обрезается построчно | `OP-AP-GREP-5` |

| Случай | Pre | Effects | ID |
|---|---|---|---|
| список по scope | — | действие + наблюдение (пути как JSON) | `OP-AP-LIST-1` |

#### 2.3.5 `run` (`OP-AP-RUN`)

`run` — одна простая **foreground**-команда. Нет критерия, нет `target` и нет механики
фоновых jobs.

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| команда | есть `command` | действие + `observation` (`command` + `exitCode`); `mutate` на каждый изменённый файл | версии; старые чтения устаревают | `repeated_action` | `OP-AP-RUN-1` |
| большой вывод | поток больше байтовой границы | наблюдение держит **хвост** inline (ошибка и exit в конце) с пометкой об усечении; полный поток — за `outputRef`/`errorRef`, достаётся `recall` | — | — | `OP-AP-RUN-2` |
| workdir | `workdir` называет путь внутри workspace, который существует | команда выполняется в этом каталоге | — | fail-наблюдение (`workdir does not exist` / `path escapes workspace`) | `OP-AP-RUN-3` |

- **`workdir`/`timeout`**: `workdir` запускает команду в подкаталоге workspace (вместо
  префикса `cd … &&`); `timeout` ограничивает одну эту команду в миллисекундах. Оба входят
  в сигнатуру повтора, поэтому один и тот же текст в другом каталоге или с другим лимитом
  — новое действие.
- **Projection** (`PRJ-AP`): результат — `tool`-ход на ленте под планом состояния; stdout
  (`output`) и stderr (`error`) раздельны; крах добавляет `signal`/`core`/`backtrace`; id узла
  стоит префиксом `tool`-сообщения для последующего `recall`/`search`.

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| создание | `path` не существует | добавить `action` (`path`/`content`); `mutate`; версия файла задана | — | — | `OP-AP-WRITE-1` |
| перезапись | файл прочитан и не менялся с того чтения; не запрещён | добавить `action`; `mutate`; версия меняется | зависимые факты устаревают | `stale_base`, `constraint_violation:<pattern>` | `OP-AP-WRITE-2` |
| запрещённый путь | запрет constraint | — | — | `constraint_violation:<pattern>` | `OP-AP-WRITE-3` |
| устаревшая база | файл изменился после последнего чтения | — | — | `stale_base` | `OP-AP-WRITE-4` |

#### 2.3.7 `fetch` (`OP-AP-FETCH`)

Получает внешние референсные данные (upstream/опубликованную/соседнюю копию) в
workspace, чтобы их можно было читать и диффить (B9, `docs/system_prompt_ru.md`).

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| fetch | URL достижим; цель не существует; не запрещена | действие; записать файл; `mutate` + `mutates`; наблюдение (`url`/`path`/`bytes`) | версия файла задана; старые чтения устаревают | — | `OP-AP-FETCH-1` |
| сбой загрузки | не-2xx / таймаут | fail-observation | — | — (fail) | `OP-AP-FETCH-2` |
| цель существует / путь вне workspace | — | fail-observation (`choose another path` / записанный отказ) | — | — | `OP-AP-FETCH-3` |
| запрещённый явный путь | запрет constraint | — | — | `constraint_violation:<pattern>` | `REF-FETCH-CONSTRAINT` |

Цель по умолчанию принадлежит движку (`refPathFor`, `.skein/ref/<hash>-<slug>`), поэтому
проверяется по constraint только явный `path`.

#### 2.3.8 `apply_patch` (`OP-AP-PATCH`)

Применяет unified diff в корне workspace (`patch -p<strip>`, по умолчанию 1), например
upstream-изменение, полученное через `fetch`.

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| примененимо | патч применяется чисто | действие; `mutate` на каждый изменённый файл (`patch -p<strip>`) | изменённые версии; старые чтения устаревают | — | `OP-AP-PATCH-1` |
| не применяется | конфликтующий/уже применённый hunk | fail-observation | — | — (fail) | `OP-AP-PATCH-2` |
| запрещённая цель | constraint запрещает путь `---`/`+++` | — | — | `constraint_violation:<pattern>` | `REF-PATCH-CONSTRAINT` |

### 2.4 `decline` (`OP-DC`)

Докса предполагает, что намерение запроса **не действенно** (болтовня, нет задачи) и
отказывается формулировать цель — вместо выдумывания цели. Доступно только пока у
запроса ещё нет `move`; записывает узел `unactionable` под запросом (связь
`unactionable`) и завершает прогон (`docs/plans/archive/request_goal_plan.md`).

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| отклонить запрос | фокус — запрос без `move` и без узла `unactionable` | добавить узел `unactionable` и связь `unactionable` от запроса; прогон завершается | запрос терминален (`request_unactionable`) | — | `OP-DC-1` |
| не у запроса | фокус — `move` или цель | — | — | `not_request` | `REF-DC-NOTREQ` |
| уже начат | у запроса уже есть `move` | — | — | `interpreted` | `REF-DC-ADDR` |

- **Projection** (`PRJ-DC`): опция `decline` предлагается у свежего запроса рядом с
  `move`.

### 2.5 `stop` (`OP-ST`)

Терминальный ход доксы и **единственное закрытие**. На открытой **цели** он завершает работу
состояния (движок возвращается к управляющему `move` и вынуждает решение о переходе); на
**терминальном состоянии** (`end`, у которого нет цели) завершает прогон. Критерия и
проверки нет: докса решает в процессе.

| Случай | Pre | Effects | Derived | Refuses | ID |
|---|---|---|---|---|---|
| завершить работу состояния | фокус — открытое состояние | добавить узел `stop` и связь `stop` от `move` состояния | состояние завершено; фокус возвращается к его `move` | — | `OP-ST-1` |
| закрытие записано на move | состояние | узел `stop` подвешен к `move` (не пункт плана); причина — в его `why` | закрытие и его причина лежат на `move` | — | `OP-ST-2` |
| запрос завершается | фокус — терминальное состояние (`end`) | добавить узел `stop` и связь `stop` от `move` | прогон завершается, stopReason `request_addressed` | — | `OP-ST-3` |
| не у закрываемого состояния | фокус — запрос или нетерминальный `move` | — | — | `not_addressed` | `REF-ST-STATE` |

- **Projection** (`PRJ-STOP`): закрытие состояния рендерится маркером `Finish state <label> —
  <why>`; сам `stop` вызова инструмента не добавляет, а ходы плана состояния уходят из ленты.
- Состояние закрывается только через `stop` (связь `stop`); терминальное состояние закрывается
  связью `stop` на его `move`. На запросе `stop` нет; запрос завершается, когда его
  терминальное состояние остановлено.

### 2.6 `recall` и `search` (`OP-RC`, `OP-SR`)

Два хода читают сохранённый результат по id (механизм «индекса», docs/ir_semantics.md §4.5):
`recall` открывает тело (при желании окно строк), `search` ищет в нём паттерн. Оба оставляют
узел — `action` + его `observation` под планом состояния, как любой шаг — поэтому вытянутое окно
остаётся в ленте, пока состояние открыто, и элизится на `stop` (docs/ir_semantics.md §7). Это
отдельные инструменты, чтобы докса не путала чтение файла/результата (`read`) с поиском
(`grep` / `search`).

`recall { id, start?, end? }` (`OP-RC`):

| Случай | Pre | Effects | ID |
|---|---|---|---|
| по id | id адресует сохранённое тело (наблюдение или тело inline/`Ref`) | `action` + `observation` под планом состояния; окно тела возвращено; курсор `continue from N`, если тело длиннее | `OP-RC-1` |
| окно | `start`/`end` | строчное окно; продолжается новым `recall` | `OP-RC-2` |
| большое тело | тело больше байтового бюджета | окно ужимается по целым строкам (`QUERY_BODY_LIMIT`, валидный JSON, без обрезки посреди строки); поток ошибок, если есть, — ограниченный inline-хвост | `OP-RC-3` |
| нет тела | id — действие/цель/и т.п. | `(nothing to recall: <id> has no stored body)` | `OP-RC-4` |
| неизвестный id | — | `(nothing to recall: <id> is not a node)` | `OP-RC-5` |
| остаётся в состоянии | — | recall рендерится ходом открытого состояния и элизится вместе с ним на `stop` (нет TTL, нет рабочего множества) | `OP-RC-6` |

`search { id, pattern, before?, after? }` (`OP-SR`):

| Случай | Pre | Effects | ID |
|---|---|---|---|
| по паттерну | id адресует сохранённое тело; `pattern` — регулярное выражение | `action` + `observation`; окна совпавших строк по stdout **и** stderr как JSON, с контекстом | `OP-SR-1` |
| stderr | у тела есть поток ошибок | совпадения в stderr несут `stream: "stderr"` | `OP-SR-2` |
| широкий паттерн | совпадений больше, чем вмещает окно | целые хвостовые результаты отбрасываются; `note` говорит `showing N of M; narrow the pattern` — никакого висящего `next` (у `search` нет пагинации) | `OP-SR-3` |
| нет совпадений | — | пустой `results` | `OP-SR-4` |
| невалидный паттерн | `pattern` — не регулярное выражение | `{ …, error: "invalid pattern" }` | `OP-SR-5` |
| нет тела | у id нет сохранённого тела | `(nothing to search: <id> has no stored body)` | `OP-SR-6` |
| контекст | `before`/`after` | строки контекста на совпадение (по умолчанию 3/3) | `OP-SR-7` |

- **Projection** (`PRJ-RC`): тело из recall/search входит в ленту как `action` + `observation`
  (узел), рендерится, пока состояние открыто, и элизится на `stop`.
- **Projection** (`PRJ-REF`): отклонённый структурный ход (узла нет) входит в ленту
  транзиентным `tool`-сообщением (`rejected <ход>: <причина>`) на следующий ход.

### 2.7 Обход и контейнеры (`TR`)

| Случай | Правило | ID |
|---|---|---|
| фокус | фокус — `branch[last]`, иначе корень | `TR-1` |
| descend | `focusEvents` спускается в текущий `move` запроса (`move`) или в цель `move` (`goal`) | `TR-2` |
| return | завершённый верх снимается (`goal → move` при `stop` цели; `move → request` когда выдан следующий `move`); `return` допустим | `TR-3` |
| плоские состояния | состояния — дети запроса (`move`), никогда не вложены; новый `move` после завершённого состояния — новый ребёнок (сиблинг) | `TR-4` |
| выбор контейнера | план цели — `plan` (`plan`); работа состояния — цель (`move.goal`); альтернативы пункта — `alts` | `TR-5` |
| порядок пунктов и курсор | пункты идут по порядку `items` (ПОСЛЕДНИЙ текущий); курсор — первый не `itemFulfilled`; пункт выполнен, когда его текущая альтернатива — успешное действие (альтернативы-цели нет) | `TR-6` |
| размещение | приходящая команда становится новым пунктом, когда текущий пункт выполнен, иначе новой альтернативой его (`OP-AP-PLACE`) | `TR-7` |
| frontier | `applicable` вычисляет move/apply/stop/decline из тех же фактов, что и гейты; докса выбирает среди них | `TR-8` |
| альтернативы пункта | альтернативы пункта (его история) рендерятся в ленте с пометкой | `TR-9` |

### 2.8 Производные факты (`DER`)

Состояние всегда выводится из инцидентных событий, никогда не хранится.

| Предикат | Правило | ID |
|---|---|---|
| состояние закрыто | у `move` есть связь `stop` к узлу `stop` | `DER-MOVE-1` |
| состояние завершено | `move` со связью `stop` (терминальный `move` закрывает запрос) | `DER-STATE-1` |
| запрос завершён | узел `unactionable`, либо текущий `move` — терминальное состояние и оно завершено | `DER-REQ-1` |
| текущее состояние | состояние (`move.state`) последнего ребёнка `move` запроса | `DER-STATE-2` |
| структурный лес | рабочие связи (`move`/`plan`/`items`/`alts`/`stop`) образуют лес (DAG с одним родителем) | `DER-FOREST-1` |
| действие `executed` | у него есть связь `result` или `mutates` | `DER-ACT-1` |
| witness прогона | наблюдение прогона несёт `witness` (основа устаревания) | `DER-STALE-1` |

## 3. Отказы и неисполнение команд (`REF`)

Гейт `classify` (`src/loop/classify.ts`) отклоняет только **структурный** ход: он эмитит
`record_rejection` и **обязан изменить проекцию** (инвариант). **Команду** обрабатывает
движок (`src/tools/index.ts`): её неисполнение записывается как `action` + `observation` с
причиной, а не отказом без узла.

**Структурные отказы (`record_rejection`):**

| Причина (токен) | Триггер | Оператор | ID |
|---|---|---|---|
| `empty_state` | некорректный `move` (неизвестный `state`) | `move` | `REF-MV-EMPTY` |
| `no_state` | `apply`, когда фокус — не открытое состояние (запрос или завершённое состояние) | apply | `REF-AP-NO-STATE` |
| `no_state` | `apply`, когда фокус — не открытое состояние | apply | `REF-NO-STATE` |
| `state_open` | `move`, пока текущее состояние ещё открыто (не остановлено) | move | `REF-STATE-OPEN` |
| `not_addressed` | `stop`, когда фокус не закрываем (запрос или нетерминальный `move` без цели) | stop | `REF-ST-STATE` |
| `not_request` | `decline` вне фокуса-запроса (`move`/цель) | decline | `REF-DC-NOTREQ` |
| `interpreted` | `decline` у запроса, уже имеющего `move` | decline | `REF-DC-ADDR` |

**Неисполнение команды (`action` + `observation` с причиной):**

| Причина | Триггер | Оператор | ID |
|---|---|---|---|
| `repeated_action` | идентичные read/grep/run при неизменном мире | read/grep/run | `REF-REPEAT` |
| `no_state` | `recall`/`search` вне открытого состояния (ходы закрытого состояния элизятся; у свежего запроса ещё нечего читать) | recall, search | `REF-RC-STATE` |
| run без команды | пустой `run` | run | `REF-RUN-EMPTY` |
| `stale_base` | edit по файлу, изменившемуся после чтения | edit | `REF-EDIT-STALE` |
| `constraint_violation:<pattern>` | edit запрещённого пути | edit | `REF-EDIT-CONSTRAINT` |
| `stale_base` | write поверх файла, изменившегося после чтения | write | `REF-WRITE-STALE` |
| `constraint_violation:<pattern>` | write запрещённого пути | write | `REF-WRITE-CONSTRAINT` |

**Провалы инструментов** (fail-observation): отсутствующий файл (`read`), плохой scope
(`grep`/`list`), `find` отсутствует (`edit`), ненулевой код/таймаут/сигнал (`run`).

## 4. Инварианты

- состояние закрывается только через `stop` (связь `stop` на `move`); прогона критерия и гейта
  по exit code нет.
- запрос завершается, когда остановлено его терминальное состояние (на запросе `stop` нет);
  запрос либо начат (`move`), либо отклонён (`unactionable`).
- прогон — обычная `observation`; её `exitCode` — вывод, не вердикт.
- неисполненная команда оставляет `action` + `observation` с причиной (никогда не отказ без
  узла); недопустимый структурный ход отклоняется без узла.
- `stale`-факт никогда не показывается как активный.
- `project` детерминирован: те же события → тот же `Context`.
- структурные связи (`move`/`unactionable`/`plan`/`stop`/`items`/`alts`) образуют DAG.
- состояние — своя собственная цель (`what` на `move`); состояния — плоские дети `move` запроса;
  план вешается на `move`.
- отказ/провал меняет проекцию.
- завершённое состояние (закрытое состояние или остановленный терминал) не остаётся фокусом;
  его ходы уходят из ленты, остаётся `Start state` / `Finish state`.
- секреты живут только в `.env`; малые результаты могут инлайниться, секреты — никогда.

Первые четыре реализуют хелперы: `tests/invariants.ts`.
