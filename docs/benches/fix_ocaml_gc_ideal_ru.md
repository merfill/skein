# fix-ocaml-gc — эталонный маршрут в IR

> Английское зеркало — `docs/benches/fix_ocaml_gc_ideal.md`.

Связанные: `docs/ir_semantics_ru.md` (источник истины по семантике),
`docs/logos_ir_ru.md`, `docs/plans/logos_roadmap_plan_ru.md`,
`docs/benches/bench_report_ru.md`. Эталонный прогон для сравнения:
`~/.skein-bench/harbor/2026-10-02__09-47-57`.

Статус: эталон. Это не спецификация движка, а образец **формы** прогона в наших
операторах и дереве IR. Содержание (гипотезы, строки, команды) наполняет LLM; здесь
фиксируется структура, по которой мы судим успех и находим расхождения.

---

## 1. Зачем

Бинарный `reward` не говорит, *почему* прогон провалился, и не задаёт цель. Эталон
даёт: (1) форму, к которой стремиться; (2) опору для сравнения фактических прогонов;
(3) вывод разрывов — не из догадки, а из несовпадения эталона и факта.

## 2. Задача и критерий

OCaml-компилятор падает при самосборке (bootstrap) после включения сжатия
свободного места в major heap (run-length compression). Нужно найти и починить
причину. Объективный критерий готовности — команда

```
make -C testsuite one DIR=tests/basic
```

должна завершиться успешно. Симптом из отчёта: сегфолт при компиляции
`utils/config.cmi`; подозрение — обработка свободных блоков в `pool_sweep` /
`pool_allocate` (`runtime/shared_heap.c`).

## 3. Принцип: форма, а не текст

Идеален не конкретный текст гипотезы (его не знает и модель), а **форма**:

- план — **узел `plan`** с упорядоченными пунктами-`item` (подцели/команды), а не
  «плоский» поток команд;
- объяснение («почему») — поле `why` цели; формальное допущение — ссылка `under` у
  закрывающего узла;
- свидетельства — **наблюдения** команд (никаких «утверждений»);
- **проверка** — узел `check` с ребром `verifies` к цели; он решает её судьбу;
- смена подхода — узел `alternatives` и выбранный вариант (`chosen`), а не повтор;
- у узлов **нет статусов**: состояние (исполнено, достигнуто, при допущении,
  опровергнуто) — производное;
- запрос в IR не закрывается: приёмка внешняя (Арбитр/харнес).

## 4. Эталонный маршрут

| Стадия | Оператор доксы | Что появляется в дереве | Почему |
|---|---|---|---|
| постановка | *(Арбитр)* | корневой `request` (текст задачи) + `constraint` (не менять тесты) | мотивация и границы |
| воспроизвести | `create goal` (план с пунктом-командой) | новая `goal` пунктом (`item`) в плане корня; у неё свой `plan` с `action` | увидеть падение, а не предполагать |
| | `apply` (`run` сборки) | `action` исполнен + `observation` (лог падения) | свидетельство |
| | `complete` | узел `complete` → цель `achieved_under` | завершение видно по наблюдению |
| локализовать | `create goal` | цель-пункт | сузить место проблемы |
| | `apply` (`read`/`grep`/`run`) | `action` + `observation` + `file` | факты о коде |
| | `complete` | `complete` → `achieved_under` | эпистемическая цель |
| починить | `create goal` (`why` = гипотеза) | цель-пункт; проверка ссылается на допущение (`under`) | проверить объяснение |
| | `apply` (`edit`) | `action` + `mutate` `from → to` | правка под гипотезой |
| | `apply` (`run` проверки) | `check` + `verifies` (+ `under`); цель → `achieved`/`achieved_under`/`refuted` (производно) | проверка решает судьбу |
| пересмотр | `create goal` (вариант через `alternatives`) | узел `alternatives` + вариант; `chosen` | не повторять, а заменить |
| приёмка | `apply` (`run` критерия, команда из `done_when`) | `check`; запрос `addressed`, приёмка внешняя | закрыть объективно |
| остановка | *(Арбитр)* | — | запрос адресован / застой |

Опровергнутые подходы не теряются: цель остаётся `refuted`, а невыбранные варианты
`alternatives` — `abandoned` (производно).

### 4.1 Конкретная траектория (ход за ходом)

Инструкция задачи: прочитать `HACKING.adoc`, разобраться со сборкой, починить
падение, затем добиться прохождения `make -C testsuite one DIR=tests/basic`.
Идентификаторы и `seq` иллюстративны; формы — как в `docs/ir_semantics_ru.md`.

| Ход | Оператор | Вызов LLM: что предложила | Дерево: что появилось |
|---|---|---|---|
| 0 | *(Арбитр)* | — | root `request` — текст инструкции; `constraint` «не менять тесты»; целей нет |
| 1 | `create goal` | цель-интерпретация «починить bootstrap» (план: воспроизвести/локализовать/починить/проверить) | `alternatives A0` под запросом; `item A0 → I`; `chosen A0 → I`; у `I` свой `plan` с пунктами; спуск в первый пункт |
| 2 | `apply` | `run` сборки | `A1` исполнен + `observation` (лог падения) |
| 3 | `complete` | «G1 достигнута» | узел `complete` → `G1`; производно `achieved_under` |
| 4 | `create goal` | цель «локализовать причину» | `goal G2` пунктом в план корня `P0` |
| 5 | `apply` | `read HACKING.adoc` | `action` + `observation` + `file` |
| 6 | `apply` | `grep "pool_sweep\|pool_allocate\|freelist"` | `action` + `observation` |
| 7 | `apply` | `read runtime/shared_heap.c` | `action` + `observation` + `file`@`V1` |
| 8 | `apply` | `grep "POOL_FREE_HEADER\|POOL_BLOCK_FREE\|Whsize_hd"` (кодирование свободных блоков run-length) | `action` + `observation` (макросы и инвариант перескока) |
| 9 | `complete` | «G2 достигнута» | `complete` → `G2`; производно `achieved_under` |
| 10 | `create goal` | цель «починить заголовок» (`why` = «при сжатии `pool_sweep` не переносит заголовок свободного блока», `done_when` = сборка) | `goal G3` пунктом в план корня `P0` |
| 11 | `apply` | `edit runtime/shared_heap.c` | `action` + `mutate` `V1 → V2` |
| 12 | `apply` | `run` сборки (проверка) | `check` + `verifies → G3` + `under → G2` (допущение локализации); производно `achieved_under`; иначе `refuted` |
| 12b | `create goal` | при `refuted`: новый вариант подхода | узел `alternatives` + вариант `G3'`; Арбитр ставит `chosen`; `G3` производно `refuted`, невыбранные — `abandoned` |
| 13 | `apply` | `run` критерия задачи (команда из `done_when`) | `check`; запрос `addressed`; приёмка внешняя |
| 14 | *(Арбитр)* | остановка | — |

Образ задачи **удаляет `.git`** (`environment/Dockerfile`: *«We don't want it cheating and
just rolling back the recent changes»*), поэтому `git log`/`git diff` недоступен:
локализация идёт по коду и инварианту свободного блока, а не по diff. Дефект — один
токен, поэтому названного подозреваемого достаточно: фикс — гипотеза, которую надо
**проверить**, а не доказать в `locate`.

Ключевое отличие от факта: в реальном прогоне агент выдавал только команды
(`read/grep/run`) и **не завёл ни одной цели с планом и ни одной проверки** —
работа была «плоской», без структуры.

## 5. Ожидаемая форма дерева

- **Корень:** `request` (текст задачи), не цель.
- **Цели:** 1 интерпретация запроса с планом из 3–5 пунктов (`воспроизвести`,
  `локализовать`, `починить`, `проверить`) плюс возможные интерпретации-альтернативы.
- **План:** узел(ы) `plan` с пунктами-`item`; у части целей план может отсутствовать
  (не специфицирован).
- **Наблюдения:** ≥1 (падение, «сжатие включено недавним коммитом»).
- **Правки (`action` edit):** ≥1, под целью с непустым `why`.
- **Проверки (`check`):** ≥1, привязаны к цели через `verifies`; при опоре на
  допущение — с рёбрами `under`.
- **Завершения (`complete`):** ≥1 у эпистемической цели.
- **Итог:** выбранная интерпретация `achieved` (проверка `pass`, без `under`) либо
  `achieved_under` (есть `under` или `complete`); запрос `addressed`; приёмка внешняя
  (харнес/пользователь).

## 6. Ветка и откат

Путь: `root → пункт плана (цель-подход) → action → check`. Успех — цель `achieved`/
`achieved_under`; провал — `refuted`, и новый подход появляется **вариантом** в узле
`alternatives`, где Арбитр отмечает `chosen`. Невыбранные варианты — `abandoned`
(производно); опровергнутые — `refuted`. Ничего не теряется: всё остаётся историей.

## 7. Прогресс

Прогресс относителен работы с целями, а не «новым узлам вообще»: новый пункт плана,
новый вариант `alternatives`, новое наблюдение, новая проверка, новое производное
состояние цели (`achieved`/`refuted`/`abandoned`). Повтор той же команды без
нового — не прогресс.

## 8. Остановка и честность

- **Успех:** выбранная интерпретация достигнута; запрос `addressed`; финальную приёмку
  даёт Арбитр (харнес) извне — в IR она не входит.
- **Честность:** `achieved` — только если закрытие не опирается на допущение (нет
  рёбер `under`); `achieved_under` — если есть `under` или цель закрыта доксой
  (`complete`).
- **Застой:** Арбитр меняет ветку или останавливает цикл.
- **Вне фрагмента:** если нужной возможности нет, а не «не придумал объяснение» —
  честный `out_of_fragment` (дизайн отложен).

## 9. Сопоставление с фактом (диагностика)

Фактические прогоны `fix-ocaml-gc` (джоб `2026-10-02__09-47-57`):

| Попытка | Ходы | Действия | Дерево | stopReason | reward |
|---|---|---|---|---|---|
| 1 | 10 | read/grep/run | 0 целей / 0 проверок | `no_progress` | 0 |
| 2 | 20 | read/grep/run | 0 целей / 0 проверок | `no_progress` | 0 |

Эталон и факт расходятся полностью: агент остался в «плоских» командах и ни разу не
завёл цель с планом и не выполнил проверку. Причины, видимые из модели:

1. **Нет структуры целей.** Работа шла командами без обрамляющих целей и планов;
   нечего было закрывать и к чему привязывать проверки.
2. **Нет проверок, привязанных к цели.** Прогонов было много, но ни один не решал
   судьбу цели.
3. **Нет обхода плана.** Механизм исполнения плана (стек) и политика выбора
   оператора отсутствовали, поэтому структура не принуждалась.
4. **Нет завершения эпистемических целей.** Их нельзя было закрыть, даже если
   разведка фактически закончилась.

## 10. Что следует для движка

- **Три оператора** (`create goal`, `apply`, `complete`) пока не реализованы; в коде
  есть инструменты и режимы старой модели.
- **Запрос** ставит Арбитр — это надо явно встроить.
- **Обход плана и политика Арбитра** — отложены, но нужны для структуры.
- **Версии:** `mutate` с `from`/`to`, `restore`; отдельного `stale` нет — актуальность
  вычисляется из текущей версии и допущений.
- **Замыкание:** узлы `check`/`complete`, рёбра `under` (допущения) и `verifies`,
  контейнер `alternatives` с выбором `chosen`.
- **Честность:** `achieved` vs `achieved_under` (есть ли `under`, либо закрытие доксой).

## 11. Метрики приёмки длинного прогона

Первично: `reward` (успех) либо честная остановка без ложного «сделано».

Форма (сравнивается с §5):

- ≥1 цель-подход; ≥1 `edit` под ней; ≥1 `check` с `verifies` к цели (при допущении —
  с `under`); ≥1 цель `achieved`/`achieved_under`; запрос `addressed` (приёмка внешняя).
- Последовательность: `создание целей → команды → проверки → (альтернатива →
  снова) → приёмка`.
- Контекст выходит на плато; повторов одинаковых `read`/`grep`/`run` — ограниченно.
