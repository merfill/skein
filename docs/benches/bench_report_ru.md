# Skein — отчёт по экспериментам (бенч и Harbor)

> Английское зеркало — `docs/benches/bench_report.md`. Это рабочий отчёт об измерениях,
> а не спецификация. Код харнесса — `bench/`, `langgraph/`.

## 1. Зачем

Tier 1 (граф, path-релевантность, узел проверки) реализован, но ценность нигде не
измерена. Цель — снять первые реальные цифры: растёт ли контекст, сколько токенов и
кэша тратится, сколько вызовов LLM, какая траектория, и задействует ли модель
рабочий граф. Результаты — повод решать, что чинить дальше.

## 2. Инструменты

- **`bench/run.ts`** — синтетика `skein-plugin` (короткие задачи): копирует репо
  кейса, гоняет `runAgent` вживую, запускает `check.sh`, считает поведенческую
  метрику `detectLoops` (импортируется из плагина, единый yardstick).
- **`langgraph/graph.ts` + `langgraph.json`** — адаптер Skein под встроенный агент
  `langgraph` в Harbor: Harbor ставит Node и зависимости проекта, запускает граф в
  рабочем каталоге задачи (`/app`) и собирает usage через callbacks.
- **`bench/harbor/*`** — конфиг (шаблон + генератор + `run.sh`), задания лежат вне
  репозитория (`~/.skein-bench/harbor`), чтобы langgraph-агент не стейджил сам себя.

## 3. Метрики

На каждый вызов LLM: `contextChars` (размер проекции), `input/output tokens`,
`cacheRead`/`cache%`, число реальных вызовов, `action`, время. Агрегаты: контекст
first/last/peak/growth, токены, кэш, стоимость, поведенческий `loopScore`/`rereads`,
и counts рабочего графа (claims/decisions/subgoals/checks).

## 4. Результаты

### 4.1 Синтетика (короткие задачи)

`hidden-hypotheses`: reward 1, 9 шагов, `loop=25%`, graph: 1 claim, 0 решений,
0 подцелей. «Повтор» — это повторный `python3 test_report.py` до/после фикса, то
есть перепроверка, а не цикл; baseline просто не перезапускал тест.

`moving-target`: reward 1, 7 вызовов, `loop=0`, контекст 1045 → 2983 симв. (peak
3526, рост +1938), вход 17 782 / выход 600, `cacheRead` 11 648 (66%), graph пуст
(0/0/0).

Наблюдение по кэшу, одинаковое на всех прогонах: `cacheRead` **всегда ровно 1664**
токена за ход — это стабильный системный префикс (system prompt + схема
инструмента). Проекция не кэшируется: её стабильный префикс обрывается сразу на
`goal`/`constraints`, дальше идёт волатильный `frontier`. Как следствие, при росте
контекста доля кэша падает (80% → 58%).

### 4.2 Harbor terminal-bench: `fix-ocaml-gc`

Baseline (сохранённый job `2026-09-26__11-50-39`, opencode): **pass**, 36 шагов,
41 инструмент, пик контекста 60 208 токенов, вход 38 852 / выход 4 220, `loop=0`,
`rereads=3`, `track=0`.

Skein, два прогона:

- **Прогон 1** (17:26): упал на `ENOENT` (см. §5), но verifier дал **reward 1** —
  то есть фикс был применён до падения. Turn-логов нет (процесс умер).
- **Прогон 2** (17:43): чистый выход, но **reward 0**. 60 ходов, действия:
  read 17, grep 18, run 23, **edit 1**, finish 1. Вход 290 564 / выход 11 536,
  `cacheRead` 129 792 (44.7%), контекст 1601 → 11 788 симв. (peak 26 281, рост
  +10 187), `checks=23`, **graph пуст (0 claims / 0 decisions / 0 subgoals)**,
  стоимость 3.76 ₽.

Итог: агент сделал один `edit` и дальше ~58 ходов крутил read/grep/run, не
сойдясь, и закончил `finish`. Нестабильность высокая: та же задача в прогоне 1
прошла, в прогоне 2 — нет.

Повторный прогон после шагов 1–6 роадмапа (джоб `2026-10-02__09-47-57`, 3 задачи ×
2 попытки, langgraph-адаптер): `fix-ocaml-gc` — **0/2**, оба раза `no_progress`,
0 subgoals / 0 claims / 0 checks, только read/grep/run, ни одной правки;
`db-wal-recovery` — 1/2 (успех на `finish`); `custom-memory-heap-crash` — ошибка
инфраструктуры (Docker build/start timeout 1200 с, не поведение агента). Эталон
формы прогона и разбор расхождений — `docs/benches/fix_ocaml_gc_ideal_ru.md`.

**Решено (2026-10-06).** После исправлений движка в `docs/benches/engine_fixes_found_ru.md`
(reasoning включён, фокус под закрытым предком, диагностика падения, удержание в
проекции, 4 CPU / 6 GB и фоновый `run`) `fix-ocaml-gc` проходит: два приёмочных
прогона, оба **reward 1.0** (`40 tests passed`) — `2026-10-06__10-57-47` и
`2026-10-06__14-53-22`. Отчёт: `docs/benches/fix_ocaml_gc_run_report_2026-10-06_ru.md`.

### 4.3 Гейт недеградации (baseline)

Чтобы шаги роадмапа (`docs/plans/logos_roadmap_plan_ru.md`) не ухудшали короткие
задачи, введён детерминированный офлайн-гейт:

- `bench/baseline.json` — замороженный референс простого набора (синтетика) со
  снятыми `reward`, шагами, токенами, стоимостью и пиком контекста;
- `bench/compare.ts` — чистая функция `compareRun(baseline, run)`: `reward` не
  ниже референса, а шаги/токены/стоимость/пик — не выше референса ×`tolerance`
  (по умолчанию 1.2);
- CLI: `npm run bench:gate -- <runDir|metrics.json>` — читает `metrics.json`
  прогона, печатает дельты и завершается кодом 1 при регрессии.

Это дымовая проверка, а не статистический тест: прогоны LLM шумят, поэтому порог
намеренно мягкий, а референс пополняется по мере появления прогонов. Длинный
сценарий (`fix-ocaml-gc`) в гейт не входит — он отслеживается в §4.2; теперь
проходит (reward 1.0).

### 4.4 Skein против opencode (длинные задачи)

Посылка Tier 1 — проекция даёт преимущество на длинных задачах. Чтобы проверить
её напрямую, оба агента идут в одном job'е Harbor с одинаковыми ресурсами и
reasoning (`bench/harbor/compare.template.yaml`):

```
SKEIN_HARBOR_CONFIG=compare.yaml bash bench/harbor/run.sh
npm run bench:compare -- ~/.skein-bench/harbor/2026-10-06__17-31-37
```

Протокол: `terminal-bench` 2.0, три задачи, одна модель
(`~deepseek/deepseek-v4-flash-latest`), `reasoningEffort: high` у обоих (Skein —
через `configurable.reasoningEffort`; opencode — через `--variant high` и опцию
модели), `override_cpus: 4`, `override_memory_mb: 5120`,
`n_concurrent_trials: 5`, `n_attempts: 3`, `timeout_multiplier: 2.0`. У Skein
`maxTurns` 60. Job `2026-10-06__17-31-37`, 18 триалов, ~1 ч 23 мин.

`ctx` — prompt-токены на один вызов LLM `min/median/mean/peak` (Skein: `SKEIN_TURN`;
opencode: `trajectory.json` `metrics.prompt_tokens` = input + cache). `tok in/out` —
среднее на триал.

**Суммарно (по 9 триалов):**

| агент | решено | вызовов LLM | tools | tok in/out | ctx (min/med/mean/peak) | cache |
|---|---|---|---|---|---|---|
| Skein (langgraph) | 4/9 | 41 | 30 | 607.8k / 207.8k | 7.2k / 16.2k / 20.0k / 60.1k | 60% |
| opencode | 6/9 | 21 | 26 | 697.9k / 3.0k | 7.4k / 30.7k / 32.9k / 79.7k | 96% |

**По задачам:**

| задача | Skein | opencode |
|---|---|---|
| `fix-ocaml-gc` | **3/3**, 69 вызовов, med 16.4k, cache 56% | **3/3**, 26 вызовов, med 43.1k, cache 96% |
| `db-wal-recovery` | 1/3 (2 × `AgentTimeoutError`) | **3/3**, cache 96% |
| `custom-memory-heap-crash` | 0/3 (2 × `no_progress`, 1 × exit 1) | 0/3 |

**Чтение:**

- **На задаче, под которую Skein настраивался, `fix-ocaml-gc`, оба агента 3/3 —
  выигрыша по точности нет.** Проекция честно делает своё на вызове: медианный
  контекст Skein ~в 2.6 раза меньше (16.4k против 43.1k) и пик ниже (60.1k против
  79.7k). Но Skein делает ~в 2.6 раза больше вызовов LLM (69 против 26) и кэширует
  куда хуже (56% против 96%), так что суммарный входной объём сходится (1.04M против
  1.06M). Экономия проекции тратится на лишние вызовы и некэшируемый frontier;
  решённых задач она не добавляет.
- **`db-wal-recovery` в пользу opencode (3/3 против 1/3), но не по качеству:** оба
  провала Skein — это таймауты агента 1800 с (`AgentTimeoutError`), то есть прогон
  слишком медленный, а не неверный. Быстрый и лучше кэшируемый агент его добивает.
- **`custom-memory-heap-crash` не различает:** никто не решает (Skein: два стопа
  `no_progress` и один ненулевой выход; opencode: три неверных ответа).
- Разброс большой (n = 3 на ячейку): сохранённый baseline opencode
  (`2026-09-26__11-50-39`, k = 1) давал `db-wal-recovery` 1/1 и
  `custom-memory-heap-crash` 0/1; здесь `db-wal-recovery` 3/3, а
  `custom-memory-heap-crash` 0/3.

**Разбор по примерам.**

`fix-ocaml-gc` (оба 3/3 — задача, под которую Skein настраивался). Куда уходят
вызовы Skein:

| попытка | ходов | вызовов LLM | ретраев | опросов job | bookkeeping | реальной работы |
|---|---|---|---|---|---|---|
| `brVESz3` | 52 | 63 | 11 | 17 | 9 (17%) | 43 |
| `fNwUyxJ` | 48 | 63 | 15 | 1 | 20 (41%) | 28 |
| `fa7HV3F` | 57 | 82 | 25 | 1 | 36 (63%) | 21 |

opencode: 24–27 шагов, 26–35 вызовов инструментов, в 7–9 шагах по два инструмента
сразу, ~10k reasoning-токенов (reasoning включён). Три источника лишних вызовов
Skein:

1. **Опрос фоновой задачи.** `brVESz3` запустил сборку OCaml как фоновый
   `run {background}`, а затем **17 раз** опрашивал её через `run {job: …}`. Каждый
   опрос — полноценный вызов LLM с полным контекстом. opencode собирает через
   блокирующий `bash` и таких ходов не платит. Стратегия неровная: одна попытка
   опросила 17 раз, две другие — по одному; но каждый опрос — это вызов, которого
   opencode не делает.
2. **Ретраи структурного вывода.** `invokeStructured` повторяет вызов при
   упоре в completion-лимит или нарушении схемы (`src/llm/structured.ts`):
   11/15/25 лишних вызовов, то есть 21–44% всех вызовов здесь, каждый с повторной
   отправкой всей проекции. У удачного прогона `db-wal` ретраев было **0**, так что
   это зависит от модели/контекста, но на длинных прогонах OCaml это большая плата.
3. **Бухгалтерия IR.** `create_goal`/`complete`/`query` — это 17–63% ходов на этих
   прогонах, у opencode такого нет; плюс Skein делает одно действие на ход, тогда
   как opencode пачками по два.

Что сработало: все три попытки дошли до фикса и остановились с `request_addressed`,
отклонённая заявка ровно одна — движковые фиксы (фокус под закрытым предком,
краш-диагностика, фоновый `run`, reasoning) на этой задаче держатся. Плата — не
корректность, а эффективность: медианный контекст ~в 2.6 раза меньше, но ретраи,
опросы и бухгалтерия пересылают его достаточно часто, чтобы **суммарные входные
токены совпали с opencode (1.04M против 1.06M)**.

`db-wal-recovery` (opencode 3/3, Skein 1/3). Единственный успех Skein (`4YD4dB5`)
был эффективным и чистым: 18 ходов / 18 вызовов / 0 ретраев / `request_addressed`,
хотя 10 из 18 ходов всё равно бухгалтерия. Два провала (`6BJGabb`, `F3YTvbt`) —
это **`AgentTimeoutError` на 1800 с**, а не неверные ответы: оба дошли до ходов
30–38 (38 и 34 заявки) и были убиты, поэтому их `SKEIN_METRICS` не сохранился.
opencode решает за 7–22 шага, только `bash`. Диагноз: Skein здесь слишком медленный
— те же ретраи + бухгалтерия + одно действие на ход против 30-минутного бюджета.

`custom-memory-heap-crash` (оба 0/3). Попытки Skein `FdQ7oRm` и `c2nVLJQ`
содержат **22–25 вызовов `query`** (58–64% ходов — бухгалтерия) и останавливаются
на `no_progress`: модель зацикливается на извлечении фактов вместо действий, и
движок корректно её останавливает. Третья попытка (`phqyVm8`) **упала** на ходу 26:
она читала `/build/patches/locale_init.cc.patch`, и guard воркспейса бросил
`path escapes workspace: /build`, что завершило процесс (`exit 1`). Инструкция
задачи указывает внутрь `/build`, вне воркспейса; `list` по тому же пути
записывается как отказ, а `read` бросает исключение и роняет прогон — это
несогласованность, которую надо чинить. opencode (19–34 шага, `bash`/`read`/
`write`/`edit`, запускает valgrind и правит `user.cpp`) её тоже не решает, так что
задача не различает агентов.

**Оговорки:** число completion-токенов opencode не включает reasoning (Harbor
суммирует только `tokens.output`), поэтому `out` занижен; сопоставимая ось — входные
токены. opencode отдаёт cost 0 у этого провайдера, а стоимость Skein считается
локально, так что cost здесь несопоставим. Уровень reasoning задаётся конфигом и из
артефактов не проверяется.

**Найденные проблемы (сравнение 2026-10-06) и что делать.** Экономия проекции на
вызове реальна (медианный контекст ~в 2.6 раза меньше), но сейчас она тратится на
накладные расходы. Конкретные дефекты:

1. **Сравнение по числу ходов смещено стратегией.** Все три прогона opencode нашли
   баг, скачав оригинальный `shared_heap.c` из апстрима и сделав `diff`
   (`curl`/`diff`/GitHub API; `edit` — последний инструмент), а ни один прогон Skein
   этого не попробовал и локализовывал руками (`edit` на ходах 19/36/51). То есть
   сырые ходы сравнивают шорткат с ручной локализацией, а не две архитектуры. Чтобы
   измерить архитектуру, надо перезапустить с выключенной сетью (или на задачах без
   публичного апстрима). Накладные расходы из пунктов ниже **не** смещены — Skein
   платит их при любой стратегии.
2. **Фоновый `run` стоит по одному вызову LLM с полным контекстом на каждый опрос.**
   `brVESz3` опросил сборку OCaml 17 раз (`run {job}`); блокирующий `bash` у opencode
   не платит ничего. Фикс: ждать завершения либо отдавать готовую задачу одним ходом,
   а не по опросу на ход.
3. **Ретраи `invokeStructured` пересылают всю проекцию** — 11/15/25 лишних вызовов
   (21–44%) на прогонах OCaml, 0 на чистом прогоне `db-wal`. Подобрать
   completion-лимит/промпт, чтобы ретраев стало меньше.
4. **Бухгалтерия IR — большая доля ходов** (`create_goal`/`complete`/`query`,
   17–64%), и на ход разрешено одно действие (opencode пачками по два).
   `custom-memory-heap-crash` зациклился на `query` (22–25 вызовов) и ушёл в
   `no_progress`.
5. **`read` по пути вне воркспейса роняет прогон.** `phqyVm8` читал `/build/…`
   (инструкция задачи указывает туда); guard воркспейса бросил
   `path escapes workspace`, и процесс завершился кодом 1. `list` по тому же пути —
   записанный отказ; `read` должен вести себя так же.
6. **Скорость — полноценная метрика.** На `db-wal-recovery` оба провала Skein — это
   `AgentTimeoutError` (1800 с): медленнее бюджета, а не неверно.
7. **Кэш стабильного префикса остаётся главным структурным разрывом:** 60% против
   96% (`implementation_plan.md`, backlog).

### 4.5 Контролируемый эксперимент: стратегия референса (Фаза 5)

opencode на тех же кейсах (локальный `opencode run --variant low --auto --pure`,

| условие | reward | steps | tools | prompt tok | out tok | cache | `diff` |
|---|---|---|---|---|---|---|---|
| on, среднее | 1.0 | 6.0 | 6.0 | 58 432 | 493 | 83% | 3/3 |

**Чтение.**

- **Сокращение вывело Skein вперёд на `on`.** A1–A4 (замыкание, отказ от `complete`,
  рабочее множество, гипотеза + ведущие действия одним вызовом) срезали Skein с 10.3
  шага / 95k prompt до **5.3 / 47k** на `on` — теперь ниже opencode (6.0 / 58k) по обоим
  осям. Это и есть целевой кейс стратегии референса.
- **Баг верификации A4 исправлен.** Авто-прогон ведущего действия `node --test` совпадал
  с `done_when.command` цели и **неявно** повышался до чека — цель опровергалась на шаге
  воспроизведения (прогоны `09:31`, `09:48`). Теперь вердикт — **только от явного чека**
  (`run {target}`); голый run — наблюдение (`docs/plans/traversal_stack_spec_ru.md` §9).
  Во всех успешных прогонах снова ровно один чек.
- **Стратегия референса держится:** `on` — `diff` 3/3 (предложен моделью или авто-прогнан
  A4); `off` — ручная локализация, `diff` 0/3.
- **`off` по-прежнему за opencode:** 8.7 шага / 101k prompt против 6.0 / 81k, и один
  прогон Skein провален (`off#3`, reward 0). Его трейс: модель зациклилась между
  `query obs:16` (вывод теста) и `query obs:26` (чтение 400 строк исходника) — без эталона
  ей нужны оба тела в поле зрения, но лимит символов рабочего множества вытесняет одно
  при подгрузке другого, и до правки дело не доходит. Это провал рабочего
  множества/контекста, а не локализации — следующий фронт.

**Оговорки.** n=3, одна задача, дефект однострочный; стоимость шумная. opencode —
локальный CLI (не Harbor): он видит весь диск, поэтому `off`-прогоны запускались при
**изоляции** — скрыты все `ledger.mjs` на диске, кроме исходника самого кейса, что
покрывает и эталоны, и **исправленные копии из рабочих папок прошлых прогонов**
(`/tmp/skein-bench/*/src/ledger.mjs`); один неизолированный `off`-прогон был уличён в
диффе против такой копии и перезапущен. Остаточный шум: opencode может читать
произвольные файлы хоста, чего Skein (sandbox воркспейса) не может; `out` у Skein
включает reasoning, у opencode — нет, так что сопоставимая ось — **prompt-токены**.
Референс локальный, а не сетевой; сетевой канал — через `network_mode` Harbor, следующий
шаг.

Артефакты: `bench/runs/2026-10-07T12-1{7,8,9}-*-ref-localize-{on,off}-skein/`.

> **Позже.** A1 (замыкание на предка) и A4 (авто-прогон ведущих действий) были **сняты**
> пошаговой переделкой (§4.6): цель теперь закрывается только своим чеком, а движок никогда
> не прогоняет план сам. Числа §4.5 — снимок того времени, когда они ещё действовали.

### 4.6 Пошаговая переделка и синтетический набор (Фаза 6)

Регрессия на длинных задачах (§4.4) и воронка `fix-ocaml-gc` (девять триалов `llm_error`;
трейс строил шесть вложенных `arbiter`-целей) были сведены к **представлению плана**:
пункт плана мог быть `goal`, `create_goal` добавлял подцели в план, а A4 прогонял новый
план в том же ходе — у `arbiter`-цели с исчерпанным планом на фронтире оставался только
`create_goal`. Движок переделан (`docs/plans/archive/plan_stepwise_redesign.md`): цель несёт
`plan` — **набросок-строку**, материализуется только первый `step` (I1–I3); подцель
входит **только** альтернативой шагу (I4, I6); A4 снят, A1 снят (цель закрывается только
своим чеком); `create_goal` принимает `{plan, step}` и отклоняет `empty_plan`/`empty_step`.
В промпт добавлено **правило команды** (B6): если запрос называет команду проверки,
интерпретация обязана быть `objective`, не `arbiter`; сообщения `unknown_revision` /
`no current step to decompose` теперь называют корректный следующий ход.

Весь синтетический набор (`skein-plugin/pilot/synthetic`, 10 кейсов), Flash,
`reasoningEffort=low`, по одному прогону (2026-10-07):

| кейс | reward | steps | checks | tok in | cost |
|---|---|---|---|---|---|
| defeasible-rules | 1 | 10 | 2 | 81 950 | 0.81₽ |
| early-fact | 1 | 8 | 1 | 64 549 | 0.73₽ |
| hidden-hypotheses | 1 | 14 | 2 | 127 925 | 1.29₽ |
| linked-decisions | 1 | 15 | 3 | 122 919 | 2.18₽ |
| log-flood | 1 | 5 | 1 | 51 540 | 0.72₽ |
| moving-target | 1 | 7 | 1 | 55 429 | 0.37₽ |
| multi-bug-calc | 1 | 9 | 1 | 76 362 | 0.86₽ |
| rounding-trap | 1 | 6 | 1 | 47 026 | 0.30₽ |
| stale-obvious-fix | 1 | 6 | 1 | 46 847 | 0.31₽ |
| tempting-wrong | 1 | 6 | 1 | 46 761 | 0.28₽ |

- **Рекурсия ушла.** Раньше `multi-bug-calc` строил **40 целей / 39 планов / 0 чеков** и
  упирался в `maxTurns` (модель повторяла `create_goal` с goal-пунктом плана). Теперь —
  1 цель, 1 чек, решено.
- **Арбитр — полноценный исход.** `defeasible-rules` раньше увязал `arbiter`-интерпретацию
  (8 × `unknown_revision` + 8 × `no current step to decompose`, 0 чеков, `maxTurns`).
  Arbiter-цель закрывает **только** внешняя приёмка (I5), поэтому синтетический раннер
  теперь играет **программу-арбитра** (`AgentDeps.arbiter`): пока в фокусе открытая
  arbiter-интерпретация, он прогоняет `check.sh` кейса и при успехе эмитит
  `record_check {actor:"user"}`. Кейс закрывается чисто (2 чека: objective-чек стадии +
  приёмка арбитра). Без хука тот же прогон может закончиться только `maxTurns` — закреплено
  тестом `tests/loop.test.ts` («an arbiter goal is settled only by the external arbiter
  (I5)»).

**Оговорка.** n=1 на кейс; один прогон `linked-decisions` вышел за таймаут харнесса 420 с и
был перезапущен чисто (15 шагов). Стоимость/шаги по одному прогону шумные; сигнал — **reward**.

Артефакты: `bench/runs/2026-10-07T18-*` и позже `*-skein/`.

## 5. Проблемы (что сломалось/мешает)

Это проблемы ранних baseline-прогонов (`2026-09-26`, `2026-10-02`); часть уже
исправлена — движковые фиксы и текущее сравнение в §4.2 и §4.4.

1. **Рабочий граф не задействован на длинной задаче.** 0 claims, 0 decisions,
   0 subgoals. Модель не заводит гипотез → отказы, устаревание проверок и
   path-релевантность не работают; поведение вырождается в плоский read/grep/run.
2. **Свидетельство = весь воркспейс — непрактично и с гонками.** `run` хэширует
   **каждый** файл воркспейса (дважды: до и после команды), чтобы построить
   witness. На большом репозитории с активной сборкой это дорого (ходы до 33 с) и
   ломается: файл-времянка сборки исчезает между листингом и чтением → `ENOENT`
   роняет агента (прогон 1).
3. **Контекст растёт внутри прогона.** В основном из-за `recent` (сырой вывод
   инструментов: тесты/сборки). Пик 26k символов. Кэшируется только системный
   префикс, поэтому рост контекста = падение cache%.
4. **`loopScore` вводит в заблуждение на коротких задачах**: повторная проверка
   (тот же тест до/после фикса) считается «повтором».

## 6. Гипотезы (почему так)

1. **Главная: промпт не оптимизирован под наш харнесс.** `SYSTEM_PROMPT`
   (`src/loop/propose.ts`) — один общий блок, писавшийся до Tier 1 и никогда не
   настраивавшийся под реальные длинные задачи. Он:
   - не требует заводить claim/подцель **до** нетривиального действия, поэтому
     граф пуст и нет памяти о том, что уже пробовали;
   - не описывает рабочую стратегию для длинной задачи (где работать, чем
     проверять, как сходить с неверной ветки);
   - из-за «одно действие за ход» без claims агент перечитывает/перезапускает одно
     и то же (17 read / 18 grep / 23 run почти без прогресса после одного edit).
   Мы промпты сознательно не трогали и не мерили — это первое, что надо чинить.
2. **Модель воспринимает агента как обычный read/grep/run-инструмент.** Нет
   структурного гейта, который заставил бы пользоваться IR, поэтому на дешёвой
   стратегии она и остаётся.
3. **Инструменты беднее, чем у baseline.** Только `edit` find/replace (у opencode
   — патчи/больше инструментов), `run` считается «проверкой» даже без claims
   (мусорные `check`-узлы), witness непрактичен.
4. **Рост `recent`** — прямое следствие п.1: при бессистемном переборе в окно
   попадают большие выводы.

## 7. Что делать дальше (пункт B)

1. **Пересмотреть промпт под харнесс** (приоритет): явно описать инструменты и
   рабочий процесс для длинных задач, потребовать фиксировать claim/подцель перед
   действием, описать, как проверять и как отказываться от ветки.
2. **Рассмотреть активный гейт** (как в плагине): нельзя `edit`/`run` без
   заведённого claim/подцели. Структурный гейт §5 из Tier 1 оказался недостаточным
   на длинной задаче.
3. **Убрать хрупкость/стоимость witness**: не хэшировать весь воркспейс; хотя бы
   не считать «проверкой» `run` без claims и не тащить билд-артефакты.
4. После правок — повторить `fix-ocaml-gc` и прогнать 2–3 задачи, сравнить с
   сохранённым baseline.

Отложено отдельно: оптимизация проекции под стабильный префикс/кэш
(`docs/plans/implementation_plan_ru.md`, бэклог).
