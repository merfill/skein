## 4. Наблюдения (дефекты, вскрытые прогоном)

1. **Корень закрывается не по критерию задачи.** Harbor-адаптер создаёт корень
   без `done_when` (по умолчанию субъективный), поэтому движок не знает
   объективного критерия `make -C testsuite one DIR=tests/basic`. Попытка B
   провела свой `run` с `target=g1`, он прошёл — и корень стал `achieved`, хотя
   задача не решена. Нужно: корневой `done_when` = критерий (объективный), и
   закрывать корень только им; иначе `root_closed` недостоверен.
2. **Проекция не ограничена — контекст взрывается.** В попытке B пик контекста
   **803 558** символов, input tokens 1.07M (в ~14 раз больше эталона). Причина —
   `artifacts`: `run` после сборки добавляет узел `file` на каждый изменённый
   файл, а список артефактов в проекции не ограничен. Усугубляет грубый
   `witness` (весь воркспейс) в payload проверки. Это нарушение Т2
   («необходимо и достаточно») и стоимости.
3. **Застой не детектируется.** Попытка A: 6 `create_goal`, 0 правок/проверок,
   остановка по бюджету, а не по `no_progress`. `knowledgeKey` считает новые
   узлы (цели, действия, наблюдения), поэтому рост фронта маскирует отсутствие
   закрытий — ровно риск §7.6 `logos_ir_ru.md` (нужна метрика closure rate /
   terminus шага).
4. **Стартовый контекст крупнее.** `first context` = 7 214 симв. против 2 200 у
   эталона — проекция избыточна ещё до работы.
5. **Повторы гасятся проверкой, но не направляются.** Много `read`-ходов в конце
   A/B отклонены (`repeated_action`, `accepted:false`); повтор зафиксирован, но
   докса не переключается на другой ход — тратит ходы.

## 5. Выводы

- **Форма изменилась в целевую сторону, но результат не улучшился.** Движок
  теперь ведёт дерево целей/планов и умеет закрывать корень; на бинарной шкале
  задача всё ещё 0.
- **Главный дефект — не семантика, а арбитр корня.** Если критерий задачи не
  внедрён как объективный `done_when` корня, честная машина закрытия работает
  вхолостую: `achieved` корня неотличим от догадки. Это первый почин.
- **Второй дефект — стоимость/Т2.** Неограниченный `artifacts` и грубый witness
  делают проекцию неограниченной; на реальном репозитории со сборкой это
  фатально. Нужны: ограничение/агрегация артефактов, точность свидетеля (или
  исключение сборочных путей на уровне мутаций), и бюджет контекста.
- **Третий дефект — детекция застоя.** Прогресс надо мерить закрытием
  обязательств, а не числом узлов.

## 6. Что делать дальше (приоритет)

1. Передавать критерий задачи в корневой `done_when` (объективный) через
   адаптер/harness; запретить `root_closed` иначе как по этому критерию.
2. Ограничить `artifacts` в проекции (окно/сводка, как `index`) и не заводить
   `file`-узел на каждый изменённый файл сборки; сузить `witness`.
3. Заменить `knowledgeKey` на метрику прогресса по обязательствам (закрытия
   целей, сдвиг курсора, вердикт), чтобы `no_progress` ловил застой при растущем
   фронте.
4. Перегнать `fix-ocaml-gc` после (1)–(3) и сравнить с этим отчётом.
