# Skein — инструменты и контракт вызова (предложение)

> Английское зеркало — `docs/tools.md`.
>
> **Статус: §4 реализован.** §3 — историческая справка (дефекты закрыты). Открытые
> вопросы — в §7, бэклог — в §8.

Связанные: `docs/ir_semantics_ru.md` (семантика операторов), `docs/projection_ru.md`
(что видит модель), `docs/testing_ru.md` (прогоны).

Цель документа — зафиксировать **честный контракт инструментов**: что модель может
вызвать, что инструмент обязуется вернуть, и какие инструкции ей дать. Ниже сперва
принципы, потом текущее состояние (as-built), потом предлагаемые изменения.

---

## 1. Принципы

1. **Инструмент честно делает то, что объявил.** Если объявлено «прочитать окно
   строк», возвращается всё окно. Если лимит есть — он **объявлен** в описании и в
   результате («показаны строки X–Y из Z»), а не молча срезается.
2. **Контекст для модели — вся её память.** Поэтому она должна получать:
   - **полный результат последнего вызова** (в пределах честно объявленных лимитов
     инструмента);
   - **сводку предыдущих вызовов без их результатов** (что вызвано, вердикт, объём).
3. **Ошибка — тоже результат.** Провал команды, отказ проверки допустимости, «файла нет» — это
   знание; оно показывается и/или попадает в сводку/`negative`, а не теряется.
4. **Пока бюджета контекста нет.** Ограничение `SKEIN_CTX_TOTAL` снимаем: сначала
   дадим инструментам честно работать, замеры — потом. (Отдельно решим, нужен ли
   аварийный предел.)
5. **Один оператор за ход.** Модель предлагает ровно одно действие; движок решает,
   принять его или отказать (см. семантику).

## 2. Обзор интерфейса

Модель предлагает действие через **нативные tool calls** (один плоский function-инструмент
на операцию, `tool_choice: "required"`); `src/llm/tools.ts` маппит вызов в IR `action` —
один из операторов:

| Оператор | Назначение |
|---|---|
| `create_goal` | завести цель (интерпретацию запроса или подцель) с планом |
| `apply` | работа с воркспейсом: `read` / `grep` / `list` / `edit` / `write` / `run` / `fetch` / `apply_patch` |
| `stop` | терминальное предложение, что запрос выполнен (принимается только если `addressed`) |
| `query` | достоверный поиск по дереву IR (не меняет состояние) |

### 2.1 `create_goal { what, why?, done_when, plan, step, revises? }`

- `what` — что достичь; непусто.
- `why?` — обоснование (текст); гипотеза для правки.
- `done_when` — **объективное** (`{kind:"objective", command}` — команда, чей код
  возврата решает) или **арбитр** (`{kind:"arbiter", text}` — внешняя приёмка; докса
  её не закрывает).
- `plan` — непустой **набросок-строка** плана (заметка себе), не список.
- `step` — **первое конкретное действие** `{ command, label? }`, исполняется verbatim;
  это единственный пункт плана, материализуемый при создании (действие).
- `revises?` — id **всех** проваленных вариантов контейнера, если сменяем подход.

Инструкция: при текущем узле-запросе создаётся интерпретация; при открытой цели —
подцель как альтернатива текущему шагу (раскладывает его). Давать набросок плана и
первый шаг. Провал перечислять в `revises` полностью, иначе отказ.

### 2.2 `apply { action }`

| tool | Поля | Смысл |
|---|---|---|
| `read` | `{ path, start?, end? }` | прочитать файл или его окно строк |
| `grep` | `{ pattern, path?, include?, exclude?, before?, after?, from?, count? }` | поиск по воркспейсу: область, окна по совпадениям, JSON (см. §4.2) |
| `list` | `{ path?, include?, from? }` | список файлов по маске, JSON (см. §4.6); движок принимает ещё `exclude`/`limit`, но инструмент модели их не отдаёт |
| `edit` | `{ path, find, replace }` | точная замена подстроки |
| `write` | `{ path, content }` | создать новый файл или полностью перезаписать (для перезаписи нужно свежее чтение) |
| `fetch` | `{ url, path? }` | загрузить URL в воркспейс как read-only референс (по умолчанию `.skein/ref/<hash>-<slug>`), чтобы прочитать и продиффить (B9); отказ: путь вне воркспейса/существует/запрещён/сбой загрузки |
| `apply_patch` | `{ patch, strip? }` | применить unified diff (`patch -p<strip>`, по умолчанию 1), например апстрим-правку из `fetch` |
| `run` | `{ command?, target?, background?, job?, under? }` | shell-команда; с `target` — проверка цели (команда берётся из цели, `command` опускается); с `background` — запуск долгой команды и опрос по `job` (см. §4.7) |

### 2.3 `query { id | kind | predicate | edgesOf, start?, end? }`

Достоверное чтение дерева/журнала: узлы, рёбра, их payload; а по `id` — **тело
сохранённого результата** (малое из payload, большое за `outputRef`), при
необходимости окном строк (`start`/`end`). Не меняет состояние. Модельный инструмент
предлагает `{ id, start?, end? }`; селекторы дерева (`kind`/`predicate`/`edgesOf`)
остаются возможностью движка, но модели не выставляются.

### 2.4 `stop { why? }`

Терминальный ход доксы: предлагает, что запрос выполнен. Принимается только если запрос
уже `addressed` (выбранная интерпретация `achieved`/`achieved_under`); иначе отказ
(`not_addressed`). Добавляет узел `stop` и останавливает прогон; запрос он не закрывает
(приёмка остаётся внешней).

## 3. Текущее поведение (as-built) и его дефекты

| tool | Что объявлено | Что реально возвращается | Дефект |
|---|---|---|---|
| `read {path,start?,end?}` | окно строк | содержимое окна → **транзиентный** текст, обрезан 8000, затем проекцией — **400 симв. с начала**; в наблюдении хранится только `{ref,version,bytes}` | содержимое **не сохраняется**; разные окна одного файла раньше считались повтором (исправлено: диапазон в сигнатуре) |
| `grep {pattern}` | поиск | совпадения `path:line:text` → транзиентный текст, затем 400 симв.; в наблюдении только `{count}` | **совпадения не сохраняются**; раньше вообще не видел `.c` (исправлено: текст по содержимому) |
| `run {command}` | выполнить команду | вывод → транзиентный текст; в наблюдении `{command,verdict,output}` (до 8000, head+tail) | в проекции всё равно 400 симв. с начала |
| `edit {path,find,replace}` | замена | факт правки | — |
| `query {...}` | чтение дерева | до 50 строк на селектор | не достаёт содержимое `read`/`grep` (его нет) |

Корень дефекта: **результат работы выбрасывается, а показывается только выдержка
из 400 символов**. Промпт при этом советует «перечитай или спроси через query»
(`src/loop/propose.ts:27`), хотя перечитать нельзя, а `query` содержимого не
возвращает. Модель просит 120 строк — видит ~8.

## 4. Предлагаемые изменения

### 4.1 `read`: окно с объявленным максимумом (решено)

- `read { path, start?, end? }`:
  - без `start/end` — с начала файла;
  - с `start/end` — окно строк (1-based, `end` включительно).
- **Максимум окна `MAX_READ_LINES = 400`** (решено) **объявлен в описании
  инструмента**: модель знает предел заранее.
- Если запрошено больше максимума или файл длиннее окна — инструмент возвращает
  максимум и **явно сообщает**: «показаны строки 1–400 из 3000; продолжение с 401».
- Результат показывается **полностью** (это `lastResult`, без среза до 400 симв.).
- Следствие: содержимое окна живёт в `lastResult` **один ход**; предыдущее чтение на
  текущей ветке держится в `shown` (и достаётся через `query {id}`). **Идентичное**
  перечитывание (то же окно, мир не менялся) отклоняется как `repeated_action`;
  **другое** окно — новое чтение. Если нужное на стыке окон (прочитали 1–100 и 101–200,
  а код в 80–120), читайте окно с запасом (например, 60–160).

### 4.2 `grep`: область, окна по совпадениям, JSON (решено)

- `grep { pattern, path?, include?, exclude?, before?, after?, from?, count? }`:
  - `path` — файл или каталог (по умолчанию корень воркспейса); область входит в
    сигнатуру действия;
  - `include`/`exclude` — glob-фильтры путей (`**/*.c`, `runtime/**`,
    `**/.depend` в `exclude`); выбор «где искать» (код/логи/тесты) — за моделью; таблиц
    язык→расширение в движке нет;
  - `before`/`after` — число строк контекста сверху/снизу, **по умолчанию `5/5`**;
  - `from`/`count` — окно **по совпадениям** (1-based, как строки в `read`);
    `count` по умолчанию `100`, максимум **`MAX_GREP_MATCHES = 200`**;
- результат — **валидный JSON**:
  `{ pattern, scope, context, total, from, returned, next?, results:
  [{ path, line, match, before: [], after: [] }] }`. Совпадения структурно отделены
  друг от друга, найденная строка (`match`) — от контекста (`before`/`after`);
  контекст соседних совпадений может дублироваться;
- байтовый предел (**`OUTPUT_LIMIT = 8000`**): при превышении отбрасываются **целые
  последние результаты**, `returned` уменьшается, `next` указывает продолжение; JSON
  остаётся валидным (середина не режется);
- пагинация — тем же `grep` с новым `from`: пересчёт детерминирован (как перечитывание
  окна в `read`); тело окна хранится через `storeOutput`, поэтому recall через
  `shown`/`query {id}` работает как у `read`;
- дефолтный скип: каталоги `SKIP_DIRS` + dot-файлы/каталоги (`.depend`, `.mailmap`);
  `.gitignore`-фильтрация — позже.

### 4.3 `run`: полный вывод, stdout и stderr раздельно (решено)

- Показывать полный вывод команды (а не 400 симв. с начала); при превышении
  **`OUTPUT_LIMIT = 8000`** — head+tail и явная пометка + `outputRef`/`errorRef`.
- **stdout и stderr захватываются раздельно и не склеиваются** (`spawnSync`).
  Результат несёт отдельные поля `output` (stdout) и `error` (stderr); `error` при
  сбое сохраняется всегда. Команда с `2>&1`/`&>` сливает потоки раньше, чем их
  увидит движок, поэтому промт это запрещает: как показывать два потока, решает
  движок, а не shell.
- Хранить оба в наблюдении (уже так) для `query`: малое тело inline, большое — за
  `outputRef`/`errorRef`, а `query {id}` читает **полное** тело, а не inline-обрезок.
- Неудачный `edit` (`find` не найден) материализует **текущее содержимое** файла в
  наблюдении-сбое и держит его в `shown`, чтобы модель скопировала `find` дословно
  оттуда, а не перечитывала уже прочитанный файл (повтор отклоняется guard'ом).
- Пере-проверка после вердикта **`inconclusive`** (таймаут) — **не** повтор: таймаут
  не принёс знания, поэтому тот же `run {target}` можно повторить. Серия
  inconclusive-проверок не считается прогрессом и оставляет цель `open`.
- `run`, убитый **сигналом** (краш, а не управляемый выход), несёт `signal` (например
  `SIGSEGV`) — а не голый ненулевой код. Обёртка поднимает `ulimit -c unlimited`,
  поэтому если платформа пишет core, движок находит новейший `core*` в воркспейсе и,
  если установлен `gdb`, прикладывает `gdb --batch -c <core> -ex bt -ex "info locals"`
  как `backtrace`. Если core не записан, движок сообщает `core_pattern` ядра — причина
  видна, а не проглатывается. `lastResult` несёт `signal`/`core`/`corePattern`/
  `backtrace`, а заметка в `calls` называет сигнал; покрыт и обычный `run`, и
  завершившийся фоновый job.

### 4.4 Проекция: последний результат + сводка (решено)

- `lastResult` — **полный** результат последнего вызова (§4.1–4.3).
- `calls` — **сводка предыдущих вызовов без результатов**: на запись
  `{ id?, action, status: ok|fail|refused, note, count }`, дедуп по сигнатуре. `action`
  включает параметры: для `read` — **диапазон** (`read f [1-100]`), для `grep` —
   **шаблон и контекст** (`grep sweep 5/5`), для `run` — команду, для `edit` —
   **короткий diff** (`-find +replace`). Это даёт модели «память о том, что уже
   делалось», не раздувая контекст, и видимое покрытие. `edit` хранит `find`/`replace`
   в payload действия, поэтому неудачная или повторная правка показывает точный уже
   испробованный `find`, а не пустое «applied».
- `negative` **сводится в `calls`** (один список): статус `refused`/`fail` + правило
  «не повторять, пока мир не изменился». Повторная команда с той же сигнатурой
  (`read`/`grep` тоже) при неизменном мире **отклоняется**, и в причине назван `id`
  уже имеющегося результата и способ его увидеть: если тело уже в `shown` — взять
  оттуда; иначе — через `query {id}` (§4.5). Совет никогда не отправляет модель в
  `query` к телу, которое уже показано: это само отклоняется, и модель зациклится
  `read → query → read`.
- `shown` — **рабочее множество**, которым владеет движок: он держит результаты **всех
  уровней текущей ветки**, не только листа, поэтому доказательство стадии (ошибка, из
  которой выросла следующая) остаётся видимым до закрытия родителя, новейшее — первым.
  `query {id}` добавляет одно **тело результата** с более раннего уровня (или вытесненное),
  и оно держится **`HELD_TURNS` (6)** ходов (повторный запрос продлевает); потолок —
  `MAX_HELD` (5) тел; вытесняются самые давно запрошенные. Каждое тело ограничено на уровне
  инструмента `OUTPUT_LIMIT` (8000 символов) — включая `read` (целые строки, с подсказкой
  продолжения), — поэтому отдельного общего лимита по символам нет: он убран, т.к. молча
  выбрасывал тело больше лимита (окно исходника, которое модель правит), зацикливая её на
  `query` (docs/benches/bench_report.md §4.4). Наблюдение `read`, чей файл с тех пор изменился, сбрасывается (не
  показываем stale как активное); `run`/`check` историчны и не стареют. Модель **не
  объявляет**, что показывать: `query {id}` — единственный вход в рабочее множество.
- `SKEIN_CTX_TOTAL` не применяется; `SKEIN_CTX_EXCERPT` больше не нужен.

### 4.5 `query`: достать результат по `id` (решено)

- `query { id, start?, end? }` возвращает **тело** сохранённого результата
  (небольшое — из payload, большое — за `outputRef`), при необходимости окном строк.
- Это и есть механизм «индекса»: прошлый результат берётся по `id`, а не повторным
  вызовом. Повторная команда с теми же входами при неизменном мире отклоняется
  (см. §4.2, семантика §2.7), в причине назван `id`.
- `query {id}` **входит в рабочее множество** (§4.4): тело показывается из `shown`
  несколько ходов. Повторный `query` того же id, **пока тело в множестве**, избыточен и
  отклоняется; тело, вытесненное по cap, из `held` ушло — его повтор **разрешён**.
  Для **не-результатов** (`action`/`goal`) держится отдельный набор недавно запрошенных
  id с тем же TTL, поэтому повторный `query` по узлу тоже отклоняется (спин). `query` по
  состоянию (`kind`/`predicate`/`edgesOf`) не пинится: его ответ меняется с ростом графа.

### 4.6 `list`: список файлов (решено)

- `list { path?, include?, from? }` (инструмент модели; схема движка принимает ещё
  `exclude`/`limit`, они не отдаются):
  - область и фильтры (`path`/`include`) — как у `grep`; тот же дефолтный
    скип (`SKIP_DIRS` + dot-файлы/каталоги);
  - `from`/`limit` — окно **по файлам** (1-based); движок берёт `limit` по умолчанию
    `LIST_LIMIT_DEFAULT` (200), максимум — `MAX_LIST_FILES` (500);
- результат — JSON: `{ root, total, from, returned, next?, files: [] }`;
- read-only и идемпотентен (повтор — не отказ); даёт модели видимость расширений,
  чтобы осмысленно задавать `include` в `grep`.

### 4.7 `run`: долгие команды в фоне (решено)

- Обычный `run` ограничен `SKEIN_RUN_TIMEOUT_MS` (по умолчанию 120 с); таймаут —
  `inconclusive`. Этого мало для полной сборки или всего набора тестов.
- `run { command, background: true }` запускает команду отдельно и возвращает управление
  **сразу** с id задачи (`job-N`); ход не блокируется.
- `run { job: "job-N" }` опрашивает задачу: `running` (повторить) или `done` вместе с
  кодом выхода и **хвостом** stdout/stderr (полный лог лежит в
  `.skein/jobs/<id>.{out,err}`). В опросе передаётся только `job` — не `command`/`target`.
- CLI пишет stdout и stderr в **разные** логи (правило §4.3 держится: потоки не
  сливаются); опрос, пока задача не `done`, вердикта не оставляет.
- Фоновая задача не бывает проверкой (`target` отвергается); опрос не повтор (каждый
  опрос читает новое состояние). Фоновый `run` отвергается, пока ограничение запрещает
  файл: его правки ложатся после хода и не могут быть откачены.

## 5. Промпт: инструкции и стратегия

Сейчас промпт описывает интерфейс, но **не задаёт стратегию** и не отражает
реальность лимитов. Предлагается:

1. **Честные лимиты** каждого инструмента (из §4) прямо в описании.
2. **Явная стратегия** для задач-багфиксов:
   1) **воспроизведи** отказ (обычно через `run` критерия из `done_when` или
      сборку/тест) и получи конкретную ошибку;
   2) локализуй по ошибке/коду;
   3) правь (`edit`);
   4) проверь тем же критерием.
3. **Воркспейс — источник истины.** Не предполагать наличие VCS/истории/diff.
   Если `git` (или иной инструмент истории) недоступен — **не искать его**, а
   работать с файлами и поведением (см. §6).
4. **Что делать с неудачей/отказом**: смотреть `calls`/`negative`, не повторять;
   менять подход, а не формулировку команды. Неудача «команда/путь не найден»
   (`No such file or directory`, `can't cd`, `No rule to make target`) — это неверный
   рабочий каталог, а не дефект кода: пересоздай интерпретацию/цель так, чтобы команда
   несла префикс `cd <dir> &&` (каталог проекта), вместо повтора голой команды.
5. **Как читать код**: `grep` для локализации, `read` окном; при необходимости —
   весь файл; не перечитывать то же окно без изменения мира.
6. **В контексте только последний результат.** Предыдущие результаты (в том числе
   прочитанные окна) **не** хранятся — есть лишь сводка вызовов (`calls`). Если
   нужен ранее прочитанный фрагмент (в т.ч. на стыке окон), **перечитай окно**,
   при необходимости с перекрытием; не полагайся на память о предыдущем результате.
7. **Где искать.** Выбирай область по улике: логика — в исходниках (`include` по
   языку проекта), отказ/лог — в выводе и лог-файлах. `path` задавай, если
   файл/каталог назван в ошибке, `done_when` или гипотезе; `grep` по всему дереву —
   только чтобы локализовать. Результат `grep` — окна по совпадениям: если
   совпадений больше окна, продолжай с `next`/`from`, **не** меняя `pattern`.

### 5.1 Как определить цель из запроса (и не уйти в git)

Это отдельное обязательное место промпта: без него модель применяет дефолтный
рефлекс кодинг-агента («посмотреть diff»).

1. `request.text` — **сырая мотивация**, а не готовое задание. Первый ход —
   `create_goal`: сформулировать интерпретацию (`what`), обоснование (`why`) и
   `done_when`.
2. Если в запросе назван **критерий/команда проверки** — берётся как объективный
   `done_when` дословно — но арбитр запускает её из **корня воркспейса**, а не из
   подкаталога проекта. Названная команда авторитетна; рабочий каталог выводится из
   дерева. Если проект в подкаталоге, литеральная команда должна нести префикс
   `cd <dir> &&` (`cd ocaml && make -C testsuite one DIR=tests/basic`), а не голую
   команду.
3. После цели первый шаг — **воспроизвести** отказ (запустить проверку/сборку), а
   не искать историю изменений.
4. **Воркспейс — источник истины.** VCS, `git`, diff, историю **не предполагай**.
   Если `git` (или подобное) упал — **не пробуй снова**; переходи к файлам и
   воспроизведению.
5. **Пример (соответствие).** Запрос: «я сломал сборку GC, компилятор падает при
   bootstrap; проверь `make -C testsuite one DIR=tests/basic`». Правильно:
   - цель: `what: "fix the GC regression so the basic testsuite passes"`,
     `done_when: { kind: "objective", command: "make -C testsuite one DIR=tests/basic" }`;
   - план из **шагов**: `reproduce` и `locate` — **действия** (запустить команду,
     прочитать/сдиффить); `fix` — сама гипотеза с `why` и `objective done_when` =
     команда, воспроизводящая падение, так что её решает её же `check` (отдельного
     `verify` и `complete` нет), а не список голых команд.
6. **Анти-пример.** `git diff`, `git log`, поиск `.git` — тупик без VCS; так делать
   не нужно. Отказ `git` в `calls` — сигнал сменить подход, а не команду.

Примеры в промпте держим **короткими** (один правильный ход + один анти-пример):
принципа «не предполагай VCS» недостаточно против сильного рефлекса.

## 6. Разбор: откуда взялся `git`

Это не вызов несуществующего инструмента — `run` может запустить `git`. Это
**непроверенное допущение**, которое среда опровергает, а промпт не корректирует.

Цепочка:

1. Текст задачи: «**I have been making some changes** to the OCaml garbage
   collector… I seem to have broken things». Формулировка «я вносил изменения»
   у человека/агента вызывает рефлекс «посмотреть несохранённые изменения» →
   `git diff`.
2. Ни промпт, ни задача не говорят, есть ли VCS. Промпт про VCS молчит.
3. Харнесс задачи **удалил `.git`**. `git` падает: `fatal: not a git repository`.
4. Провал попадает в `negative`, но **убеждение** «где-то должен быть diff» не
   опровергается — опровергается лишь конкретный запуск. Модель пробует другой
   корень/команду (`git status`, `git log`, `cd … && git diff`), снова падает.
5. Правильный ход — **воспроизвести** падение (`make`), а не искать историю.

Вывод: нужен **явный пункт промпта** «не полагайся на VCS; если истории нет —
работай с файлами и воспроизведи отказ» + стратегия из §5.

## 8. На будущее (бэклог, не сейчас)

Расширение набора инструментов, зафиксировано, чтобы не потерять. Порядок —
по величине пробела в возможностях; **в текущую реализацию не входит**.

1. **`write`** — создать/перезаписать файл целиком: `{ path, content }` — **сделан**
   (`docs/ir_operations_ru.md` §2.2.6): новый файл создаётся; для перезаписи нужно
   свежее чтение; пишет `mutate` с новой версией.
2. **`list`** (он же `glob`) — **сделан**, см. §4.6. Убирает парсинг `run ls/find`
   (неструктурный, неограниченный вывод) и даёт модели видимость расширений.
3. **`edit` по диапазону / `multiedit`** — правка по номерам строк и атомарная
   групповая правка: `find/replace` ломается на неоднозначных/повторяющихся
   фрагментах.
4. **`fetch`** (URL → воркспейс как read-only референс) — **сделан** (Фаза 4):
   `{ url, path? }`, дефолт `.skein/ref/<hash>-<slug>`; даёт путь B9 (взять
   референс и продиффить). **`apply_patch`** (unified diff) — **сделан** (Фаза 4):
   `{ patch, strip? }`.
5. **Позже:** `web_fetch`/`websearch` (документация, разбор ошибок) и LSP-операции
   `symbol` (определение/ссылки/переименование) — тяжёлые, отдельным этапом.

**Не-цели (осознанно):** VCS (`git`), `todo`-инструмент (план живёт в IR),
browser/скриншоты, subagents, MCP — вне текущего дизайна.
