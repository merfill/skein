**Статус.** У доксы **четыре оператора** (`move`, `apply`, `stop`, `decline`);
`recall`/`search` — адресация только для чтения, не ходы. Запрос проходится как **машина
состояний по островам**: докса `move` в состояние (остров работы), объявляя и остров (`state`),
и текст цели состояния (`what`) — состояние **есть** своя цель, — затем работает его через
`apply` (первый `apply` засевает план) и `stop` — что вынуждает решение о следующем переходе.
Состояния — **плоские дети запроса** (связь `move`), каждое несёт свой `what`; план висит
непосредственно на `move`. Состояние закрывается **только** через `stop`. План состоит из
**пунктов**; пункт состоит из **действий** (альтернатив), не целей. Контекст — **лента
сообщений**, собираемая из дерева. Докса предлагает; логос исполняет и записывает.
(docs/plans/archive/goal_into_move_plan_ru.md.)

## 0. Принцип: семантика есть операция над деревом IR

Всё, что делает система, описывается **как операция над деревом IR**:

- какие **узлы** и **связи** создаются;
- куда переходит **текущий узел** (фокус работы);
- какие **производные факты** меняются (они не хранятся);
- что увидит **следующая проекция** (модель на следующем шаге);
- какие **инварианты** сохраняются.

Это относится и к ходам доксы, и к реакциям логоса. Новое поведение — новая операция по этому
шаблону, а не правка состояния в обход журнала.

Дерево — не данность, а след операций. Оно ветвится там, где агент выбирает подход
(альтернативные команды), и растёт вглубь там, где состояние разворачивается планом.

## 1. Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| **Докса** | LLM | предлагает один или несколько операторов за ход (батч) | не выносит вердикты, не выводит |
| **Логос** | детерминированный движок, **включая среду и инструменты** | исполняет команды; по исходу ставит узлы и связи; пересчитывает производный вид; строит проекцию | не выводит истину; не выбирает между равносильными |
| **Арбитр** | внешний (человек; объективно — тулчейн) | первый запрос; финальная приёмка прогона; выбор равносильных гипотез | не производит содержания |

Протокола/среды как отдельной роли нет: исполнение и запись — часть логоса. Внутренние
операторы логоса — `o_rev` (пересчёт при изменении), `o_def` (отмена/опровержение), `o_ctx`
(проекция). Оператора предпочтения (`o_spec`) нет.

Ключевые следствия:

- **докса только предлагает.** Предложение входит как предложение (состояние открыто, команда
  без результата), но никогда сразу как установленный факт;
- **выбор — из применимого.** Логос детерминированно даёт *применимые* ходы в текущей точке;
  докса выбирает один и наполняет содержанием;
- **прогон — вывод, а не вердикт.** Код возврата команды — обычный вывод, который читает
  модель; на нём ничего не гейтится — состояние закрывает докса через `stop`;
- **запрос — не цель.** Сырая мотивация, корень; докса проходит его как последовательность
  состояний (`move`) либо отклоняет; приёмка остаётся внешней.

## 2. Дерево IR

### 2.1 Узлы

Два пространства.

**Рабочее пространство** — то, из чего состоит работа:

| kind | смысл |
|---|---|
| `request` | запрос арбитра: сырая мотивация (корень); проходится как последовательность состояний |
| `move` | объявление доксой состояния, в котором она будет работать, И текста цели этого состояния `what`; несёт `state` (остров) и `what` (цель состояния); ребёнок запроса; владеет планом |
| `plan` | план состояния: упорядоченный список пунктов (≥1) |
| `item` | пункт плана: упорядоченный список альтернатив (≥1) |
| `action` | команда; альтернатива пункта (никогда не состояние) |
| `observation` | результат команды (окно чтения, вывод запуска + код возврата) |
| `stop` | отметка о закрытии состояния |
| `unactionable` | отметка о том, что в запросе нет выполнимой задачи |
| `constraint` | ограничение (payload `forbid`: regex-пути) |

**Пространство артефактов** — то, что существует помимо работы:

| kind | смысл |
|---|---|
| `file` | файл |

### 2.2 Связи

Связь — именованное отношение от узла к узлу; имя — роль ребёнка у родителя. У каждого вида
узла фиксированный набор допустимых связей:

| От кого | Связь | К кому | Сколько |
|---|---|---|---|
| `request` | `move` | `move` | 0 и больше, по порядку (последний — текущее состояние) |
| `request` | `unactionable` | `unactionable` | 0 или 1 |
| `move` | `plan` | `plan` | 0 или 1 (засевается первым `apply`) |
| `move` | `stop` | `stop` | 0 или 1 (закрытие состояния) |
| `plan` | `items` | `item` | 1 и больше, по порядку |
| `item` | `alts` | `action` | 1 и больше, по порядку |
| `action` | `result` | `observation` | 0 или 1 |
| `action` | `mutates` | `file` | 0 и больше |

Порядок детей — порядок добавления; текущий (выбранный) — **последний**. Два следствия:

- закрытие состояния живёт у его `move`, в связи `move.stop`; отдельного пункта плана под
  `stop` нет;
- `file` — единственный узел, на который ссылаются несколько действий (`action.mutates`): у
  файла много «владельцев», у остальных по одному.

### 2.3 Общая форма

```
request --move--> move --plan--> plan --items--> item --alts--> action
```

Правила:

- пункт плана — **всегда** список альтернатив, минимум одна; если ветвления нет, элемент ровно
  один и это команда (`action`);
- состояние появляется только одним способом: работа висит на `move` (`move.plan`). Состояние
  никогда не альтернатива пункта, и у запроса нет своей цели;
- **`what`.** `move` несёт `what` (текст цели состояния). **Состояние** и его цель живут вместе
  на `move`. План — отдельный узел `plan`, засеваемый первым `apply` одним пунктом, чья
  единственная альтернатива — это первое действие.

### 2.4 Текущий узел

В каждый момент есть **текущий узел** — фокус работы; все операторы доксы относительны его.
Фокус — верх **стека обхода** (§2.6).

### 2.5 Статус выводится

У узлов **нет хранимых статусов**; узлы не меняются, `stateOf` нет. Нужные решению факты
читаются из узлов/связей:

- действие **исполнено** ⇔ у него есть произведённый ребёнок (`result`/`mutates`); иначе
  пункт лишь запланирован;
- действие **успешно** ⇔ оно изменило файл, либо его наблюдение-результат не провал
  (`failed`-причина или ненулевой `exitCode`; отсутствие `exitCode` — таймаут, вердикта нет);
- состояние **закрыто** ⇔ у его `move` есть связь `stop` к узлу `stop`; иначе открыто;
- `move` **завершён** ⇔ у него есть связь `stop` к узлу `stop` (терминальное состояние не имеет
  плана, но закрывается так же); иначе открыт;
- запрос **завершён** ⇔ есть узел `unactionable`, либо его текущий (последний) `move` — это
  терминальное состояние и оно завершено; сам запрос никогда не закрывается `stop`;
- **`movesOf(request)`** — дети `move` по порядку; **`currentMove(request)`** — последний;
  **`planOf(move)`** — план состояния по связи `plan`; **`unactionableOf(request)`** — узел по
  `unactionable`; **`stopOf(move)`** — узел по `stop`;
- **`lastChild(container)`** — текущий пункт/альтернатива (последний ребёнок);
- пункт **выполнен** ⇔ его текущая (последняя) альтернатива — исполненное успешное действие;
  **курсор** — первый невыполненный пункт. (Альтернативы пункта — только действия;
  альтернативы вложенного состояния больше нет.)

**Предикатов истины нет** (`achieved`/`refuted`/`abandoned`) и **критерия нет**. Прогон сам по
себе ничего не улаживает: состояние закрывается только `stop` доксы. Это правила
`project`/чтения, а не поля. Монотонен только журнал (§3).

`state` и `what` у `move` — иного рода: их **авторски пишет** докса при
`move`, они не меняются. Они фиксируют, в какой остров работы входит состояние, и его текст
цели. Это не производный статус: остров **не закрывает** состояние (закрытие по-прежнему только
`stop`, §8) и **не гейтит `move`**. Но он ограничивает **поверхность действий** открытого
состояния — набор apply-инструментов острова (`Island.applies`, §2.6), так что инструмент вне
работы состояния отвергается (`not_in_state`); остров — самодекларированный режим, который движок
удерживает, а не критерий-гейт.

### 2.6 Стек и обход

Обход — детерминированная часть логоса. Он **не выбирает**; он вычисляет *применимые* ходы в
текущей точке; выбор из них — за доксой.

**Стек** `S = [R, M]`: корневой запрос и текущий `move` (состояние в фокусе; оно же своя
цель). **Курсор** — индекс первого невыполненного пункта плана `move`. Ни то, ни другое не
хранится: стек — свёртка событий фокуса (`descend`/`return`, журнал append-only); курсор
вычисляется из плана.

Детерминированное движение:

- **спуск** `R → M` — при `move` положить `move`; фокус → `M`. Состояния — **плоские** дети
  запроса: новый `move` после завершённого состояния — новый ребёнок (сиблинг предыдущего
  состояния), никогда не вложен под него;
- **продвижение** — исполнение action-пункта стек не меняет; курсор сдвигается сам;
- **возврат** `M → R` — когда выдан следующий `move`, завершённое состояние оставлено позади
  (на его место положен сиблинг).

Движок отдаёт доксе **применимые ходы в фокусе**. Одно вычисление питает и проекцию, и
`classify`.

**Применимые ходы:**

| Фокус | Применимое | Смысл |
|---|---|---|
| запрос без `move` | `move`, `decline` | выбрать первое состояние (или отклонить) |
| открытое состояние (плана ещё нет: `plan`) | `apply`, `stop` | дать первый пункт плана — первый `apply` засевает план |
| открытое состояние (план с пунктами: `working`) | `apply`, `stop` | продолжать работу; `stop` закрывает состояние |
| завершённое состояние (`transition`) | `move` | обязательное решение о переходе |
| терминальное состояние (`finish`, `terminal`) | `stop` | запрос завершён |

### 2.7 Как команда попадает в дерево

`apply` — вызов инструмента. Логос исполняет команду и **всегда** записывает исход
наблюдением; докса читает наблюдение и выбирает следующий ход; логос только размещает
пришедший ход.

**Исход текущего пункта** берётся из его текущей альтернативы, которая всегда **команда**:
наблюдение несёт результат (**успех**) или причину (**неуспех**: инструмент не смог выполнить,
проверка допустимости не прошла, прогон вернул ненулевой код или таймаут — **нет вердикта**).

**Куда встаёт следующий ход** (логос размещает по исходу; команду выбирает докса):

- после **успеха** — **новым пунктом плана**;
- **иначе** — **новой альтернативой текущего пункта**.

Старт: `move` объявляет состояние и его цель; первый `apply` засевает план состояния одним
пунктом и сразу исполняет его действие (логос); состояние рождается с уже исполненным первым
пунктом. Каждая попытка оставляет новые узлы; существующий узел не переиспользуется и не
правится — журнал остаётся монотонным.

**Структурные ходы.** `move`, `stop`, `decline` — не исполнение команды, а
изменение дерева. Если такой ход недопустим, он **отклоняется**: узел не создаётся, а причина
приходит доксе сообщением в ленте на следующий ход (`rejected <ход>: <причина>`). То же для
**голого** адресного `recall`, который отклонён как избыточный. У команды такого отказа нет:
неисполнение (повтор, устаревший базис, запрещённый путь, пустая команда) приходит
**наблюдением с причиной**.

### 2.8 Детекция зацикливания

Зацикливание — не отдельный датчик, а **отсутствие прогресса**. Прогресс в точке — сдвиг
курсора, **новое знание** (новое наблюдение или новый исход, либо полученный фрагмент
`recall`/`search`), закрытие либо **новый `move`** (смена состояния). Слои
детерминированные: **повтор действия** (та же команда с теми же входами, неизменным миром)
отклоняется, и его наблюдение называет существующий результат;
**застой** (курсор не сдвигается, `move` не меняется и нет нового знания `K` ходов) возвращает
к родителю; **исчерпание** без прогресса на корне останавливает прогон (`no_progress`). Смена
состояния — прогресс, поэтому прогон, входящий в новые острова, не застой. Проекция может
также нести мягкий аттрактор, привязанный к **ходам с последнего `move`** (§7,
docs/plans/archive/state_protocol_plan_ru.md §4a).

## 3. Журнал и свёртка

- **Журнал** (`Event[]`) — единственная истина; только дописывается.
- **Состояние** — `fold(журнал)`, производное.
- **Проекция** — `project(состояние)`, производное; ровно то, что видит модель.

Словарь событий закрыт: `add_node`, `add_edge`, `descend`, `return`, `mutate`,
`record_rejection`. Смена состояния — **новое событие** (узел `move`, `observation`, `mutate`,
`stop`), а не правка; нет ни `set_status`, ни `record_check`. Сбой команды **не забывается**: он
материализуется наблюдением с флагом `failed` (а при неисполнении — `refused`).

Детерминизм: одни события и параметры дают одно состояние и одну проекцию. Единственный
внешний источник — изменения файлов; они входят через `mutate`.

## 4. Операторы доксы

У доксы **четыре оператора** (`move`, `apply`, `stop`, `decline`); `recall` и
`search` — адресация только для чтения, не ходы. Каждый описан по шаблону: назначение →
применимо к → вход → действие → фокус → отказ.

### 4.1 `move`

Объявляет состояние (остров работы), в котором докса будет работать, — переход автомата.

**Вход.** `{ state, what }`: `state` — одно из имён островов, перечисленных базовым промптом
(**первый** `move` выбирает стартовое состояние; последующие — следующее); `what` — конкретная
цель **этого состояния** (обязательна, кроме терминального `finish`, у которого нет плана).

**Действие.** Создать узел `move` `M` с payload `{ state, what }`; связать его новейшим
ребёнком `request.move` (`R.move += M`); испустить `descend` `R → M`. Фокус переходит на `M`.
Ход объявляет состояние И его цель: план висит непосредственно на `M`. Ход допустим на
**свежем запросе** (нет ни одного `move`) или на **завершённом состоянии** (`move` со `stop`).
Он отклоняется, пока состояние ещё открыто (`state_open`) либо при плохом имени состояния
(`empty_state`).

**Фокус.** Фокус становится `M`; следующие применимые ходы — `apply` (первый вызов засевает
план) и `stop`; на терминальном состоянии (`finish`, нет плана) — только `stop`.

### 4.2 `apply`

Исполняет одну команду в текущем состоянии.

**Вход.** `{ tool, … }`, где `tool` — один из `read`/`grep`/`list`/`edit`/`write`/`run`/
`fetch`/`apply_patch`, плюс параметры инструмента.

**Действие.** Команда исполняется; исход записывается как `A.result = observation` (read, grep,
list, run) или `A.mutates += file` (правка) — либо, когда она не исполнилась, наблюдением с
причиной. Размещение — по исходу текущего пункта (§2.7). **Первый** `apply` в открытом
состоянии засевает план состояния: создаёт `plan` и его первый `item`, единственная
альтернатива которого — эта команда. Фокус не двигается. `apply` применим только внутри
открытого состояния; в остальных местах отклоняется (`no_state`).

### 4.3 `stop`

Закрывает состояние — единственный способ его завершить.

**Вход.** `{ why? }` — причина.

**Действие.** Если фокус — открытое **состояние** (`move`, ещё не остановленный), создать узел
`stop` `S` и связать `M.stop = S`: состояние завершено; следующее решение — переход (§4.1).
Если фокус — **терминальное состояние** (`finish`, у которого нет плана), тот же `stop`
заканчивает запрос (`request_addressed`). Гейта по критерию **нет**: докса закрывает состояние
в процессе. `stop` на запросе (или на уже завершённом состоянии) отклоняется (`not_addressed`).

### 4.4 `decline`

Завершает запрос, чьё намерение неисполнимо, не изобретая состояние.

**Вход.** `{ why? }` — причина. **Применимо к.** Свежему запросу.

**Действие.** Создать узел `unactionable` `U`; связать `R.unactionable = U`. Ни `move`, ни план
не создаются. Фокус завершает прогон (`request_unactionable`). На `move` — `not_request`; на уже
истолкованном запросе — `interpreted`; на уже отклонённом — `repeated_action`.

### 4.5 `recall` и `search`

Два read-only инструмента адресуют сохранённый результат по `id`; ни один не создаёт узел и не
меняет дерево. `recall { id, start?, end? }` читает тело (при желании окно строк);
`search { id, pattern, before?, after? }` ищет регуляркой внутри тела (stdout **и** stderr).
Они разделены, чтобы чтение результата не путалось с его поиском и с `read`/`grep` (те целят
workspace). **Оконный** `recall` или любой `search` — другой фрагмент, новое содержание;
избыточно лишь **голое** recall по id, чьё тело уже в виду.

## 5. Время, версии, свидетельство

### 5.1 Версия

Версия файла — идентификатор содержимого (хэш). Содержимое старых версий в IR не хранится;
блобы живут в воркспейсе. IR хранит только имена версий.

### 5.2 История и текущая версия

`history(ref)` — версии `ref` в порядке `mutate`; `current(ref)` — последняя. Обе производны из
журнала.

### 5.3 Актуальность вычисляется

Наблюдение, полученное чтением файла, несёт его **версию**. Признака «устарело» нет:
актуальность — **отношение факта к текущему контексту**, а не свойство факта:
`actual(fact) ⇔ fact.version = current(fact.ref)`.

### 5.4 Монотонность

Журнал только растёт. Смена знания (новая версия, новое наблюдение, новая гипотеза) — новые
записи; пересчитывается только производный вид.

## 6. Завершение и честность

| Условие | Чем закрывается | Производное состояние |
|---|---|---|
| открытое состояние | `stop` (без гейта) | закрыто; связь `stop` ведёт move → stop; состояние завершено, фокус остаётся на его `move` |
| терминальное состояние (`finish`) | `stop` (без гейта) | закрыто; связь `stop` ведёт move → stop; запрос заканчивается (`request_addressed`) |
| запрос (корень) | заканчивается, когда остановлено терминальное состояние (`request_addressed`) или при `decline` (`request_unactionable`); у запроса нет `stop` | прогон заканчивается |

**Запрос в IR не закрывается.** Нет узла «принято»: молчание пользователя — согласие, а
объективный харнес оценивает прогон извне. Запрос заканчивается, когда его терминальное
состояние остановлено или когда докса отклоняет его.

**Честность.** Сила вывода не превышает силы посылок: `exitCode` прогона — обычный вывод;
запрос никогда не помечается «achieved»; никакая гипотеза не хранится как допущение.

## 7. Контекст: лента сообщений

Контекст — то, что модель видит на очередном шаге. Он выглядит как обычная лента сообщений, но
**собирается из дерева заново каждый ход** — это проекция, а не накопительная переписка. Одни
события всегда дают одну ленту.

**Роли:** `system` (стабильный базовый промпт, ограничения, инструкция состояния — один раз при
входе — и, в конце и временно, инструкция текущей ситуации), `user` (запрос — он **вверху**
ленты, на каждом ходу — и цель каждого состояния), `assistant` (маркеры состояний и вызовы
доксы), `tool` (результаты команд).
**Рабочие шаги** рендерятся **нативным tool-calling контрактом**: `apply` — это `assistant` с
`tool_calls` (имя инструмента и аргументы), результат — `tool` с `tool_call_id`. Батч — один
`assistant` с N `tool_calls`, затем N `tool`-результатов по порядку. А вот **смена состояния** —
не вызов инструмента (см. ниже). Имена и
аргументы — модельные **нативные** (`read` `edit` `write` `grep` `list` `bash` `webfetch`
`apply_patch` `move` `recall` `search` `stop` `decline`): `modelCall` рисует IR
`apply` обратно в них, а `toProposal` переводит в обратную сторону, поэтому лента и вызываемая
схема говорят на одном словаре (IR хранит `path`/`start`/`end`, `find`/`replace`, `fetch`).

**Состояния и их сообщения:**

- `move` — состояние — это решение, а не вызов инструмента, поэтому **вызова нет**: оно
  рендерится маркером `Start state <label>` (ход `assistant`), затем инструкцией состояния (ход
  `system`), затем целью состояния ходом `user` (`what: <цель острова>`). `move.what`/`move.notes`
  доксы **не показываются**: цель берётся из определения острова. Запрос — второе сообщение ленты
  (сразу после базового промпта), на **каждом** ходу, не убирается;
- `apply` — `assistant` с `tool_calls` (имя инструмента и аргументы) + `tool` (наблюдение);
  **первый** `apply` после `move` засевает план состояния (`plan` + один `item`), поэтому
  первый пункт плана — обычный вызов инструмента;
- `stop` — закрытие состояния рендерится маркером `Finish state <label> — <why>` (ход
  `assistant`), читается из связи `move.stop`; вызова инструмента не добавляет. На терминальном
  состоянии `stop` завершает запрос;
- `decline` — `assistant` с причиной (`why`): запрос отклонён;
- структурный ход отклонён — транзиентная пара `assistant` (вызов, которым ход был сделан) +
  `tool` с причиной (`rejected <ход>: <причина>`, следующий ход; узла нет); результат
  `recall`/`search` — тоже транзиентная пара `assistant` (с аргументами) + `tool`.

То есть **состояние** — это `Start state <label>` / инструкция (`system`) / цель (`user`) /
`Finish state <label>`, а пока оно открыто — его план (вызовы `apply` и их результаты). Команды-альтернативы
несут пометку (`alternative to step "…" (previous attempt: "…" — reason)`), где `reason` —
**одна строка** со ссылкой на наблюдение (`see [obsId]`), без вставки тела. Каждый результат
`apply` несёт id узла (`[id] …`), чтобы его можно было адресовать по `id` через
`recall`/`search`.

**Лента не монотонна.** Завершённое состояние — текущее в ожидании перехода или уже оставленное
позади — сворачивается в `Start state <label>` / инструкцию / цель / `Finish state <label> —
<why>`; ходы его плана (вызовы `apply` и их результаты) уходят из ленты. Уходит только вид, а не
данные: дерево остаётся полным.

**Рассуждение доксы не хранится**: сырое `thought` в дереве нет и в ленту не попадает; его
смысл живёт в полях `why`.

**Работа с данными.** Тело результата ограничено самим инструментом, с **per-tool** бюджетом:
окно `read` — 8K по байтам (без лимита строк), а `grep`/`list`/`bash` держатся малыми (8K), потому
что это указатели, а не содержимое; более крупный фрагмент файла достаётся окном `read` или
`recall` (бюджет 64K). `grep` и `search` возвращают **простой текст с номерами строк**
(`path:line:match`, контекст `path-line-text`, как `grep -n`), а не JSON: структурной обвязки,
которую модель парсит вместо кода, нет. В ленте `tool`-сообщение показывает окно
инструмента целиком, никогда не вырезая середину: результат инспекции (`read`/`grep`/`list`)
читается с начала, поэтому остаётся голова; вывод команды важен в конце, поэтому `run` держит
хвост. Усекается с пометкой об усечении лишь тело, превышающее бюджет своего инструмента. Полное тело движок сохраняет файлом, а в узле остаётся ссылка `outputRef`. Доступ —
по идентификатору, не по пути: прочитать фрагмент — `recall { id, start, end }`, поискать по
телу — `search { id, pattern }`. Команда, убитая **сигналом**, рендерится как
`killed by <SIG> (core: …)` (или `no core: core_pattern …`) плюс бэктрейс, так что краш
доходит до модели, а не только ненулевой код выхода.

**Системная часть** собирается по ситуации, а не монолитом: базовый промпт несёт только то, что
верно на любом ходу (роль, контракт, обход и набор состояний с переходами); в конце каждого хода
(временно, не хранится) добавляется инструкция текущей ситуации — по одной строке на ситуацию:
`request` (выбери первое состояние или `decline`; `what`/`done` — из запроса), `plan` (первый
шаг состояния), `working` (`turnInstruction`: критерий назван явно — «This state's done
criterion: "<criterion>". When it holds, `stop` — and nothing else; do not over-work the state»),
`transition` (`transitionInstruction(island)`: источник `what`/`done` — строка `Finish state
<label>` закрытого состояния; перечислены соседи по `next`; выбери следующее), `terminal` (вызови
`stop`, чтобы завершить). Имена/параметры/описания инструментов **не** в
промпте — они уходят полем `tools` запроса, и это поле **связано из `Context.applicable`**: на
`request`/`transition` предложен только `move` (плюс read-only `recall`/`search`), пока
состояние открыто — apply-инструменты и `stop`; поэтому ход, который движок отклонил бы, нельзя
вызвать вовсе (путь `propose` передаёт `toolNamesFor(applicable)` как `allowedTools`).

## 8. Инварианты

1. Журнал только растёт; узлы не переписываются — меняется лишь то, что мы показываем.
2. Проекция детерминирована: одни события дают один контекст.
3. Состояние закрывается только через `stop` (терминальное в том числе).
4. Докса только предлагает; логос решает.
5. Код возврата команды — обычный вывод, не приговор закрытия.
6. Каждый `move` — ребёнок запроса и несёт свою цель (`what`); план висит на `move`; каждое
   действие — альтернатива ровно одного пункта. Состояние никогда не альтернатива пункта, и у
   запроса нет своей цели.
7. `stop` — связь на `move`, а не пункт плана.
8. Ходы плана закрытого состояния уходят из ленты: остаётся только `Start state <label>` /
   инструкция / цель / `Finish state <label> — <why>` (§7).
9. `state` у `move` — авторский ярлык доксы: он никогда не гейтит ход и не закрывает состояние
   (закрытие — только `stop`). Но он ограничивает поверхность действий открытого состояния —
   инструменты, которые допускает `applies` острова; инструмент вне неё отвергается
   (`not_in_state`), а выйти из режима всегда можно через `move`.
10. Запрос заканчивается, когда остановлено терминальное состояние (`finish`), либо когда он
    отклонён; на запросе `stop` нет.
