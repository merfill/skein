**Статус.** У доксы **четыре оператора** (`create_goal`, `apply`, `stop`, `decline`); `recall`/`search` —
адресация только для чтения, не ходы. Запрос интерпретируется **один раз** как цель (связь
`goal`) либо отклоняется (узел `unactionable`). Цель закрывается **только** через `stop`.
План состоит из **пунктов**; пункт состоит из **альтернатив**. Контекст — **лента сообщений**,
собираемая из дерева. Докса предлагает; логос исполняет и записывает.

## 0. Принцип: семантика есть операция над деревом IR

Всё, что делает система, описывается **как операция над деревом IR**:

- какие **узлы** и **связи** создаются;
- куда переходит **текущий узел** (фокус работы);
- какие **производные факты** меняются (они не хранятся);
- что увидит **следующая проекция** (модель на следующем шаге);
- какие **инварианты** сохраняются.

Это относится и к ходам доксы, и к реакциям логоса. Новое поведение — новая операция по этому
шаблону, а не правка состояния в обход журнала.

Дерево — не данность, а след операций. Оно ветвится там, где агент выбирает подход
(альтернативные цели/команды), и растёт вглубь там, где цель разворачивается планом.

## 1. Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| **Докса** | LLM | предлагает ровно один оператор за ход | не выносит вердикты, не выводит |
| **Логос** | детерминированный движок, **включая среду и инструменты** | исполняет команды; по исходу ставит узлы и связи; пересчитывает производный вид; строит проекцию | не выводит истину; не выбирает между равносильными |
| **Арбитр** | внешний (человек; объективно — тулчейн) | первый запрос; финальная приёмка прогона; выбор равносильных гипотез | не производит содержания |

Протокола/среды как отдельной роли нет: исполнение и запись — часть логоса. Внутренние
операторы логоса — `o_rev` (пересчёт при изменении), `o_def` (отмена/опровержение), `o_ctx`
(проекция). Оператора предпочтения (`o_spec`) нет.

Ключевые следствия:

- **докса только предлагает.** Предложение входит как предложение (цель открыта, команда без
  результата), но никогда сразу как установленный факт;
- **выбор — из применимого.** Логос детерминированно даёт *применимые* ходы в текущей точке;
  докса выбирает один и наполняет содержанием;
- **прогон — вывод, а не вердикт.** Код возврата команды — обычный вывод, который читает
  модель; на нём ничего не гейтится — цель закрывает докса через `stop`;
- **запрос — не цель.** Сырая мотивация, корень; докса интерпретирует её один раз как цель
  либо отклоняет; приёмка остаётся внешней.

## 2. Дерево IR

### 2.1 Узлы

Два пространства.

**Рабочее пространство** — то, из чего состоит работа:

| kind | смысл |
|---|---|
| `request` | запрос арбитра: сырая мотивация (корень); интерпретируется один раз как цель или отклоняется |
| `goal` | цель: чего достичь; несёт `what` |
| `plan` | план цели: упорядоченный список пунктов (≥1) |
| `item` | пункт плана: упорядоченный список альтернатив (≥1) |
| `action` | команда; альтернатива пункта |
| `observation` | результат команды (окно чтения, вывод запуска + код возврата) |
| `stop` | отметка о закрытии цели |
| `unactionable` | отметка о том, что в запросе нет выполнимой задачи |
| `constraint` | ограничение (payload `forbid`: regex-пути) |

**Пространство артефактов** — то, что существует помимо работы:

| kind | смысл |
|---|---|
| `file` | файл |

### 2.2 Связи

Связь — именованное отношение от узла к узлу; имя — роль ребёнка у родителя. У каждого вида
узла фиксированный набор допустимых связей:

| От кого | Связь | К кому | Сколько |
|---|---|---|---|
| `request` | `goal` | `goal` | 0 или 1 |
| `request` | `unactionable` | `unactionable` | 0 или 1 |
| `goal` | `plan` | `plan` | ровно 1 |
| `goal` | `stop` | `stop` | 0 или 1 |
| `plan` | `items` | `item` | 1 и больше, по порядку |
| `item` | `alts` | `action` или `goal` | 1 и больше, по порядку |
| `action` | `result` | `observation` | 0 или 1 |
| `action` | `mutates` | `file` | 0 и больше |

Порядок детей — порядок добавления; текущий (выбранный) — **последний**. Два следствия:

- закрытие цели живёт у цели, в связи `goal.stop`; отдельного пункта плана под `stop` больше
  нет;
- `file` — единственный узел, на который ссылаются несколько действий (`action.mutates`): у
  файла много «владельцев», у остальных по одному.

### 2.3 Общая форма

```
goal --plan--> plan --items--> item --alts--> action | goal
```

Правила:

- пункт плана — **всегда** список альтернатив, минимум одна; если ветвления нет, элемент ровно
  один и это команда (`action`);
- цель появляется только двумя способами: как интерпретация запроса (`request.goal`) или как
  альтернатива пункта (`item.alts`). Больше нигде;
- **`what`.** Цель несёт `what` (чего достичь). План —
  отдельный узел `plan`, засеваемый `create_goal` одним
  пунктом, чья единственная альтернатива — первая команда.

### 2.4 Текущий узел

В каждый момент есть **текущий узел** — фокус работы; все операторы доксы относительны его.
Фокус — верх **стека обхода** (§2.6).

### 2.5 Состояние производно

У узлов **нет хранимых статусов**; узлы не меняются, `stateOf` нет. Нужные решению факты
читаются из узлов/связей:

- действие **исполнено** ⇔ у него есть произведённый ребёнок (`result`/`mutates`); иначе
  пункт лишь запланирован;
- действие **успешно** ⇔ оно изменило файл, либо его наблюдение-результат не провал
  (`failed`-причина или ненулевой `exitCode`; отсутствие `exitCode` — таймаут, вердикта нет);
- цель **закрыта** ⇔ есть связь `stop` к узлу `stop`; иначе открыта. Запрос **завершён** ⇔ его
  цель закрыта или есть узел `unactionable`; сам запрос никогда не закрывается `stop`;
- **`goalOf(request)`** — цель по связи `goal`; **`unactionableOf(request)`** — узел по
  `unactionable`; **`stopOf(goal)`** — узел по `stop`;
- **`lastChild(container)`** — текущий пункт/альтернатива (последний ребёнок);
- пункт **выполнен** ⇔ его текущая (последняя) альтернатива — исполненное успешное действие или
  закрытая цель; **курсор** — первый невыполненный пункт.

**Предикатов истины нет** (`achieved`/`refuted`/`abandoned`) и **критерия нет**. Прогон сам по
себе ничего не улаживает: цель закрывается только `stop` доксы. Это правила `project`/чтения,
а не поля. Монотонен только журнал (§3).

### 2.6 Стек и обход

Обход — детерминированная часть логоса. Он **не выбирает**; он вычисляет *применимые* ходы в
текущей точке; выбор из них — за доксой.

**Стек** `S = [R, G₀ … G_k]` — путь от корня к текущей цели. **Курсор** цели `G` — индекс
первого невыполненного пункта плана `G`. Ни то, ни другое не хранится: стек — свёртка событий
фокуса (`descend`/`return`, журнал append-only); курсор вычисляется из плана.

Детерминированное движение:

- **продвижение** — исполнение action-пункта стек не меняет; курсор сдвигается сам;
- **спуск** `G → H` — положить `H`, фокус → `H`; докса спускается в цель запроса (`goal`) или в
  подцель, только что созданную новейшей альтернативой пункта (`alts`);
- **возврат** — снять верх, фокус → родитель. Наступает, когда текущая цель **завершена**
  (`stop`) или по решению `W`. Закрытая цель не удерживает фокус на потомках: ветка обрезается
  под закрытым предком, а не только когда закрывается сама верхушка.

Движок отдаёт доксе **руку целиком** (упорядоченные соседние альтернативы фокуса), а курсор
отмечает текущий узел. Одно вычисление применимых ходов питает и проекцию, и `classify`.

**Применимое в точке `G`:**

- `G` — запрос без цели → `create_goal` (истолковать) или `decline`;
- `G` — закрытая цель → `return` (внутреннее движка);
- иначе (открытая цель) → `apply` (команда), `create_goal` (подцель, разлагающая текущий пункт)
  и `stop` (закрыть цель).

### 2.7 Как команда попадает в дерево

`apply` — вызов инструмента. Логос исполняет команду и **всегда** записывает исход
наблюдением; докса читает наблюдение и выбирает следующий ход; логос только размещает
пришедший ход.

**Исход текущего пункта** берётся из его текущей альтернативы:

- альтернатива — **команда**: наблюдение несёт результат (**успех**) или причину (**неуспех**:
  инструмент не смог выполнить, проверка допустимости не прошла, прогон вернул ненулевой код
  или таймаут — **нет вердикта**);
- альтернатива — **цель**: наблюдения нет; исход — её `stop`; закрытая цель — **успех**.

**Куда встаёт следующий ход** (логос размещает по исходу; команду или цель выбирает докса):

- после **успеха** — **новым пунктом плана**;
- **иначе** — **новой альтернативой текущего пункта**; если ход — цель, фокус спускается.

**Подцель** (`create_goal` на открытой цели) всегда становится новой альтернативой текущего
пункта, и фокус спускается; без текущего пункта — отказ.

Старт: `create_goal` засевает план цели одним пунктом и сразу исполняет его первую команду
(логос); цель рождается с уже исполненным первым пунктом. Каждая попытка оставляет новые узлы;
существующий узел не переиспользуется и не правится — журнал остаётся монотонным.

**Структурные ходы.** `create_goal`, `stop`, `decline` — не исполнение команды, а изменение
дерева. Если такой ход недопустим, он **отклоняется**: узел не создаётся, а причина приходит
доксе сообщением в ленте на следующий ход (`rejected <ход>: <причина>`). То же для **голого** адресного
`recall`, который отклонён как избыточный. У команды такого отказа нет: неисполнение (повтор,
устаревший базис, запрещённый путь, пустая команда) приходит **наблюдением с причиной**.

### 2.8 Детекция зацикливания

Зацикливание — не отдельный датчик, а **отсутствие прогресса**. Прогресс в точке — сдвиг
курсора, **новое знание** (новое наблюдение или новый исход, либо полученный фрагмент
`recall`/`search`) либо закрытие. Слои
детерминированные: **повтор действия** (та же команда с теми же входами и неизменным миром)
отклоняется, и его наблюдение называет существующий результат; **застой** (курсор не сдвигается
и нет нового знания `K` ходов) возвращает к родителю; **исчерпание** без прогресса на корне
останавливает прогон (`no_progress`).

## 3. Журнал и свёртка

- **Журнал** (`Event[]`) — единственная истина; только дописывается.
- **Состояние** — `fold(журнал)`, производное.
- **Проекция** — `project(состояние)`, производное; ровно то, что видит модель.

Словарь событий закрыт: `add_node`, `add_edge`, `descend`, `return`, `mutate`,
`record_rejection`. Смена состояния — **новое событие** (`observation`, `mutate`, `stop`), а не
правка; нет ни `set_status`, ни `record_check`. Сбой команды **не забывается**: он
материализуется наблюдением с флагом `failed` (а при неисполнении — `refused`).

Детерминизм: одни события и параметры дают одно состояние и одну проекцию. Единственный
внешний источник — изменения файлов; они входят через `mutate`.

## 4. Операторы доксы

У доксы **четыре оператора** (`create_goal`, `apply`, `stop`, `decline`); `recall` и `search` — адресация
только для чтения, не ходы. Каждый описан по шаблону: назначение → применимо к → вход →
действие → фокус → отказ.

### 4.1 `create_goal`

Интерпретирует запрос либо разлагает текущий пункт в подцель.

**Вход.** `{ what, command }`: `what` — что достичь; `command` — первый пункт плана
(конкретная команда).

**На запросе (интерпретация).** Создать цель `G` и её план `Q` с одним пунктом `I`, чья
единственная альтернатива — действие `A` (эта `command`); связать `R.goal = G`, `G.plan = Q`,
`Q.items = [I]`, `I.alts = [A]`. Логос **сразу исполняет `A`** и записывает исход; цель
рождается с уже исполненным первым пунктом. Ход отображается тремя сообщениями (assistant
цель, assistant вызов, tool наблюдение). Фокус спускается в `G`. Интерпретация создаётся
один раз: второй `create_goal` на запросе отклоняется (`interpreted`).

**На открытой цели (разложение).** Подцель становится новейшей альтернативой текущего пункта
(`I.alts += G`), со своим планом, засеянным её `command` (тоже исполняется сразу); фокус
спускается. Без текущего пункта — отказ.

### 4.2 `apply`

Исполняет одну команду в текущей цели.

**Вход.** `{ tool, … }`, где `tool` — один из `read`/`grep`/`list`/`edit`/`write`/`run`/
`fetch`/`apply_patch`, плюс параметры инструмента.

**Действие.** Команда исполняется; исход записывается как `A.result = observation` (read, grep,
list, run) или `A.mutates += file` (правка) — либо, когда она не исполнилась, наблюдением с
причиной. Размещение — по исходу текущего пункта (§2.7). Фокус не двигается.

### 4.3 `stop`

Закрывает цель — единственный способ её завершить.

**Вход.** `{ why? }` — причина.

**Действие.** Создать узел `stop` `S`; связать `C.stop = S`. Фокус — на цели; следующая
проекция возвращается к родителю. Если закрыта цель корневого запроса — прогон заканчивается.
Гейта по критерию **нет**: докса закрывает цель в процессе. `stop` на запросе отклоняется
(`not_addressed`).

### 4.4 `decline`

Завершает запрос, чьё намерение неисполнимо, не изобретая цель.

**Вход.** `{ why? }` — причина. **Применимо к.** Свежему запросу.

**Действие.** Создать узел `unactionable` `U`; связать `R.unactionable = U`. Цель и план не
создаются. Фокус завершает прогон (`request_unactionable`). На цели — `not_request`; на уже
истолкованном запросе — `interpreted`; на уже отклонённом — `repeated_action`.

### 4.5 `recall` и `search`

Два read-only инструмента адресуют сохранённый результат по `id`; ни один не создаёт узел и не
меняет дерево. `recall { id, start?, end? }` читает тело (при желании окно строк);
`search { id, pattern, before?, after? }` ищет регуляркой внутри тела (stdout **и** stderr).
Они разделены, чтобы чтение результата не путалось с его поиском и с `read`/`grep` (те целят
workspace). **Оконный** `recall` или любой `search` — другой фрагмент, новое содержание;
избыточно лишь **голое** recall по id, чьё тело уже в виду.

## 5. Время, версии, свидетельство

### 5.1 Версия

Версия файла — идентификатор содержимого (хэш). Содержимое старых версий в IR не хранится;
блобы живут в воркспейсе. IR хранит только имена версий.

### 5.2 История и текущая версия

`history(ref)` — версии `ref` в порядке `mutate`; `current(ref)` — последняя. Обе производны из
журнала.

### 5.3 Актуальность вычисляется

Наблюдение, полученное чтением файла, несёт его **версию**. Признака «устарело» нет:
актуальность — **отношение факта к текущему контексту**, а не свойство факта:
`actual(fact) ⇔ fact.version = current(fact.ref)`.

### 5.4 Монотонность

Журнал только растёт. Смена знания (новая версия, новое наблюдение, новая гипотеза) — новые
записи; пересчитывается только производный вид.

## 6. Завершение и честность

| Условие | Чем закрывается | Производное состояние |
|---|---|---|
| открытая цель | `stop` (без гейта) | закрыта; связь `stop` ведёт goal → stop |
| запрос (корень) | заканчивается, когда его цель закрыта (`request_addressed`) или при `decline` (`request_unactionable`); у запроса нет `stop` | прогон заканчивается |

**Запрос в IR не закрывается.** Нет узла «принято»: молчание пользователя — согласие, а
объективный харнес оценивает прогон извне. Запрос заканчивается, когда его цель остановлена
или когда докса отклоняет его.

**Честность.** Сила вывода не превышает силы посылок: `exitCode` прогона — обычный вывод;
запрос никогда не помечается «achieved»; никакая гипотеза не хранится как допущение.

## 7. Контекст: лента сообщений

Контекст — то, что модель видит на очередном шаге. Он выглядит как обычная лента сообщений, но
**собирается из дерева заново каждый ход** — это проекция, а не накопительная переписка. Одни
события всегда дают одну ленту.

**Роли:** `system` (базовый промпт плюс инструкция текущего узла и ограничения), `user`
(запрос), `assistant` (ходы доксы), `tool` (результаты команд).

**Ходы и их сообщения:**

- `create_goal` — `assistant` с целью (`what`), затем первая команда:
  `assistant` (вызов) + `tool` (наблюдение);
- `apply` — `assistant` (вызов) + `tool` (наблюдение);
- `stop` — `assistant` с причиной (`why`): цель закрыта;
- `decline` — `assistant` с причиной (`why`): запрос отклонён;
- структурный ход отклонён — `tool` с причиной (`rejected <ход>: <причина>`), транзиентно на
  следующий ход (узла нет); результат `recall`/`search` — тоже транзиентная пара
  `assistant` (с аргументами) + `tool`.

То есть **каждый пункт плана — пара** `assistant` + `tool`, а создание и закрытие цели —
отдельные `assistant`-сообщения. Команды-альтернативы несут пометку
(`alternative to step "…" (previous attempt: "…" — reason)`). Каждое сообщение несёт id узла
(`[id] …`), чтобы результат можно было адресовать по `id` через `recall`/`search`.

**Лента не монотонна.** Как только цель закрывается, её внутренние сообщения уходят из ленты;
на руке её родителя остаётся только сообщение о закрытии (`stop` с `why`). При подъёме выше — то
же самое. Уходит только вид, а не данные: дерево остаётся полным.

**Рассуждение доксы не хранится**: сырое `thought` в дереве нет и в ленту не попадает; его
смысл живёт в полях `why`.

**Работа с данными.** Тело результата ограничено самим инструментом, с **per-tool** бюджетом:
`read` — большой (64K; по байтам, без лимита строк), а `grep`/`list`/`run` держатся малыми
(8K), потому что это указатели, а не содержимое. В ленте `tool`-сообщение показывает окно
инструмента целиком, никогда не вырезая середину: результат инспекции (`read`/`grep`/`list`)
читается с начала, поэтому остаётся голова; вывод команды важен в конце, поэтому `run` держит
хвост. Усекается с пометкой об усечении лишь тело, превышающее бюджет своего инструмента. Полное тело движок сохраняет файлом, а в узле остаётся ссылка `outputRef`. Доступ —
по идентификатору, не по пути: прочитать фрагмент — `recall { id, start, end }`, поискать по
телу — `search { id, pattern }`.

**Системная часть** собирается из намерения текущего узла, а не монолитом: базовый промпт несёт
только то, что верно на любом ходу (роль, контракт, форма ответа, индекс инструментов,
дисциплина потока); инструкция узла несёт допустимые ходы и правила текущей ситуации (свежий
запрос / открытая цель); ограничения добавляются туда же. Эта граница — предмет следующего
этапа (составной системный промпт).

---

## 8. Инварианты

1. Журнал только растёт; узлы не переписываются — меняется лишь то, что мы показываем.
2. Проекция детерминирована: одни события дают один контекст.
3. Цель закрывается только через `stop`.
4. Докса только предлагает; логос решает.
5. Код возврата команды — обычный вывод, не приговор закрытия.
6. Каждое действие — альтернатива ровно одного пункта; цель — интерпретация запроса или
   альтернатива пункта.
7. `stop` — связь на цели, а не пункт плана.
8. Внутренности закрытой цели уходят из ленты (остаётся только сообщение о закрытии).

## 9. Открытые вопросы и не-цели

### 9.1 Открытое

- Точная граница базового промпта и промптов узлов (§7) — следующий этап.
- Переформулировать «первый невыполненный пункт» после уточнения формы пункта.
- Пометка альтернатив упрощённая; вернуться, если окажется мало.

### 9.2 Не-цели

Ни AST/символьной таблицы, ни эмбеддингов, ни CSP/арифметики, ни UI, ни мультиязычности, ни
нескольких LLM-провайдеров. Ни родов `check`/`claim`/`decision`/`subgoal`; ни гейта по
критерию.
