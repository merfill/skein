# Skein — проекция контекста: лента сообщений

> Английское зеркало — `docs/projection.md`.

> **Свёрнуто из ревизии.** Проекция — лента сообщений, собираемая из дерева каждый ход;
> прежние блоки `path`/`lastResult`/`shown`/`calls`/`budget` убраны (лента — это весь контекст;
> `Context.applicable` сохранён только чтобы связать предложенную поверхность инструментов, §2).
> Источник истины — `docs/ir_semantics_ru.md` §7; as-built — `docs/ir_ru.md`; справочник
> операторов — `docs/ir_operations_ru.md`.

## 1. Назначение

Контекст — то, что модель видит на очередном шаге: **вся её память**. Он выглядит как обычная
лента сообщений (как в ReAct-агенте), но **собирается из дерева заново каждый ход** — это
проекция, а не накопительная переписка. Одни события всегда дают одну ленту.

## 2. Роли и ходы

- `system` — базовый промпт, инструкция текущего узла и ограничения;
- `user` — запрос;
- `assistant` — ходы доксы;
- `tool` — результаты команд;
- `system` — описание состояния, показывается один раз при входе в состояние.

| Ход | Сообщения |
|---|---|
| `move` | `assistant` (вызов `move { state, what, note? }`) + `tool` (результат этого вызова): пока состояние открыто — подтверждение (`moved to <label>`), за ним `system`-сообщение с описанием состояния (`What / Done when`); когда состояние остановлено — **строка закрытия** этого состояния `State <label>: finished — <why>`, читаемая из отношения `move.stop` |
| `apply` | `assistant` (вызов) + `tool` (наблюдение); первый `apply` после `move` засевает план состояния и его первый пункт |
| `stop` | закрытие состояния; своего сообщения не добавляет — рендерится результатом `move` этого состояния (или, на терминальном состоянии, запрос завершён) |
| `decline` | `assistant` (причина `why`): запрос отклонён |

Каждый пункт плана — пара `assistant` + `tool`; первый `apply` после `move` засевает план
состояния. Команда, исполнившаяся и изменившая файл (правка), наблюдения не имеет, поэтому её
`tool`-сообщение читается как `mutated <path>`. Строка закрытия несёт **только** метку состояния
и причину `stop` (плюс `note`, переданный моделью на `move`, оставившем его) — никогда список
изменённых файлов: состояние, запускающее сборку, мутирует тысячи артефактов.

## 3. Лента собирается обходом дерева

- запрос — первый `user`-ход;
- его состояния (дети `move`) рендерятся по порядку: **открытое** состояние рендерит свой
  `move`-вызов, его результат и затем пункты плана по порядку (план засевает первый `apply`);
  **завершённое** состояние — текущее в ожидании перехода или уже оставленное позади —
  сворачивается ровно в свой `move`-вызов и его результат (строку закрытия
  `State <label>: finished — <why>`). Ни ходов плана, ни отдельного сообщения `stop` не остаётся;
- **лента не монотонна.** Когда состояние оставлено позади, его `apply`-ходы
  уходят из ленты; остаётся лишь его `move` + закрытие. Уходит только вид, а не данные: дерево
  остаётся полным;
- **рассуждение доксы не хранится**: сырое `thought` в дереве нет и в ленту не попадает; его
  смысл живёт в полях `why` и в `note` узла `move`.

## 4. Пометки и адреса

- команда-альтернатива несёт `alternative to step "…" (previous attempt: "…" — reason)`, чтобы
  модель видела, что уже не сработало;
- каждое `assistant`/`tool`-сообщение начинается с id узла (`[id] …`), чтобы результат можно
  было адресовать по `id` через `recall`/`search`.

## 5. Работа с данными

Тело результата ограничено самим инструментом, с **per-tool** бюджетом (окно `read` 8K;
`grep`/`list`/`run` 8K; `recall` 64K); `tool`-сообщение показывает окно инструмента целиком и никогда не
вырезает середину. Результат инспекции (`read`/`grep`/`list`) читается с начала, поэтому
остаётся голова; вывод команды важен в конце, поэтому `run` держит хвост. Усекается с пометкой
об усечении лишь тело, превышающее бюджет своего инструмента. Полное тело движок сохраняет файлом, а в узле остаётся ссылка. Доступ — по
идентификатору, не по пути:

- прочитать фрагмент — `recall { id, start, end }`;
- поискать по телу — `search { id, pattern }`.

`recall`/`search` не создают узел, поэтому его результата в дереве нет: он добавляется
транзиентной парой `assistant` (вызов с аргументами, не голое имя) + `tool` на следующий за ним ход.
Отказ структурного хода тоже узла не создаёт:
причина приходит транзиентным `tool`-сообщением (`rejected <ход>: <причина>`) на следующий ход.

## 6. Системная часть

Системная часть собирается из намерения текущего узла, а не монолитом:

- **базовый промпт** несёт только то, что верно на любом ходу — роль и контракт. Он стабилен,
  поэтому хорош как префикс кэша. Имён/параметров/описаний инструментов здесь **нет** — они
  уходят полем `tools` запроса;
- **поверхность инструментов** в этом поле связана из `Context.applicable`: на переходе
  предложен только `move`, пока состояние открыто — apply-инструменты и `stop`
  (`recall`/`search` всегда), поэтому ход, который движок отклонил бы, нельзя вызвать вовсе;
- **инструкция узла** несёт допустимые ходы и правила текущей ситуации (свежий запрос /
  состояние в ожидании первого пункта плана / открытое состояние / завершённое состояние в
  ожидании перехода / терминальное состояние); пока состояние в фокусе, за ней идут
  `What / Done when / Constraints` состояния;
- **ограничения** добавляются отдельными `system`-сообщениями;
- сразу после результата инструмента внутри открытого состояния добавляется **инструкция
  наблюдения** последним `system`-сообщением (`Context.result`): она повторяет правило
  состояния (`State` / `Goal` / `Done when` / `Constraints`) и спрашивает, выполнен ли уже
  `Done when` — да → `stop`; шаг удался, надо ещё → следующий ход; провал/не тот шаг → другой ход.

Точная граница базы и узла — предмет следующего этапа (составной системный промпт).

## 7. Детерминизм

`project` чист: одни события дают одну ленту. Единственный транзиентный вход — результат
`recall`/`search` текущего хода (§5); поскольку он производится тем же ходом, проекция остаётся
детерминированной.
