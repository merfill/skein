# Skein — проекция контекста: лента сообщений

> Английское зеркало — `docs/projection.md`.

> **Свёрнуто из ревизии.** Проекция — лента сообщений, собираемая из дерева каждый ход;
> прежние блоки `path`/`lastResult`/`shown`/`calls`/`budget` убраны (лента — это весь контекст;
> `Context.applicable` сохранён только чтобы связать предложенную поверхность инструментов, §2).
> Источник истины — `docs/ir_semantics_ru.md` §7; as-built — `docs/ir_ru.md`; справочник
> операторов — `docs/ir_operations_ru.md`.

## 1. Назначение

Контекст — то, что модель видит на очередном шаге: **вся её память**. Он выглядит как обычная
лента сообщений (как в ReAct-агенте), но **собирается из дерева заново каждый ход** — это
проекция, а не накопительная переписка. Одни события всегда дают одну ленту.

## 2. Роли и ходы

- `system` — базовый промпт, ограничения, инструкция состояния (один раз при входе), блок
  факта для **текущего** состояния (`Workspace` в Orientation/Patch, `Orientation result` в
  Localization/Research, `Probe` в остальных) и инструкция текущей ситуации (в конце,
  временно); у закрытых состояний блока нет;
- `user` — запрос (вверху ленты, каждый ход) и цель каждого состояния;
- `assistant` — маркеры состояний и вызовы доксы;
- `tool` — результаты команд.

| Ход | Сообщения |
|---|---|
| `move` | **состояние — это решение, а не вызов инструмента**: маркер `assistant` `Start state <label>`, инструкция состояния ходом `system`, блок факта текущего состояния ходом `system` (`Workspace`/`Orientation result`/`Probe`), затем цель состояния ходом `user` (`what: <цель острова>`). Запрос — второе сообщение ленты (сразу после базового промпта), на **каждом** ходу, не убирается |
| `apply` | `assistant` (вызов) + `tool` (наблюдение); первый `apply` после `move` засевает план состояния и его первый пункт |
| `stop` | закрытие состояния, рендерится маркером `assistant` `Finish state <label> — <why>`; вызова инструмента не добавляет. На терминальном состоянии запрос завершается |
| `decline` | `assistant` (причина `why`): запрос отклонён |

Каждый пункт плана — пара `assistant` + `tool`; первый `apply` после `move` засевает план
состояния. Команда, исполнившаяся и изменившая файл (правка), наблюдения не имеет, поэтому её
`tool`-сообщение читается как `mutated <path>`. Состояние — это тройка `Start state <label>` /
цель / `Finish state <label>`, а пока открыто — его план. Маркер `Finish state` несёт **только**
метку и причину `stop` — никогда список изменённых файлов: состояние, запускающее сборку,
мутирует тысячи артефактов.

## 3. Лента собирается обходом дерева

- запрос — первое `user`-сообщение ленты (сразу после базового промпта), на каждом ходу;
- **probe** — один сессионный `fact` (`add_node kind:"fact"`, `id: fact:session`) с
  `{ environment, material }`, записанный на старте запроса. Он не идёт отдельным сообщением
  после запроса; проекция выбирает нужный блок для цели **текущего** состояния, после `what:`.
  Orientation получает `Workspace` — карту workspace (`root`, repo, entries/paths); Localization
  и Research получают ту же карту как `Orientation result` (Research — плюс `Probe` с
  interpreters/tools); Patch получает её же как `Workspace`; Recovery/Construction/Verification —
  `Probe` (environment) отдельным заголовком. Блок идёт отдельным `system`-ходом перед целью
  (`user`), а не приклеен к `what:`. Закрытые состояния блоков не несут; на request-ходу их нет;
- карта workspace детерминирована: `root`, repo-статус, top-level entries (для маленьких
  материалов — paths), число файлов. Environment, расширения, конфиги, команды сборки и build
  state в Orientation **не** показываются; объявленная команда не выдаётся за acceptance;
- его состояния (дети `move`) рендерятся по порядку: **открытое** (и текущее закрытое в
  ожидании перехода) состояние рендерит маркер `Start state`, инструкцию (`system`) и цель
  (`user`) после блока; затем пункты плана. **Оставленное позади** состояние сворачивается в
  `Start state <label>` / инструкцию / цель / `Finish state <label> — <why>` без блока. Ни ходов
  плана, ни отдельного сообщения `stop` не остаётся;
- `move.what`/`move.notes` доксы **не показываются**: цель состояния берётся из определения
  острова (`Island.what`), а предположения запроса не переносятся как `notes`;
- **лента не монотонна.** Когда состояние оставлено позади, его `apply`-ходы уходят из ленты;
  остаётся лишь его тройка. Уходит только вид, а не данные: дерево остаётся полным;
- **рассуждение доксы не хранится**: сырое `thought` в дереве нет и в ленту не попадает; его
  смысл живёт в полях `why`.

## 4. Пометки и адреса

- команда-альтернатива несёт `alternative to step "…" (previous attempt: "…" — reason)`, чтобы
  модель видела, что уже не сработало;
- каждое `assistant`/`tool`-сообщение начинается с id узла (`[id] …`), чтобы результат можно
  было адресовать по `id` через `recall`/`search`.

## 5. Работа с данными

Тело результата ограничено самим инструментом, с **per-tool** бюджетом (окно `read` 8K;
`grep`/`list`/`run` 8K; `recall` 64K); `tool`-сообщение показывает окно инструмента целиком и никогда не
вырезает середину. Результат инспекции (`read`/`grep`/`list`) читается с начала, поэтому
остаётся голова; вывод команды важен в конце, поэтому `run` держит хвост. Усекается с пометкой
об усечении лишь тело, превышающее бюджет своего инструмента. Полное тело движок сохраняет файлом, а в узле остаётся ссылка. Доступ — по
идентификатору, не по пути:

- прочитать фрагмент — `recall { id, start, end }`;
- поискать по телу — `search { id, pattern }`.

`recall`/`search` оставляют узел (действие + его наблюдение под планом состояния), поэтому
полученное окно остаётся на ленте состояния как любой шаг и уходит вместе с состоянием на `stop`.
Отказ структурного хода узла не создаёт: причина приходит транзиентным `tool`-сообщением
(`rejected <ход>: <причина>`) на следующий ход.

## 6. Системная часть

Системная часть собирается по ситуации, а не монолитом:

- **базовый промпт** несёт только то, что верно на любом ходу — роль, контракт и набор состояний
  с переходами. Он стабилен, поэтому хорош как префикс кэша. Имён/параметров/описаний
  инструментов здесь **нет** — они уходят полем `tools` запроса;
- **поверхность инструментов** в этом поле связана из `Context.applicable`: на
  `request`/`transition` предложен только `move`, пока состояние открыто — apply-инструменты и
  `stop` (`recall`/`search` всегда), поэтому ход, который движок отклонил бы, нельзя вызвать вовсе;
- **инструкция ситуации** добавляется в конце каждого хода (временно, не хранится):
  `request` (выбери первое состояние или `decline`; `what`/`done` — **из запроса**), `plan`
  (первый шаг состояния), `working` (`turnInstruction`: критерий назван явно — «This state's done
  criterion: "<criterion>". When it holds, `stop` — and nothing else; do not over-work the state»),
  `transition` (`transitionInstruction(island)`: источник `what`/`done` — строка `Finish state
  <label>` закрытого состояния; перечислены соседи по `next`; выбери следующее или Finish),
  `terminal` (вызови `stop`, чтобы завершить);
- **ограничения** добавляются отдельными `system`-сообщениями.

Точная граница базы и ситуации — предмет следующего этапа (составной системный промпт).

## 7. Детерминизм

`project` чист: одни события дают одну ленту. Единственный транзиентный вход — результат
`recall`/`search` текущего хода (§5); поскольку он производится тем же ходом, проекция остаётся
детерминированной.
