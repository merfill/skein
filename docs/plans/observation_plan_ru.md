# Skein — план наблюдения (изменения вне движка)

> Английское зеркало — `docs/plans/observation_plan.md`.

Связанные: `docs/concepts_ru.md` (первый принцип), `docs/design_review_ru.md`
(R3), `docs/plans/check_soundness_plan_ru.md`. Общий план —
`docs/plans/implementation_plan_ru.md`.

Статус: (a),(b) реализованы; (c) открыт (см. §8).

## 1. Проблема

Движок узнаёт об изменении файла только из событий, которые произвёл сам
(`edit` → `mutate`). Остаются две дыры:

- `run` может записать не-запрещённый файл, и `mutate` не пишется
  (`constraint_guard_plan_ru.md` §6);
- файл, изменённый внешним писателем (пользователь, другая программа), вообще не
  наблюдается, пока его не перечитают.

В обоих случаях отсутствует факт наблюдения. По первому принципу это пробел в
опыте, а не выдуманное знание; лечится наблюдением, а не догадкой.

## 2. Решение

Добавить наблюдение на трёх уровнях, чтобы у любого изменения, причастного к
текущей активности, был источник.

- (a) **Записи движка.** После `run` сравнить версии отслеживаемых файлов до и
  после; писать `mutate` для каждого изменённого файла, не только запрещённого.
- (b) **Сверка.** В начале хода шаг движка перепроверяет версии `ref`, от которых
  зависит текущая активность (свидетели живых проверок и живые факты чтения), и
  при дрейфе пишет `mutate`. Это гарантия. Кэш отпечатков `mtime`/`ctime`/размер
  избавляет от повторного хэширования неизменённых файлов
  (`docs/plans/watcher_plan_ru.md`).
- (c) **Watcher.** Наблюдатель файловой системы сразу превращает внешние
  изменения в события `mutate`. Это оптимизация (быстрый путь); она не заменяет
  (b).

Наблюдение происходит в цикле, никогда внутри `project`, поэтому `project`
остаётся чистой функцией состояния.

## 3. Дизайн

- (a) `src/tools/index.ts`, `run`: расширить существующий снапшот до/после на все
  отслеживаемые файлы; на каждое изменение версии писать `mutate`.
- (b) новый чистый шаг (например, `src/loop/observe.ts`): по `State` и
  `Workspace` вычислить активный набор `ref`, сравнить записанные и текущие
  версии, вернуть события `mutate`. Подключить перед `project` в
  `src/loop/graph.ts`. Область: `ref` из свидетельств живых рёбер `verifies` и
  `ref` с живыми фактами чтения.
- (c) watcher: `fs.watch` / chokidar по воркспейсу (`.skein` исключён), с
  дебаунсом, пишет `mutate` с новой версией. Работает как вход в цикл;
  опциональная фаза.

## 4. Проверка

- `npm run typecheck`; `npm test`.
- Тесты: `run`, пишущий не-запрещённый файл, даёт `mutate`; сверка внешней правки
  (записать файл в обход движка, затем выполнить шаг наблюдения) даёт `mutate` и
  инвалидирует проверку; `project` не меняется для тех же событий.

## 5. Инварианты

- Каждое записанное изменение прослеживается до наблюдения (запись движка,
  сверка или watcher) — источник.
- `project` остаётся чистым; наблюдение — шаг цикла.
- Журнал остаётся append-only.

## 6. Границы

- События watcher'а зависят от окружения; воспроизводимость опирается на журнал,
  а не на воспроизведение окружения.
- Сетевые ФС и потерянные уведомления — причина, по которой гарантия именно
  сверка (b), а не watcher.

## 7. Порядок работ

1. (a) дыра `run`.
2. (b) прицельная сверка.
3. (c) watcher (опционально).

## 8. Статус

Реализованы (a) и (b); (c) остаётся открытым.

- (a) `run` снимает версии отслеживаемых файлов до и после команды и пишет
  `mutate` на каждый изменённый файл (`src/tools/index.ts`).
- (b) цикл сверяет активные `ref` перед `project` (`src/loop/observe.ts`,
  подключён в `src/loop/graph.ts`); замеченный дрейф становится `mutate`. Кэш
  отпечатков избавляет от повторного хэширования неизменённых файлов
  (`docs/plans/watcher_plan_ru.md`).
- (c) наблюдатель файловой системы не реализован: гарантия — это сверка,
  watcher добавляет лишь скорость и может быть добавлен позже, не затрагивая
  путь корректности.

`npm run typecheck` чист, `npm test` проходит (35 тестов). Доки обновлены:
`docs/ir_ru.md` §1, §2, §5.
