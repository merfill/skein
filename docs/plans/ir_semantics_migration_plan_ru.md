## 1. Задача

Код реализует старую модель (`claim`/`decision`/`subgoal`, статусы-поля, `stale`,
`mode`, десять действий доксы). Семантика (`ir_semantics_ru.md`) описывает другую:
дерево с узлами `goal`/`plan`/`alternatives`/`action`/`observation`/`check`/
`complete`/`constraint`/`file`, три оператора доксы (`create goal`/`apply`/
`complete`), производное состояние, обход плана и честность `achieved` /
`achieved_under`. Нужно заменить ядро, а не надстроить совместимость.

Базлайн на момент планирования: `npm run typecheck` чист, `npm test` — **103**
теста зелёные.

## 2. Стратегия

**Связная замена ядра** (решение согласовано). Словарь, операторы, обход,
честность и проекция меняются несовместимо, поэтому старая модель не тянется
параллельно: иначе появляется двойной словарь и мёртвый код.

- Внутри — под-шаги (ниже); каждый заканчивается зелёными `npm run typecheck` и
  `npm test`; где применимо — `npm run bench:gate`.
- Тесты, покрывающие старую модель, **переписываются вместе** с кодом шага, а не
  удаляются молча.
- Объём первой переделки — всё ядро: Ш1–Ш6 (словарь, операторы, обход, честность,
  проекция, промпт). Интеграции (Ш7) и документация (Ш8) следуют за ядром.

## 3. Разрыв (что именно расходится)

| Область | Сейчас в коде | Целевая семантика |
|---|---|---|
| Узлы `work` | `goal, subgoal, claim, decision, action, observation, check, constraint` | `goal, action, plan, alternatives, observation, check, complete, constraint` |
| Понятия | `claim`/`subgoal`/`decision` — узлы веры/выбора | их нет: обоснование — `why` цели, допущение — ребро `under`, подцель — `goal`, решение — логос/Арбитр |
| Рёбра | `decomposes, supports, justifies, chosen_over, locates, verifies, …` | `has_plan, item, has_alternatives, chosen, under, produces, verifies, closes, mutates` |
| План | нет узла `plan`; состав неявен | узел `plan` + упорядоченные `item`; порядок — позиция у детей контейнера |
| События | 8, включая `set_status` | те же минус `set_status`; `record_check` несёт `inconclusive` и `under` |
| Операторы доксы | 10 действий (`decompose`, `decide`, `track`, `finish`, `abstain`, …) | 3: `create goal`, `apply`, `complete` |
| Обход | стек `branch` привязан к claim/subgoal; курсора нет | курсор по пунктам плана; стек целей; «применимое» в текущей точке |
| Состояние | `statuses`/`edgeStatuses` как поля + `mode` | только производные предикаты: `executed/achieved/achieved_under/refuted/abandoned/open` |
| Честность | `claim verified/refuted`, `stale` | `achieved` (check `pass` без `under`) vs `achieved_under` (`under`/`complete`); `out_of_fragment` |
| Проекция | `header.mode`, `frontier.claims/facts/decisions/subgoals` | `header` (корень/текущая цель, ограничения, фрагмент, бюджет); `frontier` — ветка, план и состояние пунктов, обязательства, последний результат |
| Корень | остаётся `open`, закрывает харнесс | закрывает Арбитр по критерию |
| Стоп | `finish`/`abstain` — оператор доксы; `knowledgeKey` | стоп — решение Арбитра; повтор — по сигнатуре действия с версиями входов |

## 4. Под-шаги

### Ш1. IR-словарь и события

**Файлы:** `src/ir/types.ts`, `src/ir/events.ts`, `src/ir/graph.ts`.

**Что меняется:**

- `WORK_KINDS = goal, action, plan, alternatives, observation, check, complete,
  constraint`; `ARTIFACT_KINDS = file` (`symbol`/`test` — зарезервированы, вне
  этапа, §10.1 семантики).
- `EDGE_KINDS = has_plan, item, has_alternatives, chosen, under, produces,
  verifies, closes, mutates`.
- `Node.payload` цели: `{ what, why, done_when }`, где
  `done_when = { kind: "objective", command } | { kind: "subjective", text }`.
- `plan`/`alternatives` — узлы-контейнеры; порядок детей **не** хранится полем:
  выводится из порядка событий `add_edge item` (детерминированно при том же
  журнале).
- Убрать событие `set_status`. `record_check`: `targets: string[]` (id целей),
  `under?: string[]` (id целей-допущений), `verdict: pass | fail | inconclusive`.
- `fold` строит производные предикаты вместо `statuses`:
  `executed`, `achieved`, `achieved_under`, `refuted`, `abandoned`, иначе `open`;
  `abandoned` — вариант `alternatives`, у соседа есть `chosen`.
- Курсор `cursor(G)` — индекс первого невыполненного пункта плана; стек — свёртка
  `descend`/`return`; текущий узел — вершина стека.

**Готово, когда:** словарь компилируется; `fold` детерминирован; тест кодирует
производность состояния (нет статусов-полей) и порядок пунктов.

### Ш2. Операторы доксы и проверка допустимости

**Файлы:** `src/llm/schemas.ts`, `src/tools/index.ts`, `src/loop/classify.ts`.

**Что меняется:**

- Схема — ровно три оператора:
  - `create goal { what, why?, done_when, plan? }`, `plan` — непустой список
    пунктов `goal|action` (вложенность — решение, см. §7);
  - `apply { tool: read|grep|edit|run, … }` (действия над миром — частный случай
    `apply`);
  - `complete { goal, note? }`.
- `apply`:
  - `read`/`grep` → `action` + `observation` (ребро `produces`);
  - `edit` → `action` + `mutate` + ребро `mutates` `action → file`; правка на
    устаревшем базисе (`current(ref)`) отклоняется;
  - `run` как проверка → узел `check` + `verifies` к текущей цели + `under` к
    названным допущениям; `inconclusive` (таймаут/сбой/flaky) цель **не**
    опровергает.
- `create goal`: узел `goal` + (если надо) `plan` текущей цели + `item`; свой
  `plan` при заданном списке.
- `complete`: только субъективное `done_when`; корень не завершается этим
  оператором (`closes` + при необходимости `under`).
- Удалить `decompose`/`decide`/`track`. `query` сохраняем как read-only
  адресацию (не оператор; решение — §7).
- Врата `classify`: проверка ограничений, исполнимость, наличие текущей цели;
  допустимость `apply`-проверки; `complete` только для субъективной цели.

**Готово, когда:** три оператора производят узлы/рёбра §2.3; нет производства
`claim`/`decision`/`subgoal`; проверка отклоняет неприменимое с причиной.

### Ш3. Обход (логос)

**Файлы:** новый `src/ir/traversal.ts`, `src/loop/graph.ts`, `src/loop/state.ts`.

**Что меняется:**

- Детерминированный расчёт по §2.6: продвижение, `descend(G → H)`, `return`;
  «применимое в точке» = фронтир, видимый доксе.
- Цикл: `project` (с «применимым») → `propose` → `classify` (отклоняет
  неприменимое) → `execute`; производные `descend`/`return` ставит логос.
- Детекция зацикливания (§2.7): повтор действия — та же команда с теми же
  версиями входов (`tool` + цель + `ref`/`version`) → `record_rejection`; повтор
  **после** правки легитимен.
- Убрать `knowledgeKey`/`deriveMode` как примитив; прогресс — сдвиг курсора,
  новое наблюдение/проверка, закрытие.

**Готово, когда:** обход вычисляется из журнала; неприменимое отклоняется;
повтор с теми же версиями фиксируется отказом.

### Ш4. Честность, альтернативы, закрытие

**Файлы:** `src/ir/graph.ts`, `src/ir/project.ts`, `src/tools/index.ts`,
`src/loop/graph.ts`.

**Что меняется:**

- `under` у `check`/`complete`; `achieved` vs `achieved_under`; `refuted` от
  `fail`; `inconclusive` оставляет `open`.
- `alternatives` + `chosen`; невыбранные — `abandoned` (производно); смена
  подхода — предложение доксы, выбор при отсутствии критерия — Арбитр.
- Закрытие корня — Арбитр (внешне). Стоп-причины: критерий достигнут,
  `no_progress`, бюджет.
- `out_of_fragment` — честный отказ после дизайна «объявленного фрагмента»
  (§10.1); если дизайн не согласован, механизм откладывается (решение — §7).

**Готово, когда:** `achieved` недостижим с `under`; `complete` даёт
`achieved_under`; корень закрывается только Арбитром; опровергнутые/невыбранные
варианты видны как `refuted`/`abandoned`.

### Ш5. Проекция

**Файлы:** `src/ir/project.ts`.

**Что меняется:**

- Новый `Context`:
  - `header`: корень и текущая цель, ограничения, `fragment`, бюджет;
  - `frontier`: текущая ветка (цель, её узел `plan`, пункты и их состояние,
    незакрытые обязательства), последний результат;
  - `artifacts` (индекс файлов + текущая версия), `index` (обзор), `recent`.
- Никаких `mode`/`claims`/`facts`/`decisions`/`verified(claims)`.
- Детерминизм (`project(состояние)` — чистая функция), стабильный префикс
  вперёд; содержимое файлов и сырой вывод в IR не хранятся.

**Готово, когда:** проекция строится из нового состояния; тест на «одни события
→ один `Context`»; старый узел не показывается активным содержимым.

### Ш6. Промпт доксы

**Файлы:** `src/loop/propose.ts`.

**Что меняется:** системный промпт описывает три оператора и работу из
«применимого»; убраны `claim`/`decision`/`decompose`/`track`/`finish`; честность —
`achieved`/`achieved_under`; объяснительный пробел ведёт к новой цели, а не к
отказу.

**Готово, когда:** промпт соответствует `header`/`frontier` новой проекции.

### Ш7. Интеграции

**Файлы:** `bench/run.ts`, `langgraph/graph.ts`, `src/config/settings.ts` (при
необходимости).

**Что меняется:** `AgentInput` несёт первую цель Арбитра с `why`/`done_when`;
закрытие корня по критерию (правило Арбитра) и `stopReason`; приёмка —
существующий `check.sh`/харнесс без изменений семантики.

### Ш8. Тесты и документация

**Файлы:** `tests/invariants.ts`, `tests/ir.test.ts`, `tests/loop.test.ts`,
`tests/gate.test.ts`, `tests/observe.test.ts`; `docs/ir_ru.md`,
`docs/plans/implementation_plan_ru.md`, `docs/plans/logos_roadmap_plan_ru.md`

**Что меняется:**

  невозможен, `under` честен, `project` детерминирован, монотонность журнала,
  лес структурных рёбер, неприменимое отклоняется);

## 5. Инварианты, которые держим

- `achieved` — только `check` с `pass` и **без** `under`; докса не выносит
  вердикт.
- `achieved_under` — непустой `under` у закрывающего `check` либо `complete`;
  отменяемо.
- `stale`/неактуальное не показывается активным; версия и актуальность
  вычисляются.
- Журнал монотонен; смена состояния — новый узел-событие, не правка.
- `project` детерминирован; докса только предлагает; `W` и вердикт — за
  Арбитром/логосом.
- Лес структурных рёбер (`has_plan`/`item`/`has_alternatives`/`chosen`) без
  циклов; контейнер всегда несёт ≥1 пункт.
- Секреты только в `.env`; содержимое файлов в IR не хранится.

## 7. Риски и открытые решения

1. **Закрытие корня в автономном прогоне.** Сейчас — харнесс; в семантике —
   Арбитр. Решение: `AgentInput` несёт критерий (`done_when` корня), правило
   Арбитра закрывает корень; для bench — существующий `check.sh`.
2. **Формат `done_when`.** Предлагается
   `{kind:"objective", command} | {kind:"subjective", text}`. Подтвердить при Ш1.
3. **Вложенность плана.** Разрешать ли план у пункта-подцели на произвольную
   глубину (рекурсивная схема) или ограничить одним уровнем. Влияет на zod-схему
   `create goal`.
4. **`query`.** Оставляем как read-only адресацию (не оператор доксы), иначе
   теряется гарантия доставаемости §8 семантики.
5. **`out_of_fragment`.** Требует отдельного дизайна «фрагмента» (§10.1). Если не
   согласован — отложить, оставив только `no_progress` и бюджет.
6. **Синхронность ru/en.** Ведём оба зеркала в одном коммите.
7. **Судьба `symbol`/`test`.** Оставить зарезервированными (не производить).
