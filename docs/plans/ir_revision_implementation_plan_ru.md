## 1. Назначение

Внедрить `docs/ir_revision` в код: **форму** (узлы и связи), **операции** и размещение
команд, **контекст** как ленту сообщений; привести в соответствие тесты и остальную
документацию. Вне области (не меняется): разделение доксы и логоса, «цель закрывается
только через `stop`», журнал только дополняется, детерминизм.

## 2. Зафиксированные решения

| # | решение |
|---|---|
| D1 | Связи переименовываются под имена спека: `goal`, `unactionable`, `plan`, `stop`, `items`, `alts`, `result`, `mutates`. Прежние `item` (plan→action) и `has_alternatives` убраны. |
| D2 | Неисполнение команды (повтор, устаревший базис, запрещённый путь, пустая команда) — это `action` + `observation` с причиной. `record_rejection` остаётся **только** у структурных ходов (`create_goal` / `stop` / `decline`). |
| D3 | `Context` — только лента сообщений (`system` / `user` / `assistant` / `tool`), собирается из дерева каждый ход. Блоки `path` / `lastResult` / `shown` / `calls` / `applicable` / `budget` убраны. |
| D4 | `create_goal` сразу исполняет свою первую `command` (логос), поэтому цель рождается с уже исполненным первым пунктом. Ход — три сообщения: `assistant` (цель), `assistant` (вызов команды), `tool` (наблюдение). |
| D5 | Докса предлагает; логос исполняет и записывает. Движок не просит модель выполнять план. |

## 3. Дефолты для открытых вопросов (§8 спека)

- **§8.1 базовый / узловой промпт.** База = роль, контракт (один ход; решает логос), форма
  ответа, дисциплина потока, индекс инструментов — стабильно, это префикс кэша. Узел =
  допустимые ходы, правила текущей ситуации (свежий запрос / открытая цель / возврат), что
  показывает рука. Правило большого пальца: верно на любом ходу → база; вызвано состоянием
  → узел.
- **§8.2 «первый невыполненный пункт».** Пусть `I = firstUnfulfilledItem(goal)` — первый
  пункт плана, чья **текущая (последняя) альтернатива** не выполнена. Альтернатива выполнена,
  если это исполненное `action` или `stop`нутая `goal`. Нет такого → план исчерпан.
- **§8.3 пометка альтернатив.** Оставляем однострочный маркер в ленте; вернуться, если
  окажется слишком грубо.

## 4. Размещение команды (§4 спека)

Исход текущего пункта читается из его **текущей (последней) альтернативы**: команда, чьё
наблюдение несёт результат, — **успех**; несёт причину — **неуспех**; таймаут (нет
`exitCode`) — **нет вердикта**; `stop`нутая цель — **успех**.

Размещение приходящей команды (команду выбирает докса; размещает логос):

- текущий пункт `I = firstUnfulfilledItem(goal)`:
  - `I` не определён (план исчерпан) → команда становится **новым пунктом плана**;
  - `I` есть → команда становится **новой альтернативой `I`**.
- **подцель** (`create_goal` на открытой цели) всегда становится новой альтернативой `I`, и
  фокус спускается в неё; без `I` — отказ (§3.2).

Старт: `create_goal` засевает `I0 = [A]` и исполняет `A`; исход `A` решает, куда пойдёт
первый `apply` после него (успех → новый пункт; неуспех → ещё одна альтернатива `I0`). Каждая
попытка оставляет новые узлы; существующий узел не переиспользуется и не правится.

## 5. Фазы

Каждая фаза заканчивается зелёными `npm run typecheck` и `SKEIN_LIVE=false npx vitest run`
до начала следующей.

### P1 — форма (`src/ir`, `tests/invariants.ts`)

- `types.ts`: `WORK_KINDS` теряет `alternatives`, получает `item`; `EDGE_KINDS` становится
  `goal`, `unactionable`, `plan`, `stop`, `items`, `alts`, `result`, `mutates`.
- `events.ts`: подхватывает новые виды из `types.ts` (структурных правок нет).
- `graph.ts`: `children` пополняется по `items` (plan→item) и `alts` (item→action/goal);
  хелперы `planOf` / `goalOf` / `unactionableOf` / `stopOf` / `itemOf`; убрать
  `alternativesOf` и `hasStopped`.
- `traversal.ts`: `itemFulfilled` через текущую альтернативу; `cursorOf` /
  `firstUnfulfilledItem` по пунктам; `focusEvents` спускается в цель-альтернативу;
  `isFinished` читает связь `stop`.
- `tests/invariants.ts`: множество DAG-рёбер и привязка целей под новые связи.
- Отдельные shape-тесты в `tests/ir.test.ts`; `tests/ops/*` переходят на новую форму.

### P2 — операции и размещение (`src/tools`, `src/loop`)

- `tools/index.ts`:
  - `create_goal` (запрос): ребро `goal` + `G/Q/I/A` (`plan`, `items`, `alts`); сразу
    исполняет `A` (D4); спуск.
  - `create_goal` (цель): ребро `alts` `I → G`; исполняет первую команду подцели; спуск.
  - `apply`: исполняет команду; размещает её `action` по правилу §4 (новый пункт при
    успехе / новая альтернатива иначе); повтор / stale / запрещённый путь / пустая команда
    — это `action` + `observation` с причиной (D2). Переиспользования `ensureAction` нет.
  - `stop`: только связь `stop` `goal → stop`; узел `stop` больше не пункт плана.
  - `decline`: без изменений (узел `unactionable`, связь `unactionable`).
- `loop/classify.ts`: убрать command-level отказы; оставить структурные
  (`interpreted`, `not_addressed`, `not_request`, пустые поля).
- `loop/graph.ts`: `progress` / `branchSubtree` / результаты уровня по `items` / `alts`;
  завершение читает связь `stop`.
- `tests/ops/*` переписаны под новое размещение и отказы-наблюдения.

### P3 — контекст-лента и системная часть (`src/ir/project.ts`, `src/loop`, `src/llm`)

- `project` возвращает ленту сообщений (§5): роли `system` / `user` / `assistant` / `tool`;
  собирается из дерева; немонотонный срез при закрытии цели (её внутренние сообщения уходят,
  сообщение `stop` остаётся на руке родителя).
- Ход → сообщения: `create_goal` → цель + вызов + наблюдение; `apply` → вызов + наблюдение;
  `stop` / `decline` → причина. Пометка альтернатив по §8.3; `thought` не хранится.
- База / узловая системная часть (§6 и §8.1): база стабильна; инструкция узла рендерится
  вместе с ним, один раз.
- `recall`/`search` рендерятся транзиентными сообщениями `assistant` + `tool` (не узлы); адресация по
  `id` и рабочее множество сохраняются, без прежних блоков.
- `loop/graph.ts` `projectNode` упрощается; `loop/propose.ts` / `loop/prompt/blocks.ts`
  следуют сплиту база/узел.
- Тесты: `tests/prompt.test.ts`, `tests/ir.test.ts`, `tests/loop.test.ts`,
  `tests/workingset.test.ts`.
