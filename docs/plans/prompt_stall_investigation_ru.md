# Skein — расследование застоя в состояниях: промпты состояния и наблюдения

> Русский документ; английское зеркало — отдельной задачей (пока не создано).
> Статус: **в работе.** Живой документ расследования. Наблюдения фиксируются здесь, эксперименты
> идут по нему, решения — «правка здесь → правка блока/проекции → тест».
> Основной материал: прогон `bench/runs/sandbox-tasks/2026-10-13T19-02-00-767Z-fix-ocaml-gc`
> (Skein, `fix-ocaml-gc`, net on, reward 1, `request_addressed`, 46 ходов / 66 вызовов, 6.97₽).

## 0. Метод проверки (согласован)

Ключевая идея: **не перезапускать всю задачу**, а взять записанный контекст последнего прогона
на выбранном ходу, изменить его и сделать **один ход** изменённым контекстом. Так контролируемо
проверяется влияние ровно одной правки промпта.

Ресурсы:

- `contexts.ndjson` прогона: на каждый ход — `{ turn, chars, situation, constraints, history,
  messages }`, где `messages` — **готовый** массив сообщений, поданный модели (записывается в
  `tests/sandbox/live.ts:72-81`, включая нативные `tool_calls`/`tool_call_id`); плюс
  `contexts/tNNN.txt` — тот же контекст текстом.
- `bench/turn.ts` — **инструмент одного хода** (сделан): читает трейс прогона, выбирает ход,
  применяет патч контекста, восстанавливает нативные сообщения и набор инструментов из
  `situation`, делает **один** ход моделью. `--dry`/`--dump` работают офлайн (без вызова модели) —
  ими настраивается патч.
- `reasoning.ndjson` — сырые тексты размышлений по ходам.

Использование `bench/turn.ts`:

```
npx tsx bench/turn.ts <run-dir|trace> --list                 # ходы и ситуации (офлайн)
npx tsx bench/turn.ts <run-dir> --turn 16 --dry              # проверка патча/транскрипта (офлайн)
npx tsx bench/turn.ts <run-dir> --turn 16 --patch p.json --repeat 3
```

патч — JSON-массив операций: `append` (в конец), `insert {at}`, `remove {match}`,
`replace {match,text}`; сахар — `--append-system "…"`.

**Про `applicable`.** Набор инструментов хода в трейсе не сохраняется, но однозначно
восстанавливается из `situation` (`request`→`move`/`decline`; `plan`/`working`→`apply`+`stop`;
`transition`→`move`; `terminal`→`stop`) — реализовано в `frontierFor`/`toolsFor`. Писать
`applicable` в трейс всё равно полезно (устойчивость), но не блокирует эксперименты.

**Гейт.** Реплей зовёт живую модель (`SKEIN_LIVE`/API) — только по явному разрешению владельца,
как `tests/sandbox/**` и live-прогоны (`AGENTS.md`).

**Критические ходы для проверки (эталон):** `t011` (recon, спурт 7.5k ток. reasoning),
`t016`/`t020`/`t026`/`t027` (localization, пере-вывод), `t030` (первый `edit`).

## 1. Как устроен промпт (карта)

Сборка — `src/loop/propose.ts:48-67`:

## 2. Наблюдения (факты)

### O1. `relief` (Constraints состояния) не рендерится нигде

`relief` — это операционные ограничения состояния (`src/ir/islands.ts:30-31`). Для локализации:

> «if the target lines are already on the tape, name the exact replacement and edit now —
> **do not re-read or re-derive**; read only what you still need; **move to Patch in the same
> move**» (`islands.ts:64-65`)

для разведки: «**at most two rounds of inspection, then move**» (`islands.ts:43-44`);
для референса: «**at most one fetch**; an unavailable reference is a fact, not a reason to
retry» (`islands.ts:77`).

Это ровно те ограничения, что гасят наблюдаемый застой. Но:

- `stateDescription` (`islands.ts:135-137`) рендерит только `what` + `criterion`;
- `observationInstruction` (`project.ts:332-337`) его не несёт;
- `grep` по `src`: `relief` встречается только в `islands.ts` (определения) — читателей нет.

История: `5f17a80`/`8a338af` рендерили `Constraints: ${island.relief}` **каждый ход** — и в
`blocks.ts` (`ISLAND_INSTRUCTIONS`), и в `project.ts` (`observationInstruction`).
Коммит `8c252b1` («state description once») выбросил per-turn инъекцию и **не перенёс relief** в
новое `stateDescription`; поле стало мёртвым. Тест `tests/islands.test.ts:32` проверяет лишь,
что оно непустое.

Документация же требует рендерить его: `docs/prompt_state_machine_concept_ru.md:298-301`
(«инструкция состояния рендерит `What / Done when / Constraints`»),
`docs/plans/archive/state_protocol_plan.md:74-75`. То есть спецификация и код разошлись.

Подтверждение по прогону: `grep "at most two rounds|do not re-read or re-derive|at most one
fetch"` по `contexts/` = **0**.

### O2. Инструкция наблюдения обеднена против прежней

Сейчас (`project.ts:333-336`):

> «Tool result above. **Stay in this state** — work only its goal. / Decide exactly one, and
> answer this first: does the state's `Done when` already hold? Yes → `stop`. No → the next
> action for this state if the step worked, or a DIFFERENT action if it failed or was the wrong
> step (never repeat it).»

В `8a338af` та же инструкция несла `State`/`Goal`/`Done when`/**`Constraints`** рядом с
результатом. Следствия сегодня:

- **нет ветки «уверен почти, но не подтверждено»** → любое «No» уходит в «next action» = ещё
  чтение;
- **«Stay in this state» конфликтует с переходом в Reference**: тот достижим только
  `stop`+`move`, но `move` при открытом состоянии запрещён (`blocks.ts:54`,
  `traversal.ts:153-158`); недостающую истину модель добывает `webfetch` внутри локализации;
- **нет переякорения** критерия: он лежит одним system-ходом при входе (`project.ts:239`),
  а инструкция ссылается на «the state's `Done when`» без текста.

Идёт **двумя** system-сообщениями подряд с `B8` (см. хвост `contexts/t016.txt`) — дубль в
наиболее свежих позициях.

### O3. `B8` лицензирует цикл «успешный шаг → следующий шаг»

`blocks.ts:97`: «A step that succeeded but needs more: the next call is the next step.» Без
верхней границы это буквально разрешение на цепочку «успешное чтение → следующее чтение».

### O4. `B13` толкает к перечитке

`blocks.ts:63-64`: «The tape is the ONLY thing you have seen … **read it from disk** … a copy
you have not read this state is still unread. If you already know the file, read it first.».
Смешаны две вещи: (а) не выдумывать содержимое (ценно) и (б) «нераспечатанную в этом
состоянии копию не считай прочитанной» (граница состояний, фича). Формулировка читается как
«своим же наблюдениям на текущей ленте не верь — перечитай».

### O5. Прямое противоречие по git

`B19` (`blocks.ts:67-69`): «do not assume a VCS, `git`, a diff or history… Not `git diff`/`git
log`». А описание `bash` (`tools.ts:124`) заканчивается: «For version control, inspect with
`git status`/`git diff`/`git log`; do not commit or push unless the request asks.» Плюс запрос
открывается «I have been making some changes» — сильный git-триггер (`docs/tools_ru.md` §6).
В прогоне: t9 (`git status`/`git log`) и t24 (`git status`/`git diff`) — оба
`fatal: not a git repository`. Шторма нет, но противоречие осталось: база запрещает то, что
описание инструмента предлагает. Анти-VCS чистка (B19+B7) описание `bash` не тронула.

### O6. Reference недостижим из открытого состояния

Переход `Localization → Reference` есть (`islands.ts:66-69`), но `webfetch` входит в
`APPLY_TOOL_NAMES` (`tools.ts:184-193`) и доступен как `apply` внутри локализации
(`toolNamesFor`, `tools.ts:198-212`; `applicable` — `traversal.ts:157-158`). Поэтому модель
делает `fetch` **на месте**: в прогоне t19 (`fetch trunk`), t25 (`fetch 4.14` → 404), t23
(`read` референса). Reference-состояние и его ограничение «at most one fetch» обходятся.

### O7. Описание состояния показано один раз и в начале

`renderState` пушит описание после результата `move`, **до** пунктов плана (`project.ts:236-239`).
Для 15-ходовой локализации к t27 оно далеко от вершины; критерий per-turn не переякоривается.

### O8. `nudge` не срабатывает

Мягкий аттрактор (`project.ts:398-401`) сформулирован верно, но в прогоне не появлялся ни разу
(`grep "no progress for"` по `contexts/` = 0): детектор застоя считает любое новое наблюдение
прогрессом (`docs/plans/archive/state_protocol_plan.md:52-53`), поэтому пере-вывод держит `stall = 0`.

## 3. Гипотезы и эксперименты

Правило: одно изменение на эксперимент, обе ветви при возможности, метрики — reasoning до
первого `edit`, ход первого `edit`/`stop`, наличие/цена пере-вывода.

- **E1 (п.1, recency).** Рендерить `stateDescription` **после** плана (в конце ленты), состав не
  менять. Проверить на t011/t016/t020/t026: меняется ли ход/`thought`/токены.
- **E2 (п.1+O1, recency + relief).** То же + `Constraints: <relief>` в описание. Отдельно от E1,
  чтобы не смешивать recency и relief.
- **E3 (п.2, инструкция наблюдения).** Вернуть переякорение (State/Goal/Done when/Constraints)
  в `observationInstruction` — как в `8a338af`; либо, если E1/E2 уже это дают, ограничиться
  добавлением ветки «name it → edit; нужна внешняя истина → `stop` и move в Reference» и снятием
  дубля с `B8`.
- **E4 (п.3, B13).** Развести «не выдумывать содержимое» и «повторно читать на границе
  состояний»; добавить, что лента текущего состояния авторитетна.
- **E5 (п.4, git).** Убрать git-строку из описания `bash`; переформулировать B19 в редирект
  (читай код / воспроизведи падение), сохранив «упавший git не повторяй». Замер: число/ходы
  git-зондов, есть ли шторм.
- **E6 (O8, nudge).** Привязать застой не к «новому наблюдению», а к «нет нового узла/перехода»
  — порог, при котором nudge реально срабатывает.

## 4. Предлагаемые изменения промпта — РЕАЛИЗОВАНО (Фаза 18)

Внесено в код (см. `docs/system_prompt_ru.md` §4 Фаза 18, журнал §6). Что реально сделано:

2. **П.2 →** `observationInstruction` переписан в императив («Decide NOW, this turn»). Ветку
   «нужна внешняя истина → move в Reference» **убрали** как непроверенную (в первом черновике
   была) — не подгоняем под шум. Дубль с `B8` сохранён осознанно (обе инструкции активны).
3. **П.3 →** `B13` разведён: «не выдумывать содержимое» (память) vs «лента текущего состояния
   авторитетна — не перечитывать».
4. **П.4 →** `B19` переписан из запрета в редирект; `git`-строка убрана из описания `bash`.

## 5. Открытые вопросы

- **Net-off-петля (главное).** `edit` в локализации → Patch с уже сделанной правкой → петля до
  `max_turns` (§6, §7/Z3). Ни pre-fix, ни post-fix это не лечат. Общее решение — структурное:
  сохранять вывод модели на ленте (O10) и/или не открывать Patch, когда изменение уже в
  воркспейсе.
- **Reference-trap (O6).** `webfetch` доступен внутри локализации → Reference-состояние
  обходится, до 10 сетевых попыток (§7/Z1). Нужно либо вывести `webfetch` из `apply`-поверхности
  локализации, либо дать Reference реальный переход.
- **Шум метода.** Одноходовой реплей (`--rebuild`) не различает формулировки при n=3–6 (§6);
  для выводов нужны десятки проб или полный прогон.
- Записывать ли `applicable`/`allowedTools` в `contexts.ndjson` дополнительно к восстановлению
  из `situation` (сейчас достаточно восстановления в `bench/turn.ts`; запись — запас прочности).

**Итог: влияния не обнаружено.** Ни в одной из 18 проб с патчем не появилось `edit`/`stop` —
поведение качественно не изменилось (продолжение чтения/grep/bash/fetch). Разброс доминирует над
эффектом (baseline t26: 1112 против 6423). E1 на t26 меняет инструмент (`bash`→`grep`), но не
природу хода; E2 на t16 один раз дал дешёвый `recall` (37) на фоне 4123/435 — это и есть шум.

**Выводы о методе.**
1. Один ход меряет лишь *немедленный следующий шаг*, а гипотеза — про *замыкание цикла за
   несколько ходов*. На `t16` модель ещё не имеет достаточного материала, чтобы «назвать и
   править» (relief говорит «if the target lines are already on the tape»), поэтому E1/E2 там
   физически не могут сработать; на `t26` материала больше, но и там сдвига не видно.
2. Нужна траекторная проверка: патч префикса + продолжение на K ходов (исполняя инструменты),
   а не одиночный ход (`bench/turn.ts` умеет только один ход, §0) — это уровень `runTask`.
3. Либо плечо сильнее: E3 (дать «name it → edit» в инструкции наблюдения), т.к. слабое
   упоминание критерия/relief в конце ленты ход не переключает.

**Технический побочный факт.** `bench/turn.ts` кладёт добавленное сообщение **после** B8, т.е.
сдвигает инструкцию ситуации с последней позиции — при желании проверять «recency без смещения
порядка» нужен `insert` перед `context.result` (оператор `insert {at}` уже есть).

### 2026-10-14 — скан `t20–t24`, пять ходов подряд (E2 + reasoning)

`--turns 20-24` с E2 (описание+`relief` в хвосте) и, для сравнения, без патча. Каждый ход —
записанный префикс, один ход моделью, захват скрытого reasoning (`--reasoning`).

Ни baseline, ни E2 ни на одном из пяти ходов не дали `edit`/`stop` — оба продолжают
`bash diff` / `grep` / `read` референса `.skein/ref/949883b2-shared_heap.c`:

```
baseline t20 bash(diff current↔ref) · t21 bash(diff) · t22 grep+read(ref) · t23 read(ref,568) · t24 grep(arrays)
E2       t20 grep                       · t21 grep      · t22 read(ref,440) · t23 read(ref,568) · t24 bash(diff)+grep
```

Reasoning (E2) показывает, что `relief` **прочитан и проигнорирован**:

- t20: «Let me identify the bug… **Let me check the upstream reference to compare. Let me recall
  the reference file** and look for the sweep function…» — при том, что в хвосте лежит
  «…name the exact replacement and edit now — **do not re-read or re-derive**».
- t24: «I now have both the reference (upstream) version and the modified version. **Let me diff
  them carefully** to find the introduced defects.»

**Итог: пассивное ограничение не работает.** Даже пяти ходов подряд с описанием+`relief` в хвосте
недостаточно, чтобы переключить модель на правку. Причины (гипотезы):
1. условие relief «if the target lines are already on the tape» модель считает
   невыполненным/непроверяемым — она не уверена, что «уже видела нужные строки», и уходит
   сверяться с upstream;
2. собственный вывод модели **не на ленте** (hidden reasoning), поэтому на каждом ходу она
   пере-выводит с нуля (структурный пробел, §2/O10) — рекордный префикс её не «убеждает»;
3. пассивный *system*-текст слабее momentum из записанной истории (там уже fetches/diff'ы).

**Следствие для дизайна:** нужен **активный** ход — E3 (инструкция наблюдения, обязывающая
назвать правку или закрыть состояние), а не пассивный `relief`; либо сохранение вывода модели на
ленте. Baseline при этом расходится с записью (t20: `bash diff` против записанного `grep`) —
реплей при `temp=0.1` стохастичен, сравнивать надо распределения, не единичные ходы.

### 2026-10-14 — скан с АКТИВНОЙ инструкцией (`t18–t22`, `t20–t24`)

Гипотеза: пассивный `relief` не работает, активное указание сработает. Проверка тем же способом
(`--append-system` через патч, тот же скан), текст в хвосте:

> «DECIDE NOW, this turn… Stop comparing; comparing is not progress. From what is ALREADY on the
> tape, name the file, the line and the exact replacement, and make the edit with `edit` in THIS
> turn. Do not fetch again, do not diff, do not re-read a window you have already read… Ending this
> state by reading further is not allowed; end it by editing.»

Результат (`t20–t24`): `t20 grep · t21 grep+bash · t22 grep · **t23 edit** · **t24 edit**`.
В `t18–t22`: `t18 bash · t19 fetch · t20 search+grep · **t21 edit** · t22 grep`.

- Впервые появляется `edit` (в пассивных плечах и baseline за тот же диапазон — **ни одного**).
- Правка **верная**: `t24` — `find: … p += Whsize_hd(hd);` → `replace: … p += wh;` (ровно записанный
  фикс прогона `19-02`).
- Оговорки: указание **не мгновенное** — модель всё ещё делает 1–4 чтения до правки; часть правок
  упирается в кап reasoning (8192); выборка мала (по 5 ходов на окно).

**Вывод.** Различие «пассивное / активное» подтверждается на этом методе: пассивное описание+`relief`
ход не переключает, а прямое указание «решай сейчас, правь в этот ход» — переключает (с задержкой).
Про имя: `relief` (рельеф/ограничение) описывает именно **пассивную** форму, тогда как работает
**активная**; похоже, поле стоит переосмыслить как указание-действие (например, `directive`/
`imperative`), а не «ограничение».

### 2026-10-14 — устойчивость: `t23–t24` ×3 (активное vs baseline)

| плечо | t23 (3 пробы) | t24 (3 пробы) | `edit` |
|---|---|---|---|
| **активное** | edit · edit · read | grep+bash · bash+grep+read · **edit** | **3/6** |
| baseline | read+grep · read · read | bash · bash · fetch | **0/6** |

Активное указание дало `edit` (3 из 6), baseline — ни одного. **Но см. ниже: повторный контроль
не воспроизвёл это (1/6) — вывод о «качественном различии» снимается как шумовой.** Цена: правки
идут на большом reasoning (5288–8192, часть упирается в кап) — указание ускоряет переход к правке,
но не удешевляет сам вывод.

### 2026-10-14 — правки директив внесены (Фаза 18) + проверка через `--rebuild`

Внесено (см. `docs/system_prompt_ru.md` §4 Фаза 18): `Island.relief` → `Island.directive` и рендер
`Now: …` в описании состояния; B6/B7/B8/B9/B10 и `observationInstruction` в императиве; B13
разведён (память vs текущая лента); B19 в редирект + `git`-строка убрана из описания `bash`.
Офлайн-набор зелёный (310).

`bench/turn.ts --rebuild` пересобирает хвост промпта **текущим кодом** над записанным `history`.
Валидность: на `t16` пересобранные сообщения **совпадают с записанными** (0 расхождений из 15).

Скан новым промптом (`--rebuild`, `t20–t24`): правок нет. Серия сравнений на `t23–t24` ×3
(всего 6 проб на плечо):

| плечо | `edit` |
|---|---|
| `--rebuild` (директива в описании состояния) | 0/6 |
| `--rebuild` + инструкция наблюдения последней | 0/6 (1 `stop`) |
| `--rebuild` + директива локализации последней | 1/6 |
| `--rebuild` + форсированный текст последним | 0/6 |
| **контроль: старый промпт + тот же форсированный текст (повтор)** | **1/6** |

**Опровержение раннего вывода.** Тот же форсированный эксперимент, что давал `3/6`, при повторе
дал `1/6`. Значит, **метод «один ход × 3» доминируется шумом** (temp 0.1, но reasoning
длиннохвостый), и по нему нельзя выбирать формулировки/позицию. Раннее «3/6 против 0/6» —
артефакт выборки, а не эффект.

**Как есть сейчас.** Правки директив внесены как принципиальные (активная форма — то, что просил
владелец; вреда не показано) **без подгонки под шум**. Проверка эффекта — только на полном
прогоне (`fix-ocaml-gc` net on/off, Фаза L3), не на одноходовом реплее. Для честного сравнения
плеч на реплее нужны десятки проб на плечо (даже тогда — слабый сигнал).

**Про `bench/turn.ts`.** `--rebuild` — рабочий инструмент для «как выглядит текущий промпт на
записанной ленте» (дешёвая проверка формы, L1/L2), но не для A/B формулировок: слишком шумно.

### 2026-10-14 — полный прогон `fix-ocaml-gc` (Фаза 18), два варианта

После правок Фазы 18 прогнаны net on/off полностью (`tests/sandbox/sandbox-run.ts`). Прогонялись
два варианта формулировки локализации/наблюдения:

- **pre-fix** — директива локализации «make the edit this turn» + наблюдение «make it this turn»
  (форсирует правку внутри локализации);
- **post-fix** — «name it; then `stop` and move on» (выравнивание под протокол: локализация
  называет, патч правит).

| вариант | net | ходы | reason | costo | stop | каталог |
|---|---|---|---|---|---|---|
| **pre-fix** | on | **29** | **13 021** | **2.645₽** | request_addressed | `2026-10-14T05-37-29-796Z-fix-ocaml-gc` |
| pre-fix | off | 60 | 168 345 | 17.921₽ | **max_turns** | `2026-10-14T06-26-36-654Z-fix-ocaml-gc` |
| post-fix | on | 51 | 52 542 | 6.746₽ | request_addressed | `2026-10-14T06-47-00-005Z-fix-ocaml-gc` |
| post-fix | off | 57 | 97 696 | 20.408₽ | request_addressed | `2026-10-14T06-59-11-252Z-fix-ocaml-gc` |

Для сравнения (история): лучший net on #5 — 33 хода / 20 105 / 2.93₽; лучший net off #6 —
45 ходов / 77 717 / 6.04₽.

**Что видно.**
- **pre-fix net on — лучший net on за всю историю** (29 ходов, 2.645₽), вдвое дешевле #5. Механизм:
  указание «правь в этот ход» форсирует решение в локализации, гасит пере-вывод (правка на t17,
  стоп t18).
- **pre-fix net off — регресс** (`max_turns`, 17.9₽). Механизм найден: модель правит прямо в
  локализации (t28), затем переходит в **Patch**, где правка уже сделана; в reasoning она видит
  «line 650 shows `p += wh` — maybe already fixed?» и до t59 перечитывает/перевыводит, не закрывая
  состояние. Плюс reference-trap (fetch 403, Reference-состояние обходится — O6).
- **post-fix net on — хуже и pre-fix, и истории** (51 ход, 6.75₽): без «edit now» модель возвращается
  к медленному пути. То есть «edit now» — и есть рычаг, ломающий застой.
- **post-fix net off** само-закрылся (`request_addressed`), но дороже pre-fix (20.4₽).

**Решение (оставлено в коде): pre-fix** — как лучший net on (главная цель плана — застой в
локализации). Net-off-петля — **отдельная проблема**, и её не лечит ни один из двух вариантов:
  1. reference-trap: `webfetch` доступен внутри локализации, Reference-состояние обходится (O6);
  2. Patch открывается с уже сделанной правкой (правка в локализации нарушает протокол
     «локализация называет — патч правит»).
   Общее лечение — не костыль в промпте, а **структурный рычаг**: сохранять вывод модели на ленте
   (O10), либо не давать открывать Patch, когда изменение уже в воркспейсе. Оставляем владельцу.

**Оговорка.** По одной пробе на ветвь — это направление, не статистика (см. шум выше). Все четыре
прогона дали reward 1; верификатор задачи прошёл во всех.

## 7. Разбор логов: причины застоев (по фактам)

Восстановлено из `result.json` (границы состояний и действия), `metrics.json` (per-turn
reasoning), `reasoning.ndjson` (текст размышлений). Номера ходов — факты; «причины» ниже — метки
механизмов.

### 7.1 Метрика

| прогон | net | turns | первый `edit` | reasoning ДО edit | reasoning всего | fetch/curl | costo |
|---|---|---|---|---|---|---|---|
| pre-fix net on | on | 29 | **t17** | **3 711** | 13 021 | **0** | 2.64₽ |
| pre-fix net off | off | 60 | t28 | 75 097 | 168 345 | **10** | 17.92₽ |
| post-fix net on | on | 51 | t41 | 52 290 | 52 542 | 2 | 6.75₽ |
| post-fix net off | off | 57 | t43 | 86 537 | 97 696 | **7** | 20.41₽ |

**Главный факт:** застой — это фаза **до первой правки** (локализация). В чистом прогоне на неё
ушло 3 711 ток.; в застойных — 52–86 тыс. (94–99% всего reasoning). Число сетевых попыток к
upstream прямо коррелирует с длиной (0 → 29 ходов; 7–10 → 57–60).

### 7.2 Карта состояний

- pre-fix net on: recon → localization → verification → handoff (**нет** reproduction/patch;
  `edit` на t17 внутри локализации).
- pre-fix net off: recon → localization → **patch** (t32) — и всё, до `max_turns`;
  verification/handoff **нет**.
- post-fix net on: recon → **reproduction** (t7, `./configure` t13, `make -j4` t14) →
  localization → patch → verification → handoff.
- post-fix net off: recon → localization → patch → verification → handoff.

Ни в одном прогоне **не было состояния `reference`** — все `fetch` идут как `apply` внутри
локализации.

### 7.3 Застои и причины

**Z1. Reference-trap.** Модель тянет upstream-`shared_heap.c`, чтобы подтвердить правку, и
перебирает зеркала; ограничение Reference-состояния («at most one fetch») не применяется, т.к.
Reference обходится.
- pre-fix net off: t15 `raw.githubusercontent`, t18 `gitlab`, t19 `jsdelivr`, t26 `curl raw`, t30
  python `urllib` по списку URL; net off → `fetch failed: curl exit 22 … 403`.
- post-fix net off: t17, t19, t21, t22, t38, t40.
- post-fix net on: t25 (`ocaml/5.4`), t29 (`trunk`), затем `diff` t33/t35 (reasoning 25 836).

**Z2. Пере-вывод без сохранения (структурный пробел O10).** Вывод модели не на ленте → каждый ход
заново выводит то же. Факт: один и тот же разбор RLE повторяется на t14, t16, t18, t19, t21, t22,
t24, t26, t28 (pre-fix net off), с пиками reasoning ~8 000 ток. (t14 8 086, t16 8 192, t17 8 015,
t24 8 192). То же в post-fix net off (t24/t26 = 8 192) и post-fix net on (t35 = 25 836).

**Z3. Только pre-fix: правка в локализации → Patch с пустой работой → петля.** Причина `max_turns`.
- Факт: `edit` сделан на **t28 внутри локализации** (move localization seq=51 < seq edit);
  далее `move patch` (t32), и t33–t59 — **15 `read`, 6 `grep`, 3 сетевые попытки, 0 `edit`**,
  состояние не закрылось.
- Reasoning: t33 «the state says the change is already made? … Let me read pool_sweep»; t45
  «closure said p += wh … current file at line 650 shows `p += wh;` … that's confusing»; t50 «line
  650 shows `p += wh;` So maybe the fix is already there?»; t58 «I've read the whole shared_heap.c …
  Let me check git? No git». Правка уже в файле, а Patch по протоколу должен её делать — модель не
  может свести это и перечитывает весь файл.

**Z4. post-fix net on: лишняя фаза Reproduction + долгая локализация.** Не залипание, а лишняя
работа: `move reproduction` → `./configure` (t13) + `make -j4` (t14), затем локализация t16–t38
(2 фетча + `diff` t33/t35), первая правка — только t41.

**Z5. Движок: нет детекции цикла/преждевременного стопа.** Факт: pre-fix net off закрылся
`max_turns`; петля Patch (Z3) не распознана (инвариант «cycle/premature-stop — deferred»).

### 7.4 Чего в логах НЕТ (не подтверждается)

- Нет git-шторма: git-вызовы единичны (1–2 за прогон), после `fatal: not a git repository` не
  повторяются.
- Нет отказов инструментов: `ok/refused` = без отказов во всех четырёх.
- Нет большого reasoning в верификации: во всех само-закрывшихся прогонах фаза verification
  дешёвая (единицы–десятки ток.).
- Верификатор прошёл везде (reward 1); `max_turns` в pre-fix net off — сбой закрытия протокола,
  не ошибка правки.
