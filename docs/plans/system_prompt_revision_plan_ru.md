# Skein — план ревизии системного промпта

> Английское зеркало — `docs/plans/system_prompt_revision_plan.md`.

Связанные документы: `docs/plans/implementation_plan_ru.md` (роадмап и статус),
`docs/ir_semantics_ru.md` (семантика IR: промпт — политика доксы над ней),
`docs/tools_ru.md` (контракт инструментов), `src/loop/propose.ts` (текущий промпт),
`docs/bench_report_ru.md` §4.4 (сравнение с opencode).

Код пишется только после согласования фазы; план уточняется по шагам (как в
`docs/plans/tier1_plan_ru.md`).

**Статус.** Все фазы (1–5) выполнены (2026-10-07). Фазы 1–4: блоки, документ, L1/L2,
`fetch`/`apply_patch`, guard; L2 вживую 18/18. Фаза 5: контролируемый A/B
(`ref-localize-{on,off}`, n=3, оба агента) — стратегия референса принята, reward не
меняется, вход −23% (Skein) / −38% (opencode); opencode суммарно дешевле (57k против 99k
prompt-токенов), выигрыша по архитектуре на лёгкой задаче нет; отчёт —
`docs/bench_report_ru.md` §4.5.

## 1. Суть и зафиксированные решения

Системный промпт (`src/loop/propose.ts`) сейчас — один литерал без структуры, с
дублированием и накопившимся дрейфом (описывает оператор `apply`, которого нет в
нативном tool-calling; правила продублированы в блоке вывода и в «Rules»). Ревизия:

1. **Промпт = политика доксы** над семантикой IR. Источник истины — отдельный
   документ `docs/system_prompt_ru.md` (+EN); код следует за ним, как код IR следует
   за `docs/ir_semantics_ru.md`.
2. **Блочная сборка.** Промпт собирается из именованных блоков `{id, text}`; один
   блок = одно поведение. Это делает блок адресуемым и тестируемым.
3. **Единый источник контракта инструментов.** Блок B12 (имена и описания
   инструментов) генерируется из `src/llm/tools.ts` (`PROPOSAL_TOOLS`), не копируется
   руками. Стратегия (когда и зачем) живёт в поведенческих блоках.
4. **Тесты трёхуровневые** (L1/L2/L3, §6): статический контракт текста — в CI;
   фикстурные сценарии — под live-гейтом; приёмка — бенч.
5. **Поведенческие изменения** (политика VCS B8, внешний референс B9) делаются
   только после документа и L1, отдельной фазой.

Границы: не трогаем семантику IR и движок; не меняем формат контекста-проекции;
минимальный диф по фазам. Не входит: `apply_patch`/`fetch` как обязательные —
Фаза 4 отдельным решением; эмбеддинги, LSP-глубина, субагенты, UI.

## 2. Таксономия блоков

Один блок — одно поведение, со стабильным ID. ID попадают в `docs/system_prompt_ru.md`
и в L1-тесты.

| ID | Поведение | Опора | Уровень |
|---|---|---|---|
| B1 | Фрейм: докса предлагает ровно один оператор, логос решает | `ir_semantics` §1, §7 | L1 |
| B2 | Capabilities / границы фрагмента | `src/ir/fragment.ts` | L1 |
| B3 | Словарь дерева: `request`/`goal`/`plan`/`check`/`achieved_under`/`refuted`/`addressed` | `ir_semantics` §2 | L1 |
| B4 | Чтение проекции: `path`/`constraints`/`lastResult`/`calls`/`shown`/`applicable`/`checkReady`/`nextAction`/`budget` | `src/ir/project.ts` | L1 |
| B5 | Память и рабочее множество: `shown`, `query {id}`, «вне контекста нет знания» | `tools_ru` §4.4–4.5 | L1 |
| B6 | Цель из запроса: литеральные команды verbatim, корень воркспейса, `cd <dir> &&`, не угадывать команду | `tools_ru` §5.1 | L1 |
| B7 | Декомпозиция: стадии-подцели; баг = reproduce/locate/fix; нет отдельного verify | `ir_semantics` §4.1 | L2 |

| B11 | Цикл пересмотра: `refuted` = прогресс, `revises` перечисляет провалы | `ir_semantics` §4.1, §2.7 | L2 |
| B12 | Контракт инструментов: плоские имена; генерируется из `PROPOSAL_TOOLS` | `src/llm/tools.ts` | L1 |

| B16 | Ограничения/безопасность: не нарушать `constraint`, не редактировать на устаревшем | `ir_semantics` §9 | L1 |

## 3. Отдельный документ `docs/system_prompt_ru.md`

Структура (по образцу `docs/ir_semantics_ru.md`):

- §0 Принцип: промпт — операционный спек политики доксы; правка поведения идёт
  «правка здесь → правка блока → тест».
- §1 Модель сборки: блоки, порядок, инварианты (нет дублирования; один блок = одно
  поведение; технический контракт из реестра).
- §2 Блоки B1–B16: для каждого — назначение, точная инструкция, читаемые поля
  контекста, что запрещено, деградация при отсутствии, тест.
- §3 Сквозные инварианты (нет противоречий между блоками; каждый инструмент назван
  вызываемо; бюджет символов).
- §4 Что изменено и почему (git-политика, drift `apply`).
- §5 Карта тестов L1/L2/L3.
- §6 Открытые вопросы.

## 4. Фазы

### Фаза 1 — каркас и документ (без смены поведения)

**Цель.** Вынести текст в блоки, задокументировать, не меняя поведение.

**Изменения.**
- `src/loop/prompt/blocks.ts` — `PROMPT_BLOCKS: { id: string; text: string }[]` с
  текущим текстом, разложенным по B1–B16.
- `src/loop/prompt/index.ts` — сборка: `SYSTEM_PROMPT = PROMPT_BLOCKS.map(b => b.text).join("\n\n")`;
  экспорт `PROMPT_BLOCKS`/ID.
- `src/loop/propose.ts` — импортирует `SYSTEM_PROMPT` из `prompt/` и реэкспортирует
  (сохранить текущий путь импорта в `tests/prompt.test.ts`).
- `docs/system_prompt_ru.md` (+EN) — документ из §3.

**Почему.** Без шага 1 последующие правки снова будут редактировать монолит.

**Проверка.** `npm run typecheck`; `SKEIN_LIVE=false npx vitest run` (старые
`tests/prompt.test.ts` зелёные); новый L1-тест: ID уникальны, `SYSTEM_PROMPT` равен
склейке блоков. Диф — перемещение текста (byte-identical, кроме разделителей).

### Фаза 2 — устранение дрейфа (B12)

**Цель.** Промпт называет инструменты так, как они реально зарегистрированы.

**Изменения.**
- B12 генерируется из `PROPOSAL_TOOLS`: строка `- <name>: <description>` на
  инструмент; вызов по имени, без обёртки `apply { action: { tool } }` и без
  вложенной нотации `{ tool: "read", ... }`.
- Убрать дублирование между блоком инструментов и хвостовым «Rules».
- Детальная проза по аргументам — в `description` соответствующего инструмента
  (`src/llm/tools.ts`), в промпте — только сгенерированный индекс.

**Почему.** После перехода на нативные tool calls (`469be05`) промпт остался под
старую вложенную схему; `toProposal` отвергает `apply` как `unknown tool call`.

**Проверка.** L1: каждый `PROPOSAL_TOOLS[].function.name` встречается как вызываемое
имя; в промпте нет `apply {` и `{ tool:`; offline-тесты.

### Фаза 3 — поведение: VCS и внешний референс (B8/B9)

**Цель.** Снять перегиб «never git» и легитимировать локализацию по эталону.

**Изменения.**
- B8 (переформулировать): git/история — нормальный инструмент, *когда* репозиторий
  её имеет; в харнессе `.git` может отсутствовать — упавший `git` не повторять;
  «локальная история» и «внешний эталон» — разные вещи.
- B9 (новый): если у артефакта есть канонический референс (апстрим, версия из
  реестра, соседняя копия), получить эталон и продиффить — законная и часто
  быстрейшая локализация. В терминах IR: artifact `file` с провенансом `external`;
  diff — наблюдение. Первый срез — через `run` (`curl`/`diff`), без нового инструмента.
- L2-фикстуры: (a) офлайн — эталонный снапшот в воркспейсе, ожидаем diff-локализацию;
  (b) репозиторий без `.git`, ожидаем отсутствие повторных `git`-команд.

**Почему.** На `fix-ocaml-gc` opencode нашёл баг именно так (curl апстрима + diff,
один `edit`), а Skein — вручную; промпт сейчас этот путь запрещает рефлексом «нет VCS».

**Проверка.** `SKEIN_LIVE=true` фикстуры (trajectory shape); L1 не ломается;
`docs/system_prompt_ru.md` §4 фиксирует изменение.

### Фаза 4 — инструменты под стратегию

**Цель.** Дать стратегии из B9 первоклассный инструмент (по решению, отдельным
под-этапом на каждый).

**Изменения (кандидаты, каждый — своя спека и свой диф).**
- `fetch`/`webfetch`: материализует референс в воркспейс (например `.skein/ref/…`) и
  возвращает `id`; результат адресуем и recall-ится через `query`.
- `apply_patch`: применить diff из апстрима одной правкой (у opencode есть; у нас нет).
- Попутно: согласовать guard воркспейса с референсом — `read` по пути вне воркспейса
  сейчас роняет прогон (`bench_report_ru.md` §4.4, проблема 5).

**Проверка.** `tests/ops/` на новый инструмент; live-сценарий; запись в
`docs/ir_operations_ru.md` и `docs/tools_ru.md`.

### Фаза 5 — контролируемый эксперимент (промежуточный итог)

**Цель.** Показать, что Фазы 3–4 действительно меняют поведение, и отделить вклад
стратегии от конфаундера сети.

**Дизайн.**
- Задача с каноническим референсом (той же природы, что `fix-ocaml-gc`, но
  контролируемая).
- Один агент, одна модель, один бюджет — прогон в двух условиях: сеть **off** и
  сеть **on**. Вклад стратегии = разница B − A.
- Для архитектурного сравнения — оба агента (Skein и opencode) в обоих условиях.
- Метрики: ходы до локализации, reward, зафиксирован ли diff-путь в траектории.

**Изменения.** Раздел в `docs/bench_report_ru.md` (+EN); при необходимости —
офлайн-фикстура из Фазы 3 как воспроизводимая база.

**Почему последней.** Зависит от B8/B9 (Фаза 3) и опционально `fetch`/`apply_patch`
(Фаза 4); до них измерять нечего.

**Проверка.** Отчёт с числами A/B; явная оговорка про confound, если сеть влияет.

## 5. Трассируемость

Каждый блок B1–B16 получает: запись в `docs/system_prompt_ru.md` §2 → блок в
`src/loop/prompt/blocks.ts` → тест уровня L1/L2. Фазы 3–5 дополнительно получают
запись в `docs/plans/implementation_plan_ru.md` (статус/бэклог).

## 6. Тесты

- **L1 — статический контракт (офлайн, CI).** `tests/prompt.test.ts`:
  ID блоков уникальны и присутствуют; `SYSTEM_PROMPT` = склейка блоков; каждый
  `PROPOSAL_TOOLS[].function.name` назван вызываемо; нет `apply {`/`{ tool:`; каждый
  обязательный фрагмент (B6/B13/B14) на месте; бюджет символов не превышен.
- **L2 — фикстурные сценарии (под `SKEIN_LIVE=true`).** На поведение — фикстура +
  проверка **формы траектории** (наличие стратегии), а не точного вывода. Каркас —
  `tests/live/scenarios.test.ts`. Честно: флейки, в CI не входит.
- **L3 — приёмка/бенч.** Прогоны на реальных задачах, в т.ч. эксперимент Фазы 5.

## 7. Риски и открытые вопросы

- **Недетерминизм LLM.** L2 слабый и флейки; поэтому L1 обязателен, L2 — только под
  гейтом, L3 — приёмка.
- **Длина промпта.** Блоки позволяют мерить и резать; текущий промпт ~12k символов.
  Открыто: целевой бюджет и что вынести в описания инструментов.
- **Сеть как конфаундер.** Любая стратегия, завязанная на сеть, искажает сравнение
  агентов (`bench_report_ru.md` §4.4). Отсюда парный off/on в Фазе 5.
- **Объём Фазы 4.** `fetch`/`apply_patch` — отдельные решения; в обязательный объём
  не входят.
