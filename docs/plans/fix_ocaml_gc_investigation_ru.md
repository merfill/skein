## 1. Что проверяем

Единственный пробный кейс — `fix-ocaml-gc` (terminal-bench): после run-length-сжатия
свободного места в major heap компилятор OCaml падает при bootstrap. Эталонный фикс —
одна строка в `runtime/shared_heap.c` (~строка 650). Критерий:
`make -C testsuite one DIR=tests/basic` → «40 tests passed». Команда прогона:

```sh

```

Джобы (`~/.skein-bench/harbor/<ts>`), лог хода — `<trial>/agent/langgraph-run.log`
(строки `SKEIN_CONTEXT`, `SKEIN_PROPOSAL`, `SKEIN_TURN`, `SKEIN_EVENTS`,
`SKEIN_METRICS`).

## 3. Найденные дефекты и починки

### 3.1 Взрыв контекста
`frontier.lastResult` инлайнил узел `check` целиком, включая `witness` — версию
**каждого файла** воркспейса (~7000 записей ≈ 767k символов). Пики `37k→802k`.
**Починено:** проекция переписана — `path`/`constraints`/`lastResult`/`calls`,
сырые payload не инлайнятся. `SKEIN_CTX_TOTAL`/`SKEIN_CTX_EXCERPT` сняты.

### 3.2 Отказ не доходил до модели (цикл)
`record_rejection` писался, но в новой проекции `refusals` не было; контекст после
отказа был байт-в-байт тем же → модель повторяла (7× одинаковый `read`).
**Починено:** `calls` (ранее `negative`) — дедуп по сигнатуре + `count`, статус
`ok/fail/refused`. Введён инвариант: отказ/неудача обязаны менять проекцию.

### 3.3 Инструменты врали (молчаливое урезание)
- `read` резал содержимое до 400 символов, и то же окно нельзя было перечитать.
- `grep` не видел `.c/.h` (жёсткий `TEXT_EXT`).
**Починено** (`docs/tools_ru.md`): `read` — окно ≤400 строк и явный «строки X–Y из
Z, продолжение с …», повтор чтения разрешён; `grep` — по содержимому (не по
расширению), `before/after` по умолчанию 5/5, ≤200 совпадений, повтор разрешён;
`run` — полный вывод (≤8000, дальше head+tail + `outputRef`).

### 3.4 План-ловушка (`cursor=0`)
Пункты плана были командами, которые модель так и не запускала дословно → пункт
навсегда «open», модель вечно «воспроизводит».
**Починено:** (B) движок сам ветвит текущий невыполненный пункт, когда действие
отличается; вариант сохраняется append-only; план — чек-лист; пункт решён, если
`achieved/refuted/abandoned/executed` или у него выбранная решённая альтернатива.

### 3.5 Потеря рабочего множества (#9)
Проекция держала один последний результат; модель осциллировала `read ↔ make`
(«build logs are lost»). **Починено:** гипотеза несёт `need: [id…]` (≤5); тела
результатов хранятся — небольшие в узле, большие в `.skein/observations/<id>.txt`
ссылкой; на следующем ходу показываются полностью в `shown`. `calls` получил `id`.
(Инвариант 11 уточнён: секреты — нет; малые результаты — можно.)

### 3.6 Плохой план (команды вместо стадий)
План был «2 команды», без `fix`/`verify` и без гипотезы-узла.
**Починено промптом:** обязательная декомпозиция на **стадии-подцели** с конкретным
`done_when` (`reproduce → locate → fix → verify` для багфикса); `action`-пункт —
только для немедленной команды; гипотеза — узел с `why`, проверяется `check`.
Проверено на 6 синтетических запросах — все дают план из подцелей.

## 4. Текущее поведение (прогон `21-14-05`)

План сформирован правильно (стадии), `reproduce` закрыт на T14 (`complete`),
`locate` — на T57, `edit` — на T59 (последний ход), проверки (`check`) нет.

| Стадия | Итог |
|---|---|
| reproduce | `complete`, T14 |
| locate | `complete`, T57 (**43 хода!**) |
| fix | `edit` T59, без проверки |
| verify | не дошло |

`goals:5, completes:2, edits:1, checks:0`, reward 0, `stopReason=null`.

### Причина 43 ходов в locate (доказано)
`grep` ищет по всему воркспейсу, результаты сортируются по пути, поэтому первыми
идут служебные файлы. Из `lastResult` T17–T27: `grep run_length|…|compress` даёт
**410/546 совпадений**, показываются первые 200 — все из `ocaml/.depend`,
`ocaml/.mailmap`, `ocaml/Changes`; `runtime/*.c` в показ не попадают. Мысли модели:
«drowning in noise (.depend, Changes)». `SKIP_DIRS` пропускает каталоги, но **не
файлы** вроде `.depend`.

## 5. Открытые задачи (по приоритету)

1. **grep: область и служебные файлы (сейчас главный блокер locate).**
   - `grep { pattern, path?, before?, after? }` — ограничить директорией/glob
     (`grep {pattern:"sweep", path:"runtime"}`).
   - не читать скрытые/генерённые файлы (`.depend`, `.mailmap`, `Changes`) —
     аналог hidden-skip у ripgrep.
2. **Дисциплина стадии (темп).** Модель не закрывает стадию, как только `done_when`
   достигнут: `locate` копил доказательства 43 хода. Промпт: «закрывай стадию сразу,
   как только можешь назвать код; стадия — несколько ходов».
3. **Стоп по отсутствию положительного прогресса.** Новый `read`/`grep` = новое
   знание, поэтому `no_progress` не срабатывает; нужен счётчик «нет мутаций/закрытий
   K ходов».
4. **`need`: одноразовый vs постоянный.** Сейчас `shown` «мигает» (модель забывает
   переспросить); рассмотреть рабочее множество до смены моделью.
5. **Рост `calls`** (десятки записей на длинных прогонах).
6. **Возврат бюджета контекста**, если снова станет проблемой (сейчас не применяем).

### 8.2 Что починено

1. **Structured output — JSON-only** (`src/llm/structured.ts`). Провайдер под длинным
   промптом возвращал tool-call с плоскими/битыми args (`operator` на верхнем уровне
   вместо `action`, «Bad control character»), а в LangChain v1 нет `Runnable.bind`
   (per-call kwargs идут через `withConfig`). Теперь: **сырая JSON-схема в промпте +
   ручной разбор**; обрыв — по `finish_reason == "length"` (структурная проверка как
   fallback); буст `max_tokens` через `rebuild` (поле конструктора); один repair-раунд
   при нарушении схемы. `llm_error` при запуске модели ушли.
2. **`thought` ограничен** одной короткой фразой (`src/loop/propose.ts`): модель
   сваливала рассуждение в `thought` (до **30 127** выходных токенов/ход → обрывы).
   Стало ~100–300; обрывов нет.
3. **`pipefail`** в `workspace.run` (`src/tools/workspace.ts`): `make | tail` теперь
   возвращает код `make` — провал виден как `fail`, а не `pass`.
4. **История провалов** (`src/ir/project.ts`): неудачные попытки **не вычищаются**
   после `edit`, а заметка `calls` показывает строку ошибки даже при `verdict=pass`.
5. **Уровневое удержание контекста** (`src/loop/graph.ts`, `projectNode`): результаты
   действий **текущей** фокус-цели остаются в `shown` без TTL, пока фокус не уйдёт с
   уровня; `need`/`query` — кросс-уровневый возврат (TTL). Снимает осцилляцию
   `read ↔ make` (одно окно перечитывалось 5–6 раз).
6. **Гард плана** (`src/loop/classify.ts`): «all plan items fulfilled → не растить»
   срабатывает только если план **несёт проверяемый шаг** (action или objective-
   подцель). Иначе после закрытых epistemic-стадий (reproduce/locate) модель не могла
   добавить стадию fix и уходила в цикл `create_goal` (регресс `22-30-48`).
7. **Промпт «от падения к причине»** (`src/loop/propose.ts`): выцепить точный факт из
   ошибки → назвать инвариант → **прочитать определение каждого символа/макроса** →
   проверить **всех** носителей инварианта, включая «тихие» (advance), а не только
   очевидные (merge) → упавшая проверка = оракул.
8. **Реплей трассы** (`bench/replay.ts`, `npm run replay`): гоняет записанные контексты
   (`contexts.ndjson` или `SKEIN_CONTEXT` из Harbor-лога) через живую модель без Harbor;
   печатает `operator`/tool, `thought`, токены, `finish_reason`.
9. Доки синхронизированы: `testing_{ru,}.md` §8.1, `context_design_{ru,}.md` §8,
   `ir_semantics_{ru,}.md` (семантика `run target`), `tools_{ru,}.md` (`run`).

### 8.3 Диагноз: почему задача не решается

- **Данных не не хватало.** Аудит по ходам: на **каждой** правке в контексте были и
  дефектная строка (`p += Whsize_hd(hd);`), и вывод падения (`Segmentation fault`),
  и код читался повторно.
- **Корень — конкретный символ.** Модель рассуждала о `Whsize_hd`, **не прочитав его
  определение** (0 контекстов из 60). Без определения общий advance `p += Whsize_hd(hd)`
  выглядит корректным, и внимание уходит в merge/rle-логику.
- **После п. 8.2.7** определение `Whsize_hd` стало читаться (**0 → 19** контекстов),
  модель добавляет objective-стадию fix, делает правки. Гипотезы близки («при wosize=0
  `Whsize_hd` даёт 1, а не `wh`»), но патчит ветку `p += wh*Wosize_hd(hd)` и merge, а
  не общий `p += Whsize_hd(hd)` → `p += wh`. Один вывод не сделан.
- Остаётся трещотка `create_goal` (20 за прогон) — отдельная проблема.

### 8.4 Открытые задачи

1. **Общий advance после ветки, пропустившей ран.** Нудж: «если ветка уже продвинула
   указатель через ран, общий шаг — ровно один слот размерного класса (`wh`)». Формули-
   ровать общо, не хардкодить под кейс.
2. **Трещотка `create_goal`.** Дедуп/ограничение роста; повторные интерпретации подряд
   до `no_progress`.
3. **grep-scope + служебные файлы** (из §5, актуально).
4. Дисциплина закрытия стадии (из §5).

### 9.2 Почему наконец решилось

- **P0 — reasoning включён** — решающий фактор (F1): при `reasoningEffort="high"` модель
  трогает нужную строку; с выключенным — не трогала ни разу (15/15 мимо).
- **S1–S3** (фокус под закрытым предком; closing move по фокусу; повтор после
  `inconclusive`) убирают 12-ходовую петлю `unknown_revision`.
- **P1/P2** (диагностика падения; ноты `complete`, diff правок, удержание по уровням)
  кладут дефектную строку, краш и доказательства стадии в проекцию.
- **P3.1/P3.3** (4 CPU/6 GB; `run {background}` + `{job}`) позволяют агенту собрать и
  проверить, не блокируя ход.
- **P4/P5/P6** убирают единственное место, где докса формировала контекст (`need`), и
  заставляют отказ называть ход по фокусу. Второй прогон показывает, что удаление `need`
  не деградирует live-путь.

### 9.3 Траектория

Оба называют дефект в `pool_sweep` и вносят эталонную правку
`p += Whsize_hd(hd);` → `p += wh;`. Первый: правка на ходу 29 (до удаления `need`).
Второй: `locate` закрыт на ходу 45, правка на ходу 53, затем **фоновый** bootstrap-build
(`job-2`, P3.3) с опросом на ходах 56–57 перед чеком fix-цели (ходы 58–59). Оба упёрлись
в `max_turns` с уже внесённой правкой; верификатор затем пересобирает начисто и проходит.

   сборка.
2. **Трещотка `create_goal`** всё ещё видна (`14-53-22`: 10 goals / 10 plans /

3. **`P3.2`** (быстрый прокси-reward) остаётся отложенным — инфраструктура на

4. Оставлять ли `reasoningEffort=high` дефолтом для повседневных прогонов
   (стоимость/латентность) или повышать только на тяжёлых задачах? (открыто в
   `engine_fixes_found_ru.md` §10).
