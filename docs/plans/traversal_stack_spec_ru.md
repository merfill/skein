# Skein — спецификация стека обхода (спина и руки)

> Английское зеркало — `docs/plans/traversal_stack_spec.md`.
> Основание — обсуждение механики альтернатив, правок плана и обхода дерева.
> Касается `docs/ir.md`, `docs/plans/step_reduction_plan.md`, `src/ir/traversal.ts`,
> `src/ir/project.ts`.

## 1. Назначение

Зафиксировать модель обхода дерева: **стек кадров** (спина) и **руки** (сиблинги
уровня). Это нужно, чтобы:

- проекция была ограниченной (спина + рабочие тела, а не растущая лента);
- правки плана (альтернативы) попадали в контекст явно и не терялись;
- сессии сохранялись и воспроизводились детерминированно.

## 2. Инварианты

1. **IR монотонно возрастает.** Движок и докса только добавляют узлы/рёбра; ничего не
   удаляется и не переписывается.
2. **Детерминизм.** `same events → same Context`: проекция (включая стек) — чистая
   функция журнала.
3. **Закрытие только `stop`.** `exitCode` запуска-критерия — единственный факт прохода/
   провала; модель не объявляет успех.
4. **Стек = fold(журнал).** Стек обхода — не самостоятельное состояние, а вывод; он
   обязан совпадать с пересборкой из журнала.

## 3. Модель: кадр, спина, рука

**Спина** — последовательность кадров, по одному на уровень пути от корня к фокусу:

```
frame = {
  node,            // узел спины: request или goal
  arm,             // контейнер-рука этого уровня: план цели или альтернативы
  siblings[],      // упорядоченные дети контейнера (сиблинги уровня)
  cursor/chosen    // где внутри руки (первый невыполненный пункт / выбранный вариант)
}
```

- **Спина** = стек кадров (глубина = длина пути; небольшая).
- **Рука** = `siblings` кадра. Для root-кадра (request) это интерпретации; для
  goal-кадра — пункты плана. Одна механика покрывает и выбор гипотезы, и шаги плана.
- **Переход** = push нового кадра (зашли в сиблинга) или pop (вернулись).
- **Рука — это ReAct на месте.** Внутри одной руки цикл в точности ReAct: цель
  создаётся с планом из одного пункта-команды, пункт исполняется за свой ход, результат
  пишется в журнал и уходит доксе, которая добавляет следующий узел или останавливается;
  дерево появляется только там, где у пункта есть альтернативы (§6). Каждый такой шаг —
  событие IR, чего обычный ReAct не сохраняет.

Родительская рука — контейнер, из которого узел выбран: **альтернативы** (для
интерпретации/варианта) или **план родителя** (для под-цели/пункта). В проекции выбор
из альтернатив виден как `alternatives` узла, выбор внутри плана — как `plan`
родительского кадра. Симметрия: `alternatives` (как нас выбрали) + `plan` (кого
выбираем мы).

## 4. Происхождение из журнала (алгоритм пересборки)

Пересборка стека из журнала (она же — загрузка сессии):

1. Старт: стек `[root]`.
2. Реплей событий по порядку:
   - `descend node` → push кадра `node`;
   - `return` → pop.
3. **Нормализация фокуса до fixpoint** (детерминированная, не требует событий доксы):
   - если верх — request и есть выбранная, не завершённая интерпретация — push её;
   - если верх — goal и есть первая невыполненная под-цель — push её;
   - если верх завершён и не корень, либо под завершённым предком — pop.
4. Результат — стек кадров; руки выводятся из контейнеров (см. §5).

Инкрементальное ведение стека в рамках сессии (push/pop вместо пересборки каждый ход)
допустимо как оптимизация, но только если результат доказуемо равен пересборке.

## 5. Рука: контейнеры и курсор

Рука кадра — это узел-контейнер (`plan` или `alternatives`) с упорядоченными детьми
(порядок = порядок добавления по рёбрам `item`). Контейнеры и рёбра — источники
истины; отдельного хранилища руки нет.

- **Курсор** = индекс первого невыполненного пункта плана. «Выполнен» учитывает
  выбранную альтернативу пункта (см. §6).
- **chosen** (для alternatives) = последний по времени выбранный вариант
  (последовательность рёбер `chosen`; побеждает последний).
- **История руки** — все сиблинги со своим состоянием (`open` / `executed` / `stopped`;
  факты критерия и вытеснение — производные чтения, а не состояния). Исполненные никуда
  не деваются: они остаются в руке.

## 6. Правки плана (альтернативы) — append-only

«Правка плана» = **добавление узла**, а не редактирование:

- новый пункт — новое ребро `item` в план;
- замена/обход пункта — у пункта создаётся контейнер `alternatives`, и новый
  вариант кладётся туда как `item` + `chosen`; исходный пункт остаётся сиблингом;
- новая интерпретация цели, чей критерий провалился — сиблинг в контейнере альтернатив
  владельца (request или цели).

Набросок плана, заданный при создании цели, **заморожен как узлы**; все последующие
правки — добавление. Поэтому «эффективный план» и «следующий пункт» **выводятся**:
первый невыполненный пункт, с учётом выбранной альтернативы.

Критерий цели (`done_when`) **неизменяем**: если критерий оказался неверным — это
провалившийся критерий, случай для нового варианта, а не правка тела цели; новая
попытка — новый вариант.

## 7. Проекция

Проекция = стек кадров + история по адресу:

- для **каждого** кадра показывается его рука целиком: сиблинги со `state`,
  текущий помечен; плюс родительская рука узла (альтернативы);
- **фокусный** кадр — развёрнуто, включая вложенные альтернативы текущего сиблинга
  (история правок пункта видна на месте);
- **предковые** кадры — компактно (рука + курсор, без тел результатов);
- результаты-тела — только рабочим множеством; всё прочее — по адресу `query {id}`.

Формы (эскиз):

```
path: [
  { id, kind, state, text|what, why?, done_when?,
    alternatives?: { chosen?, items: [{id,label,state,chosen,why?}] },  // как выбрали узел
    plan?: { cursor?, items: [
       { id, kind, label, state, why?,
         alternatives?: { chosen?, items: [...] }                        // история правок пункта
       } ] } }
]
```

Связь с текущим кодом: `planView`/`alternativesView` (`src/ir/project.ts`) дают это,
включая рендер альтернатив внутри пунктов плана (историю правок пункта) — `TR-9`.

## 8. История и адресация

- Тела результатов **не** растут в контексте: рабочее множество ограничено
  (`MAX_HELD` / `HELD_CHARS`), вытесненное достаётся `query {id}`.
- Индекс `calls` — сжатая память о том, что уже делалось (статус, короткая заметка).
- Ничего не удаляется: вытеснение из рабочего множества ≠ потеря из IR.

## 9. Верификация

- Факт критерия производит **только явный прогон, нацеленный на цель**
  (`run { target }`): наблюдение с `target` и `exitCode`. Совпадение текста команды —
  никогда не достаточно.
- Прогон команды, совпавшей с `done_when`, как **шаг плана** (reproduce) — обычное
  наблюдение, не критерий (он не несёт `target`).
- Движок план **не** прогоняет сам (A4 снят): каждый шаг докса исполняет своим ходом,
  по одному за раз.

## 10. Сессия

- Сохраняется **журнал событий** (`events`), а не стек.
- При загрузке стек и руки пересобираются по §4–§5; кэш стека допустим, но обязан
  совпасть с пересборкой.
- Реплей (trace) — тот же механизм: журнал → стек → проекция на каждом ходу.

## 11. Решения и открытые вопросы

**Решено:**

- **Рендер ревизий — inline у пункта.** Альтернативы пункта показываются в самом
  `item`, а не отдельным блоком `revisions`: обход — «ходим по плану, при необходимости
  падаем в глубину, при необходимости возвращаемся и делаем ревизию», и ревизия должна
  быть видна там же, где пункт.
- **Отдельного узла «вставка» нет.** Порядок задаётся рёбрами `item`; правка — это
  новый `item` или альтернатива к существующему пункту (§6).

**Открыто:**

- Даёт ли докса право **вставлять** пункт в середину (а не только в конец +
  альтернативы)? Решается при реализации.
- **Приоритет вытеснения рук предковых кадров** при росте числа сиблингов — уточнить в
  процессе (сейчас руки малы, проблемы не наблюдалось).
- Точный формат родительской руки для вставленного пункта (наследование `why`).
