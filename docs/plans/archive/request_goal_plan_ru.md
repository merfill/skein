## 1. Зачем

Сейчас связь «запрос → интерпретация» — это контейнер `alternatives` с ребром `chosen`.
Из-за этого механизм ревизий протекает в обычный случай: у запроса почти всегда **одна**
интерпретация («запрос — это вот такая цель»), а он смоделирован как один вариант из
нескольких. Отсюда две проблемы:

1. **Имя/смысл.** `has_alternatives` + `chosen` говорит «одно из многих» там, где смысл —
   «вот что представляет собой запрос».
2. **Нет честного закрытия неинтерпретируемого запроса.** У запроса вида «привет, дядя
   Вася» цели нет; сейчас его можно закрыть, только выдумав цель с фиктивным критерием
   (`done_when: "true"`) — логическое противоречие (создание цели там, где её нет).

Отдельно: `chosen` и «курсор = первый невыполненный пункт» дублируют то, что и так
выражает порядок в контейнере: текущий пункт — просто **последний** (план — это
последовательность, эмулируемая порядком детей контейнера).

## 2. Целевая модель (решения)

- **Одна интерпретация.** `request --has_goal--> goal` (ровно одна). Пока интерпретация
  **фиксирована** (менять её модель не может; смена интерпретации — отдельный будущий шаг,
  не этот).
- **`unactionable`.** Запрос, намерение которого неисполнимо, получает
  `request --no_goal--> unactionable { why }`; запрос закрывается. Новый ход доксы
  `decline`.
- **Контейнеры владеют порядком детей.** Порядок детей контейнера (порядок добавления) —
  это и есть структура; `item` — концептуальное имя, а не обязательное ребро. Граф —
  **DAG**, не дерево (узел `stop` может быть одновременно последним ребёнком плана и целью
  ребра `has_stopped`) — это нормально.
- **План и шаги.** `goal --has_plan--> plan`: план — контейнер **пунктов плана**; каждый
  пункт — сам контейнер **альтернатив** (команда или подцель). То, что нужно исполнить
  сейчас, — **последняя альтернатива последнего пункта плана**.
- **`stop` закрывает цель.** При `stop` движок добавляет узел `stop` `{why}` последним
  ребёнком плана И проводит ребро `has_stopped` `goal → stop` (быстрый поиск + причина).
  Цель закрыта ⟺ у неё есть ребро `has_stopped`. Пока `stop` принимается только при
  пройденном критерии цели (успешный стоп; иначе `check_not_run`); негативные случаи
  (сдача) — отдельный будущий шаг.
- **Без `chosen`.** Текущий вариант — последний ребёнок своего контейнера.
- **Закрытость запроса выводится.** Запрос завершён ⟺ его цель закрыта (есть `has_stopped`)
  или у него есть узел `unactionable`. У запроса своего `stop` нет.
- **Ходы доксы:** `create_goal` (интерпретировать запрос), `apply` (команда), `stop`,
  `decline` (unactionable), плюс read-only `query`. Модель явно выбирает между «новый пункт
  плана (шаг)» и «новая альтернатива текущего пункта». Предлагаемое API (чтобы движок не
  угадывал):
  - `create_goal { what, why?, done_when, plan, step }` — на запросе: интерпретация
    (`has_goal`); на цели: **альтернатива**-подцель текущего пункта.
  - `apply { command }` — команда как **новый пункт плана** (новый шаг).
  - `branch { command }` — команда как **новая альтернатива** текущего пункта (повтор /
    замена).
  - `stop { why }`, `decline { why }`, `query`.

Формы:

```
request R
  has_goal ─▶ goal G { what, why?, done_when, plan }
                has_plan ─▶ plan P  [ пункт1, пункт2, …, stop ]        (порядок = последовательность)
                              пункт1 = альтернативы [ c1, c1', G' ]    (текущая = последняя)
                              пункт2 = альтернативы [ c2 ]
                has_stopped ─▶ stop   (тот же узел stop, что и последний ребёнок плана)
  либо
  no_goal ─▶ unactionable U { why }
```

## 3. Последствия (что меняется относительно текущего кода)

- `chosen` исчезает (`latestChosen`, `chosenInterpretation`, `unselectedVariant`,
  `actionSuperseded` пересчитываются через «последний ребёнок / не последний»).
- `has_alternatives` у запроса исчезает; у запроса есть `has_goal` либо `no_goal`.
- **фокус / обход** становятся «по последнему ребёнку»:
  - `focusEvents` спускается из запроса в его единственную цель; внутри цели текущий пункт
    — последний ребёнок плана; если у этого пункта есть альтернативы и их последний ребёнок
    — цель, спускаемся в него;
  - `cursorOf` (первый невыполненный) выводится из употребления; `itemFulfilled` и
    `planExhausted` пересчитываются в представлении «последний ребёнок».
- `requestSettled` заменяется чтением критерия цели (`criterionPass(goal)`).
- завершение сессии: запрос завершён, когда закрыта его цель; причины `stop` переименуем
  соответственно.
- проекция показывает цель запроса (или пометку `unactionable`), а не список альтернатив;
  в плане цели последним виден `stop`.

## 4. Открытые вопросы (решить вместе с кодом)

- **Имя ребра** для связи с неисполнимостью: `no_goal` (вид узла `unactionable`)? Ход доксы:
  `decline { why }`?
- **Только успешные стопы.** `stop` принимается только при пройденном критерии цели
  (иначе `check_not_run`). Негативные случаи (сдача) — **отдельный будущий шаг**, не этот.
- **`alternatives` на целях.** Оставить только для пунктов плана или и для целей?
  (Склоняюсь: только пункты плана; подход к цели ветвится через её пункты.)
- **`has_stopped` vs «последний пункт плана — `stop`».** Держим оба (ребро для быстрого
  поиска, пункт для последовательности) — принято; код должен держать их согласованными.

## 8. Отношение к `stop_closure_plan.md`

Рефактор закрытия через `stop` остаётся в силе: `stop` — единственное закрытие, а
запуск-критерий — обычная `observation`. Этот план меняет **где** записывается `stop`
(внутри плана, плюс ребро `has_stopped`) и **как запрос связан с целью** (`has_goal`), а
также убирает `chosen`. Он заменяет собой части текущей модели: `alternatives`/`chosen` у
запроса и «курсор = первый невыполненный».
