# Tier 4b — терминальная сессия: REPL и её драйвер

> Английское зеркало — `docs/plans/session_driver_plan.md`.
>
> Статус: **реализовано; проверено офлайн и live-синтой** (драйвер `runSessionTurn`, REPL `runRepl`, CLI
> `src/cli.ts`, сценарий на скриптованных агентах). Live-прогоны не выполнялись. За пределами
> среза остаются сохранение сессии между запусками, прерывание по Ctrl-C, потоковый вывод,
> стратегии возобновления, `revise`, пины, остров чтения и live-прогоны.

## 1. Сценарий

В терминале открыт каталог проекта. В нём запущена программа `skein`, которая подключается к
модели и показывает приглашение. Пользователь вводит строку и нажимает Enter. Агент читает
проект, выполняет работу и останавливается. Затем приглашение возвращается, и диалог можно
продолжить.

Сегодня такого сценария нет. Функция `runAgent` (`src/loop/graph.ts:346`) обрабатывает один
запрос и возвращает результат; её вызывают тесты, бенчмарки и адаптер Harbor, но не
терминальная программа. Контейнер сессии существует, однако ничто не проводит через него
несколько последовательных реплик.

Настоящий план делает сценарий реальным минимальной терминальной программой. Драйвер — это
библиотечная функция, которую программа вызывает один раз на каждую строку пользователя.

## 2. Текущее состояние

- Точки входа командной строки нет; в `package.json` отсутствует `bin`.
- `runAgent` создаёт запрос, проводит его по состояниям и возвращает `AgentResult`.
- `SessionState` и `SessionAgent` реализованы; доступны операции `respond` и `start`.
- В цикле нет понятия диалога: после возврата `runAgent` процесс, как правило, завершается.

## 3. Целевое поведение

Программа запускается из каталога проекта:

```sh
npx tsx src/cli.ts          # или: npm run cli
```

Она печатает корень рабочего пространства и приглашение `skein> `. Сценарий ниже служит
критерием приёмки.

```text
skein> почини падающую сборку

  session: start("почини падающую сборку")
  task r1: start
  [r1 t1] move orientation "назвать рабочее пространство и критерий приёмки"
  [r1 t2] apply bash: ls
  ...
  task r1: stopped (request_addressed) after 12 turns

skein> теперь добавь тест для парсера

  session: start("добавить тест для парсера к уже исправленной сборке")
  task r1: completed (trace)
  task r2: start
  ...
  task r2: stopped (request_addressed) after 7 turns

skein> что ты изменил?

  session: respond
  изменён runtime/shared_heap.c, добавлен регрессионный тест

skein> продолжи с того места

  session: start("продолжить … с учётом найденного")
  task r3: start
  ...
  task r3: stopped (max_turns)

skein> exit
```

Правила взаимодействия:

- каждая непустая строка — одна реплика и один вызов драйвера;
- команды `exit` и `quit`, а также конец ввода (Ctrl-D) завершают программу;
- задача никогда не выполняется в фоне: пока она идёт, приглашение не появляется;
- если логос отклоняет операцию, программа печатает причину и возвращается к приглашению;
- состояние задачи закрывается только собственным `stop`; `start` не закрывает предыдущую
  задачу, а лишь снимает её с фокуса;
- если включено подтверждение, агент сессии сначала отвечает формулировкой («понял задачу
  так…»), и следующий ход с согласием запускает её.

Продолжение работы над прежней задачей пока выражается новым `start` с переформулированным
запросом. Стратегии возобновления того же unit'а — отдельный будущий срез.

## 4. Устройство

### 4.1. Точка входа

`src/cli.ts` — тонкая точка сборки. Она:

1. разбирает аргументы: каталог проекта (по умолчанию текущий), `--max-turns`, при
   необходимости `--model`;
2. загружает настройки (`loadSettings`) и создаёт модель (`createChatModel`);
3. создаёт рабочее пространство (`fsWorkspace`), функцию предложения для задачи
   (`modelProposer`) и агента сессии (`createSessionAgentDeps`);
4. собирает `SessionTurnDeps` (см. ниже) и создаёт сессию (`createSession`);
5. запускает цикл readline, вызывает `runSessionTurn` на каждую строку и печатает результат;
6. завершается по `exit`/`quit` или концу ввода.

В `package.json` добавляется сценарий:

```json
"cli": "tsx src/cli.ts"
```

Упаковка через `bin` в этом срезе не добавляется.

### 4.2. Цикл REPL

`src/session/repl.ts` содержит цикл, отделённый от процесса и библиотеки readline, чтобы его
можно было тестировать офлайн:

```ts
runRepl(input: AsyncIterable<string>, deps: SessionTurnDeps, output: (line: string) => void,
        session?: SessionState): Promise<SessionState>
```

Цикл:

1. читает очередную строку и пропускает пустые;
2. завершается по `exit`/`quit` или концу ввода;
3. вызывает `runSessionTurn(deps, session, line)`;
4. печатает операцию, причину отказа (если была), ответ и сводку по задаче;
5. ожидает следующую строку.

`src/cli.ts` предоставляет `AsyncIterable<string>` на основе readline и writer на
`process.stdout`. Сам цикл не зависит от терминала и покрывается офлайн-тестом.

### 4.3. Драйвер

`src/session/driver.ts` — функция обработки одного хода. Она не является циклом и не читает
ввод.

```ts
runSessionTurn(deps, session, utterance) → {
  session,      // та же сессия, дополненная событиями и, возможно, новым модулем задачи
  operation?,   // операция, предложенная SessionAgent: respond или start
  applied?,     // результат логоса: { ok: true } либо { ok: false, reason }
  reply?,       // текст ответа; только для respond
  task?,        // { unitId, result: AgentResult }, если задача исполнялась
}
```

Входные параметры:

| Параметр | Тип | Кто формирует | Время жизни |
|---|---|---|---|
| `deps` | `SessionTurnDeps` | точка сборки (`src/cli.ts` или тест) | один раз на процесс |
| `session` | `SessionState` | `createSession()` / цикл REPL | весь диалог |
| `utterance` | `string` | readline / вход теста | одна строка |

`SessionTurnDeps` состоит из двух независимых наборов:

```ts
interface SessionTurnDeps {
  sessionAgent: SessionAgentDeps; // агент интерпретации и его инструменты обзора
  task: AgentDeps;                // агент задачи, рабочее пространство и лимиты
}
```

- `sessionAgent.agent` — `modelSessionAgent(model)` в production, скриптованная функция в
  тестах;
- `sessionAgent.tools` — `defaultSessionTools`;
- `task.propose` — `modelProposer(model)`, при необходимости обёрнутый для печати каждого
  предложенного действия;
- `task.workspace`, `task.maxTurns`, `task.probe` (`probeSession`), `task.observer`
  (`createObserverDeps`, если observer включён).

Параметра `options` нет: номер реплики хранится в `session.utteranceSeq`.

Порядок внутри одного вызова:

1. `seq = session.utteranceSeq`;
2. `runSessionAgent` интерпретирует строку; модуль сессии открывается, помещается в стек и
   снимается; логос проверяет и применяет операцию;
3. `session.utteranceSeq = seq + 1`;
4. применённая операция распределяется по исполнителю:
   - `respond` — возвращается текст, задача не запускается;
   - `start` — из `pending` извлекается текст, открывается новый модуль задачи и запускается;
5. результат возвращается вызывающему коду.

Если операция отсутствует или отклонена, дерево задачи не изменяется и прогон не выполняется.

### 4.4. Операция `start`

`start` — единственная структурная операция текущего словаря. Она:

- снимает текущий фокус со стека (старый unit остаётся следом; его состояние не закрывается);
- помещает текст новой задачи в `pending`;
- записывается в журнал сессии как `operation`;
- в драйвере превращается в новый task-unit: `runAgent` получает `open: true` и создаёт
  запрос с этим текстом.

Отдельных операций `resume` и `cancel` нет. Возобновление — будущая стратегия; отмена как
операция не вводится, а Esc трактуется как прерывание исполнения, не меняющее IR.

Отказ логоса (например, превышение лимита текста) записывается в журнал сессии событием
`refusal` и виден в L0 (`refused: …`) вместе с reasoning; интерпретация считается завершённой.

#### 4.4.1. Переформулировка и подтверждение

Задача изолирована: она видит только свой unit и не получает L0 сессии или чужие журналы. Перед
`start` агент сессии формулирует текст новой задачи на основе реплики и следов L0, при
необходимости спускаясь в L1–L4. Драйвер передаёт задаче только этот текст; перенос контекста
происходит через формулировку, а не через доступ к памяти. В L0 переформулировка видна как
`request` task-unit'а, а след session-unit'а хранит исходную реплику и операцию со ссылкой на
созданный unit.

Подтверждение необязательно и является политикой интерфейса, а не гейтом IR. Если оно включено,
агент сессии сначала отвечает формулировкой и ждёт «да»; следующий ход с согласием предлагает
`start` с тем же текстом. Драйвер лишь исполняет полученную операцию.

Это соответствует `session_concepts` §4.4 и §6.2.

### 4.5. Изменения движка

- **`runAgent.open`.** В `AgentInput` добавляется необязательный флаг `open?: boolean`:
  открыть модуль запроса и поместить его в стек даже при переданной сессии. Значение по
  умолчанию (`input.session === undefined`) сохраняет текущее поведение. Драйвер передаёт
  `open: true` для `start`.
- **Номер реплики.** `SessionState` получает поле `utteranceSeq: number` (0 при создании).
  Оно считает только обработанные строки и упорядочивает события сессии. Модули задач
  сохраняют локальный `turn`; счётчики независимы.
- **Бюджет задачи.** Каждая новая задача начинается с `startTurn = 0` и получает обычный
  `max_turns`; номер реплики на бюджет не влияет.
- **Синхронизация журнала.** `progress` проверяет закрытие запроса раньше, чем синхронизирует
  журнал модуля в фокусе, поэтому финальный `stop` может быть потерян. После каждого прогона
  драйвер дописывает недостающий хвост `result.events` в `unit.journal` и присваивает
  `unit.turn = result.turns`.

### 4.6. Вывод

Терминал показывает:

- операцию сессии и, при отказе, причину от логоса;
- каждое действие задачи в том виде, в каком его вернул `propose` (CLI оборачивает
  `task.propose`);
- сводку по завершении задачи: идентификатор модуля, причину остановки, число ходов;
- текст операции `respond`.

Задача не выполняется одновременно с приглашением: REPL ожидает возврата `runSessionTurn`.

### 4.7. Сохранение сессии

В данном срезе сессия живёт в памяти только на время процесса. Сохранение в
`.skein/session.json` и загрузка при старте — отдельный шаг.

## 5. Порядок работ

1. **План.** Настоящий документ и английское зеркало; обновить запись в указателе.
2. **Словарь операций.** Оставить `respond` и `start`; убрать `resume`/`cancel`/`redirect`
   из инструментов и union; скорректировать тесты.
3. **Номер реплики.** `SessionState.utteranceSeq`; `createSession`; тесты.
4. **`runAgent.open`.** Поведение по умолчанию не меняется; тест открытия в переданную
   сессию.
5. **Драйвер.** `src/session/driver.ts`; тесты со скриптованными агентами.
6. **REPL.** `src/session/repl.ts` и тест со скриптованным вводом; затем тонкий `src/cli.ts`
   и сценарий `cli`.
7. **Документация.** Обновить `session_concepts`, планы и handoff; выполнить офлайн-набор.

## 6. Тестовые инварианты

- **Сценарий REPL.** Скриптованный ввод: первый `start` запускает `r1`; второй `start`
  снимает `r1` с фокуса и запускает `r2`; `respond` отвечает без прогона; выход завершает
  цикл.
- **Вывод.** Напечатанный текст содержит операцию, идентификатор модуля задачи и причину
  остановки; для `respond` прогон задачи отсутствует.
- **Первый запрос.** `start` без фокуса открывает `r1`, и журнал модуля заканчивается
  событием закрытия.
- **Новый `start`.** Активный unit теряет фокус и остаётся следом; открывается новый модуль;
  `pending` расходуется; состояние старого unit'а не закрывается.
- **Изоляция.** Запрос задачи — только переформулированный текст; в журнале задачи нет
  событий чужих unit'ов.
- **Отказ.** Недопустимая операция не даёт ни прогона, ни события задачи.
- **Синхронизация.** Запрос, закрытый в терминальном состоянии, сохраняет `stop` в журнале
  модуля.
- **Счётчики.** Каждая строка увеличивает `utteranceSeq` на единицу; `result.turns` от него
  не зависит.
- **Детерминизм.** Одна и та же сессия, тот же ввод и скриптованные агенты дают одинаковый
  вывод.

Сценарная проверка: офлайн — `tests/session_scenario.test.ts` (скриптованные агенты);
live-раннер — `tests/sandbox/session-live.ts` (только с `SKEIN_LIVE=true` и go-ahead).

Проверка выполняется командами:

```sh
npm run typecheck
SKEIN_LIVE=false npx vitest run --exclude 'tests/sandbox/**'
```

## 7. Критерии приёмки

- REPL запускается командой `npx tsx src/cli.ts` в каталоге проекта и принимает строки.
- Сценарий из раздела 3 воспроизводится офлайн-тестом со скриптованными агентами.
- Проверка типов и офлайн-набор тестов проходят.
- Ни одно состояние не закрывается иначе как `stop` задачи; `start` не закрывает предыдущую
  задачу.
- `runAgent` без флага `open` работает в точности как прежде.
- Ни одного live- или bench-прогона не выполнено.

## 8. Открытые вопросы

- **Сохранение сессии.** Сейчас только в памяти; `.skein/session.json` — следующий шаг.
- **Ctrl-C.** Прерывание не является операцией IR; нужны обработчик сигнала и решение о
  судьбе идущей задачи. Отложено.
- **Первый запрос.** Первая строка проходит через `SessionAgent`. Прямое открытие первой
  задачи из CLI остаётся возможным упрощением.
- **Переформулировка и подтверждение.** Насколько подробной должна быть формулировка задачи и
  как представлять согласие: ответ `respond` + следующий `start` или отдельная операция.
- **Стратегии возобновления.** Сейчас «продолжить» = `start`; отдельный срез.
- **Вывод хода.** Действия печатает обёрнутый `propose`; потоковая передача токенов и
  результатов инструментов отложена.

## 9. Откат

- Словарь операций, номер реплики, `runAgent.open`, драйвер и REPL входят отдельными
  коммитами.
- Удаление REPL и драйвера оставляет первый срез 4b и `runAgent` нетронутыми.
