# Skein — отчёт по экспериментам (бенч и Harbor)

> Английское зеркало — `docs/bench_report.md`. Это рабочий отчёт об измерениях,
> а не спецификация. Код харнесса — `bench/`, `langgraph/`.

## 1. Зачем

Tier 1 (граф, path-релевантность, узел проверки) реализован, но ценность нигде не
измерена. Цель — снять первые реальные цифры: растёт ли контекст, сколько токенов и
кэша тратится, сколько вызовов LLM, какая траектория, и задействует ли модель
рабочий граф. Результаты — повод решать, что чинить дальше.

## 2. Инструменты

- **`bench/run.ts`** — синтетика `skein-plugin` (короткие задачи): копирует репо
  кейса, гоняет `runAgent` вживую, запускает `check.sh`, считает поведенческую
  метрику `detectLoops` (импортируется из плагина, единый yardstick).
- **`langgraph/graph.ts` + `langgraph.json`** — адаптер Skein под встроенный агент
  `langgraph` в Harbor: Harbor ставит Node и зависимости проекта, запускает граф в
  рабочем каталоге задачи (`/app`) и собирает usage через callbacks.
- **`bench/harbor/*`** — конфиг (шаблон + генератор + `run.sh`), задания лежат вне
  репозитория (`~/.skein-bench/harbor`), чтобы langgraph-агент не стейджил сам себя.

## 3. Метрики

На каждый вызов LLM: `contextChars` (размер проекции), `input/output tokens`,
`cacheRead`/`cache%`, число реальных вызовов, `action`, время. Агрегаты: контекст
first/last/peak/growth, токены, кэш, стоимость, поведенческий `loopScore`/`rereads`,
и counts рабочего графа (claims/decisions/subgoals/checks).

## 4. Результаты

### 4.1 Синтетика (короткие задачи)

`hidden-hypotheses`: reward 1, 9 шагов, `loop=25%`, graph: 1 claim, 0 решений,
0 подцелей. «Повтор» — это повторный `python3 test_report.py` до/после фикса, то
есть перепроверка, а не цикл; baseline просто не перезапускал тест.

`moving-target`: reward 1, 7 вызовов, `loop=0`, контекст 1045 → 2983 симв. (peak
3526, рост +1938), вход 17 782 / выход 600, `cacheRead` 11 648 (66%), graph пуст
(0/0/0).

Наблюдение по кэшу, одинаковое на всех прогонах: `cacheRead` **всегда ровно 1664**
токена за ход — это стабильный системный префикс (system prompt + схема
инструмента). Проекция не кэшируется: её стабильный префикс обрывается сразу на
`goal`/`constraints`, дальше идёт волатильный `frontier`. Как следствие, при росте
контекста доля кэша падает (80% → 58%).

### 4.2 Harbor terminal-bench: `fix-ocaml-gc`

Baseline (сохранённый job `2026-09-26__11-50-39`, opencode): **pass**, 36 шагов,
41 инструмент, пик контекста 60 208 токенов, вход 38 852 / выход 4 220, `loop=0`,
`rereads=3`, `track=0`.

Skein, два прогона:

- **Прогон 1** (17:26): упал на `ENOENT` (см. §5), но verifier дал **reward 1** —
  то есть фикс был применён до падения. Turn-логов нет (процесс умер).
- **Прогон 2** (17:43): чистый выход, но **reward 0**. 60 ходов, действия:
  read 17, grep 18, run 23, **edit 1**, finish 1. Вход 290 564 / выход 11 536,
  `cacheRead` 129 792 (44.7%), контекст 1601 → 11 788 симв. (peak 26 281, рост
  +10 187), `checks=23`, **graph пуст (0 claims / 0 decisions / 0 subgoals)**,
  стоимость 3.76 ₽.

Итог: агент сделал один `edit` и дальше ~58 ходов крутил read/grep/run, не
сойдясь, и закончил `finish`. Нестабильность высокая: та же задача в прогоне 1
прошла, в прогоне 2 — нет.

## 5. Проблемы (что сломалось/мешает)

1. **Рабочий граф не задействован на длинной задаче.** 0 claims, 0 decisions,
   0 subgoals. Модель не заводит гипотез → отказы, устаревание проверок и
   path-релевантность не работают; поведение вырождается в плоский read/grep/run.
2. **Свидетельство = весь воркспейс — непрактично и с гонками.** `run` хэширует
   **каждый** файл воркспейса (дважды: до и после команды), чтобы построить
   witness. На большом репозитории с активной сборкой это дорого (ходы до 33 с) и
   ломается: файл-времянка сборки исчезает между листингом и чтением → `ENOENT`
   роняет агента (прогон 1).
3. **Контекст растёт внутри прогона.** В основном из-за `recent` (сырой вывод
   инструментов: тесты/сборки). Пик 26k символов. Кэшируется только системный
   префикс, поэтому рост контекста = падение cache%.
4. **`loopScore` вводит в заблуждение на коротких задачах**: повторная проверка
   (тот же тест до/после фикса) считается «повтором».

## 6. Гипотезы (почему так)

1. **Главная: промпт не оптимизирован под наш харнесс.** `SYSTEM_PROMPT`
   (`src/loop/propose.ts`) — один общий блок, писавшийся до Tier 1 и никогда не
   настраивавшийся под реальные длинные задачи. Он:
   - не требует заводить claim/подцель **до** нетривиального действия, поэтому
     граф пуст и нет памяти о том, что уже пробовали;
   - не описывает рабочую стратегию для длинной задачи (где работать, чем
     проверять, как сходить с неверной ветки);
   - из-за «одно действие за ход» без claims агент перечитывает/перезапускает одно
     и то же (17 read / 18 grep / 23 run почти без прогресса после одного edit).
   Мы промпты сознательно не трогали и не мерили — это первое, что надо чинить.
2. **Модель воспринимает агента как обычный read/grep/run-инструмент.** Нет
   структурного гейта, который заставил бы пользоваться IR, поэтому на дешёвой
   стратегии она и остаётся.
3. **Инструменты беднее, чем у baseline.** Только `edit` find/replace (у opencode
   — патчи/больше инструментов), `run` считается «проверкой» даже без claims
   (мусорные `check`-узлы), witness непрактичен.
4. **Рост `recent`** — прямое следствие п.1: при бессистемном переборе в окно
   попадают большие выводы.

## 7. Что делать дальше (пункт B)

1. **Пересмотреть промпт под харнесс** (приоритет): явно описать инструменты и
   рабочий процесс для длинных задач, потребовать фиксировать claim/подцель перед
   действием, описать, как проверять и как отказываться от ветки.
2. **Рассмотреть активный гейт** (как в плагине): нельзя `edit`/`run` без
   заведённого claim/подцели. Структурный гейт §5 из Tier 1 оказался недостаточным
   на длинной задаче.
3. **Убрать хрупкость/стоимость witness**: не хэшировать весь воркспейс; хотя бы
   не считать «проверкой» `run` без claims и не тащить билд-артефакты.
4. После правок — повторить `fix-ocaml-gc` и прогнать 2–3 задачи, сравнить с
   сохранённым baseline.

Отложено отдельно: оптимизация проекции под стабильный префикс/кэш
(`docs/plans/implementation_plan_ru.md`, бэклог).
