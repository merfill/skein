# Skein — сквозной пример: дерево и контекст шаг за шагом

> **Заметка (лента состояний).** Дерево и таблицы ниже отражают текущую модель: состояние
> (`move`) И ЕСТЬ его цель. `move { state, what, done }` объявляет остров работы, цель состояния
> (`what`) и условие остановки (`done`); план состояния висит прямо на `move` и засевается первым
> обычным `apply`; `stop` закрывает состояние и вынуждает переход; `stop` терминального состояния
> (`finish`) завершает запрос. Контекст — лента сообщений, а состояние рендерится как
> `Start state <label>` / инструкция / цель / `Finish state <label> — <why>` (запрос — второе
> сообщение ленты, на каждом ходу). Актуальная форма — `docs/ir_semantics_ru.md`,
> справочник операторов — `docs/ir_operations_ru.md`, планы дизайна —
> `docs/plans/archive/goal_into_move_plan_ru.md` и `docs/plans/archive/state_protocol_plan_ru.md`;
> as-built — `docs/ir_ru.md`.

> Английское зеркало — `docs/walkthrough.md`.

## Преамбула

**Что такое Skein.** Skein — это агент для программирования, который хранит знание не в
переписке с моделью, а в **журнале фактов**, и на каждом ходу строит для модели
**проекцию** — строго определённый срез текущего состояния. Контекст модели — свежая
проекция на каждом ходу, собираемая из дерева заново.

**Докса и логос.** Идейная основа взята из противопоставления *доксы* и *логоса*:

- **докса** — это языковая модель. Она хорошо придумывает, но не отвечает за
  истинность придуманного, поэтому только *предлагает* один или несколько ходов за ход (батч);
- **логос** — это детерминированный движок вместе с инструментами и окружением. Он
  исполняет команды, записывает их результаты в журнал, пересчитывает производные
  факты и строит проекцию. Логос не выдумывает содержание — он решает, допустим ли
  предложенный ход и что из него следует.

Отсюда главный принцип: **докса предлагает — логос решает.** Модель сама никогда не
объявляет работу выполненной: это делают результаты инструментов (прежде всего код
возврата команды) и правила движка.

**Арбитр.** Над доксой и логосом стоит **арбитр** — внешняя инстанция. В текущей
модели это пользователь (человек или харнес, который оценивает результат). Арбитр
задаёт самый первый запрос и принимает итоговый результат снаружи. Он не участвует в
приёмке отдельных состояний: состояние закрывает докса через `stop`.

**Что закрывает работу.** Единственная рамка, которую можно закрыть, — это **состояние**.
Состояние закрывается **только явным ходом `stop`** — гейта по критерию нет. У запроса нет
собственного `stop`: он интерпретируется **ровно один раз** как состояние (`move`) или
отклоняется (`unactionable`), и прогон **завершается, когда остановлено его терминальное
состояние** (или когда запрос отклонён).

**Зачем этот документ.** Формальные документы описывают модель по частям. Здесь
**главное — раздел 4**: одна задача прослеживается целиком, от запроса до закрытия,
ход за ходом, с показом того, что происходит в журнале, в дереве, в производных фактах
и в проекции. Раздел 5 добавляет отдельные особые случаи, которых нет в основном
прогоне (недейственный запрос, корректирующий цикл, нерешающий прогон, версии файлов).

**Как читать.** Это иллюстрация, а не второй формализм. Источник истины —
`docs/ir_semantics_ru.md`; реализация — `docs/ir_ru.md`; справочник операторов —
`docs/ir_operations_ru.md`; описание проекции — `docs/projection_ru.md`. Если текст и
код расходятся, прав код вместе с `docs/ir_semantics_ru.md`.

## 1. Понятия

Ниже — словарь терминов, которые встречаются в тексте и таблицах. Английские слова в
обратных кавычках — это имена из кода; их мы не переводим.

### 1.1 Роли

| Термин | Значение |
|---|---|
| **докса** | языковая модель; предлагает один или несколько ходов за ход (батч) |
| **логос** | детерминированный движок: исполняет команды, ведёт журнал, пересчитывает факты, строит проекцию |
| **арбитр** | внешняя инстанция: задаёт первый запрос и принимает итоговый результат снаружи |

### 1.2 Слои данных

| Термин | Значение |
|---|---|
| **журнал** (`journal`) | неизменяемый список событий — единственный источник истины; только дополняется |
| **состояние** (`state`) | результат свёртки журнала (`fold`): узлы, рёбра, порядок пунктов, стек обхода, версии файлов |
| **проекция** (`projection`), он же **контекст** | строго определённый срез состояния, который видит докса на текущем ходу |
| **узел** | объект дерева: `request`, `move`, `plan`, `item`, `action`, `observation`, `stop`, `constraint`, `file`, `unactionable` |
| **ребро** | связь между узлами: `move`, `plan`, `items`, `alts`, `result`, `mutates`, `stop`, `unactionable` |

### 1.3 Работа

| Термин | Значение |
|---|---|
| **запрос** (`request`) | неструктурированная мотивация пользователя; корень дерева; интерпретируется **ровно один раз** как состояние (`move`) или отклоняется (`unactionable`); у него нет плана и `stop`; прогон завершается, когда остановлено его терминальное состояние |
| **состояние** (`move`) | остров работы, объявленный доксой: `state` (имя острова) + `what` (текст цели этого состояния); состояние И ЕСТЬ его цель |
| **план** (`plan`) | контейнер пунктов; пункт плана — всегда **действие** (`action`); порядок задаёт список, и **последний** пункт — текущий |
| **действие** (`action`) | один вызов инструмента (`read`/`grep`/`list`/`edit`/`write`/`bash`/`webfetch`/`apply_patch`); исполняется по одному за ход |
| **наблюдение** (`observation`) | записанный результат: окно чтения, вывод запуска, код возврата |
| **альтернативы** (`alternatives`) | контейнер вариантов: пересмотр пункта плана (новая попытка становится самым новым вариантом пункта) |
| **`stop`** | терминальный ход: закрывает текущее состояние (или, на терминальном состоянии, завершает запрос) |
| **`decline`** | ход, который фиксирует недейственный запрос (`unactionable`) и завершает прогон |

### 1.4 Запуск и его вывод

| Термин | Значение |
|---|---|
| **действие** | один вызов инструмента; **первый** вызов состояния засевает план и исполняется сразу; часто одна простая foreground-команда |
| **`exitCode`** | код возврата: `0` — успех, не ноль — провал, отсутствует — вердикта нет (таймаут) — обычный вывод, не гейт |

Запуск — обычное `observation`; код возврата ничего не закрывает — докса решает, что
состояние готово, и вызывает `stop`.

### 1.5 Факты, выводимые из журнала

| Факт | Значение |
|---|---|
| **`actionExecuted`** | у действия есть ребро `result` или `mutates` |
| **`hasStopped`** | у `move` состояния есть ребро `stop` к узлу `stop` (оно закрыто) |

У запроса нет собственного производного факта «улажен»: его завершённость читается
напрямую по терминальному состоянию — прогон завершается, когда остановлен
терминальный `move`.

### 1.6 Статус узла

Хранимого статуса у узла нет; факты производны:

- действие `executed`, когда оно произвело результат;
- состояние закрыто, когда у его `move` есть ребро `stop`.

Статусов «достигнуто» или «опровергнуто» на узлах нет и гейта по критерию нет.

### 1.7 Обход и допустимые ходы

- **стек**, он же **ветка** (`path`) — запрос плюс текущее состояние; верх стека — **фокус**;
- **курсор** — индекс первого невыполненного пункта плана;
- **соседний ряд** — упорядоченные варианты одного уровня (пункты плана или варианты альтернатив); **последний** ребёнок — текущий;
- **допустимые ходы** (`applicable`) — набор ходов, разрешённых правилами в текущем фокусе; докса выбирает один из них; из него собирается предложенная поверхность инструментов;
- **`descend` / `return`** — движение фокуса вниз по дереву и возврат на уровень выше.

### 1.8 Отказы, мир и адресация

- **отказ** (`record_rejection`) — запись о том, что предложение отклонено, с причиной;
- **`mutate`** — событие об изменении файла; повышает **версию** файла;
- **`recall` / `search`** — адресное чтение: тело прошлого результата достаётся по `id` (окно) или ищется по паттерну, без повторного вызова команды.

## 2. Четыре уровня, на одной картинке

Весь цикл работы укладывается в четыре ступени: журнал накапливается, состояние из него
выводится, проекция из состояния строится, докса по проекции предлагает следующий ход.

```
                    только дополняется   чистая         чистая
  предложение доксы ─▶ журнал (Event[]) ──fold──▶ Состояние ──project──▶ Контекст ──▶ докса
        ▲                                                                       │
        └────────── один или несколько операторов за ход, выбранных из допустимых ходов ──┘
```

- **Журнал** — `Event[]`, единственная истина (`add_node`, `add_edge`, `descend`,
  `return`, `mutate`, `record_rejection`).
- **Состояние** — `fold(журнал)`: узлы, рёбра, порядок контейнера, стек обхода, версии
  файлов. Узлы никогда не меняются.
- **Контекст** — `project(состояние)`: лента сообщений, ситуация, глобальные ограничения,
  фронтир (допустимые ходы), инструкция наблюдения.
- **Докса** — читает `Context` и предлагает один или несколько операторов (батч) (`move` /
  `apply` / `stop` / `decline`; `recall`/`search` — адресация только для чтения).

Ничего из того, что докса «думает», не хранится. План — это заметка для себя; след
работы — дерево.

## 3. Нотация

| символ | смысл |
|---|---|
| `R` | корневой `request` |
| `I`, `I0`, `I1`, `H` | состояния (`move`): фокус острова и терминальный `finish` |
| `a1`, `a2` | пункты плана (`action`) |
| `obs` | `observation` (окно чтения, вывод запуска вместе с кодом возврата) |
| `→` | фокус движется; `+` узел или ребро создаётся; `⟂` отказ (`record_rejection`) |
| `open` / `executed` / `stopped` | три отображаемых состояния (`stateOf`) |

## 4. Сквозной пример: одна задача от начала до конца

Это главный раздел. Задача:

> «Я сломал сборку; проверь командой `make test`.»

Одно ограничение `k1` — не трогать тесты. Прогон длится 16 ходов (0–15). Первая попытка
не помогает; докса **остаётся в том же состоянии** — добавляет ещё один пункт и проверяет
снова — и делает `stop` по состоянию, когда его `Done when` выполнен. Затем она проходит
остальные состояния и завершается в `finish`. В каждой строке показано, что делает докса,
что за событие дописывает логос, как растёт дерево, какие факты появляются и что докса
увидит на следующем ходу.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 0 | `[R]` | — *(запрос задаёт арбитр)* | `+ request R {text}` | `rootId=R` | `situation=request`; `applicable=[move, decline]` |
| 1 | `[R] → [R,I0]` | `move I0 {state:"reproduction", what:"reproduce the failure: make test fails"}` | `+ move I0 {state, what}`; `+ move R→I0` | `I0=open`; `situation=plan` | `path=[R, I0]`; `I0.what="reproduce the failure…"`; план пуст; `applicable=[apply, stop]` |
| 2 | `[R,I0]` | `apply bash {command:"make test"}` (ПЕРВЫЙ пункт плана состояния) | `+ plan Q0`; `+ items Q0→a1`; `+ action a1 "make test"`; `+ obs o1 {command:"make test", exitCode:1}`; `produces a1→o1` | `a1=executed`; `situation=working` | `lastResult={command:"make test", exitCode:1}`; `applicable=[apply, stop]` |
| 3 | `[R,I0]` | `stop {why:"the failure is reproduced"}` | `+ stop s1`; `+ stop I0→s1` | `I0=stopped`; `situation=transition` | `applicable=[move]` — состояние завершено; предложен только `move` |
| 4 | `[R,I0] → [R,I1]` | `move I1 {state:"localization", what:"name the file, the line and the exact change"}` | `+ move I1`; `+ move R→I1` | `I1=open`; `situation=plan` | `path=[R, I1]`; план пуст; `applicable=[apply, stop]` |
| 5 | `[R,I1]` | `apply grep {pattern:"run-length"}` (первый пункт — локализовать) | `+ plan Q1`; `+ items Q1→a2`; `+ action a2 "grep …"`; `+ obs o2` | `a2=executed` | `lastResult` — совпадения в `runtime/shared_heap.c` |
| 6 | `[R,I1]` | `apply read runtime/shared_heap.c [40-120]` | `+ action a3`; `+ items Q1→a3`; `+ obs o3 {ref, version:v1}` | `observed(file)=v1` | `lastResult` — окно кода |
| 7 | `[R,I1]` | `stop {why:"the exact change is named"}` | `+ stop s2`; `+ stop I1→s2` | `I1=stopped`; `situation=transition` | `applicable=[move]` |
| 8 | `[R,I1] → [R,I2]` | `move I2 {state:"patch", what:"apply the fix"}` | `+ move I2`; `+ move R→I2` | `I2=open`; `situation=plan` | `path=[R, I2]`; `applicable=[apply, stop]` |
| 9 | `[R,I2]` | `apply edit runtime/shared_heap.c {oldString, newString}` (первый пункт) | `+ plan Q2`; `+ items Q2→a4`; `+ action a4 {find,replace}`; `+ mutates a4→file`; `mutate v1→v2` | `currentVersion(file)=v2` | `lastResult={kind:"action", ref:"…"}` |
| 10 | `[R,I2]` | `stop {why:"the change is in the workspace"}` | `+ stop s3`; `+ stop I2→s3` | `I2=stopped`; `situation=transition` | `applicable=[move]` |
| 11 | `[R,I2] → [R,I3]` | `move I3 {state:"verification", what:"the acceptance command make test passes"}` | `+ move I3`; `+ move R→I3` | `I3=open`; `situation=plan` | `path=[R, I3]`; `applicable=[apply, stop]` |
| 12 | `[R,I3]` | `apply bash {command:"make test"}` (первый пункт — команда приёмки) | `+ plan Q3`; `+ items Q3→a5`; `+ action a5 "make test"`; `+ obs o5 {command:"make test", exitCode:0}` | `a5=executed` | `lastResult={command:"make test", exitCode:0}` |
| 13 | `[R,I3]` | `stop {why:"the acceptance command passes"}` | `+ stop s4`; `+ stop I3→s4` | `I3=stopped`; `situation=transition` | `applicable=[move]` |
| 14 | `[R,I3] → [R,H]` | `move H {state:"finish"}` (без `what` — терминальное состояние) | `+ move H {state}`; `+ move R→H` | `H=open`; `situation=terminal` | `applicable=[stop]` |
| 15 | `[R,H]` | `stop {why:"done"}` | `+ stop s5`; `+ stop H→s5`; прогон завершается | `H=stopped`; `hasStopped(H)=true` | сессия завершается с причиной `request_addressed` |

### 4.1 Итоговое дерево

После хода 15 дерево выглядит так. Состояния запроса висят на нём **плоскими детьми** по
ребру `move`, в порядке обхода. У каждого состояния план висит прямо на его `move` по
ребру `plan`, а пункты плана связаны рёбрами `items` (порядок задаёт список, а не форма
дерева); состояние закрыто ребром `stop` от его `move` к узлу `stop`. Контейнера
альтернатив у запроса нет, и ребра `chosen` нет нигде: порядок контейнера — это его
список, а последний ребёнок — текущий.

```
R  request "I broke the build; verify with make test"      (корень: без плана и stop)
│  move
├─▶ I0  move {state:"reproduction", what:"reproduce the failure: make test fails"}   stopped ✔
│      │  plan
│      └─▶ Q0  plan   [ a1 ]
│      │      └─ items ─▶ a1  action "make test"     executed → obs o1 (exit 1)
│      └─ stop ─▶ s1  stop {why:"the failure is reproduced"}
├─▶ I1  move {state:"localization", what:"name the file, the line and the exact change"}   stopped ✔
│      │  plan
│      └─▶ Q1  plan   [ a2, a3 ]
│      │      ├─ items ─▶ a2  action "grep …"        executed → obs o2
│      │      └─ items ─▶ a3  action "read …"        executed → obs o3 (ref@v1)
│      └─ stop ─▶ s2  stop
├─▶ I2  move {state:"patch", what:"apply the fix"}   stopped ✔
│      │  plan
│      └─▶ Q2  plan   [ a4 ]
│      │      └─ items ─▶ a4  action "edit …"        executed → mutates file v1→v2
│      └─ stop ─▶ s3  stop
├─▶ I3  move {state:"verification", what:"the acceptance command make test passes"}   stopped ✔
│      │  plan
│      └─▶ Q3  plan   [ a5 ]
│      │      └─ items ─▶ a5  action "make test"     executed → obs o5 (exit 0)
│      └─ stop ─▶ s4  stop
└─▶ H   move {state:"finish"}                       stopped ✔ (терминальное; его stop завершает запрос)
       └─ stop ─▶ s5  stop
```

Порядок пунктов плана задаёт **список** (порядок добавления), а не форма дерева: рёбра
`items` показывают принадлежность контейнеру, а порядок — это порядок элементов списка, и
**последний** ребёнок — текущий. Проекция в каждый момент показывает **не** это дерево
целиком, а только ленту сообщений текущего состояния, ограничения и допустимые ходы. Всё
остальное — на расстоянии одного `recall`/`search`.

### 4.2 На что обратить внимание в основном прогоне

- **Состояние И ЕСТЬ его цель.** `move { state, what }` несёт и остров работы, и текст цели
  состояния; отдельного узла цели нет. План висит на `move`.
- **Первый пункт плана — обычный вызов инструмента.** Отдельного оператора конкретизации
  нет: первый `apply` после `move` засевает план и исполняется сразу (ходы 2, 5, 9, 12).
- **`stop` закрывает состояние.** После `stop` состояние завершено; единственный допустимый
  ход — переход `move` (ходы 3, 7, 10, 13). Поэтому поверхность не может продолжать
  предлагать работу после того, как состояние сделано.
- **Гейта по критерию нет.** `stop` принимается на открытом состоянии; докса сама решает,
  когда `Done when` состояния выполнен (инструкция наблюдения повторяет его после каждого
  результата инструмента). Провал — это факт, а не закрытие: докса добавляет ещё пункт.
- **Запрос завершается на терминальном состоянии.** `stop` на рабочем состоянии не завершает
  запрос; это делает только `stop` терминального `move` `finish` (ход 15).
- **Поверхность модели — это фронтир.** На запросе — `move`/`decline`; на открытом
  состоянии — словарь `apply` плюс `stop`; на завершённом — только `move`; на терминальном —
  `stop`; `recall`/`search` всегда.
- **Ничего не решается «само».** Движок не запускает план, не закрывает состояния по коду
  возврата и не выбирает шаги — на каждом ходу один или несколько ходов делает докса.

### 4.3 Как устроено дерево: план, альтернативы и `stop`

**План.** У состояния ровно один план: ребро `plan` ведёт от `move` к узлу `plan`, а пункты
плана связаны с планом рёбрами `items`. Порядок пунктов задаётся не рёбрами, а **списком**
детей узла `plan`: рёбра показывают принадлежность, список — последовательность. Ребра
`chosen` **нет**: текущий пункт контейнера — это просто его **последний** ребёнок. Пункт
плана — всегда действие (`action`); состояние пунктом плана быть не может.

**Альтернативы.** Контейнер `alternatives` — это способ «переделать, не переписывая». Он
вешается на **пункт плана** (история редакций шага, который не сработал). Ребра `chosen`
нет: **текущий вариант — последний ребёнок**; остальные просто не текущие и остаются в
дереве как «то, что не сработало».

Когда докса выполняет команду, **отличную** от текущего невыполненного пункта, движок не
переписывает пункт, а вешает на него ребро `alts` и добавляет туда новое действие как
**самый новый (последний) вариант**:

```
состояние (move)
│  plan
└─▶ Q  plan   [ список пунктов: s, … ]
       │
       └─ items ─▶ s  action "cat HACKING.adoc"          (не сработал)
                  │  alts
                  └─▶ a'  action "make test"  (самый новый = текущий; выполняется)
```

**`stop`.** Ход `stop` действует **на состояние**. Движок добавляет узел `stop` и проводит
ребро `stop` от `move` состояния к этому узлу — так состояние помечается закрытым; stop не
является пунктом плана. Гейта по критерию нет: `stop` принимается на открытом состоянии.
`stop` на рабочем состоянии вынуждает переход (следующий допустимый ход — `move`);
`stop` на терминальном `move` `finish` завершает запрос. У запроса `stop` нет.

## 5. Особые случаи

В основном прогоне не встретились четыре ситуации. Разберём их отдельно, каждый раз
как небольшой фрагмент.

### 5.1 Недейственный запрос (`decline`)

Запрос вроде «привет, дядя Вася» не содержит выполнимой задачи. Докса не выдумывает
состояние; она отклоняет запрос.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 0 | `[R]` | — *(запрос задаёт арбитр)* | `+ request R {text}` | `rootId=R` | `applicable=[move, decline]` |
| 1 | `[R]` | `decline {why:"there is no actionable task in the request"}` | `+ unactionable U {why}`; `+ unactionable R→U`; прогон завершается | у запроса нет состояния; `unactionableOf(R)=U` | сессия завершается; у запроса остаётся пометка `unactionable` |

`decline` принимается только на **свежем** запросе (у которого ещё нет ни состояния, ни
`unactionable`). Он ничего не закрывает: он фиксирует, что намерение запроса невыполнимо, и
на этом прогон останавливается.

Отметим парное правило: **провал команды — это не `stop`.** После неудачной проверки
докса продолжает работать в том же состоянии (дописывает пункты и проверяет снова, как в
разделе 4); она не должна закрывать состояние и не переинтерпретирует запрос.

### 5.2 Корректирующий цикл: провалившаяся верификация возвращает в локализацию

У острова `verification` есть корректирующий переход: когда команда приёмки проваливается,
следующее состояние — `localization`, с новой уликой. Докса не переписывает состояние — она
делает `stop` по состоянию верификации и `move` в новое состояние локализации.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| k | `[R,I3]` | `apply bash {command:"make test"}` | `+ action`; `+ obs {command:"make test", exitCode:1}` | `I3` остаётся `open` | провал; команда приёмки всё ещё падает |
| k+1 | `[R,I3]` | `stop {why:"it still fails; back to localization"}` | `+ stop`; `+ stop I3→stop` | `I3=stopped`; `situation=transition` | `applicable=[move]` |
| k+2 | `[R,I3] → [R,I4]` | `move I4 {state:"localization", what:"name the change given the new failure"}` | `+ move I4`; `+ move R→I4` | `I4=open`; `situation=plan` | `path=[R, I4]` |

**Состояния — плоские дети запроса**: новое состояние входит как свежий `move`-ребёнок
запроса, никогда не вложенное в другое состояние. Провалившееся состояние `verification`
остаётся в дереве как «то, что не сработало»; обход продолжается из нового состояния
локализации.

### 5.3 Нерешающий прогон (таймаут)

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 1 | `[R,I3]` | `apply bash {command:"make test", timeout:60000}` | исполнить `make test`; процесс убит таймаутом; `+ obs{**нет exitCode**}` | вердикта нет: `I3` остаётся `open` | `lastResult={command:"make test", error:"…timed out…"}`; модель может повторить |
| 2 | `[R,I3]` | `apply bash {command:"make test"}` (повтор) | новое наблюдение | — | это **не** повтор: таймаут не принёс знания |

`exitCode` — это весь сигнал «прошло или нет». Его **отсутствие** (таймаут, сигнал без
контролируемого выхода) означает «вердикта нет»: состояние остаётся `open`, и модель может
повторить ту же команду — незавершившийся запуск не является ни повтором, ни прогрессом.
Запуск никогда не оракул закрытия: состояние закрывается только через `stop`.

### 5.4 Мир, версии и адресация

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| r | `[R,I]` | `apply read runtime/shared_heap.c [10-80]` | `+ action`; `+ obs{ref, version:v1}`; `result` | `observed(file)=v1` | окно входит в ленту как `tool`-результат |
| e | `[R,I]` | `apply edit runtime/shared_heap.c` | `+ action`; `+ mutates`; `mutate v1→v2` | `currentVersion(file)=v2`; чтение `v1` теперь устарело | устаревшее чтение **не** показывается активным содержанием |
| q | `[R,I]` | `recall {id:"obs:…"}` | узла нет; тело возвращается | — | тело входит в ленту транзиентным `tool`-результатом |

Изменение файла порождает событие `mutate` (повышение версии); актуальность
**вычисляется**, а не хранится флагом. Факт чтения о `v1` не удаляется — он просто
перестаёт принадлежать активному содержанию, и устаревшее содержание никогда не
показывается активным. Всё адресуемо: тело прошлого результата достаётся по `id` через
`recall`, без повторного вызова. Поэтому повторная команда с теми же входами и неизменным
миром отклоняется — знание уже есть, возьмите его по адресу.

## 6. Что иллюстрирует этот сквозной пример

1. **Контекст — это проекция, а не лента собственных слов модели.** На каждом ходу докса
   видит ленту сообщений, собранную из дерева, а не накапливающийся транскрипт.
2. **Докса предлагает — логос решает.** Докса выбирает ход из допустимых; правила и
   производные факты решают, состоится ли он.
3. **Закрытие ровно одно — `stop`, и только доксы.** Состояние завершается своим `stop`;
   запрос завершается, когда остановлено его терминальное состояние, либо когда запрос
   отклонён как недейственный. Гейта по критерию нет.
4. **Состояние И ЕСТЬ его цель.** `move { state, what }` объявляет состояние и его цель;
   план висит на `move` и засевается первым `apply`.
5. **Поверхность модели — это фронтир.** В каждой ситуации предложены ровно допустимые ходы
   (`Context.applicable`), поэтому отклоняемый ход никогда не предлагается.
6. **На узлах нет истины.** Есть только `open` / `executed` / `stopped` плюс производные
   факты; провал — это факт, а не статус.
7. **След монотонен.** Пересмотр или добавленное состояние только добавляют узлы; ничего не
   переписывается — провалившийся шаг остаётся видимым как «то, что не сработало», а первое
   состояние запроса создаётся один раз через `move`.
8. **Всё адресуемо.** Тела результатов живут в журнале и вспоминаются по `id`; контекст
   остаётся ограниченным срезом.
