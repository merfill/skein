# Skein — сквозной пример: дерево и контекст шаг за шагом

> **Актуально на 2026-10-27.** Состояние (`move`) И ЕСТЬ его цель: `move { state, what?,
> done?, notes? }` объявляет остров работы; `what` — непроверенная догадка доксы о конкретном
> предмете (необязательна), `done` — переопределение критерия (необязательно), `notes`
> записываются, но на ленту не попадают. В блоке состояния рендерится **`island.what`** как
> `Goal:` и, если задана, догадка доксы (`Your earlier guess (may be wrong): …`); per-turn
> хвост несёт критерий и closure. Маркеры `Start state` / `Finish state` —
> **`system`**, transition-инструкция — `system`, запрос — второе сообщение ленты на каждом ходу.
> `recall`/`search` доступны только пока состояние открыто; провал Verification по умолчанию
> ведёт в **Patch** (Localization — только если объект/координаты под сомнением), и движок
> откатывает последний Patch.
>
> Источник истины — `docs/ir_semantics_ru.md`; справочник операторов —
> `docs/ir_operations_ru.md`; проекция — `docs/projection_ru.md`; as-built — `docs/ir_ru.md`.
> Английское зеркало — `docs/walkthrough.md`.

## Преамбула

**Что такое Skein.** Skein — агент для программирования, который хранит знание не в переписке
с моделью, а в **журнале фактов**, и на каждом ходу строит **проекцию** — строго
определённый срез текущего состояния. Контекст модели — свежая проекция на каждом ходу,
собираемая из дерева заново.

**Докса и логос.** Идейная основа — противопоставление *доксы* и *логоса*:

- **докса** — языковая модель. Она хорошо придумывает, но не отвечает за истинность
  придуманного, поэтому только *предлагает* один или несколько ходов за ход (батч);
- **логос** — детерминированный движок с инструментами и окружением. Он исполняет команды,
  записывает результаты в журнал, пересчитывает производные факты и строит проекцию. Логос
  не выдумывает содержание — он решает, допустим ли ход и что из него следует.

Отсюда главный принцип: **докса предлагает — логос решает.** Модель сама не объявляет
работу выполненной: состояние закрывает её `stop`, а провал — это факт инструмента, а не
статус.

**Арбитр.** Над доксой и логосом стоит **арбитр** — внешняя инстанция (пользователь или
харнес). Он задаёт первый запрос и принимает результат снаружи; в приёмке отдельных
состояний не участвует.

**Что закрывает работу.** Единственная закрываемая рамка — **состояние**. Оно закрывается
**только явным `stop`**; гейта по критерию нет. У запроса нет своего `stop`: он
интерпретируется ровно один раз (`move` или `decline`), а прогон завершается, когда
остановлено терминальное состояние `end` (или запрос отклонён).

**Зачем этот документ.** Формальные документы описывают модель по частям. Здесь главное —
раздел 4: одна задача прослеживается целиком, от запроса до закрытия, с журналом, деревом,
производными фактами и проекцией. Раздел 5 добавляет особые случаи (decline, корректирующий
цикл Verification, таймаут, версии/адресация).

**Как читать.** Это иллюстрация, а не второй формализм. Если текст и код расходятся, прав
код вместе с `docs/ir_semantics_ru.md`.

## 1. Понятия

### 1.1 Роли

| Термин | Значение |
|---|---|
| **докса** | языковая модель; предлагает один или несколько ходов за ход (батч) |
| **логос** | детерминированный движок: исполняет команды, ведёт журнал, пересчитывает факты, строит проекцию |
| **арбитр** | внешняя инстанция: задаёт первый запрос и принимает итоговый результат снаружи |

### 1.2 Слои данных

| Термин | Значение |
|---|---|
| **журнал** (`journal`) | неизменяемый список событий — единственный источник истины; только дополняется |
| **состояние** (`state`) | результат свёртки журнала (`fold`): узлы, рёбра, порядок пунктов, стек обхода, версии файлов |
| **проекция** (`projection`), он же **контекст** | строго определённый срез состояния, который видит докса на текущем ходу |
| **узел** | объект дерева: `request`, `move`, `plan`, `item`, `action`, `observation`, `stop`, `constraint`, `file`, `unactionable` |
| **ребро** | связь между узлами: `move`, `plan`, `items`, `alts`, `result`, `mutates`, `stop`, `unactionable` |
| **события мира** | `mutate` (изменение файла), `revert` (откат последнего Patch) |

### 1.3 Работа

| Термин | Значение |
|---|---|
| **запрос** (`request`) | неструктурированная мотивация пользователя; корень дерева; интерпретируется **ровно один раз** как состояние (`move`) или отклоняется (`unactionable`); у него нет плана и `stop`; прогон завершается, когда остановлено его терминальное состояние |
| **состояние** (`move`) | остров работы: `state` (имя острова) + необязательные `what` (артикуляция доксы), `done` (переопределение критерия), `notes` (записываются, но не рендерятся); состояние И ЕСТЬ его цель |
| **план** (`plan`) | контейнер пунктов; пункт плана — всегда **действие** (`action`); порядок задаёт список, и **последний** пункт — текущий |
| **действие** (`action`) | один вызов инструмента (`read`/`grep`/`list`/`edit`/`write`/`bash`/`webfetch`/`apply_patch`); за ход их может быть несколько — движок исполняет их по порядку |
| **наблюдение** (`observation`) | записанный результат: окно чтения, вывод запуска, код возврата |
| **альтернативы** (`alternatives`) | контейнер вариантов: пересмотр пункта плана (новая попытка становится самым новым вариантом пункта) |
| **`stop`** | терминальный ход: закрывает текущее состояние (или, на терминальном состоянии, завершает запрос) |
| **`decline`** | ход, который фиксирует недейственный запрос (`unactionable`) и завершает прогон |
| **`revert`** | событие движка: на переходе из провалившейся Verification откатывает последний Patch и обновляет версии файлов |

### 1.4 Запуск и его вывод

| Термин | Значение |
|---|---|
| **действие** | один вызов инструмента; **первый** вызов состояния засевает план и исполняется сразу |
| **`exitCode`** | код возврата: `0` — успех, не ноль — провал, отсутствует — вердикта нет (таймаут) — обычный вывод, не гейт |

Запуск — обычное `observation`; код возврата ничего не закрывает — докса решает, что
состояние готово, и вызывает `stop`.

### 1.5 Факты, выводимые из журнала

| Факт | Значение |
|---|---|
| **`actionExecuted`** | у действия есть ребро `result` или `mutates` |
| **`hasStopped`** | у `move` состояния есть ребро `stop` к узлу `stop` (оно закрыто) |
| **версия файла** | повышается событием `mutate`; `revert` возвращает версию к pre-patch |

У запроса нет собственного факта «улажен»: его завершённость читается по терминальному
состоянию — прогон завершается, когда остановлен терминальный `move`.

### 1.6 Статус узла

Хранимого статуса у узла нет; факты производны:

- действие `executed`, когда оно произвело результат;
- состояние закрыто, когда у его `move` есть ребро `stop`.

Статусов «достигнуто» или «опровергнуто» на узлах нет; гейта по критерию нет.

### 1.7 Обход и допустимые ходы

- **стек**, он же **ветка** (`path`) — запрос плюс текущее состояние; верх стека — **фокус**;
- **курсор** — индекс первого невыполненного пункта плана;
- **соседний ряд** — упорядоченные варианты одного уровня; **последний** ребёнок — текущий;
- **допустимые ходы** (`applicable`) — набор ходов в текущем фокусе; из него собирается
  поверхность инструментов:
  - на запросе — `move` / `decline`;
  - в открытом состоянии — `apply`-словарь состояния + `stop` + `recall` / `search`;
  - в закрытом (ждущем перехода) — только `move`;
  - в терминальном — `stop`;
- **`descend` / `return`** — движение фокуса вниз по дереву и возврат на уровень выше.

### 1.8 Отказы, мир и адресация

- **отказ** (`record_rejection`) — запись о том, что предложение отклонено, с причиной;
- **`mutate`** — событие об изменении файла; повышает **версию**;
- **`revert`** — откат последнего Patch на `Verification → Patch/Localization` по провалу:
  файлы возвращаются к pre-patch, версии в IR обновляются;
- **`recall` / `search`** — адресное чтение: тело прошлого результата по `id` (окно) или по
  паттерну, без повторного вызова; доступны только в открытом состоянии.

## 2. Четыре уровня на одной картинке

```
                    только дополняется   чистая         чистая
  предложение доксы ─▶ журнал (Event[]) ──fold──▶ Состояние ──project──▶ Контекст ──▶ докса
        ▲                                                                       │
        └────────── один или несколько операторов за ход, выбранных из допустимых ходов ──┘
```

- **Журнал** — `Event[]`, единственная истина (`add_node`, `add_edge`, `descend`, `return`,
  `mutate`, `revert`, `record_rejection`).
- **Состояние** — `fold(журнал)`: узлы, рёбра, порядок контейнера, стек обхода, версии файлов.
- **Контекст** — `project(состояние)`: лента сообщений, ситуация, ограничения, фронтир,
  инструкция ситуации.
- **Докса** — читает `Context` и предлагает операторы (`move` / `apply` / `stop` /
  `decline`; `recall`/`search` — адресация только для чтения, в открытом состоянии).

Ничего из того, что докса «думает», не хранится. План — её заметка; след работы — дерево.

## 3. Нотация

| символ | смысл |
|---|---|
| `R` | корневой `request` |
| `I`, `I0`, `I1`, `H` | состояния (`move`): фокус острова и терминальный `end` |
| `a1`, `a2` | пункты плана (`action`) |
| `obs` | `observation` (окно чтения, вывод запуска вместе с кодом возврата) |
| `→` | фокус движется; `+` узел или ребро создаётся; `⟂` отказ |
| `open` / `executed` / `stopped` | три отображаемых состояния (`stateOf`) |

## 4. Сквозной пример: одна задача от начала до конца

Задача:

> «Я сломал сборку; сделай так, чтобы `make test` проходил.»

Одно ограничение `k1` — не трогать тесты. Маршрут:
`O → L → P → V (провал) → P → V (успех) → End`. Прогон — 21 ход (0–20). Первая
Verification проваливается: движок откатывает Patch и переносит работу в новый Patch;
вторая Verification проходит. В каждой строке — предложение доксы, событие журнала, рост
дерева, производные факты и то, что докса увидит на следующем ходу.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 0 | `[R]` | — *(запрос задаёт арбитр)* | `+ request R {text}` | `rootId=R` | `situation=request`; `applicable=[move, decline]` |
| 1 | `[R] → [R,I0]` | `move I0 {state:"orientation"}` | `+ move I0`; `+ move R→I0` | `I0=open`; `situation=plan` | `Start state Orientation`; Workspace map; инструкция; `Goal: name the workspace root… acceptance…` |
| 2 | `[R,I0]` | `stop {why:"/app is the repo; acceptance is make test"}` | `+ stop s0`; `+ stop I0→s0` | `I0=stopped`; `situation=transition` | `Finish state Orientation — …`; `applicable=[move]` |
| 3 | `[R,I0] → [R,I1]` | `move I1 {state:"localization"}` | `+ move I1`; `+ move R→I1` | `I1=open`; `situation=plan` | `Start state Localization`; карта + Environment; `Goal: find the target…` |
| 4 | `[R,I1]` | `apply grep {pattern:"def parse"}` *(первый пункт)* | `+ plan Q1`; `+ items Q1→a1`; `+ action a1`; `+ obs o1` | `a1=executed`; `situation=working` | `lastResult` — совпадения; `applicable=[apply, stop, recall, search]` |
| 5 | `[R,I1]` | `apply read src/parse.py [40-90]` | `+ action a2`; `+ items Q1→a2`; `+ obs o2 {version:v1}` | `observed(file)=v1` | `lastResult` — окно кода |
| 6 | `[R,I1]` | `stop {why:"line 63 drops the last token — off-by-one in the loop"}` | `+ stop s1`; `+ stop I1→s1` | `I1=stopped`; `situation=transition` | `Finish state Localization — …`; `applicable=[move]` |
| 7 | `[R,I1] → [R,I2]` | `move I2 {state:"patch"}` | `+ move I2`; `+ move R→I2` | `I2=open`; `situation=plan` | `Start state Patch`; карта; `Goal: make the named change…`; tail с критерием |
| 8 | `[R,I2]` | `apply edit src/parse.py {old,new}` *(первый пункт)* | `+ plan Q2`; `+ items Q2→a3`; `+ action a3`; `+ mutates a3→file`; `mutate v1→v2` | `currentVersion(file)=v2` | `lastResult` — правка применена |
| 9 | `[R,I2]` | `stop {why:"the change is in the workspace"}` | `+ stop s2`; `+ stop I2→s2` | `I2=stopped` | `Finish state Patch — …`; `applicable=[move]` |
| 10 | `[R,I2] → [R,I3]` | `move I3 {state:"verification"}` | `+ move I3`; `+ move R→I3` | `I3=open`; `situation=plan` | `Start state Verification`; Environment; `Goal: check the changed artifact…` |
| 11 | `[R,I3]` | `apply bash {command:"make test"}` *(первый пункт)* | `+ plan Q3`; `+ items Q3→a4`; `+ action a4`; `+ obs o4 {exitCode:1}` | `a4=executed` | `lastResult` — `make test` упал (literal) |
| 12 | `[R,I3]` | `stop {why:"make test: exit 1 — <literal failure>"}` | `+ stop s3`; `+ stop I3→s3` | `I3=stopped`; `situation=transition` | `Finish state Verification — …`; `applicable=[move]` |
| 13 | `[R,I3] → [R,I4]` | `move I4 {state:"patch"}` | `+ revert {files, v2→v1}`; `+ move I4`; `+ move R→I4` | `currentVersion(file)=v1`; `I4=open` | `Start state Patch`; выше в ленте — `Finish state Verification — <literal why>`; план провалившейся Verification элидирован; `applicable=[apply, stop, recall, search]` |
| 14 | `[R,I4]` | `apply edit src/parse.py {old2,new2}` *(другой diff)* | `+ plan Q4`; `+ items Q4→a5`; `+ action a5`; `+ mutates`; `mutate v1→v3` | `currentVersion(file)=v3` | `lastResult` — правка применена |
| 15 | `[R,I4]` | `stop {why:"a different change is in the workspace"}` | `+ stop s4`; `+ stop I4→s4` | `I4=stopped` | `Finish state Patch — …` |
| 16 | `[R,I4] → [R,I5]` | `move I5 {state:"verification"}` | `+ move I5`; `+ move R→I5` | `I5=open`; `situation=plan` | `Start state Verification`; Environment |
| 17 | `[R,I5]` | `apply bash {command:"make test"}` | `+ plan Q5`; `+ items Q5→a6`; `+ action a6`; `+ obs o6 {exitCode:0}` | `a6=executed` | `lastResult` — `make test` прошёл |
| 18 | `[R,I5]` | `stop {why:"the acceptance command passes"}` | `+ stop s5`; `+ stop I5→s5` | `I5=stopped`; `situation=transition` | `Finish state Verification — …`; `applicable=[move]` |
| 19 | `[R,I5] → [R,H]` | `move H {state:"end"}` | `+ move H`; `+ move R→H` | `H=open`; `situation=terminal` | `Start state End`; `applicable=[stop]` |
| 20 | `[R,H]` | `stop {why:"request complete"}` | `+ stop s6`; `+ stop H→s6`; прогон завершается | `H=stopped`; `hasStopped(H)=true` | сессия завершается с причиной `request_addressed` |

На ходу 13 движок пишет `revert` **до** входа в новый Patch: последний Patch откатан,
дерево вернулось к pre-patch. Провал остаётся на ленте в `Finish`-строках закрытых
`Patch` и `Verification` (буквальный `stop.why`); планы закрытых состояний элидированы,
отдельного блока `Previous failed attempt` текущая реализация не рендерит.

### 4.1 Итоговое дерево

Состояния запроса висят **плоскими детьми** по ребру `move`, в порядке обхода. Планы висят
на `move`; провалившиеся состояния остаются закрытыми в дереве («то, что не сработало»), а
`revert` не удаляет события — он только возвращает файлы и версии.

```
R  request "I broke the build; make test must pass"        (корень: без плана и stop)
│  move
├─▶ I0  move orientation                                  stopped ✔
│      └─ stop ─▶ s0
├─▶ I1  move localization                                 stopped ✔
│      │  plan
│      │   ├─ items ─▶ a1 grep        executed → obs o1
│      │   └─ items ─▶ a2 read        executed → obs o2 (v1)
│      └─ stop ─▶ s1
├─▶ I2  move patch                                        stopped ✔
│      │  plan
│      │   └─ items ─▶ a3 edit        executed → mutates (v1→v2)
│      └─ stop ─▶ s2
├─▶ I3  move verification                                 stopped ✔ (провал)
│      │  plan
│      │   └─ items ─▶ a4 bash "make test"  executed → obs o4 (exit 1)
│      └─ stop ─▶ s3
│      ┆  revert: v2→v1 (на переходе I3→I4)
├─▶ I4  move patch                                        stopped ✔
│      │  plan
│      │   └─ items ─▶ a5 edit        executed → mutates (v1→v3)
│      └─ stop ─▶ s4
├─▶ I5  move verification                                 stopped ✔
│      │  plan
│      │   └─ items ─▶ a6 bash "make test"  executed → obs o6 (exit 0)
│      └─ stop ─▶ s5
└─▶ H   move end                                          stopped ✔
       └─ stop ─▶ s6
```

Закрытое состояние на ленте — только `Start state <label>` / `Finish state <label> — <why>`:
его brief, инструкция, цель и план элидируются. Они доступны в открытом состоянии (или через
`recall`).

### 4.2 На что обратить внимание

- **Состояние И ЕСТЬ его цель.** `move` объявляет остров; в блоке состояния рендерится
  `island.what` как `Goal:`. `move.what` — непроверенная догадка доксы на ходе `Goal:`, а не в
  tail. `move.done` переопределяет критерий в tail; `notes` записываются, но не рендерятся.
- **Первый пункт плана — обычный вызов инструмента.** Отдельного оператора конкретизации
  нет: первый `apply` после `move` засевает план и исполняется сразу (ходы 4, 8, 11, 14, 17).
- **Батч разрешён.** За ход можно предложить несколько независимых вызовов; движок исполнит
  их по порядку и вернёт N результатов. `move` и `stop` батчить нельзя.
- **`stop` закрывает состояние.** После `stop` единственный допустимый ход — `move`
  (ходы 2, 6, 9, 12, 15, 18). Терминальный `stop` на `end` завершает запрос (ход 20).
- **Гейта по критерию нет.** `stop` принимается на открытом состоянии; докса сама решает,
  когда критерий выполнен (tail повторяет его после каждого результата). Провал — факт, не
  закрытие.
- **Провал Verification → Patch по умолчанию.** Движок откатывает последний Patch (`revert`),
  и новый Patch начинает с pre-patch дерева. Провал остаётся на ленте в `Finish`-строках
  закрытых Patch/Verification (буквальный `why`); отдельного блока `Previous failed attempt`
  текущая реализация не рендерит. В Localization переходят, только если провал указывает на
  другой объект/координаты.
- **Поверхность модели — фронтир.** Запрос — `move`/`decline`; открытое состояние — applies +
  `stop` + `recall`/`search`; закрытое — только `move`; терминальное — `stop`.
- **Ничего не решается «само».** Движок не запускает план и не закрывает состояния по коду
  возврата; единственное его вмешательство — детерминированный `revert` на провале
  Verification.

### 4.3 План, альтернативы и `stop`

**План.** У состояния ровно один план: ребро `plan` от `move` к узлу `plan`; пункты связаны
рёбрами `items`. Порядок — это **список** детей плана; текущий пункт — **последний**
ребёнок. Пункт плана — всегда действие.

**Альтернативы.** Контейнер `alternatives` висит на пункте плана (история редакций шага,
который не сработал). Текущий вариант — последний ребёнок; остальные остаются в дереве как
«то, что не сработало».

```
состояние (move)
│  plan
└─▶ Q  plan   [ список пунктов: s, … ]
       │
       └─ items ─▶ s  action "cat HACKING.adoc"          (не сработал)
                  │  alts
                  └─▶ a'  action "make test"  (самый новый = текущий; выполняется)
```

**`stop`.** Действует на состояние: узел `stop` + ребро `stop` от `move`. `stop` не пункт
плана; гейта нет. На рабочем состоянии он вынуждает переход (только `move`); на `end` —
завершает запрос. У запроса `stop` нет.

## 5. Особые случаи

### 5.1 Недейственный запрос (`decline`)

Запрос вроде «привет, дядя Вася» не содержит выполнимой задачи. Докса не выдумывает
состояние; она отклоняет запрос.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 0 | `[R]` | — *(запрос задаёт арбитр)* | `+ request R {text}` | `rootId=R` | `applicable=[move, decline]` |
| 1 | `[R]` | `decline {why:"there is no actionable task"}` | `+ unactionable U {why}`; `+ unactionable R→U`; прогон завершается | у запроса нет состояния; `unactionableOf(R)=U` | сессия завершается; у запроса остаётся пометка |

`decline` принимается только на **свежем** запросе. Провал команды — это **не** `stop`:
докса продолжает работать в том же состоянии (дописывает пункты и проверяет снова).

### 5.2 Провал Verification: Patch по умолчанию и revert

Провал приёмки не закрывает Verify «сам» — состояние закрывает `stop` доксы (ход 12). На
переходе `Verification → Patch/Localization` движок:

1. пишет событие `revert` для последнего Patch (файлы — к pre-patch, версии обновляются);
2. делает новый `move` плоским ребёнком запроса;
3. оставляет провал на ленте в `Finish`-строках закрытых `Patch` и `Verification` (буквальный
   `stop.why`). Планы закрытых состояний элидированы; отдельного блока
   `Previous failed attempt` текущая реализация **не рендерит**.

Переход в **Localization** — только когда провал указывает на другой объект/координаты;
иначе Patch. Если откат невозможен (`write`/`apply_patch` без preimage), движок оставляет
изменение в дереве и не выводит отдельного предупреждения на ленту; провал по-прежнему
виден в `Finish`-строках. Это известный пробел — см. handoff.

### 5.3 Нерешающий прогон (таймаут)

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 1 | `[R,I3]` | `apply bash {command:"make test", timeout:60000}` | `+ obs {**нет exitCode**}` | вердикта нет: `I3` остаётся `open` | `lastResult={command, error:"…timed out…"}`; можно повторить |
| 2 | `[R,I3]` | `apply bash {command:"make test"}` (повтор) | новое наблюдение | — | таймаут не принёс знания |

`exitCode` — основной сигнал «прошло/нет». Его отсутствие — «вердикта нет»; состояние
остаётся открытым, и повтор допустим. Запуск никогда не закрывает состояние.

### 5.4 Мир, версии и адресация

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция |
|---|---|---|---|---|---|
| r | `[R,I]` | `apply read src/parse.py [10-80]` | `+ action`; `+ obs{ref, version:v1}`; `result` | `observed(file)=v1` | окно входит в ленту как `tool`-результат |
| e | `[R,I]` | `apply edit src/parse.py` | `+ action`; `+ mutates`; `mutate v1→v2` | `currentVersion=v2`; чтение `v1` устарело | устаревшее чтение **не** показывается активным |
| v | `[R,I]` | `stop` → `move` после провала Verification | `+ revert`; версии назад | `currentVersion=v1` | провал в `Finish`-строках; отдельного блока нет |
| q | `[R,I]` | `recall {id:"obs:…"}` | узла нет; тело возвращается | — | тело входит транзиентным `tool`-результатом |

Изменение файла порождает `mutate`; актуальность **вычисляется**, а не хранится флагом.
`revert` возвращает файлы и версии, не удаляя события. `recall`/`search` доступны только в
открытом состоянии; повторная команда с теми же входами и неизменным миром отклоняется —
знание уже есть, возьмите его по адресу.

## 6. Что иллюстрирует этот сквозной пример

1. **Контекст — это проекция, а не лента собственных слов модели.** Каждый ход — новая
   лента из дерева.
2. **Докса предлагает — логос решает.** Ход выбирается из допустимых; правила и факты
   решают, состоится ли он.
3. **Закрытие ровно одно — `stop`, и только доксы.** Запрос завершается на `stop`
   терминального `end` (или `decline`).
4. **Состояние И ЕСТЬ его цель.** `move { state }` объявляет остров; блок рендерит
   `island.what`; `move.what` — непроверенная догадка, `move.done` — переопределение критерия.
5. **Поверхность модели — это фронтир.** Запрос — `move`/`decline`; открытое — applies +
   `stop` + `recall`/`search`; закрытое — только `move`; терминальное — `stop`.
6. **На узлах нет истины.** Есть `open`/`executed`/`stopped` и производные факты; провал —
   факт, а не статус.
7. **След монотонен.** Ничего не переписывается; провалившийся шаг остаётся видимым, а
   `revert` — детерминированное событие движка, не удаление истории.
8. **Всё адресуемо.** Тела результатов живут в журнале и вспоминаются по `id`; контекст
   остаётся ограниченным срезом.
