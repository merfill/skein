# Skein — сквозной пример: дерево и контекст шаг за шагом

> Английское зеркало — `docs/walkthrough.md`.

## Преамбула

**Что такое Skein.** Skein — это агент для программирования, который хранит знание не в
переписке с моделью, а в **журнале фактов**, и на каждом ходу строит для модели
**проекцию** — строго определённый срез текущего состояния. Контекст модели не
накапливается, как лента сообщений: каждый ход — это свежая проекция журнала.

**Докса и логос.** Идейная основа взята из противопоставления *доксы* и *логоса*:

- **докса** — это языковая модель. Она хорошо придумывает, но не отвечает за
  истинность придуманного, поэтому только *предлагает* ровно один ход за ход;
- **логос** — это детерминированный движок вместе с инструментами и окружением. Он
  исполняет команды, записывает их результаты в журнал, пересчитывает производные
  факты и строит проекцию. Логос не выдумывает содержание — он решает, допустим ли
  предложенный ход и что из него следует.

Отсюда главный принцип: **докса предлагает — логос решает.** Модель сама никогда не
объявляет работу выполненной: это делают факты (прежде всего код возврата команды) и
правила движка.

**Арбитр.** Над доксой и логосом стоит **арбитр** — внешняя инстанция. В текущей
модели это пользователь (человек или харнес, который оценивает результат). Арбитр
задаёт самый первый запрос и принимает итоговый результат снаружи. Он не участвует в
приёмке отдельных целей: у каждой цели есть собственный критерий.

**Что закрывает работу.** Единственная рамка, которую можно закрыть, — это **цель**. Цель
закрывается **только явным ходом `stop`**, и (пока) только после того, как её критерий
прошёл. Прохождение критерия само по себе ничего не закрывает: это лишь факт о коде
возврата. У запроса нет собственного `stop`: он интерпретируется **ровно один раз** как
цель (`has_goal`) или отклоняется (`no_goal` → `unactionable`), и прогон **завершается,
когда его цель закрыта** (или когда запрос отклонён).

**Зачем этот документ.** Формальные документы описывают модель по частям. Здесь
**главное — раздел 4**: одна задача прослеживается целиком, от запроса до закрытия,
ход за ходом, с показом того, что происходит в журнале, в дереве, в производных фактах
и в проекции. Раздел 5 добавляет отдельные особые случаи, которых нет в основном
прогоне (недейственный запрос, разложение шага, таймаут и фон, версии файлов).

**Как читать.** Это иллюстрация, а не второй формализм. Источник истины —
`docs/ir_semantics_ru.md`; реализация — `docs/ir_ru.md`; справочник операторов —
`docs/ir_operations_ru.md`; описание проекции — `docs/projection_ru.md`. Если текст и
код расходятся, прав код вместе с `docs/ir_semantics_ru.md`.

## 1. Понятия

Ниже — словарь терминов, которые встречаются в тексте и таблицах. Английские слова в
обратных кавычках — это имена из кода; их мы не переводим.

### 1.1 Роли

| Термин | Значение |
|---|---|
| **докса** | языковая модель; предлагает ровно один ход за ход |
| **логос** | детерминированный движок: исполняет команды, ведёт журнал, пересчитывает факты, строит проекцию |
| **арбитр** | внешняя инстанция: задаёт первый запрос и принимает итоговый результат снаружи |

### 1.2 Слои данных

| Термин | Значение |
|---|---|
| **журнал** (`journal`) | неизменяемый список событий — единственный источник истины; только дополняется |
| **состояние** (`state`) | результат свёртки журнала (`fold`): узлы, рёбра, порядок пунктов, стек обхода, версии файлов |
| **проекция** (`projection`), он же **контекст** | строго определённый срез состояния, который видит докса на текущем ходу |
| **узел** | объект дерева: `request`, `goal`, `plan`, `action`, `observation`, `stop`, `constraint`, `file`, `unactionable` |
| **ребро** | связь между узлами: `has_goal`, `no_goal`, `has_plan`, `item`, `has_alternatives`, `produces`, `has_stopped`, `mutates` |

### 1.3 Работа

| Термин | Значение |
|---|---|
| **запрос** (`request`) | неструктурированная мотивация пользователя; корень дерева; интерпретируется **ровно один раз** как цель (`has_goal`) или отклоняется (`no_goal` → `unactionable`); у него нет плана, критерия и `stop`; прогон завершается, когда его цель закрыта |
| **цель** (`goal`) | интерпретация запроса или подцель: поле `what`, необязательное `why`, критерий `done_when`, набросок плана `plan` |
| **план** (`plan`) | контейнер пунктов; пункт плана — всегда **действие** (`action`); порядок задаёт список, и **последний** пункт — текущий |
| **действие** (`action`) | одна команда; исполняется по одному за ход |
| **наблюдение** (`observation`) | записанный результат: окно чтения, вывод запуска, код возврата |
| **альтернативы** (`alternatives`) | контейнер вариантов: варианты пересмотренной цели и ветвление/разложение шага (подцель становится самым новым вариантом шага) |
| **`stop`** | терминальный ход: закрывает текущую цель |
| **`decline`** | ход, который фиксирует недейственный запрос (`no_goal` → `unactionable`) и завершает прогон |

### 1.4 Критерий и вердикт

| Термин | Значение |
|---|---|
| **`done_when`** | буквальная команда — критерий цели; движок исполняет именно её |
| **запуск критерия** (`apply run {target}`) | запуск команды `done_when` цели, явно нацеленный на неё |
| **`target`** | поле наблюдения: какую цель проверяли; отличает критерий от обычного запуска |
| **`exitCode`** | код возврата: `0` — успех, не ноль — провал, отсутствует — вердикта нет (таймаут) |

Важное различие: **обычный запуск (`run` без `target`) — это не критерий**, а просто
наблюдение. Поэтому воспроизведение ошибки не закрывает цель до исправления.

### 1.5 Факты, выводимые из журнала

| Факт | Значение |
|---|---|
| **`criterionPass`** | последний запуск критерия цели вернул `exitCode 0` |
| **`criterionFailed`** | последний запуск вернул ненулевой `exitCode` |
| **`planExhausted`** | в плане цели не осталось невыполненных пунктов |
| **`hasStopped`** | у цели есть ребро `has_stopped` к узлу `stop` |

У запроса нет собственного производного факта «улажен»: его завершённость читается
напрямую по цели — прогон завершается, когда цель закрыта.

### 1.6 Состояние узла

Отображаемое состояние узла — одно из трёх:

- `open` — цель ещё открыта, действие ещё не исполнено;
- `executed` — действие произвело результат;
- `stopped` — цель закрыл ход `stop`.

Статусов «достигнуто» или «опровергнуто» на узлах нет. Прохождение или провал
критерия — это факт о наблюдении, а не свойство узла.

### 1.7 Обход и допустимые ходы

- **стек**, он же **ветка** (`path`) — путь от запроса к текущей цели; верх стека — **фокус**;
- **курсор** — индекс первого невыполненного пункта плана;
- **соседний ряд** — упорядоченные варианты одного уровня (пункты плана или варианты альтернатив); **последний** ребёнок — текущий;
- **допустимые ходы** (`applicable`) — набор ходов, разрешённых правилами в текущем фокусе; докса выбирает один из них;
- **`descend` / `return`** — движение вниз по дереву и возврат на уровень выше.

### 1.8 Отказы, мир и адресация

- **отказ** (`record_rejection`) — запись о том, что предложение отклонено, с причиной;
- **`mutate`** — событие об изменении файла; повышает **версию** файла;
- **свидетель** (`witness`) — снимок версий файлов на момент запуска критерия; по нему вычисляется устаревание;
- **`query`** — адресное чтение: тело прошлого результата достаётся по `id`, без повторного вызова команды.

## 2. Четыре уровня, на одной картинке

Весь цикл работы укладывается в четыре ступени: журнал накапливается, состояние из него
выводится, проекция из состояния строится, докса по проекции предлагает следующий ход.

```
                    только дополняется   чистая         чистая
  предложение доксы ─▶ журнал (Event[]) ──fold──▶ Состояние ──project──▶ Контекст ──▶ докса
        ▲                                                                       │
        └────────── один оператор за ход, выбранный из допустимых ходов ────────┘
```

- **Журнал** — `Event[]`, единственная истина (`add_node`, `add_edge`, `descend`,
  `return`, `mutate`, `record_rejection`).
- **Состояние** — `fold(журнал)`: узлы, рёбра, порядок контейнера, стек обхода, версии
  файлов. Узлы никогда не меняются.
- **Контекст** — `project(состояние)`: ветка обхода (`path`) с её контейнерами,
  глобальные ограничения, последний полный результат, рабочее множество, сводка вызовов,
  допустимые ходы, бюджет.
- **Докса** — читает `Context` и предлагает ровно один оператор (`create_goal` / `apply`
  / `stop` / `decline`; `query` — адресация только для чтения).

Ничего из того, что докса «думает», не хранится. План — это заметка для себя; след
работы — дерево.

## 3. Нотация

| символ | смысл |
|---|---|
| `R` | корневой `request` |
| `I`, `G` | цели: интерпретация `R`, разложенная подцель |
| `a1`, `a2` | пункты плана (`action`) |
| `obs` | `observation` (окно чтения, вывод запуска вместе с кодом возврата) |
| `Aₛ`, `A_G` | контейнеры `alternatives` (под шагом `s`, под целью `G`) |
| `→` | фокус движется; `+` узел или ребро создаётся; `⟂` отказ (`record_rejection`) |
| `open` / `executed` / `stopped` | три отображаемых состояния (`stateOf`) |
| `✓` критерий прошёл (`exitCode 0`), `✗` провал (не ноль), `∅` нет вердикта (таймаут) |

## 4. Сквозной пример: одна задача от начала до конца

Это главный раздел. Задача:

> «Я сломал сборку; проверь командой `make test`.»

Одно ограничение `k1` — не трогать тесты. Прогон длится 11 ходов (0–10). Первая попытка
не помогает; докса **остаётся в той же цели** — добавляет ещё один шаг и проверяет
снова — и делает `stop` по цели, когда критерий прошёл. Затем прогон завершается, потому
что цель закрыта. В каждой строке показано, что делает докса, что за событие дописывает
логос, как растёт дерево, какие факты появляются и что докса увидит на следующем ходу.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 0 | `[R]` | — *(запрос задаёт арбитр)* | `+ request R {text}` | `rootId=R` | `path=[R:open]`; `applicable=[create_goal, decline]` |
| 1 | `[R] → [R,I]` | `create_goal I` `{what:"fix the build so make test passes", why:"the request says the build is broken", done_when:"make test", plan:"reproduce, localize, fix, re-check", step:{command:"make test"}}` | `+ goal I`; `+ has_goal R→I`; `+ plan Q`; `+ has_plan I→Q`; `+ action a1 "make test"`; `+ item Q→a1`; `descend → I` | `I=open`; интерпретация запроса — это `I` | `path=[R, I]`; `I.done_when="make test"`; `I.plan.items=[a1:open]`; `applicable=[apply, create_goal]`; `nextAction=a1` |
| 2 | `[R,I]` | `apply run "make test"` (**без `target`** — воспроизвести) | исполнить; `+ obs o1 {command:"make test", exitCode:1}`; `produces a1→o1` | `a1=executed`; текущий пункт — теперь последний | `lastResult={command:"make test", exitCode:1}`; `calls=[run make test: fail]`; `applicable=[apply, create_goal]` |
| 3 | `[R,I]` | `apply grep "run-length"` (локализовать) | `+ action a2`; `+ item Q→a2`; `+ obs o2`; `produces a2→o2` | текущий пункт смещается на `a2` | `lastResult` — совпадения в `runtime/shared_heap.c`; `calls` растёт |
| 4 | `[R,I]` | `apply read runtime/shared_heap.c [40-120]` | `+ action a3`; `+ item Q→a3`; `+ obs o3 {ref, version:v1}`; `produces a3→o3` | `observed(file)=v1` | `lastResult` — окно кода; `shown=[o3]` |
| 5 | `[R,I]` | `apply edit runtime/shared_heap.c` (попытка №1) | `+ action a4 {find,replace}`; `+ mutates a4→file`; `+ item Q→a4`; `mutate v1→v2` | `currentVersion(file)=v2`; чтение `o3` устарело | `lastResult={kind:"action", ref:"…"}`; `calls` |
| 6 | `[R,I]` | `apply run {target:"I"}` (первая проверка) | исполнить `I.done_when`; `+ action a5`; `+ item Q→a5`; `+ obs o5 {command:"make test", target:"I", exitCode:1, witness}`; `produces a5→o5` | `criterionFailed(I)=true`; `I` остаётся `open` | `lastResult={command:"make test", exitCode:1}`; `applicable=[apply, create_goal]` — продолжаем работать в той же цели |
| 7 | `[R,I]` | `apply read runtime/shared_heap.c [200-260]` (посмотреть ближе) | `+ action a6`; `+ item Q→a6`; `+ obs o6 {ref, version:v2}`; `produces a6→o6` | `observed(file)=v2` | `lastResult` — окно кода |
| 8 | `[R,I]` | `apply edit runtime/shared_heap.c` (попытка №2) | `+ action a7 {find,replace}`; `+ mutates a7→file`; `+ item Q→a7`; `mutate v2→v3` | `currentVersion(file)=v3`; чтение `o6` устарело | `lastResult={kind:"action", ref:"…"}` |
| 9 | `[R,I]` | `apply run {target:"I"}` (вторая проверка) | исполнить `I.done_when`; `+ action a8`; `+ item Q→a8`; `+ obs o8 {command:"make test", target:"I", exitCode:0, witness}`; `produces a8→o8` | `criterionPass(I)=true` | `lastResult={command:"make test", exitCode:0}`; `applicable=[apply, stop]`; `checkReady=true` |
| 10 | `[R,I]` | `stop {why:"the suite is green"}` (закрыть `I`) | `+ stop s1`; `+ item Q→s1` (**последний** пункт плана); `+ has_stopped I→s1`; прогон завершается | `I=stopped`; `hasStopped(I)=true` | сессия завершается с причиной `request_addressed` |

### 4.1 Итоговое дерево

После хода 10 дерево выглядит так. Запрос связан со своей единственной интерпретацией
ребром `has_goal`. У цели есть ребро `has_plan` на узел `plan`, а пункты плана — это
**список** действий (порядок задаёт список, а не форма дерева); **последний** пункт плана
— узел `stop`, и ребро `has_stopped` от цели указывает на тот же узел. Контейнера
альтернатив у запроса нет, и ребра `chosen` нет нигде: порядок контейнера — это его
список, а последний ребёнок — текущий.

```
R  request "I broke the build; verify with make test"      (корень: без плана, критерия и stop)
│  has_goal
└─▶ I  goal "fix the build so make test passes"            (stopped ✔)
       │  has_plan
       ├─▶ Q  plan   [ список пунктов: a1, a2, a3, a4, a5, a6, a7, a8, s1 ]
       │      ├─ item ─▶ a1  action "make test"        executed → obs o1   (exit 1)
       │      ├─ item ─▶ a2  action "grep …"           executed → obs o2
       │      ├─ item ─▶ a3  action "read …"           executed → obs o3   (ref@v1)
       │      ├─ item ─▶ a4  action "edit …"           executed → mutates file v1→v2
       │      ├─ item ─▶ a5  action "run {target:I}"   executed → obs o5   (target:I, exit 1)
       │      ├─ item ─▶ a6  action "read …"           executed → obs o6   (ref@v2)
       │      ├─ item ─▶ a7  action "edit …"           executed → mutates file v2→v3
       │      ├─ item ─▶ a8  action "run {target:I}"   executed → obs o8   (target:I, exit 0)
       │      └─ item ─▶ s1  stop {why:"the suite is green"}   (ПОСЛЕДНИЙ пункт плана)
       └─ has_stopped ─▶ s1  stop
```

Порядок пунктов плана задаёт **список** (порядок добавления), а не форма дерева: рёбра
`item` показывают принадлежность контейнеру, а порядок — это порядок элементов списка, и
**последний** ребёнок — текущий. Проекция в каждый момент показывает **не** это дерево
целиком, а только текущую ветку, её контейнеры, последний результат, сводку вызовов и
допустимые ходы. Всё остальное — на расстоянии одного `query`.

### 4.2 На что обратить внимание в основном прогоне

- **Ходы 2, 6 и 9** — все запускают `make test`, но ход 2 идёт **без `target`**, а ходы 6
  и 9 — **с `target:"I"`**. Это и есть различие: обычный запуск — наблюдение
  (воспроизведение ошибки), запуск с `target` — критерий. Без `target` воспроизведение не
  решило бы цель до исправления.
- **Ход 6 не закрывает `I`.** Код возврата `1` — это факт (`criterionFailed(I)`), а не
  приговор. Цель остаётся `open`, и докса **продолжает работать в той же цели**: добавляет
  ещё один шаг (ход 7) и ещё одно исправление (ход 8), затем проверяет снова (ход 9).
- **Интерпретация создаётся один раз.** Запрос интерпретируется ровно один раз
  (`has_goal`); после провалившегося критерия докса не переинтерпретирует запрос и не
  переписывает цель — она дописывает пункты плана. Переинтерпретация — отложенная
  возможность.
- **Ход 9 не закрывает `I`.** Прохождение критерия — только код возврата. Закрытие
  происходит ходом 10 (`stop`). Это единообразное правило: сначала работа, потом `stop`.
- **У запроса нет собственного `stop`.** Прогон завершается на ходу 10 потому, что цель
  запроса `I` закрыта (`request_addressed`). Приёмка запроса остаётся внешней — её делает
  арбитр.
- **Ничего не решается «само».** Движок не запускает план, не закрывает цели по коду
  возврата и не выбирает шаги — на каждом ходу ровно один ход делает докса.

### 4.3 Как устроено дерево: план, альтернативы и `stop`

**План.** У цели ровно один план: ребро `has_plan` ведёт от цели (`goal`) к узлу `plan`,
а пункты плана связаны с планом рёбрами `item`. Порядок пунктов задаётся не рёбрами, а
**списком** детей узла `plan`: рёбра показывают принадлежность, список — последовательность.
Ребра `chosen` **нет**: текущий пункт контейнера — это просто его **последний** ребёнок.
Пункт плана — всегда действие (`action`); подцель пунктом плана быть не может.

**Альтернативы.** Контейнер `alternatives` — это способ «переделать, не переписывая». Он
вешается либо на **цель** (варианты подхода), либо на **пункт плана** (история редакций
шага, который не сработал). Ребра `chosen` нет: **текущий вариант — последний ребёнок**;
остальные просто не текущие и остаются в дереве как «то, что не сработало».

Когда докса выполняет команду, **отличную** от текущего невыполненного пункта, движок не
переписывает пункт, а вешает на него контейнер `alternatives` и добавляет туда новое
действие как **самый новый (последний) вариант**:

```
goal
│  has_plan
└─▶ Q  plan   [ список пунктов: s, … ]
       │
       └─ item ─▶ s  action "cat HACKING.adoc"          (не сработал)
                  │  has_alternatives
                  └─▶ As  alternatives   [ список вариантов: a', … ]
                             item ─▶ a'  action "make test"  (самый новый = текущий; выполняется)
```

Важно: движок **никогда не «входит» в действие** — он входит либо в подцель (самый новый
вариант шага), либо остаётся на месте и продвигает текущий пункт.

**`stop`.** Ход `stop` действует **только на цель**. Движок добавляет узел `stop` как
**последний пункт плана** цели И проводит ребро `has_stopped` от цели к этому же узлу —
так цель помечается как закрытая (но не «достигнутая»: её критерий не меняется). Пока
`stop` принимается только после того, как критерий цели прошёл (иначе отказ
`check_not_run`). У запроса `stop` нет: запрос завершается (прогон завершается), когда его
цель закрыта.

## 5. Особые случаи

В основном прогоне не встретились четыре ситуации. Разберём их отдельно, каждый раз
как небольшой фрагмент.

### 5.1 Недейственный запрос (`decline`)

Запрос вроде «привет, дядя Вася» не содержит выполнимой задачи. Докса не выдумывает цель с
фиктивным критерием; она отклоняет запрос.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 0 | `[R]` | — *(запрос задаёт арбитр)* | `+ request R {text}` | `rootId=R` | `applicable=[create_goal, decline]` |
| 1 | `[R]` | `decline {why:"there is no actionable task in the request"}` | `+ unactionable U {why}`; `+ no_goal R→U`; прогон завершается | у запроса нет цели; `unactionableOf(R)=U` | сессия завершается; у запроса остаётся пометка `unactionable` |

`decline` принимается только на **свежем** запросе (у которого ещё нет ни цели, ни
`unactionable`). Он ничего не закрывает: он фиксирует, что намерение запроса невыполнимо, и
на этом прогон останавливается.

Отметим парное правило: **провал критерия — это не `stop`.** После неудачной проверки
докса продолжает работать в той же цели (дописывает шаги и проверяет снова, как в разделе
4); она не должна закрывать цель и не переинтерпретирует запрос.

### 5.2 Разложение шага на подцель

Шаг плана нуждается в собственном критерии. Докса раскладывает **текущий шаг**, а не всю
цель.

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| k | `[R,I]` | `create_goal G {what:"make the sub-suite pass", done_when:"ctest -R heap", plan:"…", step:{command:"ctest -R heap"}}` | `+ G`; `+ Aₛ` под текущим шагом `s`; `+ item Aₛ→G`; `descend → G` | у шага `s` появляется новый (самый новый) вариант `G`; текущий пункт `I` — всё ещё `s` | `path=[R, I, G]`; `I.plan.items=[s{alternatives:[G]}, …]` |
| k+1 | `[R,I,G]` | `apply run {target:"G"}` | `+ obs{target:"G", exitCode:0}` | `criterionPass(G)=true` | `applicable=[apply, stop]` |
| k+2 | `[R,I,G]` | `stop` (закрыть `G`) | `+ stop` (последний пункт плана `G`); `+ has_stopped G→stop` | `G=stopped`; шаг `s` выполнен через свой самый новый вариант | возврат к `I`; текущий пункт продвигается за `s` |
| k+3 | `[R,I]` | продолжить оставшийся план `I` … | … | | |

**Подцель никогда не является пунктом плана**: она входит только как **самый новый
вариант** шага, который раскладывает. Движок никогда не «переходит в действие» — он
переходит в подцель. Шаг `s` считается выполненным, когда его самый новый (текущий)
вариант `stopped`, поэтому разложение шага не блокирует план. `stop` на `G` закрывает
только `G`; движок делает `return` к `I` и продолжает.

### 5.3 Незавершившийся запуск и фоновая команда

**E1. Запуск критерия, который прерывается по таймауту.**

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| 1 | `[R,I]` | `apply run {target:"I"}` | исполнить `make test`; процесс убит таймаутом; `+ obs{target:"I", **нет exitCode**}` | вердикта нет: `I` остаётся `open` | `lastResult={command:"make test", error:"…timed out…"}`; модель может повторить |
| 2 | `[R,I]` | `apply run {target:"I"}` (повтор) | новое наблюдение | — | это **не** повтор: таймаут не принёс знания |

**E2. Долгая команда в фоне.**

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| j | `[R,I]` | `apply run {command:"make bootstrap", background:true}` | `+ action`; `+ obs{job:"job-1", state:"running"}` | — | `lastResult={job:"job-1", state:"running"}` |
| j+1 | `[R,I]` | `apply run {job:"job-1"}` | `+ action "poll job-1"`; `+ obs{state, exitCode?}` | когда состояние `done`, появляется `exitCode` | каждый опрос читает новое состояние, поэтому это никогда не повтор; опрос никогда не критерий |

`exitCode` — это весь сигнал «прошло или нет». Его **отсутствие** (таймаут, сигнал без
контролируемого выхода) означает «вердикта нет»: цель остаётся `open`, и модель может
повторить тот же критерий — незавершившийся запуск не является ни повтором, ни
прогрессом. Критерий никогда не уходит в фон (отказ `background_target`): проверка должна
дойти до вердикта в пределах хода. Фоновая команда — это обычное наблюдение.

### 5.4 Мир, версии и адресация

| Ход | Стек | Предложение доксы | Журнал / изменение дерева | Производные факты | Проекция (что видит докса) |
|---|---|---|---|---|---|
| r | `[R,I]` | `apply read runtime/shared_heap.c [10-80]` | `+ action`; `+ obs{ref, version:v1}`; `produces` | `observed(file)=v1` | `lastResult={ref:"…", output:"…"}` |
| e | `[R,I]` | `apply edit runtime/shared_heap.c` | `+ action`; `+ mutates`; `mutate v1→v2` | `currentVersion(file)=v2`; чтение `v1` теперь устарело | устаревшее чтение **убрано** из `shown` |
| q | `[R,I]` | `query {id:"obs:…"}` | узла нет; тело возвращается | — | тело входит в `shown` на несколько ходов |

Изменение файла порождает событие `mutate` (повышение версии); актуальность
**вычисляется**, а не хранится флагом. Факт чтения о `v1` не удаляется — он просто
перестаёт принадлежать текущему контексту, и устаревшее содержание никогда не
показывается активным. Всё адресуемо: тело прошлого результата достаётся по `id` через
`query`, без повторного вызова. Поэтому повторная команда с теми же входами и неизменным
миром отклоняется — знание уже есть, возьмите его по адресу.

## 6. Что иллюстрирует этот сквозной пример

1. **Контекст — это проекция, а не лента.** На каждом ходу докса видит ветку и её
   контейнеры, а не транскрипт.
2. **Докса предлагает — логос решает.** Докса выбирает ход из допустимых; правила и
   производные факты решают, состоится ли он.
3. **Закрытие ровно одно — `stop`, и (пока) только положительное.** Прохождение критерия —
   только код возврата; цель завершается, когда докса предлагает `stop` и правило его
   принимает (прохождение критерия). У запроса нет собственного `stop` — он завершается,
   когда его цель закрыта, либо когда запрос отклонён как недейственный.
4. **Проверка — это запуск критерия**: обычное наблюдение с полями `target` и
   `exitCode`. Отдельного узла `check` нет, вердикта нет, `under` нет.
5. **На узлах нет истины.** Есть только `open` / `executed` / `stopped` плюс факты
   критерия; провал — это факт, а не статус.
6. **След монотонен.** Пересмотр или добавленный шаг только добавляют узлы; ничего не
   переписывается — провалившийся шаг остаётся видимым как «то, что не сработало», а
   интерпретация запроса создаётся один раз через `has_goal`.
7. **Всё адресуемо.** Тела результатов живут в журнале и вспоминаются по `id`; контекст
   остаётся ограниченным срезом.
