# Skein — ревизия IR: форма, операции и контекст

## 1. Назначение документа

Документов об устройстве IR становится всё больше, и они уже разошлись между собой:
`concepts`, `ir_semantics`, `ir`, `projection`, `context_design`, `traversal_stack_spec` и
`walkthrough` описывают разные срезы одной системы, а местами противоречат коду. Например,
`done_when`, `checkReady` и `state` давно убраны из кода, но всё ещё живут в текстах.

Нужен один короткий свод, по которому можно понять модель целиком, не собирая её из семи
документов. Этот документ — такой свод.

Он отвечает на три вопроса:

- **форма** — из каких узлов и связей состоит дерево;
- **операции** — какими ходами дерево растёт и куда после каждого хода смотрит фокус работы;
- **контекст** — что из дерева видит модель на очередном шаге.

В ревизию не входят и остаются как есть: разделение доксы и логоса, правило «цель
закрывается только через `stop`», требование «журнал только дополняется» и детерминизм —
«одни и те же события дают один и тот же контекст».

## 2. Форма дерева

### 2.1 Узлы

Узлы делятся на два пространства.

**Рабочее пространство** — то, из чего состоит сама работа:

- `request` — запрос пользователя; корень дерева;
- `goal` — цель: чего нужно достичь;
- `plan` — план цели: упорядоченный список пунктов;
- `item` — пункт плана: список альтернатив для этого пункта (**новый вид узла**);
- `action` — команда; служит альтернативой пункта;
- `goal` — цель может быть и подцелью, то есть тоже альтернативой пункта;
- `observation` — результат выполненной команды;
- `stop` — отметка о том, что цель закрыта;
- `unactionable` — отметка о том, что запрос не содержит выполнимой задачи;
- `constraint` — ограничение: что запрещено.

**Пространство артефактов** — то, что существует помимо работы:

- `file` — файл.

Прежний вид `alternatives` (контейнер вариантов) убран: его роль теперь целиком у пункта
плана `item`.

### 2.2 Связи

Связь — это именованное отношение от одного узла к другому. У каждого вида узла есть
фиксированный набор допустимых связей:

| От кого | Связь | К кому | Сколько |
|---|---|---|---|
| `request` | `goal` | `goal` | 0 или 1 |
| `request` | `unactionable` | `unactionable` | 0 или 1 |
| `goal` | `plan` | `plan` | ровно 1 |
| `goal` | `stop` | `stop` | 0 или 1 |
| `plan` | `items` | `item` | 1 и больше, по порядку |
| `item` | `alts` | `action` или `goal` | 1 и больше, по порядку |
| `action` | `result` | `observation` | 0 или 1 |
| `action` | `mutates` | `file` | 0 и больше |

Название связи — это и есть роль, которую играет ребёнок у родителя. Поэтому отдельного
«списка рёбер» не нужно: связь добавляется очередным событием, а узел при этом не
переписывается. Так сохраняется главное свойство журнала — он только дополняется.

Порядок детей — это порядок добавления. Текущим (выбранным) считается **последний** ребёнок.

Отдельно отметим два места:

- закрытие цели хранится прямо у цели, в связи `goal.stop`; отдельного пункта плана под
  `stop` больше нет;
- файл (`file`) — единственный узел, на который могут ссылаться сразу несколько действий
  (через `action.mutates`). Это и есть настоящее разделение: у файла много «владельцев»,
  у остальных узлов — по одному.

### 2.3 Общая форма

```
goal --plan--> plan --items--> item --alts--> action | goal
```

Отсюда следуют правила:

- пункт плана — **всегда** список альтернатив, и в нём минимум один элемент; если ветвления
  нет, элемент ровно один и это команда (`action`);
- цель может появиться только двумя способами: как интерпретация запроса (`request.goal`)
  или как альтернатива пункта (`item.alts`). Больше нигде.

## 3. Как дерево растёт: операции

Обозначения:

- `R` — корневой запрос (`request`);
- `C` — открытая цель, на которой сейчас стоит фокус;
- `I` — текущий пункт плана цели `C` (первый невыполненный; см. §4).

Каждая операция описана по одному шаблону: назначение → применимо к → вход → действие →
фокус → отказ.

### 3.1 `create_goal` на запросе — интерпретация

**Назначение.** Один раз истолковать запрос как цель.

**Применимо к.** Свежему `request` — у которого ещё нет ни цели, ни отметки `unactionable`.

**Вход.** `{ what, why?, sketch, command }`: `what` — что достичь; `why?` —
гипотеза-обоснование; `sketch` — заметка плана; `command` — первый пункт плана.

**Действие.** Создаются узлы: цель `G`, план `Q`, пункт `I`, команда `A`. Связываются:
`R.goal = G`, `G.plan = Q`, `Q.items = [I]`, `I.alts = [A]`. У запроса появляется цель, у
цели — план из одного пункта, у пункта — одна альтернатива-команда.

**Фокус.** Спускается в `G`.

**Отказ.** На уже истолкованном запросе — `interpreted` (интерпретация создаётся один раз).

### 3.2 `create_goal` на цели — разложение пункта

**Назначение.** Разложить текущий пункт в подцель, когда шаг требует собственной подзадачи.

**Применимо к.** Открытой `goal`, у которой есть текущий пункт.

**Вход.** Тот же `{ what, why?, sketch, command }`; `command` становится первой командой
пункта новой подцели.

**Действие.** Создаются узлы: подцель `G`, план `Q`, пункт `I'`, команда `A`. Связываются:
`I.alts += G` (подцель становится последней, то есть текущей альтернативой пункта),
`G.plan = Q`, `Q.items = [I']`, `I'.alts = [A]`.

**Фокус.** Спускается в `G`.

**Отказ.** Нет текущего пункта (план уже выполнен).

### 3.3 `apply` на цели — команда

**Назначение.** Исполнить одну команду в текущей цели.

**Применимо к.** Открытой `goal`.

**Вход.** `{ tool, … }`, где `tool` — один из `read`/`grep`/`list`/`edit`/`write`/`run`/
`fetch`/`apply_patch`, плюс параметры инструмента (`path`, `pattern`, `find`/`replace`,
`command`, …). Признака «продолжение или ветка» во входе нет — отсюда §4.

**Действие.** Команда исполняется; результат записывается: либо `A.result = observation`
(чтение, поиск, запуск), либо `A.mutates += file` (правка файла). Новым пунктом команда
становится или альтернативой — определяет исход исполнения (§4).

**Фокус.** Не двигается: действие исполняется на месте, в текущей цели.

**Отказ.** Отдельного отказа у команды нет: неисполнение (повтор, устаревший базис,
запрещённый путь, пустая команда) приходит **наблюдением с причиной** (§4), а не отклонением
без узла.

### 3.4 `stop` на цели — закрытие

**Назначение.** Закрыть цель. Это единственный способ её завершить.

**Применимо к.** Открытой `goal`.

**Вход.** `{ why? }` — причина закрытия.

**Действие.** Создаётся узел `S`; связывается `C.stop = S`.

**Фокус.** Цель закрыта; следующая проекция уводит фокус к родителю. Если закрыта цель
корневого запроса — прогон заканчивается.

**Отказ.** На `request` — `not_addressed` (у запроса нет `stop`; запрос заканчивается, когда
закрыта его цель).

### 3.5 `decline` на запросе — отказ

**Назначение.** Зафиксировать, что в запросе нет задачи, которую можно взять в работу; цель не
выдумывается. Возникает, когда в запросе вообще нет задачи (приветствие, благодарность,
обратная связь), когда он не про работу с кодом или воркспейсом, или когда намерение не
сводится к выполнимой задаче. Отказ завершает прогон, но не «закрывает» запрос: приёмка
запроса остаётся внешней, пользователь может уточнить и прислать новый. Если задача есть и
понятна — это `create_goal`; если задача есть, но не хватает инструмента или процедуры — это
отдельный, пока отложенный случай (нехватка возможностей).

**Применимо к.** Свежему `request`.

**Вход.** `{ why? }` — причина отказа.

**Действие.** Создаётся узел `U`; связывается `R.unactionable = U`. Цель, план и команды не
создаются.

**Фокус.** Прогон заканчивается (`request_unactionable`).

**Отказ.** На цели — `not_request`; на уже истолкованном запросе — `interpreted`; на уже
отклонённом — `repeated_action`.

Отдельно: `query` — не ход доксы, а чтение. Его вход — `{ id?, kind?, edgesOf?, start?, end? }`;
узлов он не создаёт и дерево не меняет.

## 4. Как команда попадает в дерево

`apply` — это вызов инструмента. Движок исполняет команду и **всегда** записывает её исход как
`observation`; докса читает наблюдение и сама решает следующий ход, а движок только размещает
пришедший ход. Какой ход дать, выбирает модель (может взять прежнюю команду чуть изменённой по
причине из наблюдения) — движок этот выбор не ограничивает.

**Исход пункта** берётся из текущей альтернативы:

- альтернатива — **команда**: её `observation` несёт либо результат (**успех**), либо причину
  (**неуспех**), либо ничего при обрыве по таймауту (**нет вердикта**). Причина неуспеха:
  инструмент не смог выполнить (нет файла, пустой паттерн), проверку допустимости не прошла
  (повтор, устаревший базис, запрещённый путь) или прогон вернул ненулевой код;
- альтернатива — **цель**: наблюдения нет, исход — её `stop`; причина остановки берётся из
  `why` узла `stop`. Закрытая цель считается **успехом**.

**Куда встаёт следующий ход** (движок размещает по исходу; команду или цель выбирает докса):

- после **успеха** — **новым пунктом плана**;
- **иначе** (неуспех или отсутствие вердикта) — **альтернативой текущего пункта**; если новый
  ход — цель, фокус спускается в неё.

Каждая попытка команды оставляет узлы: исполненная — `action` и `observation` с результатом,
неисполненная — `action` и `observation` с причиной. Даже повтор той же команды оформляется
новыми узлами; существующий узел не переиспользуется и не правится — журнал остаётся
монотонным.

**Структурные ходы.** `create_goal`, `stop`, `decline` — не исполнение команды, а изменение
дерева. Если такой ход недопустим в текущем контексте, он **отклоняется**: доксе возвращается
причина, узел не создаётся.

**Следствие для воспроизведения.** Падающий прогон — это неуспех, поэтому следующая за ним
команда ложится альтернативой того же пункта, а не новым пунктом.

## 5. Контекст: лента сообщений

Контекст — то, что модель видит на очередном шаге. Он выглядит как обычная лента сообщений
(как в ReAct-агенте), но **каждый раз собирается заново из дерева** — это проекция, а не
накопительная переписка. Поэтому один и тот же набор событий всегда даёт одну и ту же ленту.

**Роли:**

- `system` — системный промпт;
- `user` — запрос;
- `assistant` — ходы доксы;
- `tool` — результаты команд.

**Ходы и их сообщения:**

- `create_goal` — `assistant` с целью (`what`/`why`/`sketch`), затем первая команда:
  `assistant` (вызов) + `tool` (наблюдение);
- `apply` — `assistant` (вызов команды), затем `tool` (наблюдение);
- `stop` — `assistant` с причиной (`why`): цель закрыта;
- `decline` — `assistant` с причиной (`why`): запрос отклонён.

То есть **каждый пункт плана — это пара** `assistant` + `tool`, а создание и закрытие цели —
отдельные `assistant`-сообщения.

**Пометка альтернатив.** Если команда — альтернатива к уже начатому шагу, это видно из её
`assistant`-сообщения: `альтернатива шага «<метка>» (прошлая попытка: «<команда>» — <причина>)`.
Так модель видит, что уже не сработало.

**Лента не монотонна.** Как только цель закрывается, все её внутренние сообщения убираются из
ленты; на руке её родителя остаётся только сообщение о закрытии (`stop` с `why`). При подъёме
выше — то же самое. Уходит только вид, а не данные: дерево остаётся полным и неизменным.

**Рассуждение доксы не хранится.** Сырое `thought` в ленту не попадает: его нет в дереве, и его
включение сломало бы детерминизм. Смысловая часть рассуждения сохранена там, где важна, — в
полях `why`.

### 5.1 Формат контекста

Контекст — это **только лента сообщений**, то есть история. Никаких отдельных блоков
(`brief`, `path`, `calls`, `shown`, `applicable`, `budget` и подобных) нет.

- Чего нет в ленте — того модель не знает: лента и есть вся её память.
- **Ограничений на контекст нет.** Показываем историю целиком; единственное сокращение —
  немонотонный срез при закрытии цели, когда её внутренние сообщения уходят (см. выше).
- Всё, что раньше было полем состояния, теперь либо сообщение, либо инструкция системной части:
  - план цели и альтернативы — это сообщения (пары `assistant` + `tool`);
  - ограничения — `system`-сообщения (§6);
  - применимые ходы — инструкция узла (§6).

### 5.2 Работа с данными

**Принцип.** Большие данные в IR не хранятся: тело результата, не влезающее в ленту,
сохраняется файлом (движок владеет им), а в дереве остаётся только ссылка `outputRef`. Это не
часть IR, а обычные данные.

- Результат инструмента приходит `tool`-сообщением в объёме, честно ограниченном самим
  инструментом (`read` — до 400 строк с начала, `run`/`grep` — до 8000 символов и т. д.).
- Небольшое тело лежит прямо в узле; большое — в файле, в узле остаётся `outputRef`.
- **Доступ — по идентификатору, не по пути.** Пути `.skein/...` модели не показываем:
  - прочитать фрагмент — `query { id, start, end }` (окно строк);
  - поискать по телу — `query { id, pattern }`.

## 6. Сборка системной части

Системная часть ленты собирается **не монолитом**, а из намерения текущего узла. На свежем
запросе нужна только инструкция «истолковать или отклонить»; появилась цель — инструкция про
работу с целью; и так далее. Ограничения добавляются туда же.

**Добавляем один раз.** Инструкция привязана к узлу, который её вызывает, и рендерится вместе
с ним: один узел — одно появление в ленте. Повторно добавлять её не нужно, и отдельный счётчик
для этого не требуется. Счётчик понадобился бы только для более позднего приёма — «скрыть
инструкцию через N ходов и вернуть позже»; сейчас этого не делаем.

### 6.1 Принципы разделения

- **Базовый промпт — только то, что верно на любом ходу:** роль (кто такая докса), контракт
  (предлагает ровно один ход; логос решает), общая форма ответа. Он не зависит от узла и
  стабилен — это ещё и хороший префикс для кэша.
- **Промт узла — только то, что вызвано текущим узлом:** какие ходы сейчас допустимы и как их
  оформлять; правила текущей ситуации (свежий запрос / открытая цель / возврат); что
  показывает рука.
- **Правило большого пальца:** нужна на любом ходу → в базу; вызвана конкретным состоянием →
  в промт узла и привязывается к нему.
- **Следствие:** набор применимых операторов и их поля — контекстны (совпадают с фронтом), а не
  перечисляются в базе целиком.

### 6.2 Открыто

Точная граница — что именно уходит в базовый промпт, а что в узлы (например, где живёт форма
ответа и общие правила ветвления) — подлежит исследованию (§8).

## 7. Что не меняется

- журнал только дополняется; узлы не переписываются, меняется лишь то, что мы показываем;
- проекция детерминирована: одни события дают один контекст;
- цель закрывается только через `stop`;
- докса только предлагает, решение принимает логос;
- код возврата команды — обычный вывод, а не приговор; на нём ничего не закрывается.
