# Skein — агент кодирования с детерминированным IR-контекстом

> **Заметка (ревизия IR свёрнута).** Разделы ниже о дереве, обходе и проекции отражают модель
> **до** ревизии IR. Актуальная форма (`item`/`alts`, `stop` на цели, лента сообщений) —
> в `docs/ir_semantics_ru.md`; as-built — `docs/ir_ru.md`. Концептуальный каркас
> (докса/логос, журнал, проекция) сохраняется.

## Ядро идеи

Обычный агент трактует контекст как ленту сообщений: LLM читает ленту и пишет в неё;
IR, если есть, стоит сбоку.

Skein это переворачивает: **контекст — проекция IR**. Лента существует только для
коммуникации с LLM. Память живёт в IR. LLM не «помнит» — она видит срез состояния, и
то, что она видит, определяется **функцией проекции**, а не историей. Следствие:
контекст не накапливается. Каждая итерация — свежая проекция текущего состояния.

## Дерево, а не лента (раскрутка ReAct)

ReAct-цикл — плоская растущая лента: LLM читает её и добавляет следующий вызов
инструмента, а единственный сигнал «задача кончилась» — сама модель выдала финальный
ответ. Skein **раскручивает этот цикл по дереву**:

```
запрос ─(has_goal)▶ цель (гипотеза) ─(has_plan)▶ план (набросок-строка; последний пункт — текущий) ─▶ действие ─▶ наблюдение
```

Запрос интерпретируется **один раз** как цель (`has_goal`); интерпретация пока
фиксирована. Недейственный запрос вместо этого **отклоняется** (`no_goal` →
`unactionable`).

**Рука — это ReAct на месте.** Внутри одного уровня — руки — выдвигается цель, план
которой материализует ровно один пункт (команду); этот пункт исполняется за свой ход;
его результат записывается (`observation`/`mutate`) и передаётся доксе; докса
затем либо добавляет следующий узел, либо останавливается. Это ReAct-цикл без
изменений: один шаг за ход, следующий выбирается из результата. Чего ReAct не может —
это *сохранить* его: здесь каждый шаг есть событие в append-only журнале. Рука
перестаёт быть плоской только когда шаг **ветвится**: докса предлагает альтернативу
этому шагу (другую команду) или раскладывает его в составную под-цель — и каждая ветка
снова рука, то есть снова ReAct, на уровень ниже. В этом смысле дерево — «ReAct,
размотанный по дереву»: не другая политика, а ReAct плюс явная память, ветвление и
критерий остановки.

- Материализуется только первый шаг цели как пункт плана; последующие шаги выбираются по
  одному за раз. Рёбра `item` плана добавляются по порядку, и
  **последний** пункт — текущий. Дерево растёт по одному узлу за ход.
- Без альтернатив дерево — плоский, но типизированный и адресуемый список, то есть в
  точности предел ReAct, не хуже.
- Дерево даёт то, чего не может лента: явный **критерий остановки** (команда
  `done_when`), **проверяемое закрытие** (код возврата критерия), **ветвление** при
  провале гипотезы и контекст как ограниченный срез (спина с руками), а не
  растущую ленту.
- «Мы закончили?» решает движок по критерию, а не отдельный ход LLM.

План — живой, а не контракт: он правится **добавлением узлов** (альтернатив,
новых пунктов), никогда переписыванием. IR только растёт.

## Первый принцип: знание имеет источник

Каждое событие журнала — знание, полученное из опыта: чтение, поиск, запуск-критерий,
высказывание пользователя или собственное детерминированное действие движка. Знание
не появляется из ниоткуда, и у каждого факта прослеживается опыт, который его
породил, — его **источник**. Вердикт, угаданный из изменения файла, цель, объявленная
LLM достигнутой, убеждение без начала — нарушают принцип.

Три следствия, используемые везде:

- изменение файла известно только потому, что его произвело детерминированное
  действие (`mutate`), а не догадка;
- «pass» — это только код возврата запуска-критерия самой цели; изменение кода
  может сделать этот запуск устаревшим, но никогда не выдумывает вердикт;
- отклонённое предложение фиксируется (`record_rejection`) с причиной, а не просто
  показывается на один ход.

## Докса и логос

Каркас — из различения доксы и логоса (Ankyra, `doxa_and_logos.tex`):

- **Докса** — это LLM. Она только *предлагает*: ровно один оператор за ход
  (`create_goal`, `apply`, `stop`, `decline`; `recall`/`search` — read-only адресация). Её мысль
  нарративна и в IR не входит. Предложенная цель входит `open`; сразу закрытой она не
  бывает.
- **Логос** — детерминированная сторона: врата (`classify`), исполнение и
  запись команд, и вывод состояния (`fold`, `project`), включая **обход**, решающий,
  куда уходит фокус. Код возврата запуска-критерия читается здесь — а не выдаётся узлом.
- **Арбитр** — власть вне доксы и логоса на **границах**: инструментарий (команда
  критерия) и пользователь (первый запрос, финальная приёмка запроса). Приёмки на цель
  нет.

Докса никогда не закрывает цель вердиктом: цель закрывается только `stop` доксы,
через врата факта критерия (pass).

## IR в одной странице

Один граф, два пространства (`docs/ir_ru.md` — as-built-справка):

- **work** — `request`, `goal`, `plan`, `alternatives`, `action`, `observation`,
  `stop`, `unactionable`, `constraint`.
- **artifact** — `file` (канонический id `file:src/foo.ts`).

**done_when** — одна **строка-команда**: критерий, который запускает движок, читается по
коду возврата (0 = pass, ненулевой = fail, отсутствует = нет вердикта). Код возврата —
единственный вердикт, а не узел.

**Рёбра.** `has_goal`, `has_plan`, `item`, `has_alternatives`, `produces`, `has_stopped`,
`no_goal`, `mutates`.

**Состояние** (не хранится; вычисляет `fold`): узел — `open`/`executed`/`stopped`:
действие `executed`, когда произвело результат; цель `stopped`, когда у неё есть ребро
`has_stopped`; `achieved`/`refuted`/`abandoned` нет. Факты критерия (pass/fail/нет
вердикта из `exitCode` запуска) и устоявшийся запрос — выводимые чтения, а не статусы.

**События** (закрытый словарь): `add_node`, `add_edge`, `descend`, `return`, `mutate`,
`record_rejection`. `set_status` нет и `record_check` нет: смена состояния — новое
узел-событие (`observation`/`stop`).

**Операторы.** `create_goal { what, command }`
интерпретирует запрос один раз или раскладывает текущий пункт в подцель (альтернативу); цель
получает контейнер плана, чей первый пункт — `command` (исполняется сразу). `apply { action }`
запускает/читает/правит мир.
`decline { why? }` отвечает на недейственный запрос (`unactionable`). `stop { why? }` —
единственное закрытие: `stop` доксы закрывает цель — критерия и проверки нет; у запроса
`stop` нет. `recall`/`search` — read-only адресация.

## Цикл

```
project → propose → classify → execute → progress
```

1. `project` строит контекст (срез дерева).
2. `propose` просит у доксы ровно один оператор.
3. `classify` пропускает его через врата (логос решает допустимость).
4. `execute` применяет детерминированно, дописывая события.
5. `progress` останавливает цикл, когда остановлена цель запроса (прогон заканчивается),
   при отсутствии прогресса или по бюджету.

Одно предложение за ход, поэтому каждый ход оставляет проверяемый след.

## Обход: спина и руки

Позиция работы — **стек рамок** — **спина** — от запроса к фокусу, по рамке на
уровень. У каждой рамки есть **рука**: упорядоченные соседние варианты уровня (цель под
запросом, пункты плана под целью) с текущей позицией внутри (последний пункт). Переход —
это `descend` (push) или `return` (pop); куда должен встать фокус, движок вычисляет
детерминированно.

Ни стек, ни курсор не хранятся: стек — свёртка `descend`/`return` по журналу, курсор
выводится из плана. Значит `same events → same context`. История (исполненные пункты,
наблюдения, запуски-критерии) на спине не держится — она в дереве и достаётся **по
адресу** (`recall { id }`). Полная модель — `docs/plans/traversal_stack_spec_ru.md`.

## Проекция

Проекция — сердце Skein: не «что было сказано», а «что действует сейчас». Это
детерминированная функция состояния, а не LLM-пересказ. `Context` несёт:

- `path` — спину (`request → … → фокус`); узел несёт свои `plan` и `alternatives`
  (поэтому ревизия плана видна там, где произошла);
- `constraints`, `lastResult` (полный результат последнего вызова), `shown` (рабочее
  множество), `calls` (дедуплицированный индекс прошлых вызовов), `applicable`,
  `checkReady`, `nextAction`, `budget`.

Всё прочее — содержимое файлов, сырой вывод, старые тела — достаётся по `recall`/`search`.
Адресуемость гарантирована всегда: любой узел либо показан, либо в одном запросе.

## Устаревание по версии

Знание о коде немонотонно, но журнал остаётся монотонным. Мост — **устаревание по
версии**:

- факт `read` фиксирует хэш файла (`version`) на момент чтения;
- мутация порождает `mutate`, что детерминированно делает факты о старой версии
  устаревшими;
- наблюдение запуска-критерия несёт свидетеля `ref → version`; последующий `mutate`
  делает факты о старой версии устаревшими, поэтому pass не может молча остаться
  валидным.

Свидетель — снимок всего воркспейса — надёжно, но грубо; точность отложена.

## Арбитр

Арбитр — **граничная власть**, а не действующее лицо на каждую цель:

- **инструментарий** (тесты, тайпчекер, repro-скрипты) производит код возврата
  критерия, когда запускается `done_when` цели;
- **пользователь** владеет первым запросом и финальной приёмкой запроса.

`record_check` нет и приёмки на цель нет. Цель закрывается только `stop` доксы,
с опорой на факт критерия (pass). LLM не производит ни того, ни другого.

Корень-запрос в IR не закрывается: приёмка внешняя и неявная. Внутри вычисляется только
`requestSettled`.

## Чем отличается от существующих подходов

- **MemGPT / Letta** — LLM управляет текстовыми блоками памяти. Skein: правилами
  управляется типизированное состояние; LLM предлагает изменения.
- **Deepagents** — вытеснение и суммаризация сжимают ленту, но оставляют её. Skein:
  контекст — проекция, а не пересказ; ничего не теряется, только адресуется.
- **LangGraph state** — типизированный dict для оркестрации, а не для управления
  контекстом. Skein: проекция в контекст — основная функция.
- **RAG** — поиск по похожести. Skein: детерминированная релевантность по структуре,
  статусу и провенансу, с адресным возвратом.

Новизна: **контекст как проекция** над append-only-деревом, с детерминированным
обходом и верификацией только запуском критерия цели.
