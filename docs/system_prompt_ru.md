# Skein — системный промпт: поведение и блоки

> Английское зеркало — `docs/system_prompt.md`.

Связанные документы: `docs/ir_semantics_ru.md` (семантика IR: промпт — политика доксы
над ней), `docs/tools_ru.md` (контракт инструментов), `docs/projection_ru.md` (что
видит модель), `docs/plans/archive/system_prompt_revision_plan_ru.md` (план ревизии и фазы),
`src/loop/prompt/` (сборка), `tests/prompt.test.ts` (L1-тесты).

Это **источник истины о поведении промпта**. Код следует за ним: правка поведения идёт
«правка здесь → правка блока → тест».

## 0. Принцип

Промпт — **операционный спек политики доксы**, а не абзац текста. Он состоит из
**блоков**, и один блок отвечает за **одно поведение**. Поведение блока проверяется
на трёх уровнях:

- **L1 — статический контракт** (`tests/prompt.test.ts`, офлайн, CI): структура, имена
  инструментов, обязательные формулировки;
- **L2 — фикстурные сценарии** (под `SKEIN_LIVE=true`): форма траектории на фикстуре;
- **L3 — приёмка/бенч**: реальные задачи, в т.ч. контролируемый эксперимент.

Честно: L2–L3 зависят от недетерминизма LLM и потому слабые; L1 обязателен, L2 — под
гейтом, L3 — приёмка.

## 1. Модель сборки

- Промпт собирается в `src/loop/prompt/index.ts` из `PROMPT_BLOCKS`
  (`src/loop/prompt/blocks.ts`): `SYSTEM_PROMPT = PROMPT_BLOCKS.map(b => b.text).join("\n\n")`.
- Блок — `{ id: string; text: string }`; ID стабильны (B1…).
- `src/loop/propose.ts` реэкспортирует `SYSTEM_PROMPT` (сохраняет путь импорта тестов).
- Технический контракт инструментов **генерируется из реестра** `PROPOSAL_TOOLS`
  (`src/llm/tools.ts`), а не копируется в текст (Фаза 2).

**Инварианты сборки:**

1. один блок = одно поведение; нет дублирования между блоками;
2. каждое поведение имеет ID и запись в §2;
3. собранный промпт равен склейке блоков (проверяется L1);
4. имена инструментов совпадают с реестром (проверяется L1).

### Детализация по блокам

- **B1** задаёт роль: докса только предлагает; отказы и провалы инструментов — единственные
  факты, которые добавляет движок, а проекция — не диалог.
- **B2** перечисляет `FRAGMENT` (inspect/modify/execute/verify/abduce).
- **B3** вводит словарь узлов; отдельного рода `claim`/
  `decision` нет. Называет виды узлов, которые может добавить ход, — команда (apply),
  цель (create_goal), stop, decline, — так что каждый принятый ход добавляет ровно один
  узел. Запрос интерпретируется ровно один раз (ребро `has_goal`) или отклоняется
  (`unactionable`); интерпретация ФИКСИРОВАНА. Цель несёт `what`/`why?`/`sketch`, её план
  засеян первой `command`, и она закрывается только через `stop` (критерия нет).
- **B4** описывает поля `Context`, которые видит модель; в любом контейнере текущий
  пункт — последний добавленный (ребра `chosen` нет). Когда предложены только
  `create_goal`/`decline` (фокус — свежий запрос), запрос ещё не интерпретирован.
- **B5** фиксирует: рабочее множество engine-owned; `query {id}` — единственный вход.
- **B6** запрещает угадывать команду; первая команда — литеральная, из корня
  воркспейса, с префиксом `cd <dir> &&` при подкаталоге. **Правило команды:** если запрос
  упоминает любую команду, проверяющую работу, `command` интерпретации **обязан** быть
  этой литеральной командой. То же правило изложено в `description` инструмента
  `create_goal` (B12) — схеме, которую модель видит на каждом вызове (Фаза 9).
- **B7** фиксирует декомпозицию: каждый `create_goal` несёт `sketch` (свободный
  набросок-строку) и `command` — первый конкретный пункт плана. Движок план **не**
  прогоняет сам; вы делаете по одной команде за ход и выбираете следующую по результату.
  Каждый принятый ход добавляет ровно один узел — команда (apply), цель (create_goal),
  stop или decline. Текущий пункт в контейнере — последний добавленный (ребра `chosen`
  нет). Подцель допустима только как **альтернатива** текущему пункту (разложить его), не
  как пункт плана и не обязательна. Repair-routine **сначала готовит дерево**: у запуска
  обычно есть предпосылка СБОРКИ, и провал из несобранного/несконфигурированного дерева —
  это SETUP, а не дефект; прочитайте собственные build-доки проекта
  (README/HACKING/INSTALL) и соберите (напр. `./configure && make`) до локализации.
  Эту сборку (и любой набор тестов) запускайте в ФОРГРАУНДЕ: он блокируется до
  завершения (один ход на всю команду). Цель завершается только через `stop`, который
  добавляет узел `stop` как последний пункт плана цели и ребро `has_stopped`. `stop` на
  запросе нет — запрос/прогон заканчивается, когда остановлена его цель. Цепочку предков
  ничто не закрывает.
- **B8** (пересмотрен в Фазе 3): git/история — нормальный инструмент при наличии; в этом
  воркспейсе `.git` может отсутствовать, и упавшую history-команду нельзя повторять или
  искать в других корнях; локальная история и внешний референс — разное.
- **B9** (Фазы 3–4): если у артефакта есть канонический референс (апстрим, опубликованная
  версия, соседняя/бэкап-копия), взять его и продиффить — законная и часто быстрейшая
  локализация. Внешний референс затягивается инструментом `fetch { url, path? }` (или
  `curl` через `run`) как read-only свидетельство; апстрим-правка применяется
  `apply_patch`. В IR: artifact `file`; diff — наблюдение. Diff-референс — **зацепка, а не
  чеклист**: у апстрима может быть много посторонних дельт, поэтому он называет
  подозреваемого, а не список ханков, которые надо выверить.
- **B10** задаёт переход от лога к месту и различает две причины «not found»: отсутствующий
  ИСХОДНЫЙ путь (нет самого сьюта/входного каталога → неверный рабочий каталог →
  `cd <dir> &&`) и отсутствующий АРТЕФАКТ СБОРКИ, который генерирует проект
  (`Makefile.config`/`config.status`/скомпилированный бинарь → дерево не
  сконфигурировано/не собрано → выполнить сборку проекта; это setup, а не дефект).
- **B11** задаёт поведение при провале: упавшая команда — это прогресс, а не тупик.
  Следующий ход ветвит текущий пункт — подцель (create_goal) или другую команду (apply,
  новейшая альтернатива пункта) — и новый `what` обязан задавать ДРУГУЮ гипотезу
  (`ir_semantics` §4.1).
- **B12** перечисляет инструменты; генерируется из `PROPOSAL_TOOLS`, поэтому дрейф
  (например, несуществующий `apply`) невозможен.
- **B13** ограничивает `thought`.
- **B14** запрещает `2>&1`/`&>` и pipe через `tail`/`head`.
- **B15** завершает цель: докса предлагает `stop`, а движок добавляет узел `stop` как
  последний пункт плана цели и ребро `has_stopped` — гейта по критерию нет; затем движок
  возвращается к запросу и прогон заканчивается. `stop` на запросе нет — он
  заканчивается, когда остановлена его цель.
- **B16** сокращён до уникальных правил безопасности (ограничения, устаревшее чтение,
  «подозреваемый → правка», объяснительный пробел); дубликаты вынесены в B6/B7/B11/B14/B15
  и в `description` инструментов. Он задаёт триггер **локализовано**: как только докса может
  указать точное выражение для правки, единственный ход вперёд — `edit` (или проверка,
  которая его опровергает), а не дальнейшее чтение.

## 3. Сквозные инварианты

1. нет противоречий между блоками (проверяется ревью и L1-формулировками);
2. каждый инструмент из реестра назван вызываемо (L1, Фаза 2);
3. бюджет символов промпта — **открытый вопрос** (§6): целевое значение не зафиксировано
   и тестом не проверяется.
