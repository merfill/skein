# Skein — системный промпт: поведение и блоки

> **Заметка (ревизия IR свёрнута; следующий этап).** Промпт теперь разделён на стабильную
> **базу** и **инструкции узлов** (request/goal) — см. `src/loop/prompt/blocks.ts` и
> `docs/ir_semantics_ru.md` §6–7. Детализация блоков ниже — до этого сплита и до ленты;
> составной базово-узловой промпт — следующий этап, поэтому документ ещё изменится.

> Английское зеркало — `docs/system_prompt.md`.

Связанные документы: `docs/ir_semantics_ru.md` (семантика IR: промпт — политика доксы
над ней), `docs/tools_ru.md` (контракт инструментов), `docs/projection_ru.md` (что
видит модель), `docs/plans/archive/system_prompt_revision_plan_ru.md` (план ревизии и фазы),
`src/loop/prompt/` (сборка), `tests/prompt.test.ts` (L1-тесты).

Это **источник истины о поведении промпта**. Код следует за ним: правка поведения идёт
«правка здесь → правка блока → тест».

## 0. Принцип

Промпт — **операционный спек политики доксы**, а не абзац текста. Он состоит из
**блоков**, и один блок отвечает за **одно поведение**. Поведение блока проверяется
на трёх уровнях:

- **L1 — статический контракт** (`tests/prompt.test.ts`, офлайн, CI): структура, имена
  инструментов, обязательные формулировки;
- **L2 — фикстурные сценарии** (под `SKEIN_LIVE=true`): форма траектории на фикстуре;
- **L3 — приёмка/бенч**: реальные задачи, в т.ч. контролируемый эксперимент.

Честно: L2–L3 зависят от недетерминизма LLM и потому слабые; L1 обязателен, L2 — под
гейтом, L3 — приёмка.

## 1. Модель сборки

- Промпт собирается в `src/loop/prompt/index.ts` из `PROMPT_BLOCKS`
  (`src/loop/prompt/blocks.ts`): `SYSTEM_PROMPT = PROMPT_BLOCKS.map(b => b.text).join("\n\n")`.
- Блок — `{ id: string; text: string }`; ID стабильны (B1…).
- `src/loop/propose.ts` реэкспортирует `SYSTEM_PROMPT` (сохраняет путь импорта тестов).
- Технический контракт инструментов **генерируется из реестра** `PROPOSAL_TOOLS`
  (`src/llm/tools.ts`), а не копируется в текст (Фаза 2).

**Инварианты сборки:**

1. один блок = одно поведение; нет дублирования между блоками;
2. каждое поведение имеет ID и запись в §2;
3. собранный промпт равен склейке блоков (проверяется L1);
4. имена инструментов совпадают с реестром (проверяется L1).

## 2. Блоки

Промпт намеренно простой («opencode-style» сокращение, Фаза 11): он задаёт требования
движка, а не способ думать. Стратегия живёт в `description` инструментов и в ленте.
Текущие блоки:

| ID | Поведение | Опора | Статус |
|---|---|---|---|
| B1 | Фрейм: докса предлагает ровно один оператор, логос решает; контекст — лента сообщений, пересобираемая каждый ход | `ir_semantics` §1, §7 | в коде |
| B2 | Capabilities из `FRAGMENT`; всё прочее — вне фрагмента | `src/ir/fragment.ts` | в коде |
| B6 | Цель из запроса: литеральные команды verbatim, корень воркспейса, `cd <dir> &&`, не угадывать команду | `tools_ru` §5.1 | в коде |
| B7 | Одна команда за ход; `apply` следует исходу шага; подцель раскладывает шаг; `stop` закрывает цель (без критерия); большое тело адресуется по id через `recall`/`search` | `ir_semantics` §4.1 | в коде |
| B12 | Контракт инструментов: плоские имена, генерируется из `PROPOSAL_TOOLS` | `src/llm/tools.ts` | в коде (генерируется) |
| B13 | Дисциплина вывода: `thought` ≤1 фразы, ровно один вызов; вывод+reasoning короткие — без припоминания/восстановления кода и без код-сниппетов в reasoning | `tests/prompt.test.ts` | в коде |
| B14 | Дисциплина потоков: без `2>&1`/`&>`, без pipe через `tail`/`head` | `tools_ru` §4.3 | в коде |
| B16 | Ограничения/безопасность: не нарушать `constraint`, не править на устаревшем чтении | `ir_semantics` §9 | в коде (сокращён) |

Удалены в «opencode-style» сокращении (Фаза 11): **B3/B4/B5** (свёрнуты), **B8** (политика
VCS), **B9** (внешний референс / diff-плейбук), **B11** (цикл ревизии), **B15** (stop — теперь
пункт в B7), **B17** (форграунд — теперь в описании `run`). Также вырезаны: **B10**
(плейбук «отказ → причина») и триггер локализовано→правь из **B16**, а из описаний
`fetch`/`grep` — наведение на diff/локализацию. Причина: это были мнения-эвристики; промпт
держит только контракт движка, а стратегию модель берёт из ленты и описаний инструментов.

### Детализация по блокам

- **B1** задаёт роль: докса только предлагает; отказы и провалы инструментов — единственные
  факты, которые добавляет движок. Контекст — лента сообщений, пересобираемая из дерева
  каждый ход, не диалог.
- **B2** перечисляет `FRAGMENT` (inspect/modify/execute/verify/abduce).
- **B6** запрещает угадывать команду; первая команда — литеральная, из корня воркспейса, с
  префиксом `cd <dir> &&` при подкаталоге. Если команда в запросе не названа, первый пункт —
  discovery-команда (`ls`, `cat README.md`). То же правило — в `description` `create_goal` (B12).
- **B7** фиксирует цикл: одна команда за ход; `apply` следует исходу текущего шага (успешная
  команда — новый пункт плана, упавшая — новая альтернатива с пометкой `alternative to step …`).
  `create_goal` при открытой цели раскладывает шаг в подцель. `stop` закрывает цель и это
  единственный способ её завершить (гейта по критерию нет). Большое тело результата
  адресуется по id: `recall { id, start?, end? }` перечитывает фрагмент, `search { id, pattern }`
  ищет в нём паттерн.
- **B10** удалён: плейбук «отказ → причина» (неверный каталог vs несобранное дерево) был
  мнением-эвристикой; его несут лог на ленте и описания инструментов.
- **B12** перечисляет инструменты; генерируется из `PROPOSAL_TOOLS`, поэтому дрейф невозможен.
- **B13** ограничивает `thought` (≤1 фразы; решение, не анализ) и держит вывод/reasoning короткими — без припоминания/восстановления кода и без код-сниппетов в reasoning (чтобы увидеть код — `read`/`grep`/`fetch`).
- **B14** запрещает `2>&1`/`&>` и pipe через `tail`/`head`.
- **B16** держит только уникальные правила безопасности (ограничения, устаревшее чтение);
  триггер локализовано→правь удалён как стратегический костыль.

## 3. Сквозные инварианты

1. нет противоречий между блоками (проверяется ревью и L1-формулировками);
2. каждый инструмент из реестра назван вызываемо (L1, Фаза 2);
3. бюджет символов промпта — **открытый вопрос** (§6): целевое значение не зафиксировано
   и тестом не проверяется.

## 6. Открытые вопросы

- Целевой бюджет символов промпта и что вынести в `description` инструментов.
- Степень жёсткости B6/B7 (насколько задавать порядок против гибкости модели).
- В промпте больше нет эвристики diff/локализации (Фаза 11); если она понадобится — это
  опциональный тул-хинт, а не базовый блок.
