# Skein — системный промпт: поведение и блоки

> **Заметка.** Промпт разделён на стабильную **базу** и **инструкции ситуации**
> (`request` / `plan` / `working` / `transition` / `terminal`) — см. `src/loop/prompt/blocks.ts`
> и `docs/ir_semantics_ru.md` §6–7. Текст блока — это system-сообщение; контракт инструментов
> отдельно (`PROPOSAL_TOOLS` → поле `tools` запроса).

> Английское зеркало — `docs/system_prompt.md`.

Связанные документы: `docs/ir_semantics_ru.md` (семантика IR: промпт — политика доксы
над ней), `docs/tools_ru.md` (контракт инструментов), `docs/projection_ru.md` (что
видит модель), `docs/plans/archive/system_prompt_revision_plan_ru.md` (план ревизии и фазы),
`src/loop/prompt/` (сборка), `tests/prompt.test.ts` (L1-тесты).

Это **источник истины о поведении промпта**. Код следует за ним: правка поведения идёт
«правка здесь → правка блока → тест».

## 0. Принцип

Промпт — **операционный спек политики доксы**, а не абзац текста. Он состоит из
**блоков**, и один блок отвечает за **одно поведение**. Поведение блока проверяется
на трёх уровнях:

- **L1 — статический контракт** (`tests/prompt.test.ts`, офлайн, CI): структура, имена
  инструментов, обязательные формулировки;
- **L2 — фикстурные сценарии** (под `SKEIN_LIVE=true`): форма траектории на фикстуре;
- **L3 — приёмка/бенч**: реальные задачи, в т.ч. контролируемый эксперимент.

Честно: L2–L3 зависят от недетерминизма LLM и потому слабые; L1 обязателен, L2 — под
гейтом, L3 — приёмка.

## 1. Модель сборки

- Промпт состоит из стабильной **базы** (`BASE_PROMPT`, верна на любом ходу) и **инструкций
  ситуации** (`NODE_INSTRUCTIONS` по `Situation`: `request` / `plan` / `working` / `transition` /
  `terminal`), собираемых в `src/loop/prompt/blocks.ts` (реэкспорт —
  `src/loop/prompt/index.ts`): каждый — склейка своих блоков через `\n\n`.
- Блок — `{ id: string; text: string }`; ID стабильны (B1…).
- `src/loop/propose.ts` кладёт в список сообщений `BASE_PROMPT`, затем инструкцию ситуации
  (`docs/ir_semantics_ru.md` §6).
- Контракт инструментов (имена, параметры, описания) **не** копируется в текст промпта: он
  уходит полем `tools` запроса (нативный function-calling), генерируется из единого реестра
  `PROPOSAL_TOOLS` (`src/llm/tools.ts`). Промпт лишь говорит вызывать доступные инструменты.

**Инварианты сборки:**

1. один блок = одно поведение; нет дублирования между блоками;
2. каждое поведение имеет ID и запись в §2;
3. собранный промпт равен склейке блоков (проверяется L1);
4. промпт **не** повторяет описания инструментов — они уходят в поле `tools` (проверяется L1).

## 2. Блоки

Промпт намеренно простой («opencode-style» сокращение, Фаза 11): он задаёт требования
движка, а не способ думать. Стратегия живёт в `description` инструментов и в ленте.
Текущие блоки:

| ID | Поведение | Опора | Статус |
|---|---|---|---|
| B1 | Фрейм: агент кодирования с доступом к файлам/каталогам на диске; один или несколько ходов за ход (батч, независимые вызовы) | `ir_semantics` §1 | в коде |
| B0 | Фрейм: агент кодирования, реализованный как машина состояний — состояния с критериями выхода, переходы как предусловия | `prompt_state_machine_concept` | в коде |
| B4 | Обход (`move { state, what }` объявляет состояние И его цель — состояние ЕСТЬ его цель; первый `apply` засевает план; `stop` завершает и вынуждает переход); начальные состояния-кандидаты (`Start`); обусловленные переходы, сгруппированные по источнику, из `ISLANDS` | `src/ir/islands.ts` | в коде |
| B6 | Ситуация запроса: первый ход — `move { state, what }` (выбрать стартовое состояние и его цель) или `decline`; литеральная команда / корень воркспейса / `cd <dir> &&` | `tools_ru` §5.1 | в коде |
| B7 | Ситуация плана: дать ПЕРВЫЙ пункт плана состояния — обычный вызов инструмента (`apply`); подсостояний нет | `ir_semantics` §4.2 | в коде |
| B8 | Ситуация работы: искать → править; когда критерий состояния выполнен — `stop` (гейта нет); `move` при открытом состоянии отклоняется | `ir_semantics` §4.3–4.4 | в коде |
| B9 | Ситуация перехода: состояние завершено — `move { state, what }` в следующее или `move { state: "handoff" }` для завершения | `ir_semantics` §4.1 | в коде |
| B10 | Ситуация терминала: состояние hand-off — `stop`, чтобы завершить запрос | `ir_semantics` §4.4 | в коде |
| B18 | Микро-примеры хода: `move { state, what }`; разведка/правка одним батчем; `stop` состояния; `move`-переход | `tests/prompt.test.ts` | в коде |
| B13 | Дисциплина вывода: reasoning короткий; без припоминания/восстановления кода (используй `read`/`grep`/`webfetch`); без код-сниппетов в reasoning | `tests/prompt.test.ts` | в коде |

Пока состояние прорабатывается (`plan` / `working`), за инструкцией ситуации идёт
`ISLAND_INSTRUCTIONS[state]` — работа текущего состояния, критерий закрытия и ограничения
(`What / Done when / Constraints`), ключ — авторский `state` узла `move`
(`src/ir/islands.ts`, `docs/prompt_state_machine_concept_ru.md`). Завершённое состояние
(`transition` / `terminal`) их **не** показывает (критерий уже выполнен). Застрявшее состояние
также получает мягкий пинок (`Context.nudge`, `docs/ir_semantics_ru.md` §2.8), а сразу после
результата инструмента внутри открытого состояния проекция добавляет **инструкцию наблюдения**
последним system-сообщением (`Context.result`, `src/ir/project.ts`): прочитай результат и реши —
критерий выполнен → `stop`; шаг удался, надо ещё → следующий ход; провал/не тот шаг → другой ход.

Удалены в «opencode-style» сокращении (Фаза 11): **B3/B4/B5** (свёрнуты), **B8** (политика
VCS), **B9** (внешний референс / diff-плейбук), **B11** (цикл ревизии), **B15** (stop — теперь
пункт в B7), **B17** (форграунд — теперь в описании `bash`). Также вырезаны: **B10**
(плейбук «отказ → причина») и триггер локализовано→правь из **B16**, а из описаний
`webfetch`/`grep` — наведение на diff/локализацию. Причина: это были мнения-эвристики; промпт
держит только контракт движка, а стратегию модель берёт из ленты и описаний инструментов.

Затем (Фаза 13) промпт лишается всей механики инструментов и переходит в поле `tools`:
**B12** (индекс инструментов — дословная копия описаний из `tools`), **B14** (потоки — в
описании `bash`) и **B16** (ограничения/устаревшее чтение — в описаниях `edit`/`write` и
принуждаются движком) убраны; **B1**/**B2**/**B13** переписаны как обычный агент кодирования
(без словаря докса/логос), **B7** сжат до контракта ситуации.

### Детализация по блокам

- **B1** задаёт обычного агента кодирования с доступом к файлам и каталогам на диске; за ход он
  делает один или несколько ходов, движок исполняет их по порядку и возвращает результаты. Батч
  должен быть независим: ни один вызов не зависит от результата соседа. Лента/проекция — забота
  движка, не текст промпта.
- **B4** задаёт обход: `move { state, what }` объявляет состояние И его цель (состояние ЕСТЬ
  его цель), первый `apply` засевает план, дальнейшие `apply` работают, `stop` завершает
  состояние и вынуждает решение о переходе; `move` при открытом состоянии отклоняется. Рендерит
  начальные состояния-кандидаты (`Start`) и обусловленные переходы из `ISLANDS`.
- **B6** (запрос) фиксирует первый ход: `move { state, what }` выбирает стартовое состояние и
  его цель (или `decline` для невыполнимого запроса). bash-команда остаётся литеральной, из корня
  воркспейса, с префиксом `cd <dir> &&` при подкаталоге; если команда в запросе не названа,
  первое действие состояния — discovery (`ls`, `cat README.md`). Правило `cd` продублировано в
  `description` `move`.
- **B7** (ситуация плана) даёт ПЕРВЫЙ пункт плана объявленного состояния — обычный вызов
  инструмента (`apply`): любой инструмент, обычно bash-команда. Движок исполняет его сразу, и он
  засевает план состояния. Подсостояний нет.
- **B8** (ситуация работы) фиксирует цикл **искать → править**: сначала широкий поиск (батч
  независимых чтений/grep), а как только точная правка названа — сразу `edit`/`write`; когда
  критерий состояния выполнен — `stop` (гейта нет). `move` при открытом состоянии отклоняется.
  `stop` закрывает состояние и это единственное закрытие.
- **B9** (переход) — вынужденное решение после `stop`: `move { state, what }` в следующее
  состояние (маршруты из B4) или `move { state: "handoff" }`, когда всё сделано. `note`
  суммирует оставляемое состояние.
- **B10** (терминал) — hand-off: `stop`, чтобы завершить запрос.
- **B18** — короткие микро-примеры хода, задающие его форму.
- **B13** держит reasoning коротким — без припоминания/восстановления кода и без код-сниппетов
  в reasoning (чтобы увидеть код — `read`/`grep`/`webfetch`).
- **B12/B14/B16** больше не блоки: имена/параметры/описания инструментов, потоковый
  `pipefail`-совет и правила ограничений/устаревшего чтения живут в `description` инструментов
  (`src/llm/tools.ts`) и, где возможно, в движке (отказы repeat и `stale_base`).

## 3. Сквозные инварианты

1. нет противоречий между блоками (проверяется ревью и L1-формулировками);
2. промпт не повторяет описания инструментов — они уходят в поле `tools` запроса (L1, Фаза 13);
3. бюджет символов промпта — **открытый вопрос** (§6): целевое значение не зафиксировано
   и тестом не проверяется.

  три правки, самоостановка и вдвое дешевле.
- **Фаза 15 (2026-10-13).** Протокол состояний (`docs/plans/state_protocol_plan_ru.md`): промпт
  учит обходу — `move` объявляет состояние, второй ход конкретизирует работу этого состояния
  (без подцелей), `apply` работает, `stop` завершает и вынуждает переход. Ситуации разбиты на
  пять, с новыми блоками B8, B9 (переход), B10 (терминал); B4/B6/B7/B18 переписаны. Модель
  объявляет состояние и конкретизирует его разными ходами (`move` завершает батч).
- **Фаза 16 (2026-10-13).** Цель-в-`move` (`docs/plans/goal_into_move_plan_ru.md`): узел цели и
  отдельный оператор конкретизации убраны — состояние И ЕСТЬ его цель. `move { state, what }`
  объявляет состояние И его цель; план висит прямо на `move` и засевается первым обычным
  `apply` состояния. Ситуации становятся `request` / `plan` / `working` / `transition` /
  `terminal`; B4/B6/B7/B8/B9 переписаны (B7 даёт первый пункт плана, а не цель). Модельная
  поверхность на каждом ходу — это фронтир (`Context.applicable`).
