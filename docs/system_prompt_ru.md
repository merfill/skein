# Skein — системный промпт: поведение и блоки

> **Заметка.** Промпт разделён на стабильную **базу** и **инструкции ситуации**
> (`request` / `plan` / `working` / `transition` / `terminal`) — см. `src/loop/prompt/blocks.ts`
> и `docs/ir_semantics_ru.md` §6–7. Текст блока — это system-сообщение; контракт инструментов
> отдельно (`PROPOSAL_TOOLS` → поле `tools` запроса).

> Английское зеркало — `docs/system_prompt.md`.

Связанные документы: `docs/ir_semantics_ru.md` (семантика IR: промпт — политика доксы
над ней), `docs/tools_ru.md` (контракт инструментов), `docs/projection_ru.md` (что
видит модель), `docs/plans/archive/system_prompt_revision_plan_ru.md` (план ревизии и фазы),
`src/loop/prompt/` (сборка), `tests/prompt.test.ts` (L1-тесты).

Это **источник истины о поведении промпта**. Код следует за ним: правка поведения идёт
«правка здесь → правка блока → тест».

## Терминология

| Понятие | Термин | Где |
|---|---|---|
| состояние работы | **state** | `move { state, … }`, `Start state <label>` |
| переход в состояние | **move** | инструмент `move` |
| критерий состояния | **`done`** | `move.done`, «когда `done` выполнен» |
| инструмент остановки | **`stop`** | инструмент `stop { why }`; вызывается только когда `done` выполнен |
| запись завершения состояния | **`Finish state <label> — <why>`** | маркер на ленте |
| терминальное состояние | **End** (`end`) | `move { state: "end" }` |

`stop` встречается только как имя инструмента и в «call `stop` when `done` holds»; никогда как
«stop the state», «stop applies to a state», «stop reason» или «stop then move». Завершение
состояния — строка `Finish state`; запрос заканчивается после завершения состояния End.

## 0. Принцип

Промпт — **операционный спек политики доксы**, а не абзац текста. Он состоит из
**блоков**, и один блок отвечает за **одно поведение**. Поведение блока проверяется
на трёх уровнях:

- **L1 — статический контракт** (`tests/prompt.test.ts`, офлайн, CI): структура, имена
  инструментов, обязательные формулировки;
- **L2 — фикстурные сценарии** (под `SKEIN_LIVE=true`): форма траектории на фикстуре;
- **L3 — приёмка/бенч**: реальные задачи, в т.ч. контролируемый эксперимент.

Честно: L2–L3 зависят от недетерминизма LLM и потому слабые; L1 обязателен, L2 — под
гейтом, L3 — приёмка.

## 1. Модель сборки

- Промпт состоит из стабильной **базы** (`BASE_PROMPT`, верна на любом ходу) и **промтов
  ситуаций** (`request` / `transition`), собираемых в `src/loop/prompt/blocks.ts` (реэкспорт —
  `src/loop/prompt/index.ts`): каждый — склейка своих блоков через `\n\n`.
- Блок — `{ id: string; text: string }`; ID базовых блоков — `B1`…`B4`, они задают порядок в
  системном промпте. Промты ситуаций именованные (`request`, `transition`), никогда не `B…`.
- `src/loop/propose.ts` собирает список сообщений так: `BASE_PROMPT`, ограничения, лента
  (история), затем — только вне состояния — промт ситуации **в конец**, временно: он
  пересобирается из ситуации каждый ход и никогда не хранится в истории
  (`docs/ir_semantics_ru.md` §6).
- Контракт инструментов (имена, параметры, описания) **не** копируется в текст промпта: он
  уходит полем `tools` запроса (нативный function-calling), генерируется из единого реестра
  `PROPOSAL_TOOLS` (`src/llm/tools.ts`). Промпт лишь говорит вызывать доступные инструменты.

**Инварианты сборки:**

1. один блок = одно поведение; нет дублирования между блоками;
2. каждое поведение имеет ID (базовый блок) или имя (промт ситуации) и запись в §2;
3. собранный промпт равен склейке блоков (проверяется L1);
4. промпт **не** повторяет описания инструментов — они уходят в поле `tools` (проверяется L1).

## 2. Блоки

Промпт намеренно простой («opencode-style» сокращение, Фаза 11): он задаёт требования
движка, а не способ думать. Стратегия живёт в `description` инструментов и в ленте.
Текущие блоки:

| ID | Блок | Поведение | Опора | Статус |
|---|---|---|---|---|
| B1 | `role` | Агент кодирования; ровно одно состояние за раз; состояние — его цель с собственным `done`-критерием; каждый ход — tool calls, движок исполняет по порядку, независимые вызовы батчатся; tool calls состояния — его шаги | `prompt_state_machine_concept` | в коде |
| B2 | `principles` | Понять до действия (код, тесты, импорты, конфиги; поиск; чтение; соседи; сравнение с сиблингом); следовать конвенциям и паттернам проекта; комментарии скупо; работать только цель состояния; источник — единственная опора (без внешней версии); provenance; без секретов; краткий вывод | `specializing`/`keep-going` (opencode), `docs/ir_semantics_ru.md` §6 | в коде |
| B3 | `states` | Карта состояний: `label — what`, из `ISLANDS` | `src/ir/islands.ts` | в коде |
| B4 | `moves` | Переходы, сгруппированные по источнику, из `ISLANDS`; `End` терминален | `docs/prompt_state_machine_concept_ru.md` §4.3 | в коде |

Промты ситуаций — **именованные**, без номеров. Дописываются только вне состояния:

| Имя | Ситуация | Роль |
|---|---|---|
| `request` | свежий запрос | `system` |
| `transition` | после строки `Finish state` | `system` |

### Лента состояния

Состояние рендерится на ленте по порядку:

| Имя | Сообщение | Роль |
|---|---|---|
| `start` | `Start state <Label>` — маркер состояния | `system` |
| `brief` | факты probe для острова (`stateBrief`) | `system` |
| `instruction` | `instruction` острова — как действовать | `system` |
| `what` | `what: <island.what>` — цель состояния (только открытого) | `user` |
| `finish` | `Finish state <Label> — <why>` | `system` |

Запрос **вверху** ленты (второе сообщение, сразу после базового промпта), на каждом ходу.
`start`/`brief`/`instruction`/`what` показываются один раз при входе в состояние и только пока
оно открыто. На `plan`/`working` последним сообщением каждого хода идёт per-turn tail
(`planInstruction`/`turnInstruction`): hint → `what:` → `done`-критерий → closure; он не
хранится и на следующем ходу пересобирается. При закрытии остаются только `start` + `finish`.
Блока `Previous failed attempt` больше нет: запись несут строки `finish` предыдущих состояний.

### Базовые блоки

- **B1 — role.** Агент кодирования; ровно одно состояние за раз; состояние — его цель с
  собственным `done`-критерием. Каждый ход — tool calls; движок исполняет их по порядку;
  независимые вызовы батчатся. Работать состояние: его tool calls — его шаги.
- **B2 — principles.** Понять до действия: прочитать запрос, окружающий код, тесты, импорты и
  конфигурацию; использовать поиск; проверять допущения чтением; смотреть соседние файлы;
  сравнивать цель с сиблингом, выполняющим ту же операцию. Следовать стилю, структуре, именам,
  типам и паттернам проекта; изменения идиоматичны; комментарии скупо. Работать только цель
  состояния; план, малые шаги, отладка по свидетельствам. Provenance: источник — единственная
  опора; результат — из source/spec, без синтеза; acceptance сравнивает с source. Без секретов;
  краткий вывод.
- **B3 — states.** Карта состояний: `label — what`.
- **B4 — moves.** Переходы: `from → to — when`; `End` терминален.

### Промты ситуаций

- **`request`** — выбрать стартовое состояние (`move`) или `decline`; стартовые состояния.
- **`transition`** — после `Finish state`: следующие состояния и правило выбора.

## 3. Сквозные инварианты

1. нет противоречий между блоками (проверяется ревью и L1-формулировками);
2. промпт не повторяет описания инструментов — они уходят в поле `tools` запроса (L1, Фаза 13);
3. бюджет символов промпта — **открытый вопрос** (§6): целевое значение не зафиксировано
   и тестом не проверяется.

- **Фаза 20 (2026-10-15).** **Состояние — это решение, а не вызов инструмента**: `move`/`stop`
